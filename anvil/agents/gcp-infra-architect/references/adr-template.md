# ADR (Architecture Decision Record) 템플릿

팀에 제출할 설계 결정 문서의 표준 형식. 주요 결정마다 1건씩 작성.

---

## 왜 ADR인가?

- 결정의 **근거와 맥락**을 후세(+미래의 나)에게 전달
- 결정 **시점의 정보**로 평가되게 함 (나중에 "왜 이랬지?" 방지)
- 팀 검토·승인의 **투명한 기록**

---

## 파일명 규칙

```
ADR-{NNN}-{kebab-case-title}.md
```

예:
- `ADR-001-cloud-run-retain-vs-gke-migration.md`
- `ADR-002-regional-database-isolation-for-healthcare.md`
- `ADR-003-terraform-state-per-environment-region.md`

번호는 **연번**(001부터). 한 번 할당된 번호는 재사용하지 않음.

## 작성 가이드

### 컨텍스트 작성 요령

- **"현재 이렇고, 이런 제약이 있다"**까지만. 해결책 금지.
- 이해관계자 전원이 읽고 고개 끄덕일 수 있는 수준으로 중립적으로.
- 제약은 **구체적 숫자**로 (팀 인원, SLA %, RTO 분 등).

### 옵션 나열 요령

- **최소 2개, 권장 3개**
- 각 옵션 분량 비슷하게 (편향 방지)
- "Status quo 유지" 옵션도 항상 포함 검토
- 단점·리스크 숨기지 말 것 — **솔직한 트레이드오프**가 ADR의 가치

### 결정 서술 요령

- 선택 근거는 **컨텍스트의 제약과 매핑**되어야 함
- "팀이 K8s 경험 부족 (컨텍스트) → 운영 부담 적은 Cloud Run 선택 (결정)"
- 포기한 것도 명시 — "향후 Kafka가 필요해지면 재평가" 같이

### 리스크 작성 요령

- **이 결정 때문에 새로 생긴 리스크만** (기존 리스크 X)
- 완화 방안은 실행 가능해야 함 (추상적 "모니터링 강화" 금지)

## ADR 상태 전이

```
Proposed → Accepted → (나중에 번복 시) Superseded by ADR-XXX
                    ↘ Deprecated (대체 없이 폐기)
```

- **Proposed**: 초안, 팀 리뷰 대기
- **Accepted**: 팀 합의, 실행 중
- **Deprecated**: 더 이상 유효하지 않음 (이유 명시)
- **Superseded**: 새 ADR로 대체됨 (링크 필수)

한 번 Accepted된 ADR은 **수정하지 않는다**. 바뀌면 **새 ADR**을 쓴다.
