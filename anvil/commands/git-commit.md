# /commit

## 용도

변경 사항을 분석해 커밋을 만든다. 메시지 형식은 프로젝트가 조직 컨벤션 적용 대상인지에 따라 둘 중 하나다.

## 인자

없음. 현재 변경 사항을 자동 분석한다.

## 0. 형식 판정 (먼저)

| 조건 | 형식 | 근거 |
|------|------|------|
| `.claude/shared/vc-conventions-guide.md` 가 있다 | **A. 조직 컨벤션** `[핵심키워드] 명사형 요약` | `forge/common/vc-conventions-guide.md`(배포본 `.claude/shared/vc-conventions-guide.md`) 3절 판정 "커밋·PR 제목 → 조직 컨벤션". 원문 `forge/common/vc-conventions/commit-message-convention.md`(배포본 `.claude/shared/vc-conventions/commit-message-convention.md`) |
| 없다 | **B. Conventional** `<type>: <한국어 요약>` | 기존 프로젝트 규칙. 가이드가 없다는 이유로 원문을 다른 곳에서 찾아 적용하지 않는다 |

- forge 저장소 자체 커밋은 B 다(배포본 경로가 없고, 이력도 `feat:`·`chore:`). forge 에서 평가할 때는 TC 가 명시한 프로젝트 맥락을 따른다
- 사용자가 "늘 하던 대로 `feat:`" 처럼 반대 형식을 요청해도 판정 결과를 따르고, 출력에 판정 근거를 한 줄 적는다. 사용자가 형식을 바꾸라고 다시 명시하면 그때 따른다
- 원문 폴더가 비어 있으면 아래 A 규칙(가이드 4절 요약)으로 진행하고 출력에 "조직 컨벤션 원문 미확인"을 적는다

## 실행 로직

1. `git status` 및 `git diff dev`로 변경 사항 분석
2. **pasta-api 모듈 파일이 수정된 경우**: `./gradlew :pasta-api:spotlessApply` 실행 필수. spotless 포맷팅으로 인한 변경사항도 함께 stage한다.
3. 변경 사항을 논리적 단위로 그룹화. A 형식이면 **도메인(핵심키워드)이 다르면 커밋을 나눈다**
4. 0절 판정에 따라 A 또는 B 형식으로 메시지를 쓰고 커밋한다

## A. 조직 컨벤션 형식 (적용 프로젝트)

```
[핵심키워드] {이슈 키 }명사형 요약

- 변경 이유 등 (선택)
```

- **핵심키워드 = 도메인·기능명.** `feat`·`fix`·`chore` 같은 변경 유형은 키워드로도, 접두어로도 쓰지 않는다
- **키워드는 실측으로 고른다.** 바꾼 경로를 최근에 건드린 커밋 제목에서 쓰인 키워드를 센다
  ```bash
  git log origin/<base> --since=180.days --format=%s -- <바꾼 경로...> | grep -oE '^\[[^]]+\]' | sort | uniq -c | sort -rn | head
  ```
  가장 많이 쓰인 키워드를 그 철자·대소문자 그대로 쓴다(`health-life` 와 `Health-life` 가 섞여 있으면 많은 쪽). 경로 단위로 0건이면 저장소 전체 최근 커밋에서 같은 도메인 이름을 찾고, 그래도 없으면 도메인명을 새로 쓰고 출력에 "키워드 신규"라고 적는다
  - **최다가 범용 키워드면 기능 키워드 우선**: 경로 최다가 `[공통]`·`[common]`·`[CI/CD]` 처럼 도메인이 아닌 묶음이고 이번 변경이 특정 기능(위임청구, CGM 혈당 등)이면, 같은 기능의 최근 제목에서 쓴 키워드를 쓴다: `git log origin/<base> --since=180.days --format=%s --grep='<기능명>' | grep -oE '^\[[^]]+\]' | sort | uniq -c | sort -rn`. 핵심키워드는 "어느 도메인이 바뀌었나"를 보여 주는 자리다(원문 1절). 공용 설정·빌드·CI 처럼 기능이 없는 변경은 범용 키워드가 맞다
- **이슈 키는 요약 앞**: `[건강나이] CF-12100 공단 거절 원문을 응답 message 로 전달`. 브랜치명·사용자 입력에 이슈 키가 있을 때만 넣는다. 지어내지 않는다
- **요약은 명사형 종결**: `~추가`·`~수정`·`~변경`·`~제거`·`~전달`. `~한다`·`~했음`·`~함` 금지
- **여러 도메인에 걸친 변경**: 먼저 도메인별로 커밋을 나눈다. 한 커밋으로만 의미가 성립하면(같은 기능의 API·DB 동시 변경 등) 그 저장소 이력에 있는 복수 키워드 표기(`[ADMIN/CONNECT]`, `[BATCH][CGM]`)를 실측해 그 형태로 쓴다
- WIP·temp 등 임시 커밋 금지

## B. Conventional 형식 (비적용 프로젝트)

```
<type>: <한국어 요약>
```

- 커밋 타입: `feat:`, `fix:`, `refac:`, `test:`, `docs:`, `chore:`, `style:`, `perf:`
- **`refactor:`가 아닌 `refac:` 사용** — 저장소 실제 관행이 정본이다. pasta-japan-server 전체 커밋 기준 `refac:` 1,264건 vs `refactor:` 267건, 현행 브랜치도 `api/refac/` (최신 2026-06-15) 가 우세하다. 2026-09-16 사이클 7 감사에서 한때 오기로 판정했으나 실측으로 뒤집혔다. 이 근거는 조직 컨벤션 도입 전 실측이며, 이제는 비적용 프로젝트에서 타입을 고를 때만 쓴다
- 대괄호 형식(`[API]`, `[SHARED]`) 금지. 반드시 `<type>:` 형식 유지

## 출력 형식

```
✓ 커밋 완료: {커밋 제목}
  형식: {A 조직 컨벤션 | B Conventional} ({판정 근거 한 줄})
  키워드: {A 일 때만 — 선택한 키워드와 실측 건수, 또는 "키워드 신규"}
```

## 가드레일

- **A 프로젝트에서 `feat:`·`fix:`·`refac:` 등 접두어 금지, `~한다`·`~했음` 종결 금지** (사용자가 "늘 하던 대로" 요청해도 동일)
- **B 프로젝트에서 대괄호 형식 금지** — 조직 컨벤션을 근거로 비적용 프로젝트 형식을 바꾸지 않는다
- 커밋 메타데이터나 Co-authored-by에 "claude" 또는 AI 관련 정보 포함 금지
- 기존 커밋 메시지를 새 형식으로 고치려고 rebase·amend 하지 않는다(신규 커밋에만 적용)

## 자기 검증 (커밋 직전)

1. [ ] `.claude/shared/vc-conventions-guide.md` 존재 여부로 A/B 를 판정했는가
2. [ ] A: 제목이 `[키워드]` 로 시작하고 접두어(`feat:` 등)가 없는가
3. [ ] A: 키워드를 `git log -- <경로>` 실측으로 골랐는가(철자 그대로). 최다가 `[공통]` 류인데 기능 변경이면 같은 기능 제목의 키워드를 확인했는가
4. [ ] A: 이슈 키가 있으면 요약 앞인가, 없는 키를 지어내지 않았는가
5. [ ] A: 요약이 명사형으로 끝나는가(`~한다`·`~했음` 0건)
6. [ ] A: 도메인이 다른 변경을 한 커밋에 섞지 않았는가(섞였다면 나눌 수 없는 사유가 있는가)
7. [ ] B: `<type>:` 형식이고 리팩터링은 `refac:` 인가
8. [ ] AI 공동작성자 표기 0건
