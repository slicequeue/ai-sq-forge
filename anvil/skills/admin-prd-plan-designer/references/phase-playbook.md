# Phase Playbook

## Phase 설계 원칙
- 각 Phase는 하나의 명확한 목표와 검증 가능한 종료 조건을 가진다.
- 한 Phase에서 다중 목적을 처리하지 않는다(분할 우선).

## TODO 작성 공식
- `행동 + 산출물 + 완료 기준`으로 작성한다.
- 예: “권한 문자열 매핑 표 작성 -> 문서 표 완성 -> 리뷰 통과”.

## 권장 기본 구조
1. Context 정합(기존 패턴/제약 확인)
2. 문서 본문 작성(PRD 또는 TDD)
3. 실행 계획/테스트 전략 확정
4. Self-check 및 리스크 정리

## 우선순위 기준
- Must: 없으면 릴리즈/구현 진행 불가
- Should: 리스크 높음, 가능하면 이번 사이클
- Could: 다음 사이클 이관 가능

## 큰 기능: SSOT + `works/` 분할 (권장)
- **한 문서(HYBRID 등)**에 FR·Phase·기술이 모두 있으면 읽기는 좋지만, 구현 시 체크하기 어렵다.
- **SSOT**에는 요구·결정·Alignment·Open Questions만 유지하고, **`works/<기능>/plan.md`** 에 Phase 순서·`plan-01`~ 파일별 `- [ ]` TODO·DoD·**규칙(13~16) 교차 참조**를 둔다.
- **이벤트성 AdminHistory**(대량 작업·CSV 등)는 “마지막 Phase에 일괄”보다, **해당 기능 완료 직후 스모크** TODO를 넣어 누락을 막는다.
