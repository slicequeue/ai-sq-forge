# 신규 배치 평가

신규·변경 배치 1건에 대해 "어디에(언제) 스케줄해야 하나, 무엇과 겹치나, 리소스는 적정한가"를 평가.

---

## 입력 받기

다음을 확보한다. 코드가 이미 있으면 코드에서 추출하고, 없으면 사용자에게 묻는다.

- 무슨 일을 하나 — 읽는 테이블 / 쓰는 테이블 / 외부 호출
- 대상 규모 — 전체 유저? 조건 한정?
- 예상 빈도 — 일 / 시간 / N분
- 코드 위치 (있으면). 없으면 설계 단계 평가로 진행하고 **추정임을 명시**한다

---

## 평가 절차

1. **부하 프로파일 산정** — `load-rubric.md` 기준으로 A~G + 자원(read_db / write_db) 산정. 코드가 있으면 file:line 근거.
2. **자원 결정** — 무거운 읽기면 REPLICA(읽기 전용 프로파일) 권장. 운영 테이블 쓰기면 PRIMARY 불가피 → 시간대를 신중히 고른다.
3. **충돌 검사** — 기존 `joined.csv` + 부하 프로파일에서 **같은 자원**을 쓰는 잡들의 cron을 KST로 깔고, 신규 잡 후보 시각에 Heavy·baseline 잡이 있는지 확인. 판정은 `conflict-analysis.md` 규칙 적용.
4. **시간대 추천** — 충돌 없는 한산 구간 제시. 운영 트래픽 피크(아침 08~10, 저녁 20~22) 회피. 고빈도면 정시 offset(`2-59/5` 등) 권장.
5. **리소스 권고** — 유사 부하 기존 잡의 cpu/memory 한도를 참고로 초기값 제안 (예: ALL 스캔 + 대량 쓰기 → 4Gi 이상). 과소 설정 시 OOM 경고.
6. **코드 리스크 점검** — 무범위 풀스캔 / BULK `saveAll` / N+1 / 푸시 미배치 같은 안티패턴이 있으면 **스케줄 전 수정 권고**.

---

## 산출

1줄 결론 형식:

> 권장 cron `<...>` (KST `<...>`), 자원 `<PRIMARY | REPLICA+AGGREGATE>`, 리소스 `<cpu/mem>`, 주의 `<겹침·안티패턴>`

근거로 함께 적는다.

- 어느 기존 잡과 왜 안 겹치는지 (또는 겹쳐서 왜 다른 시각으로 미뤘는지)
- 부하 산정 근거 (코드가 있으면 file:line)
- 정적 추정 한계 명시 + **배포 후 첫 실행 duration 실측 권고**

---

## 체크리스트 (빠른 판정)

- [ ] 운영 PRIMARY에 쓰는가? → 피크 회피, 다른 PRIMARY Heavy와 시각 분리
- [ ] 전체 스캔인가? → REPLICA 가능한지, 청크·페이징 적용했는지
- [ ] 고빈도인가? → 정시 offset, baseline 누적 영향
- [ ] 외부 I/O 폭이 큰가? → rate limit, 배치 분할, 동일 외부 집중 시간대 회피
- [ ] 같은 테이블 대량 UPDATE/DELETE 하는 기존 잡이 있나? → **동시 실행 절대 회피(락)**
- [ ] 리소스 한도가 충분한가? → 유사 잡 대비
