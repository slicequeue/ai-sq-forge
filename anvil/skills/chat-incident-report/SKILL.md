# chat-incident-report — 장애/CS 대응 챗 보고 라이터

> 원칙: **사용자 안내 요청 섹션을 CS 담당자가 바로 복붙해 쓸 수 있는 품질로 뽑는다.** 개발 내부 용어·과잉 설명은 제거.

**범위**: Google Chat에 장애·CS 대응 결과를 공유하는 메시지
**비범위**: 슬랙·PR 본문·문서, QA 버그 리포트·회고 공유 (별도 스킬 대상)

---

## Phase 0. 작성 전 확인

다음 6가지가 갖춰졌는지 확인. 갖춰지지 않았으면 사용자에게 먼저 묻는다.

| # | 항목 | 예시 |
|---|------|------|
| 1 | 요청 맥락 | "어제 알려주신" / "공유주신" |
| 2 | 담당자 멘션 | `@hattie.lee(이현정)` |
| 3 | cc 대상 | `@seol.park(박설하)` |
| 4 | 유저 식별 (1명 이상) | `アプリコット#9304(795)` 형식 — 닉네임#ID(userId) |
| 5 | 유저별 현재 상태·대응 방향 | "복구 시도 중" / "재연결 후 확인 예정" 등 |
| 6 | 원인 한두 문장 (추정 허용, 미확정이면 솔직하게) | "자동 구독이 끊긴 상태. 정확한 원인은 로그 보강 후 규명" |

**확인 방법**:
- 같은 세션에서 조사가 끝난 직후면 컨텍스트에서 자동 추출
- 새 세션에서 요청받으면 위 항목들을 짧게 인터뷰

## 메시지 구조 (고정)

아래 섹션 순서·이름을 고정. 불필요한 섹션은 비우지 말고 **삭제**.

```
{담당자 멘션} {요청 맥락} 사용자 {유저 표기 나열} {도메인} 건 조사 공유드립니다.

상황
{유저 표기 A}: 한 줄 현재 상태
{유저 표기 B}: 한 줄 현재 상태

원인
기술용어 최소화한 한두 문단. 추정·미확정이면 "좀 더 명확한 원인은 로그 내역 보강하여 추후 모니터링을 통해 규명" 식으로 솔직하게.

대응
{유저 표기 A}: 본인이 할 조치 한 줄
{유저 표기 B}: 본인이 할 조치 한 줄

{유저 표기 A} 사용자 안내 요청
CS 담당자가 유저에게 전달해줄 문구. 한두 문장.

{유저 표기 B} 사용자 안내 요청
CS 담당자가 유저에게 전달해줄 문구. 번호 리스트 필요하면 사용. 복구 범위 등 불확실한 사항은 괄호로 부가 안내.

후속 작업
개발 측 대응 예정 한 줄. 장황 X.

cc. {cc 멘션}
```

### 섹션별 상세 규칙

#### "상황"
- 유저별 *한 줄* 현재 상태. 장애 발생 시점·기간·자가 복구 여부 포함
- 예: "어제 12:47 유저가 재연결해서 지금은 정상 수집 복귀. 다만 그 이전 구간에 일부 수집 공백 있음"

#### "원인"
- 한두 문단. 비개발자가 읽어도 이해 가능한 수준으로
- 기술 용어 대체 사전 (`references/tech-term-replacement.md` 참조)
- 불확실하면 단정하지 말고 *"추후 모니터링을 통해 규명"* 류 문구로 유보
- 출처 없는 정책·수치 단정 금지

#### "대응"
- 유저별 *본인(작성자)이 할* 조치
- "복구 시도 중" / "재연결 안내 후 서버 수신 확인 → 누락분 복구 가능 여부 파악" 식

#### "{유저} 사용자 안내 요청"
- **핵심 섹션** — CS 담당자가 유저에게 바로 복붙해 전달할 수 있는 수준
- 번호 리스트 허용. 불확실성은 괄호로 병기
- CS팀 내부 지시(예: "~해달라고 안내 부탁")가 아니라, 유저에게 전달할 문구 자체를 쓸 것

#### "후속 작업"
- 1줄. 개발 측 예정 작업 *간단히*만
- PR 우선순위(P0/P1/P2) 등 내부 관리 표기 노출 금지
- "원인 파악용 로그 추가 + 재연결 보강 로직 강화 예정" 수준

#### "cc."
- 팀 리더·관련 개발자 멘션

## 절대 금지 / 반드시 수행

### 절대 금지

- **개발 내부 용어 노출**: 토큰 row, OAuth, refresh, removeAuthorizedClient, JPA 등
- **PR 우선순위·내부 관리 표기**: P0/P1/P2, 에픽, 스프린트 번호 등
- **내부 문서 경로 노출**: `docs/works/...` 경로 등. 필요하면 cc 받은 개발자가 별도로 찾게
- **출처 없는 단정**: "외부 서비스 정책상 N일만 복구", "통상 ~시간 내 복구" 등 확인 안 된 수치. 대신 "시스템 상황에 따라 복구가 어려울 수 있음" 식 유보
- **두괄식 위반**: 배경·경위부터 늘어놓지 않는다. 상황 요약이 첫 섹션
- **AI 냄새 표현**: "~하는 것이 좋을 것 같습니다", "혹시 괜찮으시다면" 등

### 반드시 수행

1. 작성 전 Phase 0 체크리스트 6항목 점검. 부족하면 사용자에게 질문
2. 유저는 *닉네임#ID(userId)* 형식. userId만 표기 X
3. "사용자 안내 요청" 섹션 — CS팀이 복붙 가능한 수준인지 마지막에 다시 점검
4. 톤은 [sq-tone-writer](../sq-tone-writer/SKILL.md) 규칙 준수 (짧은 문장, 구어체 존댓말 기반)
5. 작성 완료 후 사용자에게 "이 느낌 맞아?" 확인

## 톤 참조

본 스킬은 *구조* 를 담당. *톤* 은 `sq-tone-writer` 에 위임.

핵심만 요약:
- 30자 초과 문장 지양
- 존댓말 기반, 딱딱하지 않게
- 불필요한 접속사·수식어 제거
- "~하는 것이 좋을 것 같습니다" 금지

세부 규칙은 `sq-tone-writer/SKILL.md` 참조.
