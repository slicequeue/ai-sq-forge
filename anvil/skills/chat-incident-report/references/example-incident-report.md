# 실제 사용 예시 — 외부 기기 연동 장애 (2인 사용자 케이스)

> 이 문서는 pasta-japan-server 실전 운영에서 검증된 메시지의 **마스킹 버전**.
> 실제 사용자 식별자·담당자 실명은 모두 placeholder로 치환됨.
> 작성 맥락: CS 접수된 외부 기기(혈당 측정기 등) 연동 장애 건. 조사·원인 분석 완료 후 담당자에게 공유.

---

## 최종 메시지 (마스킹)

```
@{담당자_id}({담당자_이름}) 어제 알려주신 사용자 {닉네임_A}#{닉네임ID_A}({uid_A}), {닉네임_B}#{닉네임ID_B}({uid_B}) {외부 서비스} {도메인} 건 조사 공유드립니다.

상황
{uid_A}: 어제 12:47 유저가 재연결해서 지금은 정상 수집 복귀. 다만 그 이전 구간에 일부 수집 공백 있음
{uid_B}: {N}일 전 06:48 이후 약 5일간 수집 0건. 같은 날 23:13 재연결했으나 복구 안 된 상태

원인
{외부 서비스}가 우리 서버로 {데이터} 보내주는 자동 구독이 끊긴 상태. 재연결해도 경우에 따라 구독이 재개 안 되는 케이스 있음.
좀 더 명확한 원인은 로그 내역 보강하여 추후 모니터링을 통해 규명

대응
{닉네임_A}#{닉네임ID_A}: 끊긴 구간 데이터 복구 시도 중
{닉네임_B}#{닉네임ID_B}: 재연결 안내 후 서버 수신 확인 → 누락분 복구 가능 여부 파악해서 작업 진행

{닉네임_A}#{닉네임ID_A} 사용자 안내 요청
끊긴 구간 데이터는 복구 시도 중이며, 일부 또는 전부 복구될 수 있음을 전달 부탁드립니다. 결과는 추후 공유드리겠습니다.

{닉네임_B}#{닉네임ID_B} 사용자 안내 요청
아래 순서로 안내 부탁드립니다.

  1. 앱에서 {외부 서비스} 연결 해제
  2. 앱 완전 종료 후 재실행
  3. {외부 서비스} 재연결
  4. 10~60분 후 {데이터} 표시 확인

  누락된 5일치 과거 데이터의 복구 가능 범위는 재연결 후 확인해서 별도 공유드리겠습니다. ({외부 서비스} 정책이나 시스템 상황에 의해 복구가 어려울 수 있음)

후속 작업
원인 파악용 로그 추가 + 재연결 보강 로직 강화 예정

cc. @{cc_id}({cc_담당자_이름})
```

---

## 이 메시지가 통과한 이유 (체크리스트 대조)

| 체크 항목 | 통과 |
|---|---|
| 섹션 순서: 상황→원인→대응→사용자별 안내 요청→후속 작업→cc | ✅ |
| 유저 표기 닉네임#ID(userId) | ✅ `{닉네임_A}#{닉네임ID_A}({uid_A})` |
| 개발 내부 용어 노출 X | ✅ 토큰·OAuth·refresh 등 표현 없음 |
| 출처 없는 단정 X | ✅ "일부 또는 전부 복구될 수 있음", "시스템 상황에 의해 복구가 어려울 수 있음" 등 유보 |
| 안내 섹션 복붙 가능 | ✅ 번호 리스트 + 유보 문구 포함 |

## 초안에서 수정된 포인트 (실제 피드백 반영 — 시행착오 기록)

최종 메시지에 도달하기 전 **5번 수정**을 거침.

### 1차 초안 (거부됨)
- **문제**: 너무 장황. 개발 구조 설명(`removeAuthorizedClient` 류 메서드명)이 본문에 포함됨. 대응 섹션에 우선순위(P0/P1) 노출
- **피드백**: "어떻게 대응해달라는 내용이 너무 없는 것 아냐? 원인 설명이 비개발자가 보기에는 이해가 어려워"

### 2차 초안 (거부됨)
- **문제**: 여전히 작업 이야기가 많고 밀도가 높음
- **피드백**: "너무 장황하고 그냥 담백하게 내가 말한 내용 위주로 만들면 될 것 같은데"

### 3차 초안 (거부됨)
- **문제**: 담백해졌으나 "어떤 안내해달라"는 내용이 부족
- **피드백**: "이거 관련해서 어떤 안내해달라고 내용도 아주 명료하게 담아줘"

### 4차 초안 (거부됨)
- **문제**: "{외부 서비스} 보존 정책상 일부만 복구" 출처 없는 단정
- **피드백**: "이 내용 출처는?"
- **교훈**: **출처 없는 정책·수치 단정 금지**. 불확실하면 유보 표현으로

### 5차 (최종)
- 두 유저 상황 요약 섹션 추가 (명료성↑)
- 복구 가능 범위는 "재연결 후 별도 공유" + 괄호로 유보 문구

---

## 이 예시가 보여주는 패턴

**핵심 인사이트**: 대응 공유 메시지는 *보고서*가 아니라 *CS 담당자의 실무 도구*다. 담당자가 유저에게 바로 전달할 수 있는 안내 문구를 제공하는 게 최우선 가치.

- 개발 배경 설명은 최소화, "왜 이게 필요한가"보다 "CS가 뭘 해야 하는가"에 집중
- 불확실성은 솔직하게 유보 — 나중에 말 바꾸는 것보다 처음부터 범위 명시
- 유저 표기는 CS 시스템에서 식별 가능한 닉네임 우선

## 재사용 시 치환 가이드

실제 메시지 작성 시 아래 placeholder를 실제 값으로 치환:

| Placeholder | 실제 값 예시 |
|---|---|
| `{담당자_id}` | 이메일 alias (예: `firstname.lastname`) |
| `{담당자_이름}` | 실명 |
| `{닉네임_A}`, `{닉네임_B}` | 사용자 앱 닉네임 (언어·이모지 포함 가능) |
| `{닉네임ID_A}`, `{닉네임ID_B}` | 4자리 이상 공개 ID (앱 내 표시용) |
| `{uid_A}`, `{uid_B}` | 내부 user ID (숫자) |
| `{외부 서비스}` | 연동된 외부 서비스 이름 (Dexcom, Garmin, Fitbit 등) |
| `{도메인}` | 데이터 도메인 (혈당, 심박, 수면, 운동 등) |
| `{데이터}` | 구체 데이터 명 (혈당, 심박수 등) |
