# git-pr — PR 생성/갱신 스킬

> 트리거: "PR 만들어줘", "PR 본문 갱신", "PR 리프레시", "/git-pr"

원칙: **리뷰어가 1~5분 안에 "뭘 바꿨고 효과가 어땠나" 파악**할 수 있도록 짧고 명료하게.

이 스킬은 다음 순서로 동작한다:
1. 변경사항 분석 → 표준 양식으로 본문 작성
2. 신규 또는 기존 PR 판단
3. 생성/수정 후 URL 출력

---

## Phase 1. 변경사항 분석

```bash
git status
git log <base>..HEAD --oneline
git diff <base>..HEAD --stat
git branch --show-current
gh pr list --head "$(git branch --show-current)" --state open
```

**base 결정**:
- 일반: `dev`
- hotfix / 긴급 prd 적용: `main` (사용자 명시 요청 시)

**푸시 전 품질 게이트 (v0.4, 하드 가드레일)**:
- `forge/common/review-lint.py` 가 있으면 실행한다: `python3 forge/common/review-lint.py --base origin/<base>`
- **위반이 1건이라도 있으면 푸시·PR 생성을 멈추고** 사용자에게 보고한다. 고친 뒤 다시 실행한다
- 확인 항목은 해당 여부를 판단해서, 해당 없으면 사유를 PR 본문 "리뷰 포인트"에 한 줄씩 적는다. **lint 가 `[확인]` 을 실제로 출력한 항목만** 적는다. `[확인]` 0건이면 적을 것이 없다 (v0.6)
- `self-code-reviewer` 를 아직 돌리지 않았으면 먼저 돌린다. 리뷰어가 사람 리뷰에서 지적할 것을 PR 올리기 전에 잡는 단계다
- **최신 dev 병합 컴파일 (v0.5)** — 푸시·머지 직전에 `git fetch origin dev && git merge --no-commit --no-ff origin/dev` 상태(또는 임시 워크트리)에서 `./gradlew :{module}:compileTestJava` 를 돌린다. CI 는 PR 을 **최신 dev 와 합친 상태**로 빌드하므로, 내 브랜치가 통과해도 다른 PR 이 같은 인터페이스를 바꾸거나 그 인터페이스의 테스트 Fake 를 추가했으면 깨진다. 확인 뒤 `git merge --abort`. 2026-10-16 #793(인터페이스 메서드 추가)·#794(그 인터페이스 Fake 추가)가 순서대로 머지돼 dev 테스트 컴파일이 깨졌고, 배포 워크플로는 테스트를 컴파일하지 않아 성공으로 보였다(#803 핫픽스)
- **인터페이스를 바꿨다면 구현체 전수 확인** — `grep -rn "implements {인터페이스}" */src/test */src/main` 로 테스트 Fake·대역까지 찾아 함께 고친다. 다른 PR 의 Fake 는 내 diff 에 안 보이므로 머지 직전 dev 기준으로 다시 grep 한다

**원격 push 확인**:
- 원격에 없으면 `git push -u origin HEAD`

## Phase 2. PR 본문 작성 (표준 양식)

### 2-0. 저장소 PR 템플릿 확인 — 하드 가드레일

본문을 쓰기 **전에** 저장소 템플릿이 있는지 먼저 확인한다.

```bash
ls .github/PULL_REQUEST_TEMPLATE.md .github/pull_request_template.md 2>/dev/null
```

| 결과 | 처리 |
|------|------|
| 템플릿 있음 | **섹션명을 이모지·기호까지 문자 그대로 복사해 쓴다.** 순서도 템플릿을 따른다. 임의 축약·번역·재작명 금지 |
| 템플릿 없음 | 아래 2-2 표준 구성을 쓴다 |

템플릿 섹션명을 임의로 바꾸는 것이 가장 자주 지적받은 위반이다. `## Why need this PR❓` 를 `## Why` 로 줄이거나 `## Test list 📝` 를 `## Test` 로 쓰면 위반이다.

**근거**: 2026-08-31 pasta-japan-server PR #726 에서 `## Why` / `## 측정` / `## 배포` / `## Test` 라는 자체 제목으로 작성해 "제발 좀 PR 양식 좀 지켜라" 지적을 받고 전면 재작성했다. 같은 날 2회 지적. 당시 `pr-feedback-resolver` 스킬이 정상 발동한 상태였는데도 위반했다 — 스킬 본문에 없는 규칙은 스킬이 켜져도 지켜지지 않는다는 근거다.

**선택 섹션은 템플릿 섹션을 대체하지 않는다.** 측정 결과·배포·후속 작업·기존 동작 변경·리뷰 포인트는 템플릿 필수 섹션을 모두 채운 **뒤에** 조건이 성립할 때만 덧붙인다.

**선택 섹션 위치 (v0.6)**: `Changes` 뒤, `Test list` 앞에 둔다 (2-2 순서, PR #551 실례). `Why`·`Changes` 보다 앞에 두지 않는다. 템플릿에 `Test list` 뒤 섹션(`Screenshoot 🌅 (optional)` 등)이 있으면 그 섹션은 템플릿 순서대로 맨 뒤에 그대로 둔다.

### 2-1. 분량/구조 원칙

- **100~200줄 이내**, **표 위주**
- 큰 코드 스니펫 / SQL / mermaid 본문 금지 → 작업 문서로 위임
- 영문 jargon 한국어 풀어쓰기

### 2-2. 표준 구성 (있을 때만 섹션 추가)

```markdown
## Why need this PR❓
- 현상 + 원인 1~2문장 (핵심 단어만 굵게)

## Changes ✌️
**파일 N개, +M / -K lines** (영향 범위 한 줄)

| 파일 | 변경 |
|---|---|
| `경로/파일명` | 사람 표현으로 무엇을 바꿨는지 |

## 측정 결과 (운영 효과 측정이 있을 때만)
| 지표 | 변경 전 | 변경 후 | 효과 |
|---|---|---|---|
| ... | ... | ... | ✅ ... |

> ⚠️ 한계/잔존 1줄

## 배포 (Canary / 단계적 배포가 있을 때만)
- 시점 KST: 무엇을 …

## 후속 작업 (별도 PR 항목이 있을 때만)
1. 짧은 항목명 — 1줄 설명

## 기존 동작 변경 (기존 API·배치의 응답·검증·에러가 바뀔 때만)
- `PUT /...` — 지난 시각이면 400 (기존: 통과). 의도: ...

## 리뷰 포인트 (판단이 필요한 지점이 있을 때만)
- 실패 시 동작: 일정 조회가 실패하면 카드는 NO_PLAN, 마지막 기록은 유지
- 범위 밖으로 둔 위험: 푸시 예약 성공 후 DB 저장 실패 시 보상 없음 (사유)
- review-lint 확인 항목 중 해당 없음: `ResponseEntity` 미사용 — 같은 컨트롤러 기존 메서드 관례

---

📘 **상세 분석/측정 결과/근거 문서는 Notion으로 별도 공유 예정**

## Test list 📝
- [x] 빌드/테스트 통과
- [ ] 후속 검증 (예정)
```

### 2-3. 섹션 추가/생략 판단

| 섹션 | 추가 조건 |
|---|---|
| Why | **항상** |
| Changes | **항상** |
| 측정 결과 | 운영 효과 측정이 있을 때만 |
| 배포 | Canary / 단계적 배포가 있을 때만 |
| 후속 작업 | 별도 PR로 분리할 항목이 있을 때만 |
| 기존 동작 변경 | 기존 API·배치의 응답·검증·에러 코드가 바뀔 때 **반드시**. 리뷰어가 "의도한 변경인가요?"라고 묻게 만들지 않는다 (#800) |
| 리뷰 포인트 | 실패 시 동작·범위 밖으로 둔 위험·lint 확인 항목 사유가 있을 때. 미리 적으면 같은 질문이 리뷰로 돌아오지 않는다 (#799) |
| Test list | **항상** |

저장소 템플릿이 있으면 **템플릿의 필수 섹션이 이 표보다 우선**한다. 템플릿에 없는 섹션(측정 결과·배포·후속 작업·기존 동작 변경·리뷰 포인트)만 조건부로 추가한다.

**조건이 성립하지 않으면 섹션을 통째로 생략한다 (v0.6).** "기존 동작 변경 없음", "해당 없음" 한 줄을 쓰려고 섹션을 만들지 않는다. 리뷰 포인트에 "기존 동작 변경 없음"을 적는 것도 같다. 읽을 게 없는 섹션은 리뷰어 시간을 쓴다. 사용자가 요청했지만 조건이 안 되는 섹션(예: 단계적 배포가 없는데 배포 순서)은 사용자에게 사유를 말하고, 리뷰어가 알아야 할 사실(예: 신규 테이블 마이그레이션 포함)이 있을 때만 리뷰 포인트에 한 줄 적는다.

### 2-4. 표현 원칙 (사람 친화)

| ❌ 피할 표현 (jargon) | ✅ 바꿀 표현 (자연어) |
|---|---|
| `NEW 100% 후 ~56h, D+2d` | "4/27 시점, 100% 적용 약 2일 후" |
| `Retries exhausted` (영문 그대로) | "사용자 영향까지 도달한 실패" |
| `pendingAcquireTimeout 등` | "새로운 부작용 (풀 고갈 등)" |
| `maxIdleTime=20s, evictInBackground=60s` | "idle 20초 후 정리, 백그라운드 60초 주기 점검" |
| `burst 패턴` | "1분 burst (한꺼번에 ~10건)" |

규칙:
- **절대 시점 명시 필수** — 상대 표현(`D+2d` 등) 단독 금지. "4/27 (D+2d)" 처럼 절대값 우선
- **영문 기술용어 한국어 풀어쓰기** — 의미 전달 우선
- **수치 단독 노출 지양** — "20초/60초" 같은 의미가 드러나는 단위로

### 2-5. 링크 가드레일 (중요)

- ❌ `docs/...` 상대 링크 사용 금지
  - 본 프로젝트는 `docs/`가 `.git/info/exclude`로 git 추적 제외
  - GitHub PR 페이지에서 클릭해도 404
- ✅ "**상세 분석/측정 결과는 Notion으로 별도 공유 예정**" 한 줄로 안내
- ✅ 외부 공식 문서 링크 (Spring docs, AWS docs, RFC, 외부 API 제공자 공식 문서 등)는 OK

## Phase 3. PR 생성/수정

### 신규 생성

```bash
gh pr create \
  --base <dev|main> \
  --head <branch> \
  --title "<커밋 메시지 형식 한국어>" \
  --body "$(cat <<'EOF'
<본문>
EOF
)"
```

### 기존 PR 갱신

```bash
gh pr edit <PR번호> \
  --body "$(cat <<'EOF'
<본문>
EOF
)"
```

### 출력

PR URL 출력. 신규/갱신 여부 한 줄.

---

## 가드레일

- **target branch**: 일반 `dev`, hotfix는 사용자 명시 요청 시 `main`
- **제목/본문 한국어** (영문 commit type prefix는 OK: `fix:`, `feat:`, `refactor:` 등)
- **AI 공동작성자 표기 금지** (Co-authored-by 등)
- **Mermaid 사용 지양** — PR 본문 길어짐. 작업 문서로 위임
- **이미 열린 PR 있으면 신규 생성 금지** → `gh pr edit`으로 갱신
- **(v0.4) `review-lint.py` 위반이 있으면 푸시·PR 생성 금지** — 고친 뒤 재실행
- **저장소 `.github/PULL_REQUEST_TEMPLATE.md` 가 있으면 섹션명을 문자 그대로 사용** — 이모지 포함. 임의 축약·재작명 금지 (2-0 참조)

## 자기 검증 체크리스트

PR 생성/갱신 직전에 본문이 아래 기준을 모두 만족하는지 확인한다:

1. [ ] **저장소 템플릿**: `.github/PULL_REQUEST_TEMPLATE.md` 존재를 확인했고, 있으면 섹션명을 이모지까지 그대로 썼는가?
2. [ ] **분량**: 본문 100~200줄 이내 (코드 스니펫·SQL·mermaid 없음)
3. [ ] **Why 섹션**: 현상 + 원인 1~2문장. 자세한 분석은 위임
4. [ ] **Changes 섹션**: 파일별 표 (코드 스니펫 없음, 1파일 1줄)
5. [ ] **측정 결과**: 운영 효과 측정이 있을 때만, 표 형태 (baseline/method 등 자세한 건 ⚠️ 한계/잔존 1줄로 위임)
6. [ ] **배포**: Canary/단계적 배포가 있을 때만, 시점(절대 KST) + 무엇만
7. [ ] **후속 작업**: 별도 PR 항목이 있을 때만, 항목명 + 1줄
8. [ ] **Test list**: 항상 포함
9. [ ] **사람 친화 표현**: 영문 jargon 한국어 풀어쓰기, 절대 시점 명시, 수치 단독 노출 지양
10. [ ] **링크 가드레일**: `docs/...` 상대 링크 0개, 외부 공식 문서는 OK
11. [ ] **target branch**: 일반 `dev`, hotfix는 사용자 명시 시 `main`
12. [ ] **AI 공동작성자 표기 없음** (Co-authored-by 등)
13. [ ] **기존 PR 있으면**: 신규 생성 금지, `gh pr edit`으로 갱신
