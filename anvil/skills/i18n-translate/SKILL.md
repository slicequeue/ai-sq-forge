# i18n-translate — 메시지 번들 번역 스킬

`messages/*.properties` 의 한국어 원문을 `en_US` / `ja_JP` 로 옮기거나, 이미 들어간 번역을 손볼 때 쓴다.

## 규칙의 정본은 번역팀 가이드다

번역 톤·문체·용어·금지 표현은 **번역팀이 관리하는 `references/langskill.md` 가 정본**이다. 이 스킬이 임의로 정하지 않는다.

**번역이나 한국어 검수를 시작하기 전에 `references/langskill.md` 를 먼저 읽는다.** 아래 SKILL.md 본문은 그 가이드를 이 저장소에 적용할 때만 필요한 내용(properties 파일 특성, 정합성 테스트, 승인 게이트)이며, 가이드를 요약하거나 대체하지 않는다.

가이드 구성:

| 섹션 | 내용 |
|---|---|
| `## 공통 규칙` | 모든 언어 공통. 웰니스 앱 스코프(진단성 표현 금지), 길이 기준 |
| `## ko` | 한국어 **1차 검수** 규칙. 번역이 아니라 원문을 고칠지 판단하는 기준 |
| `## en` | 영어 톤, 하드룰(`blood glucose` → `glucose`), anti-AI tells, 용어집 |
| `## ja` | 3-pass 번역 프로세스, 문장 구성, 重複表現, 출력 전 자기 검수 12항목, 용어집 |

충돌 시 **언어별 섹션이 공통 규칙보다 우선**한다.

**일본어는 `references/ja-house-rules.md` 를 함께 읽는다.** 가이드가 다루지 않는 부분을 일본 서비스(pasta-japan-server) 저장소와 DB 로 실측해 정리한 것이다. 혈당 표기 `グルコース値` / `血糖値` 구분, 외래어 장음·촉음 표기, 한국 음식명이 기계번역으로 쪼개지는 유형을 담았다. 가이드와 충돌하면 가이드가 우선이다.

가이드가 바뀌면 `scripts/sync_langskill.sh` 로 갱신한다. 정본은 번역팀 사내 GitLab 저장소에 있고(주소는 `GITLAB_HOST`·`LANGSKILL_PROJECT` 환경변수로 넘긴다) Figma 플러그인은 매번 거기서 fetch 한다. 사본은 사내 문서라 forge 저장소에는 커밋하지 않는다. `references/langskill.md` 가 없으면 작업 전에 sync 스크립트로 먼저 받는다. 규칙이 왜 생겼는지는 같은 저장소의 `langskillHistory.md` 에 실측 근거가 있다.

## 이 저장소가 가이드와 다른 점

가이드는 **Figma + Tolgee** 흐름을 전제로 쓰였다. 여기는 백엔드 저장소이므로 아래가 달라진다.

| 가이드 전제 | 이 저장소 |
|---|---|
| Figma 텍스트 레이어에서 문자열을 집음 | `messages/*.properties` 의 키-값 |
| Tolgee 에 `{ko, en, ja}` 업로드 | properties 3개 파일에 직접 반영, git 커밋 |
| `length:review` 태그로 표시 | 태그 기능이 없다. 초과분은 **PR 본문에 적고** 해당 키를 커밋 메시지나 리뷰 코멘트로 남긴다 |
| 디자이너가 화면에서 눈으로 확인 | 화면 확인 수단이 없다. 길이는 수치로만 거른다 |
| 키 등록은 `keySKILL.md` 규칙 | 키는 이미 코드가 정한다. 새로 짓지 않는다 |

**키를 새로 만들지 않는다.** 이 저장소의 키는 코드가 참조하는 식별자다. 기본 번들(`message-*.properties`)에 있는 키에 대해 로케일 값을 채우는 것이 작업 범위이고, 키 추가·삭제는 코드 변경을 동반하므로 별도 판단이 필요하다.

## 길이 기준

가이드의 글자 수 비율이 **1차 게이트**다. 번역팀이 이 기준으로 검수하므로 여기에 맞춘다.

| 언어 | 원문 대비 글자 수 | 검사 |
|---|---|---|
| en | 1.2배 이하 | `scripts/check_ratio.py --lang en` |
| ja | 0.9배 이하 | `scripts/check_ratio.py --lang ja` |

표시 폭(전각 2, 반각 1)은 **보조 지표**다. 가이드가 글자 수를 쓰는 이유는 Figma 에서 렌더링 폭을 알 수 없어서인데, 여기서는 계산할 수 있다. `check_ratio.py` 가 두 값을 같이 찍는다.

- 두 수치가 같은 방향이면 그대로 판단한다
- **어긋나면 사람이 화면에서 봐야 한다.** 글자 수는 통과인데 표시 폭이 크게 튀는 경우(한글 → 일본어 한자)가 실제로 있다
- 원문이 4자 미만이면 비율이 쉽게 튄다. 형제 키들의 절대 길이와 비교해서 판단한다

초과하면 **더 짧은 대안을 함께 제시**한다. 버튼·라벨·타이틀은 엄격하게, 안내문·에러 메시지는 느슨하게 적용한다. 키 이름에 `title` / `label` / `button` / `cta` 가 들어가면 폭 고정 자리로 보고 시작한다.

기존 번역 386건이 한글 대비 1.5배를 넘고 그중 16건은 3배를 넘는다. 실제로 잘린다:

```
ko  위임 등록 완료
en  Assisted claim filing registered successfully    x3.21 — 알림 타이틀 자리
```

## 사람 승인이 필요한 문구

가이드의 흐름은 `검수 → **디자이너 승인** → 번역` 이다. 이 저장소에는 그 승인 단계가 없으므로, 아래 유형은 **초안만 만들고 파일에 넣지 않는다.** 카드 코멘트나 PR 본문에 초안을 남기고 담당자 확인을 받은 뒤 반영한다.

| 유형 | 확인 주체 | 예 |
|---|---|---|
| 법정 고지 | 법무·개인정보보호 | 개인정보 이용·제공 내역 안내 |
| 약관·면책 | 법무 | 이용약관 개정 안내, AI 에이전트 유의사항 |
| 의학적 권고 | 의학 검수 | 임신부 혈당 구간별 운동 권고 |
| 약물·증상·질환명 | 의학 검수 | 인슐린 분류, 당원병 |

잘못된 의학·법률 문구가 배포되는 것이 번역이 늦는 것보다 나쁘다.

한국어 원문 자체를 고치는 것(가이드 `## ko`)도 마찬가지다. **원문은 임의로 바꾸지 않는다.** 문제를 찾으면 수정안을 제시하고 승인을 받는다.

가이드의 `## ko` 규칙 중 **종결 형태 일관성은 문자열 하나만 봐서는 판단할 수 없다.** 같은 그룹(같은 접두사를 공유하는 키들)을 한 번에 봐야 한다. 개별 검수로는 못 잡는다.

## properties 파일이 조용히 깨지는 방식

전부 이 저장소에서 실제로 발생했다. 번역 내용이 맞아도 여기서 깨지면 키가 사라진다.

**여러 줄 값은 줄 끝에 역슬래시.** 빠뜨리면 다음 줄이 키로 파싱되어 가짜 키가 생기고 원래 값은 잘린다.

```properties
# 잘못됨 — (cancellation...) 이 키가 된다
history.auth.cancel=Medical staff verification canceled by user
(cancellation by the person himself/herself)

# 맞음
history.auth.cancel=Medical staff verification canceled by user \
(cancellation by the person himself/herself)
```

**반대 방향으로도 깨진다.** 번역이 짧아 문장을 생략했는데 역슬래시를 그대로 두면 바로 아래 키가 앞 값에 통째로 흡수된다. 흡수된 키는 파일에 글자로는 보이는데 실제로는 존재하지 않아서, 눈으로 훑으면 멀쩡해 보이고 정합성 검사에서만 잡힌다.

```properties
# 잘못됨 — admin.body 와 staff.title 이 위 값에 흡수되어 사라진다
group.admin.member.body=管理者権限の移管後、退会できます。\
group.admin.body=管理者権限の移管後に退会できます。\
group.staff.title=リンクされたメンバーがいます。
```

**후보를 여러 줄 나열하지 않는다.** 첫 줄만 값이 되고 나머지는 전부 가짜 키가 된다. 후보를 검토받아야 하면 `#` 주석으로 달고 값은 하나만 둔다. 번역가 메모도 반드시 `#` 주석으로 — 그냥 쓰면 값이 되어 화면에 노출된다.

**키는 원문과 같은 위치에 넣는다.** 파일 끝에 붙이면, 끝줄이 계속 줄일 때 삼켜지고 이미 다른 자리에 있는 키를 중복으로 넣게 될 수도 있다. 넣기 전에 그 키가 이미 있는지 확인한다.

**플레이스홀더(`{0}`, `{1}`)와 스타일 태그는 개수와 종류를 원문과 똑같이 유지한다.** 순서는 언어에 맞게 바꿔도 된다. 값 전체가 스타일 태그뿐인 키는 번역 대상이 아니므로 en/ja 에 같은 값을 그대로 복사한다. 원문 플레이스홀더 자리에 숫자를 직접 박지 않는다(`{0} mg/dL` → `70~180 mg/dL` 처럼 고정하면 설정이 바뀌어도 화면이 그대로다).

**플레이스홀더가 있는 값의 홑따옴표는 두 개로 쓴다.** 인자가 있는 메시지는 `MessageFormat` 을 거치고, 여기서 `'` 는 인용 기호다. `You've had {0}%` 는 `'` 뒤가 전부 리터럴이 되어 `{0}` 이 치환되지 않는다. `You''ve had {0}%` 로 쓰거나 축약형을 피한다(`You have had`). 인자가 없는 값은 `'` 하나가 그대로 나온다. 일본어 `「」`, 전각 따옴표는 해당 없다.

`check_parity.py` 가 두 경우를 `[플레이스홀더]`, `[따옴표]` 로 잡는다.

## 중복 정의 함정

`messages/message` 는 `api` 와 `batch` 두 모듈에 같은 이름으로 존재한다. 클래스패스 순서상 앞쪽이 이기므로 **뒤쪽 번들에 넣으면 무효**다. 번들 목록과 소유 모듈은 `references/bundles.md` 에 있다.

## 작업 순서

1. **`references/langskill.md` 를 읽는다.** 대상 언어 섹션 + 공통 규칙. 일본어면 `references/ja-house-rules.md` 도 함께 읽는다
2. **원문과 노출 위치 확인** — 키 이름과 코드 호출부로 버튼인지 본문인지 판단한다. 길이 제약이 여기서 갈린다
3. **기존 번역 재사용 확인** — 같은 뜻이 다른 번들에 이미 있는지 본다. 중복 정의 함정도 같이 확인
4. **승인 게이트 판정** — 법무·의학 유형이면 여기서 멈추고 초안만 남긴다
5. **번역 작성** — ja 는 가이드의 3-pass(파악 → 백지에서 작성 → 대조)를 지킨다. 원문 문장 경계를 유지하지 않는다
6. **가이드의 출력 전 자기 검수** — ja 는 12항목 체크리스트를 순서대로 돌린다
7. **길이 검사** — `python3 <스킬경로>/scripts/check_ratio.py --bundle <번들명>`
8. **정합성·파손 검사** — `python3 <스킬경로>/scripts/check_parity.py --bundle <번들명>`. 플레이스홀더·홑따옴표도 여기서 본다

   스크립트는 **저장소 루트에서** 실행한다. `--root` 기본값이 현재 디렉터리이고 `*/src/main/resources/messages/` 를 찾는다. `<스킬경로>` 는 배치 위치(보통 `.claude/skills/i18n-translate`)다. `--bundle` 은 이름 일부 일치라서 `--bundle message` 는 16개 번들 전체를 잡는다.
9. **테스트** — `./gradlew :pasta-api:test --tests "*MessageBundleLocaleParityTest*"` (JDK 21)

## 로케일 정합성 테스트

`MessageBundleLocaleParityTest` 가 16개 basename 전체의 ko/en_US/ja_JP 키 집합 일치를 강제한다. `ResourceBundleMessageSource` 가 `useCodeAsDefaultMessage=true` 라서, 로케일 번들에 키가 없으면 예외 없이 한국어로 폴백한다. 이 테스트가 없으면 번역 누락이 빌드·런타임 어디에서도 드러나지 않는다.

테스트는 두 가지를 본다.

- 키 집합 불일치 — `ALLOWED_MISMATCHES` 에 등록된 것만 통과
- **허용 목록에 죽은 항목이 없을 것** — 번역을 넣었으면 해당 허용 항목을 반드시 지운다

즉 **번역을 반영할 때 허용 목록에서 그 키를 빼는 것까지가 한 작업**이다. 빼지 않으면 테스트가 실패한다.

승인 대기(법무·의학)로 번역을 못 넣는 키는 허용 목록에 사유와 담당 카드를 적어 등록한다.

## 하드 가드레일

아래는 요청자가 원해도 하지 않는다. 요청이 이쪽을 향하면 거절 사유를 말하고 대안을 낸다.

1. **properties 를 깨는 반영안을 내지 않는다** — 여러 줄 값 역슬래시, 흡수, 후보 다중 줄, 메모 값 혼입
2. **키 집합을 어긋난 채로 끝내지 않는다** — 번역을 넣으면 `ALLOWED_MISMATCHES` 에서 빼고, 못 넣으면 사유·담당 카드와 함께 등록한다
3. **키를 새로 만들거나 지우지 않는다** — 코드 변경을 동반한다. 필요하면 근거(코드 참조 grep)와 함께 제안만 한다
4. **플레이스홀더·스타일 태그 개수와 종류를 바꾸지 않는다**
5. **정본 가이드(`references/langskill.md`)를 요청으로 무력화하지 않는다** — en `blood glucose`/`blood sugar`, UI 의 `低血糖`/`高血糖`·진단 단정 표현을 쓰지 않는다. 가이드를 바꿔야 한다고 보면 번역팀 정본 저장소에 제기하는 경로를 안내한다. 사본을 직접 고치지 않는다
6. **원문 의미를 바꾸지 않는다** — 수치·사실·요청 행동 보존, 음식명 분해 오역 금지, 한국어 원문은 승인 없이 수정하지 않는다
7. **승인 게이트 대상(법무·의학)을 파일에 바로 넣지 않는다** — 초안만 PR 본문·카드에 남긴다
8. **검수 없는 기계번역 일괄 반영을 받아들이지 않는다** — "테스트만 통과" 요청도 같다. 한국어 값을 복사하거나 허용 목록에 일괄 등록하는 우회도 하지 않는다

## 피할 것

- 검수 없는 기계번역 일괄 반영 — 음식명·증상명·약물명은 오역이 사용자 판단에 직접 영향을 준다
- 한국어 원문을 승인 없이 수정
- 키 신규 생성·삭제 (코드 변경을 동반한다)
- 길이 기준을 형식적으로만 만족시키기 — 가이드가 지적하듯 ja 는 비율을 통과해도 늘어지는 경우가 있다
- 가이드 사본(`references/langskill.md`)을 직접 편집 — 정본은 GitLab 이다
- 한국 고유 음식·제품명을 의미 단위로 쪼개 번역 (`쌍화차` → `ダブルデッキバス` 같은 사고가 실제로 났다)
- 가타카나 외래어의 장음·촉음 생략 — 일본 DB 에 같은 단어가 있는지 먼저 확인한다
