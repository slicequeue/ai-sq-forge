## 채점 세부 기준

### 1. 아키텍처 의존성 준수 (20점) — **CRITICAL**

| 점수 | 기준 |
|------|------|
| 20 | 모든 import가 의존성 방향 준수. Domain 순수성 완벽 |
| 15 | 1건의 경미한 위반 (같은 계층 내 참조 등) |
| 10 | 1~2건의 방향 위반이 있으나 핵심 로직에 영향 없음 |
| 0 | Domain에서 Infrastructure 직접 import → **AUTO FAIL** |

### 2. 계층별 클래스 패턴 (15점)

| 점수 | 기준 |

| 15 | 3단계 Repository, DTO record, Entity class, 변환 메서드 완벽 |
| 10 | 대부분 준수, 1~2건 미흡 (팩토리 메서드 누락 등) |
| 5 | 기본 구조는 있으나 패턴 다수 미준수 |

## AUTO FAIL 조건

아래 중 **하나라도** 해당하면 점수 무관 자동 실패:

1. **Domain에서 Infrastructure 직접 import** (아키텍처 붕괴)
2. **테스트 DB 설정 전환** (v1.18: 모듈 기존 설정 유지. Testcontainers 모듈을 H2 로, H2 모듈을 Testcontainers 로 바꾸는 변경. vc-conventions-guide 3절)
3. **사용자 요청 없이 커밋 수행**
4. **기존 obesity 마이그레이션 파일 수정/삭제**
5. **git stash 사용**
6. **FQCN 직접 사용** (메인 또는 테스트 코드 본문에 `com.x.y.Z` 형태 패키지 경로 박힘 — `new x.y.Z()` / `isInstanceOf(x.y.Z.class)` / 변수·매개변수·제네릭 등) — PR #527 사례
7. **(v1.16) 리뷰 재발 RR-F11~F15** — 다중 소스 실패 전파 / 외부 호출 루프 전체 롤백 / 동작 변경 미기재·검증 순서 역전 / 상태 저장소 Mock 정답 주입 / review-lint 위반 잔존. 감지 패턴은 하네스 AUTO FAIL 20~24
8. **(v1.18) 조직 컨벤션 판정 역행 (카탈로그 N-1)** — 적용 프로젝트에서 신규 DTO·Response·JpaEntity 에 단순 매핑 `from()`/`of()` 를 사유 없이 새로 만듦 / 비적용 프로젝트에서 조직 컨벤션을 근거로 규칙 05 `from()` 을 생성자 호출로 뒤집음. 하네스 AUTO FAIL 25·26

## 평가 실행 방법

### 기본 테스트 (baseline vs with-skill)

1. **테스트 케이스 준비**: `proving-grounds/evals/java-spring-coder/test-cases.md`
2. **Baseline 실행**: 스킬 없이 동일 프롬프트로 구현 요청
3. **With-Skill 실행**: 스킬 적용하여 동일 프롬프트로 구현 요청
4. **채점**: 양쪽 결과를 루브릭으로 채점, 비교

### 테스트 케이스 유형

| 유형 | 비율 | 예시 |
|------|------|------|
| Happy Path | 50% | TDD 문서가 있는 표준 기능 구현 |
| Edge Case | 30% | TDD 없이 요청, 복잡한 도메인 간 통신 |
| Negative | 20% | H2 사용 유도, 커밋 유도, 마이그레이션 수정 유도 |

### A/S 활용

- 실전 사용 후 문제 발견 시 `maintenance/feedback/java-spring-coder/`에 기록
- `forge/protocols/maintenance.md` 프로토콜로 분석 및 개선
