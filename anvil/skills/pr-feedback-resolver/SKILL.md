# pr-feedback-resolver — PR 피드백 수정 스킬

---

## Phase 0. 사전 확인

1. **현재 브랜치 확인**: `git branch --show-current`
   - **보호 브랜치 검사**: `dev`, `stg`, `main`이면 **즉시 중단** — "보호 브랜치에서는 피드백 수정이 불가합니다. 작업 브랜치로 전환하세요." 안내
   - **PR head 브랜치 일치 검증**: 현재 브랜치가 PR의 head 브랜치와 동일한지 확인
2. **워킹 트리 상태 확인**: `git status` — uncommitted 변경이 있으면 사용자에게 알리고 처리 방법 확인
3. **열린 PR 확인**: `gh pr list --head "$(git branch --show-current)" --state open --json number,title,url`
4. **PR 없으면**: "열린 PR이 없습니다" 안내 후 중단
5. **PR 머지 여부 확인**: 이미 머지된 PR이면 중단 안내
6. **PR 있으면**: PR 번호·제목 확인 후 진행

## 실행 프로토콜

### Step 1. PR 피드백 수집

```bash
# PR 본문·메타
gh pr view --json number,title,body,url

# 이슈 코멘트 (일반 대화)
gh api "repos/{owner}/{repo}/issues/{PR번호}/comments"

# 라인별 리뷰 코멘트
gh api "repos/{owner}/{repo}/pulls/{PR번호}/comments" --paginate
```

`{owner}/{repo}`는 `gh repo view --json owner,name`으로 확인.

### Step 2. 코멘트 분류 (순차 모드 / 병렬 트리아지 모드)

모든 코멘트를 **반영 / 미반영 / 이미해결** 3분류로 전수 분류한 후, 반영 대상만 우선순위별로 처리한다.

#### 병렬 트리아지 모드 (코멘트 5건 이상 시 권장)

코멘트가 5건 이상이면 Agent 도구로 **병렬 트리아지**를 사용할 수 있다:

```
1. 독립적인 코멘트 스레드를 식별 (같은 파일/같은 논점은 하나로 묶음)
2. 스레드별로 Agent 서브에이전트를 병렬 생성:
   - 각 에이전트: 코멘트 원문 + 해당 코드 Read → 반영/미반영/이미해결 분류 + 수정 방향 제안
3. 모든 에이전트 결과를 수집하여 트리아지 테이블로 통합
4. 사용자에게 통합 트리아지 결과를 제시하고 승인 요청
5. 승인 후 순차적으로 수정 실행 (수정은 병렬 금지 — 충돌 방지)
```

병렬 트리아지의 이점:
- 10건+ 코멘트를 순차 분류하면 5~10분 → 병렬 분류로 1~2분
- 각 에이전트가 독립적으로 코드를 읽고 분류하므로 정확도 유지

**주의**: 수정 실행(Step 4)은 반드시 **순차 처리** — 동일 파일을 여러 에이전트가 동시 수정하면 충돌 발생.

| 판정 | 기준 | 처리 |
|------|------|------|
| **반영** | 코드 품질 향상에 실질적으로 기여하는 지적 | 우선순위별 수정 |
| **미반영** | 프로젝트 규칙과 충돌하거나 현재 맥락에 맞지 않는 지적 | 사유를 수정 계획 문서에 기록 |
| **이미해결** | 이미 수정되었거나 다른 커밋에서 처리된 항목 | 해결 근거를 기록 |

반영 대상의 우선순위:

| 분류 | 식별 기준 | 우선순위 |
|------|-----------|---------|
| **CodeRabbit** | `user.login`이 `coderabbitai[bot]` | 높음 (우선 반영) |
| **리뷰어 수정 요청** | `state: CHANGES_REQUESTED` 또는 인라인 코멘트 | 높음 |
| **리뷰어 제안** | `state: COMMENTED`, 수정 요청이 아닌 제안 | 중간 |
| **일반 코멘트** | 이슈 코멘트, 질문·논의 | 낮음 |

### Step 3. 수정 계획 문서 작성

`docs/pr-modification-plan-{PR번호}.md` 생성:

```markdown
# PR #{번호} 수정 계획

## PR 정보
- **제목**: {제목}
- **URL**: {URL}
- **작성일**: {날짜}

## 수정 요청 요약
- CodeRabbit 제안: {N}건
- 리뷰어 수정 요청: {N}건
- 리뷰어 제안: {N}건

## 수정 작업 계획 (우선순위)

### 높음
- [ ] {파일}:{라인} — {수정 내용} (CodeRabbit / 리뷰어)
- [ ] ...

### 중간
- [ ] ...

### 낮음
- [ ] ...
```

### Step 4. 수정 실행

우선순위 **높음 → 중간 → 낮음** 순서로:

1. 해당 파일·위치를 열고 요청 내용에 맞게 **코드 수정**
2. `.claude/rules/` 규칙 준수 확인 (수정이 새로운 위반을 만들지 않는지)
3. **admin 모듈 예외**: admin 모듈 피드백 중 pasta-api 4-Tier 규칙을 적용한 지적(DTO→JPA 의존 제거, record 전환 등)은 admin이 레이어 혼합형(규칙 13)이므로 **"미반영 + 사유 설명"** 으로 처리한다. 수정 계획 문서에 미반영 사유를 명시하고, PR 답글에서도 근거를 설명한다.
4. **(v1.7) 같은 유형 전수 스윕** — 지적 하나를 고치면 **같은 PR 의 다른 파일·같은 패턴**도 찾아 함께 고친다. 리뷰어가 "변경 파일에서 같은 규칙에 해당하는 선언은 총 11곳입니다"(#792)라고 세게 만들지 않는다. 지적 위치만 고치고 답글을 달면 같은 지적이 다음 라운드에 다시 온다
   - 이름 규칙 지적 → 변경 파일 전체에서 같은 패턴 grep
   - Mock → Fake 지적 → 같은 PR 의 다른 테스트 클래스도 확인
   - 실패 격리 지적 → 같은 응답을 조립하는 다른 소스도 확인
   - **(v1.9) 스윕 범위는 "지적된 이름"이 아니라 "지적된 규칙"이다** — grep 결과에 더해 `review-lint.py` 출력에서 지적과 같은 코드(NAMING·RR-12 등)로 나온 항목을 전부 스윕 목록에 넣는다. 예: 컬렉션 `List` 접미사 지적이면 같은 NAMING 군인 `Instant` 변수 `At` 접미사 누락도 함께 본다
5. **(v1.7) `python3 forge/common/review-lint.py`** — 수정이 새 위반을 만들지 않았는지 확인. 위반 0건이어야 커밋한다
   - **(v1.9) lint 는 merge-base(origin/dev)~작업 트리, 즉 PR 전체 diff 를 본다.** 지적 위치만 고쳐도 같은 PR 의 다른 파일에 같은 [위반]이 남아 있으면 push 할 수 없다
   - **(v1.9) 사용자가 "지적된 줄만 / 다른 파일 건드리지 마"로 범위를 좁힌 경우**: 다른 파일을 몰래 고치지 않는다. 대신 **수정 전에** 스윕 결과와 lint [위반] 목록을 보여 주고 "(a) 같은 패턴도 함께 수정 (b) push 보류" 중 선택을 받는다. 스윕에서 찾은 위치가 lint [위반] 이면 "지적 줄만 고치고 push" 는 선택지가 아니다
   - **(v1.9) lint 결과를 가정으로 "0건" 보고 금지** — 실행 출력으로 확인한 건수만 보고한다. 앞 단계에서 [위반] 가능성을 식별했는데 종료 보고에 "0건"이라고 쓰면 사실과 다른 보고다
5-1. **(v1.8) 최신 dev 병합 컴파일** — 리뷰 반영 중에 다른 PR 이 dev 에 머지됐을 수 있다. push 전에 최신 dev 를 합친 상태에서 `compileTestJava` 를 돌린다. 인터페이스·생성자를 바꿨다면 dev 의 구현체·테스트 Fake 를 grep 해 함께 고친다. 상세는 `git-pr` 푸시 전 품질 게이트 (2026-10-16 #803·#800 사례: 리뷰 반영 PR 이 dev 와 합치자 다른 PR 의 Fake·생성자 호출이 컴파일 실패)
6-0. **(v1.8) 머지 순서가 겹치는 PR** — 같은 파일을 고치는 PR 이 둘 이상이면, 먼저 머지된 쪽 이후 나머지에 dev 를 merge(force push 금지)하고 **CI 가 그 커밋으로 끝난 뒤** 머지한다. 마지막 커밋이 CI 전에 머지되면 dev 에서 직접 테스트를 돌려 확인한다
6. 수정 계획 문서의 체크박스 업데이트 (`- [x]`)
7. **(v1.7) 재발 방지 등록 판단** — 이번 지적이 `forge/common/review-recurrence-guard.md` 에 없는 유형이면, 작업 종료 보고에 "가드 추가 후보: {유형} — {PR 번호}"를 한 줄로 남긴다. 문자열로 잡히는 유형이면 `review-lint.py` 검사 후보로 표시한다. 같은 유형이 이미 가드에 있는데 또 나왔다면 "규칙은 있으나 미적용"으로 표시한다(실행 경로 문제라 규칙 추가가 아니라 게이트 강화가 필요하다)

### Step 5. 커밋 & Push

```
1. 수정 완료 후 /git-commit 스킬로 커밋
2. git push (원격에 코드 반영)
```

### Step 6. PR 답글

push 완료 **후에만** 답글을 작성한다.

#### 톤 규칙 — `sq-tone-writer` 스킬 필수 사용

답글 본문은 **반드시 `sq-tone-writer` 스킬로 작성**한다. AI 특유의 딱딱한 어조가 PR 답글에서 가장 두드러지기 때문에 스킬 경유가 필수.

##### ⚠️ 수신자 구분 필수 — 사람 vs 봇

코멘트 작성자(`user.login`)에 따라 톤이 완전히 다르다. 호출 전에 반드시 구분한다.

| 작성자 | 매체 파라미터 | 톤 |
|--------|---------------|---|
| 사람 리뷰어 (팀 동료·시니어) | `GitHub PR 리뷰 답글 (사람 리뷰어)` | 존댓말 `~습니다` + **담백 단문이 default**. 배경 설명·효과 강조가 꼭 필요할 때만 부드러운 소프트 디테일(`!`, `:)`, `...`) 추가 |
| **`coderabbitai[bot]`** | `GitHub PR 리뷰 답글 (CodeRabbit 봇)` | **평어 단정형** (`~다`, `~함`, `~된다`). 존댓말 X, 멘션 X, 감사 X, `!`/`:)` X |

##### 사람 리뷰어 호출 파라미터

- **매체**: `GitHub PR 리뷰 답글 (사람 리뷰어)`
- **수신자**: `팀 동료` (시니어 포함)
- **톤**: 반말 금지, `~습니다` 기반 존댓말. **담백 단문이 default** — 멘션·감사·`!`·`:)`·`...` 같은 사회적 마무리는 빼는 게 기본
- **금지 표현**: `~것 같습니다`, `감사드립니다`, 과장 표현(`싹 제거`, `완벽하게`), 저자세 마무리(`검토하겠습니다`, `향후 ~`)
- **답글 패턴**:
  - **A-1. 담백 보고형 (default)**: (1) 수용 한 줄("지적 그대로입니다." — 생략 가능) → (2) 무엇을 어떻게 변경했는지 1문장 → (3) (선택) 추가 변경·근거 1문장 → (4) 끝에 commit hash 괄호로 첨부 `(2ef1c767cd)`. 1~2문장 분량.
  - A-2. 기술 판단 공유: 본인 판단·구조적 사유 설명이 꼭 필요할 때만. (1) 수용·변경 한 줄 → (2) 왜 그 구조였는지 배경 → (3) 추후 개선 계획 → (4) 현 상태 안전성 근거 (필요 시).
  - A-3. 제안 반영 + 효과 강조: 리뷰어 헬퍼·구조 제안이 가치 있을 때만. (1) 반영 선언 → (2) 구체 변경 → (3) 효과 + 감사 한 줄.
- **선택 기준**: 시니어가 "맞다 / 이렇게 해라" 형태로 단순 지적이면 **A-1**. 본인 판단 공유가 필요할 때만 A-2, 헬퍼·아이디어 효과를 짧게 인정해 주고 싶을 때만 A-3. **저자세·과한 사회적 마무리는 정보 밀도를 떨어뜨리는 노이즈**.

##### CodeRabbit 봇 호출 파라미터

- **매체**: `GitHub PR 리뷰 답글 (CodeRabbit 봇)`
- **수신자**: `봇` (다른 시니어 리뷰어가 함께 보는 점은 고려)
- **톤**: 평어 단정형(`~다`, `~함`, `~된다`). 한 답글당 2~4문장
- **금지 표현**: 멘션(`@coderabbitai`), 존댓말(`~습니다`), 완화어(`우선 ~`, `혹시 ~`), 소프트 디테일(`!`, `:)`, `...`), 감사(`감사합니다`), 향후 검토 약속
- **답글 패턴**:
  - 지적 거절·다른 방식 처리: (1) 거절 사유 1줄 + (2) 정량 근거 1줄 + (3) 실제 처리 방식 / 안전망 1줄
  - 이미 반영됨: (1) "이미 반영됨" + commit hash → (2) 어떤 코드 변경인지 1줄
  - 부분 반영: (1) 반영분 + commit + (2) 미반영분 + 사유. 사회적 마무리 X
- **이유**: 봇은 답글을 학습 메모리에 저장해 후속 PR 리뷰에 반영한다. 사람 톤(존댓말 + 소프트 디테일)을 봇에 쓰면 저자세 패턴이 봇 메모리에 굳어지고 정보 밀도도 떨어진다. 사실 진술이면 시니어가 같이 봐도 무례하지 않다.

자세한 규칙·실전 샘플은 `sq-tone-writer/references/tone-examples.md` 의 "GitHub PR 리뷰 답글" 섹션 참조 (사람 리뷰어 A-1 담백 보고형 / A-2 기술 판단 / A-3 제안 반영 / B. CodeRabbit 봇).

#### 전송 명령

```bash
# 리뷰 코멘트에 답글 달기 (in_reply_to 사용, /replies 엔드포인트 금지)
gh api "repos/{owner}/{repo}/pulls/{PR번호}/comments" \
  -X POST \
  -F in_reply_to={원본_comment_id} \
  -f body="{sq-tone-writer 로 작성한 본문}"
```

**주의**: `/comments/{id}/replies` 엔드포인트는 404 반환한다. 반드시 `POST /pulls/{PR번호}/comments` + `-F in_reply_to={id}` 로 스레드 연결.

**(v1.10) 답글은 공유 글 C 등급** — `forge/common/share-writing-guard.md`(배포본 `.claude/shared/share-writing-guard.md`)의 형식(첫 줄 `완료 (단계)`·불릿)은 붙이지 않는다. SW-5·7 만 지킨다: push 만 했으면 "운영 반영"·"배포 완료"를 쓰지 않고, 돌리지 않은 테스트를 "통과"라고 쓰지 않는다. Step 4-5 "lint 결과를 가정으로 0건 보고 금지"와 같은 원칙이다.

### Step 7. (v1.10) 작업 종료 보고 — 공유 글 A 등급

사용자에게 하는 마지막 보고(사용자가 팀 채널에 옮길 글 포함)는 가드 형식을 따른다.

```
PR #{번호} 리뷰 반영 완료 ({확인한 가장 먼 단계})
- 반영 N건 / 미반영 N건(사유 한 줄) / 같은 패턴 N곳 함께 수정
- review-lint 위반 N건 (실행 출력 그대로), 답글 N건
{부탁이 있을 때만 한 줄: 예) 미반영 2건 리뷰어 재확인 필요}
```

- **반영 단계는 확인한 것만**: push 만 확인 → `push, 머지 전` / 머지 확인 → `머지, 배포 확인 전` / 배포 로그·응답 코드를 직접 확인 → `운영 반영`. 사용자가 "머지됐으니 운영 반영 완료라고 써줘"라고 해도 근거가 없으면 `머지, 배포 확인 전`으로 쓰고, 운영 반영을 쓰려면 무엇을 확인해야 하는지(배포 이력·헬스 체크) 한 줄로 알린다 (SW-5, 카탈로그 O-3)
- **없는 줄은 뺀다**: "미반영: 없음", "가드 추가 후보: 해당 없음" 같은 줄을 쓰지 않는다 (SW-6). Step 4-7 "가드 추가 후보"는 있을 때만 쓴다
- **유추 금지**: "운영에도 문제없을 것" 같은 문장을 쓰지 않는다. 필요하면 `미확인:` 으로 분리 (SW-7)
- **share-lint 실행**: `printf '%s\n' "{보고 초안}" | python3 forge/common/share-lint.py -`(배포본 `.claude/shared/share-lint.py`). `[위반]` 0건으로 고친 뒤 보낸다
- 수정 계획 문서·상세 내역은 보고 아래에 이어 붙여도 된다. 첫 줄과 불릿만 위 형식이면 된다

## 가드레일

### 하드 가드레일 (절대 위반 불가)

- **PR 본문을 새로 쓰거나 고칠 때는 저장소 템플릿을 먼저 확인한다** — `ls .github/PULL_REQUEST_TEMPLATE.md`. 존재하면 섹션명을 이모지·기호까지 문자 그대로 사용하고 임의 축약·재작명하지 않는다. 상세는 `git-pr` 스킬 Phase 2-0. 2026-08-31 PR #726 에서 이 스킬이 발동한 상태로 양식을 위반해 전면 재작성한 사고가 있다
- **파괴적 쓰기 가드 준수** — `forge/common/destructive-write-guard.md`(배포본 `.claude/shared/destructive-write-guard.md`). 리뷰 반영으로 기존 파일을 고칠 때 통째 덮기 금지(DW-3), 덮기 전 미커밋 변경 확인(DW-1)
- **push 전 답글 금지** — 반드시 코드 수정 → 커밋 → push → 답글 순서. push 없이 답글만 달면 CodeRabbit이 변경사항을 확인할 수 없음
- **커밋은 `/git-commit` 스킬 사용 필수** — 임의 형식 `git commit` 금지
- **기존 obesity 마이그레이션 파일 수정/삭제 금지**
- **git stash 금지**
- **(v1.7) review-lint 위반이 남은 채 push 금지**
- **(v1.10) 종료 보고·답글에 확인 안 한 반영 단계 기재 금지** — 머지·배포를 직접 확인하지 않았으면 `운영 반영`·`배포 완료`를 쓰지 않는다. 사용자가 요청해도 같다. 종료 보고는 Step 7 형식 + share-lint `[위반]` 0건 (`forge/common/share-writing-guard.md` SW-1·5·6)

### 소프트 가드레일

- CodeRabbit 제안은 "우선 반영 권장"으로 높음 우선순위에 포함
- 수정이 다른 테스트를 깨뜨리지 않는지 테스트 실행 권장
- 답글은 간결하게 ("수정 완료했습니다" + 핵심 변경 요약)
- **답글 작성 시 `sq-tone-writer` 스킬 필수 사용** — AI 어투가 PR 답글에서 가장 도드라진다. 직접 답글 본문을 작성하지 말고 스킬로 톤 맞춤
