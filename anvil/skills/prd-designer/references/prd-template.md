## 문서 구조

```markdown
# [기능명] PRD

## 1. 배경 및 목적
## 2. 목표 (Goals)
## 3. 범위 (Scope)
## 4. 사용자 시나리오 (User Stories / Scenarios)
## 5. 기능 요구사항 (Functional Requirements)
## 6. 비기능 요구사항 (Non-Functional Requirements)
## 7. 제약 및 가정 (Constraints & Assumptions)
## 8. 성공 지표 (Success Metrics)
## 9. 미결 사항 (Open Questions)
```

## 섹션별 작성 가이드

### 1. 배경 및 목적

- 이 기능이 왜 필요한가? (현재 문제, 사용자 불편, 비즈니스 목표)
- 해결하려는 핵심 문제를 **한 문장으로** 요약
- 좋은 예: "현재 종료된 레이스가 수동으로만 완료 처리되어, 운영팀이 매일 30분씩 수작업을 하고 있다"
- 나쁜 예: "레이스 완료 처리 기능이 필요하다" (왜 필요한지 빠져있음)

### 2. 목표

- **측정 가능한 형태**로 작성
- 좋은 예: "종료일이 지난 레이스가 자동으로 완료 상태로 전환된다"
- 나쁜 예: "레이스 관리를 개선한다" (무엇이 개선인지 불분명)

### 3. 범위

- **In Scope**: 이번에 포함되는 것 (구체적으로)
- **Out of Scope**: 이번에 포함되지 않는 것 (오해 방지용으로 명시)
- Out of Scope는 "안 하는 이유"를 간단히 덧붙이면 좋다

### 4. 사용자 시나리오

- **Who**: 대상 사용자
- **What**: 사용자가 하는 행동 또는 시스템이 자동으로 처리하는 내용
- **Why**: 그 행동의 목적
- 예시: "사용자가 레이스 상세 페이지에 접근하면, 이미 종료된 레이스는 '완료' 배지가 표시된다"

### 5. 기능 요구사항

- 시스템이 **반드시 해야 하는 것** (번호 목록)
- 각 항목은 완전한 문장으로
- 예: "FR-1. 매일 자정, 종료일이 지난 진행 중인 레이스는 자동으로 완료 처리된다"

### 6. 비기능 요구사항

- 성능, 안정성, 보안 등 (기술 방식은 기술하지 않음)
- 예: "NFR-1. 자동 완료 처리는 서비스 운영에 영향을 주지 않는 시간대에 실행된다"
- 예: "NFR-2. 처리 대상이 10,000건 이상이어도 정상 동작해야 한다"

### 7. 제약 및 가정

- 전제하는 조건, 외부 의존성, 알려진 제약
- 예: "레이스 종료일은 항상 UTC 기준으로 저장되어 있다고 가정한다"

### 8. 성공 지표

- 이 기능이 잘 동작하는지 확인하는 **구체적 방법**
- 예: "배치 실행 후 진행 중 상태인 만료 레이스가 0건이다"
- 예: "운영팀의 수동 완료 처리 건수가 0건으로 감소한다"

### 9. 미결 사항

- 아직 결정되지 않은 것, 확인이 필요한 것
- 반드시 **누구에게** 확인해야 하는지 함께 기록
- 예: "종료일 당일에 완료 처리할지, 익일에 할지 — 기획팀 확인 필요"

## 경량 PRD 구조

단순한 기능(CRUD, 필드 추가 등)은 아래 4섹션으로 충분하다:

```markdown
# [기능명] PRD (경량)

## 1. 배경 및 목적
## 2. 목표 (Goals)
## 3. 기능 요구사항 (Functional Requirements)
## 4. 범위 (Scope)
```
