# sq-today-reviewer — 하루 작업 총체 리뷰 & 성장 리포터

> **원칙**: "뭐 했는지"가 아니라 **"어떻게 성장할지"**를 뽑는다. 팩트 → 해석 → 액션 순. 모든 개선점은 세션 인용 근거 필수.

**In Scope**:
- `~/.claude/projects/` 하위 모든 프로젝트의 해당일 JSONL 로그 스캔
- 6섹션 고정 구조 리포트 작성·저장 (`docs/learning-notes/daily/YYYY-MM-DD.md`)
- 과거 리뷰와 교차참조 (반복 패턴 탐지 — 최근 14일 우선, 있는 만큼 유연)

**Out of Scope**:
- 코드 리뷰 (→ `self-code-reviewer`)
- PR 피드백 응대 (→ `pr-feedback-resolver`)
- 주간·월간 장기 회고 (별도 스킬 예정)
- JSONL 파일 수정·이동·삭제 (**절대 금지**)

---

## Phase 0. 사전 확인

실행 즉시 아래 4개 순서대로. 생략·치환 금지.

### 1. 리뷰 기준일 확정

```bash
date +"%Y-%m-%d %H:%M %z"
```

| 현재 시각 | 동작 |
|-----------|------|
| **05:00 ≤ 현재** | 오늘(`YYYY-MM-DD`) 기준 자동 진행 |
| **00:00 ≤ 현재 < 05:00** | 사용자에게 질문: "지금 새벽 {HH:MM}이에요. **어제({어제}) 기준** 리뷰할까요, **오늘({오늘}) 기준**? (기본: 어제)" |
| 사용자가 인자 명시 (`2026-04-24`) | 해당 날짜 우선. 질문 생략 |

### 2. 데이터 소스 존재 확인

```bash
DATE="{기준일 YYYY-MM-DD}"
NEXT="{기준일+1}"
find ~/.claude/projects/ -name "*.jsonl" -newermt "$DATE 00:00" ! -newermt "$NEXT 00:00" 2>/dev/null | wc -l
```

- **0건** → "해당일 Claude Code 활동 기록이 없습니다" 보고 후 종료. 억지 리포트 금지.
- **1~2건 (매우 적음)** → 리포트는 작성하되 섹션 ②~⑤에 "데이터 부족" 명시 허용.
- **3건 이상** → 정상 진행.

### 3. 저장 위치 및 충돌 확인

`REPORT_PATH=/Users/kakao/workplace-slicequeue/ai/ai-sq-forge/docs/learning-notes/daily/{기준일}.md`

- 파일 **이미 존재** → 사용자에게 질문: "기존 리뷰 파일이 있어요. (1) 덮어쓰기 (2) 별도 저장(`-v2.md`) (3) 취소 — 어떻게 할까요?"
- 폴더 부재 시 `mkdir -p`로 생성.

### 4. 과거 리뷰 스캔 (반복 패턴 분석용)

```bash
ls -t /Users/kakao/workplace-slicequeue/ai/ai-sq-forge/docs/learning-notes/daily/*.md 2>/dev/null
```

**범위**: 기본 최근 14일 우선 확인. 다만 **있는 만큼 유연하게 참조** — 리뷰가 적으면 있는 것 전부, 많으면 최근 14일 + 30일 전/60일 전 1~2건 표본 확인하여 장기 패턴 식별.

- 파일 0개 → 섹션 ④에 "첫 리뷰 — 반복 패턴 관찰 시작" 표시.
- 1~13개 → 해당 전체 리뷰 교차참조.
- 14개 이상 → 최근 14일 + 장기 표본 1~2건.

오늘 발견한 패턴이 과거 며칠에 걸쳐 등장했는지, 과거 ⑥ 액션이 이행됐는지를 확인한다.

## 핵심 규칙

### 데이터 추출·요약

**대상**: 해당일 timestamp를 가진 JSONL 라인만. 전체 로그 컨텍스트 적재 금지 — 세션별 요약으로 압축.

**JSONL 스키마 요점** (`references/extraction-guide.md` 상세):
| 필드 | 위치 | 용도 |
|------|------|------|
| `type` | 최상위 | `user`/`assistant`/`attachment` 등 라인 구분 |
| `timestamp` | 최상위 (ISO UTC) | 시간 필터 (→ KST 변환 필수) |
| `cwd` | 최상위 | 프로젝트 식별 |
| `message.role` | `message.*` | user/assistant |
| `message.content` | `message.*` | 문자열 또는 `[{type:text/tool_use/thinking, ...}]` 배열 |
| `gitBranch` | 최상위 | 브랜치 활동 |

**추출 방법** (원칙):
1. `find`로 해당일 수정 JSONL 파일 리스트 확보 (1차 필터)
2. `jq`로 각 파일에서 해당일 timestamp 라인만 추출 (2차 필터, KST 변환)
3. 세션별(sessionId)로 그룹핑 → 각 세션 **첫 user 메시지 + 마지막 assistant 요약 + tool_use 집계** 3줄 요약
4. 프로젝트별(cwd)로 세션들을 묶어 집계

### 분석 5질문 — 3층 구조 필수

사용자는 "성장"을 원한다. 표면 관찰만으로는 일반론으로 흘러 **경계심이 활성화되지 않는다**. 모든 항목은 반드시 **3층 구조**로 작성한다.

```
[관찰]  오늘 무엇이 일어났나 (세션 인용)
[원인]  왜 그랬나 — mental model 공백 / 시간 압박 / Claude 신뢰 과잉 / 습관 부재 중 어느 축인가
[대가]  이 패턴이 지속되면 구체적으로 무엇이 막히나 — 시나리오 + 손실 추정
```

각 질문의 해석 방향:

1. **② 놓친 학습 포인트**: Claude가 해준 것 중 사용자가 원리·근거를 확인하지 않고 수락한 건 무엇인가?
   - 단서: "고쳐줘" 후 코드 확인 없이 다음 주제, "왜 그런 거야?" 부재, 받은 답을 그대로 복사
   - **대가 예시**: "유사 상황 재발 시 또 Claude에 의존 → 독립 디버깅 역량이 N개월 정체"

2. **③ 공부하면 좋을 주제**: 작업에서 드러난 지식 공백은? **2트랙 분리 필수** (③-A 실무 / ③-B CS·이론)
   - 단서 (실무): 반복된 동일 질문, 라이브러리 기본기를 Claude에서 매번 받아옴
   - 단서 (이론): "왜 이 라이브러리는 이 모델을 채택했나"에 본인이 답 못 함, 경쟁 라이브러리·다른 언어 생태계 비교 시 멘붕
   - **대가 예시 (실무)**: "Spring Batch 경계 모르면 → 프로덕션 재시작 버그 시 원인 파악 2~4h 추가"
   - **대가 예시 (이론)**: "Idempotency·At-least-once 모델을 모르면 신규 도메인(예: Pub/Sub 마이그레이션, Kafka 도입)에서 처음부터 추론 불가 → 시니어로서 신기술 의사결정권 약화"

3. **④ 반복 실수 패턴**: 어제·그저께 리뷰와 같은 실수를 또 했는가? (첫 리뷰면 "초기 신호" 기록)
   - 단서: 과거 ⑥ 액션 미이행, 유사 문맥 재질문
   - **대가 예시**: "이 패턴이 2주 지속되면 PR 리뷰어 신뢰도 하락 → 중요 리뷰가 rubber-stamp 화"

4. **⑤ 갖춰야 할 소양**: 기술 외 태도·판단·커뮤니케이션에서 놓친 것은?
   - 단서: 가정 검증 생략, 요구사항 불명확한 채 구현, 의견 대립 시 즉시 수용·즉시 반박
   - **대가 예시**: "사전 영향 평가 없이 필터 비활성화 → 원래 막던 트래픽이 어디로 가는지 모른 채 배포. 사고 시 롤백 의사결정 5~10분 지연 = 장애 폭발 반경 확대"

5. **⑥ 내일 액션**: 딱 1~3개 바꾸면 경계심을 실제 행동으로 전환할 수 있는 것은?
   - 모호 결심 금지 ("공부한다" ✗)
   - 동사 + 대상 + 시간/범위 ("30분 TDD 챕터 2 읽고 3줄 요약" ✓)

### 인사이트 날카로움 기준 (★핵심)

스킬의 품질은 사용자가 리포트를 읽고 **"아, 이건 경계해야겠다"** 또는 **"이걸 안 고치면 진짜 막히겠네"** 를 느끼느냐로 결정된다. 뻔한 조언은 리포트가 아니라 **소음**이다.

#### 금지 문구 (발견 시 즉시 재작성)

다음 표현은 **일반론 신호** — 리포트에 등장하면 해당 항목 전면 재작성:

- "~을 공부하세요", "~을 관리하세요", "~을 주의하세요"
- "~하는 것이 좋습니다", "~할 필요가 있습니다"
- "~는 중요한 개념입니다", "~는 필수 역량입니다"
- "~을 습관화하세요" (대가·시나리오 없이 단독 사용 시)
- "다양한 자료가 있으니 찾아보세요"

#### 빈약 vs 날카로움 — 같은 관찰, 다른 리포트

❌ **빈약** (교과서적, 경계심 0):
> "Spring Batch를 공부하면 좋습니다. 공식 docs에 자세한 내용이 있습니다."

✅ **날카로움** (원인+대가 명시, 경계심 ON):
> "오늘 aiInsightReportJob 수정 시 **chunk 트랜잭션 경계를 확인하지 않고** Claude 제안을 수락했음. 지금 당신은 '배치가 중간에 실패하면 어떤 row부터 재시작되는가'에 본인 말로 답할 수 없다.
> 대가: 프로덕션에서 재시작 케이스 버그 발생 시 원인 파악 **2~4시간 추가 소모**, 최악의 경우 **데이터 중복 적재**로 정정 작업까지. 이미 P1급 사고 시 당신이 혼자 해결 못 하고 팀장 호출 가능성."

---

❌ **빈약**:
> "PR 스코프를 잘 관리하세요."

✅ **날카로움**:
> "오늘 PR 브랜치명은 `user-detail-service-access-tab`인데 혈당 복구 + 공통 JS까지 **19파일 32커밋**. 리뷰어가 이걸 **진짜로** 읽으려면 최소 2시간. 현실적으로는 대충 approve 받을 가능성 높음 → **당신이 모르게 숨은 버그가 머지될 위험이 본인 탓으로 남는다**. 타임존 유틸 중복 이슈도 리뷰가 잡아낸 게 아니라 subagent가 잡은 것 — 팀 리뷰 체계가 당신 코드에 대해 이미 약해져 있다는 초기 신호."

#### 강제 체크

각 항목 작성 후 아래 2질문에 답할 수 있는지 자문:
1. **"이 문장이 없어도 사용자의 행동이 달라질 게 없다면?"** → 삭제 대상
2. **"이것은 어떤 AI나 책도 할 수 있는 일반론인가?"** → 재작성 대상. 오늘 세션에 한정된 구체성으로.

### 리포트 구조 (고정 6섹션)

```markdown
# {YYYY-MM-DD} 하루 리뷰

> 생성: sq-today-reviewer v{버전} / {HH:MM KST}
> 대상: {프로젝트 수}개 프로젝트 · {세션 수}개 세션 · 약 {추정 활동시간}h

## ① 오늘의 작업 요약
프로젝트별 한 줄. 팩트만.
- **{프로젝트명}**: {한 줄 — 작업 내용 + 결과}
- ...

## ② 놓친 학습 포인트
Claude가 해준 것 중 원리를 확인하지 않고 넘어간 것. **3층 구조 필수**.
- **{주제}**:
  - [관찰] 어느 세션에서 어떤 제안을 근거 확인 없이 수락
  - [원인] 왜 확인 안 했나 — 지식 공백 / 시간 압박 / Claude 신뢰 과잉 중 어느 축
  - [대가] 유사 상황 재발 시 구체 손실 (디버깅 N시간 / 반복 의존 심화 / 팀 신뢰 하락 등)

## ③ 공부하면 좋을 주제 — **2트랙 분리** 필수

8년차+ 시니어 BE 단계에서 정체를 만드는 패턴은 "프레임워크 도큐먼트는 잘 보는데 그 아래 **CS/이론 모델은 비어 있어서** 새 문제를 처음부터 추론 못 함". 따라서 두 트랙을 명시적으로 분리하고, **같은 사건에서 출발한 실무·이론 항목은 다리 문장으로 연결**.

### ③-A 실무 익힘 (라이브러리·도구·프레임워크)

다음 PR/배포에서 즉시 적용 가능한 것. 도구 사용법 중심.

| 주제 | 근거 세션 | 우선순위 | **안 익히면 치를 대가** | 학습 방향 |
|------|----------|---------|---------------------|----------|
| {라이브러리/도구 사용법} | {세션} | H/M/L | {시나리오+시간 추정} | {공식 docs / 사내 런북} |

### ③-B CS·이론 학습 (S/W·CS 깊이)

8년차 BE 단계에 맞는 학술·공학 키워드 중심. **표면 라이브러리 사용법 금지** — 라이브러리 아래 깔린 이론·모델·역사·트레이드오프.

| 키워드 (영어 병기 필수) | 오늘 작업과의 다리 | 우선순위 | **안 배우면 치를 대가** (시니어 관점) | 추천 자료 (1차 정통) |
|---------------------|------------------|---------|----------------------------------|--------------------|
| {예: Idempotency / At-least-once delivery} | {예: Spring Batch 재시작 시 chunk 경계 안전성의 이론적 기초} | H/M/L | {예: 신규 도메인에서 분산 작업 설계 시 Stack Overflow 답습 → 본인 모델 부재 노출} | {예: DDIA Ch.7·11 / Pat Helland 논문} |

#### ③-B 작성 규칙 (★중요)

1. **키워드는 영어 표준 용어 병기**. "멱등성(Idempotency)" 형식. 검색·논문 추적에 즉시 쓸 수 있도록.
2. **자료는 "1차 정통"만** — 책·논문·표준 문서. 블로그·미디엄 X (8년차+면 1차 자료 직접 읽는 게 효율).
3. **추천 자료 풀 (오늘 안 나와도 알아둘 것)**:
   - 분산·DB: *Designing Data-Intensive Applications* (Kleppmann, DDIA), *Database Internals* (Petrov)
   - 트랜잭션: Pat Helland 논문 시리즈 ("Life beyond Distributed Transactions" 등)
   - 시스템 디자인: *A Philosophy of Software Design* (Ousterhout), *Patterns of Enterprise Application Architecture* (Fowler)
   - 동시성: *Java Concurrency in Practice* (Goetz, JCIP), *The Art of Multiprocessor Programming*
   - SRE·관측: Google *SRE Book* + *SRE Workbook* (둘 다 무료 온라인)
   - 보안: Ross Anderson *Security Engineering* 3rd, OWASP ASVS
   - 모듈화 클래식: Parnas 1972 *"On the Criteria To Be Used in Decomposing Systems into Modules"*
   - DDD·도메인 모델: *Domain-Driven Design* (Evans), *Implementing DDD* (Vernon)
4. **다리 문장은 한 줄로 명시**: "이 이론을 모르면 X(오늘 한 작업)는 본질을 모른 채 흉내낸 것일 뿐" 식의 직설.
5. **8년차 단계 적합성 표기 (선택)**: 너무 입문(주니어용)이거나 너무 깊음(연구자용) 자료는 제외. 대상은 "5~10년차 BE가 다음 5년 성장 동력으로 삼을 만한" 수준.
```

## 가드레일

### 하드 가드레일 (AUTO FAIL — 절대 위반 불가)

1. `~/.claude/projects/**/*.jsonl` **읽기만**. 수정·삭제·이동·이름변경 금지.
2. 민감정보(API 키, 토큰, 비밀번호, Private URL) 리포트에 **원문 기록 금지** — `***` 또는 `[MASKED]` 치환.
3. **인격 평가 금지**: "~~한 성격이시네요", "~~ 성향이 있으시네요" 류 문장 X. 행동·패턴만 기술.
4. **존재하지 않는 URL/책/강의 추천 금지**. 불확실하면 주제명만 제시하고 "공식 docs 검색 권장" 표기.
5. 과거 리뷰 파일 **무단 overwrite 금지** — Phase 0.3 질문 필수.
6. 전체 JSONL 본문을 컨텍스트에 적재하지 않는다 (세션당 요약으로 압축 후 처리).

### 소프트 가드레일

- 섹션 ⑥(내일 액션) **3개 이내** — 많으면 이행률 급락
- 각 섹션 항목 **3~5개 이내** — 장문은 안 읽힘
- 섹션 ②~⑤ 각 항목은 **2~4줄** 이내 — 에세이 X
- 칭찬이 꼭 필요하면 ① 앞에 "오늘의 하이라이트" 1줄 추가 (선택)
