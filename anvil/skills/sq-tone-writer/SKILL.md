# sq-tone-writer — 사용자 톤 라이터

> 원칙: **"AI가 쓴 티"를 없앤다.** 사용자가 직접 쓴 것처럼 자연스러운 톤으로 작성한다.

**범위**: 내부 커뮤니케이션, 문서 작성 전반 (슬랙, 보고, PR, 리뷰, 문서 초안)
**비범위**: 외부 공식 문서, 고객 대면 이메일, 법적 문서

---

## Phase 0. 작성 전 확인

1. **톤 적용 여부**: 사용자가 "내 말투로", "내 스타일로" 등 톤 적용을 요청했는가?
2. **대상 매체**: 슬랙 / PR / 리뷰 코멘트 / 문서 / 보고서 중 무엇인가?
3. **수신자**: 팀 동료 / 리더 / 전체 공유 중 누구인가? (수신자에 따라 반말↔존댓말 조절)

## 톤 프로파일: SQ Style

### 핵심 특성 5가지

| # | 특성 | 설명 | 예시 |
|---|------|------|------|
| 1 | **간결 직설** | 한 문장에 하나의 메시지. 불필요한 수식어/접속사 제거. 짧게 끊는다. | "싹다 가져와", "진행할 것" |
| 2 | **구어체 자연스러움** | 딱딱한 문어체가 아니라 말하듯이 쓴다. 구어 표현 허용. | "팍팍 써서", "어떄?", "없지?" |
| 3 | **결과 위임형** | 과정을 세세히 지시하지 않고 목표만 던진다. "알아서 해" 스타일. | "알아서 파악해서 개선하고 평가까지 해" |
| 4 | **관찰→제안** | 패턴을 발견하면 바로 개선을 제안한다. 수동적으로 기다리지 않는다. | "이런 패턴이 발견되었다. 체인화 해보면 어떄?" |
| 5 | **솔직한 피드백** | 과장 없이 있는 그대로 말한다. 좋으면 좋다, 아쉬우면 아쉽다. | "크게 느끼진 않았지만 반영 부탁한다" |

### 문체 규칙

#### 해야 하는 것

| 규칙 | 설명 | Good | Bad |
|------|------|------|-----|
| 짧은 문장 | 한 문장 15자 이내 권장, 최대 30자 | "진행해줘" | "그러면 이제 다음 단계를 진행해주시면 감사하겠습니다" |
| 구어 표현 | 자연스러운 일상어 사용 | "싹다 가져와" | "전부 가져오도록 하겠습니다" |
| 명령/요청 직접 표현 | 돌려 말하지 않고 바로 말한다 | "커밋해라" | "커밋을 진행하는 것이 좋을 것 같습니다" |
| 확인형 질문 | 짧은 질문으로 상태 체크 | "다 했니?", "없지?" | "혹시 완료 여부를 확인할 수 있을까요?" |
| 반말+존댓말 혼용 | 상황에 따라 자연스럽게 섞는다 | "이거 좀 봐줘", "성능 평가좀 해줄래?" | 전부 존댓말 또는 전부 반말로 통일 |

#### 하지 않는 것

| 금지 패턴 | 이유 | 예시 |
|-----------|------|------|
| 과도한 공손 표현 | AI가 쓴 티가 남 | "~해주시면 감사하겠습니다", "~하는 것이 좋을 것 같습니다" |
| 불필요한 접속사 | 문장이 길어짐 | "그러므로", "따라서", "이에 따라" |
| 감정 표현/이모지 | 사용자 스타일 아님 | "정말 좋은 것 같아요!", "완벽해요!" |
| 나열형 장문 | 핵심이 묻힘 | "첫째... 둘째... 셋째..." 식 장황한 나열 |
| 자기 검열 표현 | 단정 회피 | "아마도", "어쩌면", "~일 수도 있습니다" |

## 매체별 톤 조절

### 슬랙 메시지

가장 짧고 직접적. 1~3문장이 이상적.

```
Good:
"쿠폰 API 구현 완료. PR 올렸으니 확인 부탁."
"chaos monkey 테스트 돌려봤는데 60초 타임아웃이면 네트워크 에러 UI 안 뜸. 65초로 올려야 함."

Bad:
"안녕하세요, 쿠폰 API 구현을 완료하였습니다. PR을 올렸으니 확인해주시면 감사하겠습니다."
```

### PR 본문 / 리뷰 코멘트 (내부 작성)

약간 더 구조적이지만 여전히 간결. 핵심 변경만 요약.

```
Good:
"Domain JPA 위반을 가드레일급으로 격상.
이전에는 우선순위 2(아키텍처)로 보고했는데, 실전에서 놓치는 경우가 있어서
우선순위 1(가드레일 — 즉시 수정)로 올림."

Bad:
"본 PR에서는 Domain 계층의 JPA 어노테이션 위반 감지 시 보고되는 우선순위 등급을
기존 아키텍처 위반(우선순위 2)에서 가드레일 위반(우선순위 1)으로 상향 조정하였습니다."
```

### GitHub PR 리뷰어 답글 (외부 리뷰어 대응)

**상위 규칙 — 수신자에 따라 톤이 갈린다**:

| 수신자 | 톤 | 표현 |
|--------|---|------|
| 사람 리뷰어 (팀 동료·시니어) | **존댓말 `~습니다` 기반** + 부드러운 소프트 디테일 | `!`, `:)`, `...`, `우선 ~`, `~판단됩니당`, `@닉네임` 멘션 허용 |
| **CodeRabbit 봇** | **평어 단정형** (`~다`, `~함`) — 존댓말도 X | 멘션 X, 감사 표현 X, `!`/`:)` X, 사실 진술만 |

봇은 수치·근거를 학습 메모리에 저장해 후속 PR에 반영하므로 **사실 위주 컴팩트한 진술**이 가장 효율적이다. 사람 톤(존댓말 + 소프트 디테일)을 봇에게 쓰면 저자세로 보이고 정보 밀도도 떨어진다.

다만 봇 답글도 **다른 시니어 리뷰어가 함께 본다**는 점은 고려해 — 욕설·비속어·방어적 변명은 금지. 담담한 사실 진술이면 충분.

#### 사람 리뷰어 — 지적 수용 + 배경 설명 + 향후 계획 (표준 패턴)
```
Good:
"@리뷰어 우선 @Transactional 제거하고 사유 Javadoc 에 남겼습니다.

이 서비스 Spring 빈으로 등록하면 OAuth2 자동설정 부분 영향으로 구글 OIDC 로그인에 문제가 있었습니다... 이 부분 때문에 로그인 자체가 안 되는 이슈가 있었습니다. 그래서 불가피하게 빈이 아닌 new 로 생성하는 구조로 둔 상태입니다.

api 모듈 OAuth2AuthorizedClientService 구현 참고해서 추후 빈 등록하면서도 로그인 영향 없게 만들 수 있는지 시도해볼 예정입니다. 관련 우려사항은 Javadoc 에 주석으로 달아뒀습니다!

SimpleJpaRepository 가 단일 save/delete 트랜잭션을 자체 보장하므로 현 사용처는 문제 없을 것으로 판단됩니당"

Bad (반말):
"지적 정확. 제거했음. 빈 등록하면 로그인 깨졌음. new 로 둠."

Bad (AI 표현):
"좋은 지적 감사드립니다. 말씀하신 대로 @Transactional 이 무효인 것 같습니다.
혹시 괜찮으시다면 제거하는 것이 좋을 것 같아서 수정했습니다."
```

#### 사람 리뷰어 — 제안 반영 (짧게 감사)
```
Good:
"제안 그대로 반영했습니다.
redirectWithError, restoreSecurityContext 헬퍼로 분리하니 반복 5회 모두 제거되었습니다.
가독성 확실히 좋아졌습니다! 감사합니다:)"

Bad (과장):
"정말 완벽한 제안이었습니다! 덕분에 코드가 훨씬 깔끔해졌어요!"
```

#### 사람 리뷰어 — 구성 요소

| 요소 | 사용 규칙 |
|------|-----------|
| `@닉네임` 멘션 | 지적 수용 답글 첫머리에 권장 |
| "우선 ~" | 완화어, 첫 문장에 1회 |
| `...` | 해명 뒤 늘어뜨려 딱딱함 누그러뜨림 (1~2회, 남용 금지) |
| `!` | 동의/감사/결론 문장 끝에 강조용 |
| `:)` | 감사 마무리에 가끔. 매 답글에 쓰지 말 것 |
| `~판단됩니당` | 확언 살짝 부드럽게. 1회 이내 |
| 멘션 없이 시작 | 제안 반영 같이 짧은 답글에 |

#### 사람 리뷰어 — 피해야 할 표현

| 금지 | 대체 |
|------|------|
| `~것 같습니다` | `~로 판단됩니다`, `~인 상태입니다` |
| `감사드립니다`, `감사하겠습니다` | `감사합니다` 단독 |
| `싹 제거`, `완벽하게` 같은 과장 | `모두 제거되었습니다`, `확실히 좋아졌습니다` |
| 방어적 변명 ("제 의도는 그게 아니었고") | 수용 → 배경 → 계획 순으로 담담하게 |
| 장황한 서론 | 첫 문장부터 본론 |

#### CodeRabbit 봇 — 평어 단정형 (담담한 사실 진술)

봇 답글은 **사실 → 근거 → 안전망** 순서로 컴팩트하게. 멘션·감사·소프트 디테일 전부 제거. 한 답글당 2~4문장이 적정.

```
Good (지적 거절·운영 절차로 처리):
"cgm_measurement 에 연계 기록까지 묶여 있어서 어느 device row 를 살릴지 일괄 정책으로 묶기 어렵다. 운영 시작 이래 누적 케이스도 1건이라 자동 dedup 마이그레이션은 과함.

별도 DML 로 중복 정리 완료. V202604202053 은 그 위에서 적용된다."

Good (이미 반영된 경우):
"이미 반영됨 (commits ebd00ae~fa4ca83).

verify(eventPublisher, never()).publishEvent(any()) 로 fallback 경로 이벤트 발행 0회를 강제."

Bad (사람 톤을 봇에 적용 — 저자세):
"@coderabbitai 우선 의도를 정리하자면... 향후 동일 패턴이 반복되면 자동 마이그레이션 도입을 검토하겠습니다! 감사합니다:)"

Bad (반말 + 비속어):
"이거 케이스 하나뿐이라 굳이 자동 dedup 안 함. 알아서 봐."
```

##### 봇 전용 구성 요소

| 요소 | 사용 규칙 |
|------|-----------|
| 평어 어미 (`~다`, `~함`, `~된다`) | 기본형. 존댓말·반말 둘 다 X |
| 멘션 (`@coderabbitai`) | **사용 금지**. 첫 문장부터 본론 |
| `!`, `:)`, `~판단됩니당` | **사용 금지**. 평어로 단정 |
| `우선 ~`, `혹시 ~` 같은 완화어 | **사용 금지** |
| 감사 / 향후 검토 같은 사회적 마무리 | **사용 금지**. 마지막 문장도 사실 진술 |
| 코드 식별자 (commit hash, 메서드 시그니처) | 적극 사용 — 봇이 학습 메모리에 저장 |

##### 봇 답글 패턴

| 상황 | 패턴 |
|------|------|
| **지적 거절·다른 방식으로 처리** | (1) 거절 사유 1줄 + (2) 누적 사례·정량 근거 1줄 + (3) 실제 처리 방식 / 안전망 1줄 |
| **이미 반영됨** | (1) "이미 반영됨" + commit hash → (2) 어떤 코드 변경인지 1줄 |
| **부분 반영·향후 처리** | (1) 반영분 1줄 + (2) 미반영분 + 사유 1줄 (사회적 마무리 X) |

### 문서 / 보고서

구조는 갖추되 문장은 여전히 짧게. 표를 적극 활용.

```
Good:
"## 변경 요약
| 스킬 | 변경 | 이유 |
|------|------|------|
| self-code-reviewer | JPA 가드레일 격상 | 실전에서 누락 발생 |

크게 느끼진 않았지만, 놓치면 아키텍처가 무너지는 건이라 선제 반영."

Bad:
"본 보고서에서는 self-code-reviewer 스킬의 변경 사항을 상세히 기술합니다.
JPA 어노테이션 관련 위반 감지 시 보고되는 우선순위 등급이 변경되었으며..."
```

## 수신자별 톤 레벨

| 수신자 | 톤 레벨 | 반말/존댓말 | 예시 |
|--------|--------|-----------|------|
| 나 자신 (메모) | 가장 짧음 | 반말 | "배포 완료. 동기화 OK." |
| 팀 동료 | 간결 캐주얼 | 반말+존댓말 혼용 | "이거 확인 좀 해줘. PR 올렸으니." |
| 팀 리더 | 간결 존댓말 | 존댓말 기반 | "쿠폰 API 구현 완료했습니다. PR 확인 부탁드립니다." |
| 전체 공유 | 구조적 존댓말 | 존댓말 | 표/체크리스트 활용, 핵심만 |
| **CodeRabbit 봇** | 평어 단정형 | `~다`, `~함` (존댓말 X) | "이미 반영됨 (commits ebd00ae~fa4ca83). verify(eventPublisher, never())로 변경." |

## 절대 금지 / 반드시 수행

### 절대 금지

- **AI 냄새나는 표현**: "~하는 것이 좋을 것 같습니다", "혹시 괜찮으시다면"
- **장황한 서론**: "안녕하세요, 다름이 아니라..."
- **과도한 겸양**: "부족하지만", "혹시 실례가 안 된다면"
- **이모지 남용**: 사용자가 명시적으로 요청하지 않으면 사용 금지
- **반복 강조**: 같은 말을 표현만 바꿔 두세 번 반복. 특히 **요약과 이유 섹션에 동일 내용 중복 금지**
- **빈 껍데기 출력**: `[내용]`, `[여기에 작성]` 같은 플레이스홀더로 채우지 않는다. 내용이 부족하면 사용자에게 먼저 물어본다

### 반드시 수행

1. 작성 전 매체(슬랙/PR/문서)와 수신자 확인
2. 첫 문장에 핵심 결론 배치 (두괄식)
3. 문장 길이 체크 — 30자 초과 문장은 분리
4. 작성 후 "AI가 쓴 것 같은 표현" 셀프 체크
5. 사용자에게 초안 보여준 후 톤 확인 ("이 느낌 맞아?")
6. 거절/안내 메시지도 간결성 원칙 동일 적용 — 거절도 3문장 이내로
