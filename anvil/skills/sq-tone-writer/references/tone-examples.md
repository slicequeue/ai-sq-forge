## GitHub PR 리뷰 답글

수신자가 **사람인지 봇(CodeRabbit)인지에 따라 톤이 갈린다**.

| 수신자 | 톤 | 어미 | 멘션 / 소프트 디테일 |
|--------|---|-----|---------------------|
| 사람 리뷰어 (팀 동료·시니어) | 존댓말 + 부드럽게 | `~습니다` | 멘션 O, `!`, `:)`, `...` 허용 |
| **CodeRabbit 봇** | 평어 단정형 | `~다`, `~함`, `~된다` | 멘션 X, 소프트 디테일 X, 감사 X |

봇은 답글 내용을 학습 메모리에 저장해 후속 PR 리뷰에 반영하므로, **사실 → 근거 → 안전망** 구조의 컴팩트한 진술이 가장 효율적이다.

---

### A. 사람 리뷰어 — 실전 원문 샘플

반말 금지, `~습니다` 기반 존댓말 유지. 사용 케이스에 따라 톤 강도가 다르다.

| 케이스 | 패턴 | 길이 | 소프트 디테일 |
|--------|------|------|---------------|
| **A-1. 담백 보고형** (대부분의 단순 반영) | 사실 + commit hash | 1~2문장 | 멘션 X, `!`/`:)` X |
| A-2. 기술 판단 공유 | 수용 → 배경 → 계획 → 안전성 | 4문단 | 멘션 O, `!`/`:)`/`...` O |
| A-3. 제안 반영 + 효과 강조 | 반영 선언 → 변경 → 감사 | 3줄 | `!`/`:)` 가볍게 |

**기본은 A-1**. 시니어 리뷰가 "맞다 / 이렇게 해라" 형태로 단순 지적이면 담백 보고가 가장 깔끔하고 정보 밀도도 높다. 저자세·과한 사회적 마무리(감사 남발, "관련 이슈는 향후 ~") 는 오히려 노이즈.

A-2는 본인 판단·구조적 사유가 있어 **배경 설명이 꼭 필요한 경우**, A-3는 **리뷰어가 좋은 헬퍼·아이디어를 줘서 효과를 짧게 인정해 주고 싶을 때** 사용.

#### A-1. 담백 보고형 — 실전 원문 (PR #527, kyle-gy-khc 시니어 리뷰)

```
지적 그대로입니다. saveAndFlush 로 변경해서 INSERT 시점을 try 블록 안으로 강제했습니다. 테스트도 saveAndFlush 기준 stub 으로 갱신했습니다. (2ef1c767cd)
```

```
FQN 제거하고 import 로 정리했습니다. (2ef1c767cd)
```

```
ALGORITHM=INPLACE, LOCK=NONE 추가했습니다. 다른 모듈(pghd, commerce 등) ALTER TABLE 마이그레이션 관행과도 통일됩니다. (2ef1c767cd)
```

##### 구조

```
1. (필요 시) 수용 한 줄: "지적 그대로입니다." / 생략 가능
2. 무엇을 어떻게 변경했는지 1문장: "X 로 변경해서 Y 하도록 처리했습니다."
3. (필요 시) 추가 변경·근거 1문장: "테스트도 ~ 갱신했습니다." / "다른 모듈 관행과 ~ 통일됩니다."
4. 끝에 commit hash 괄호로 첨부: "(2ef1c767cd)"
```

##### 이 패턴의 핵심

- **존댓말은 유지**, 그러나 **`!`·`:)`·`...`·"감사합니다"·"검토하겠습니다" 같은 마무리는 빼는 게 default**
- "`X 로 변경해서 Y 하도록 처리했습니다`" — **변경 + 효과**를 한 문장에 압축
- commit hash 첨부로 변경 경로를 즉시 추적 가능하게 — 시니어가 다음 PR 리뷰 때 같은 코드 다시 안 들춰도 됨
- 시니어가 "그냥 이렇게 고치세요" 라고 단순 지적한 데에 본인 판단 길게 늘어놓지 않는다 — 정보 밀도 우선

#### A-2. 기술 판단을 공유할 때 (지적 수용 + 배경 설명 + 향후 계획)
```
@리뷰어 우선 @Transactional 제거하고 사유 Javadoc 에 남겼습니다.

이 서비스 Spring 빈으로 등록하면 OAuth2 자동설정 부분 영향으로 구글 OIDC 로그인에 문제가 있었습니다... 이 부분 때문에 로그인 자체가 안 되는 이슈가 있었습니다. 그래서 불가피하게 빈이 아닌 new 로 생성하는 구조로 둔 상태입니다.

api 모듈 OAuth2AuthorizedClientService 구현 참고해서 추후 빈 등록하면서도 로그인 영향 없게 만들 수 있는지 시도해볼 예정입니다. 관련 우려사항은 Javadoc 에 주석으로 달아뒀습니다!

SimpleJpaRepository 가 단일 save/delete 트랜잭션을 자체 보장하므로 현 사용처는 문제 없을 것으로 판단됩니당
```

#### A-3. 제안을 그대로 반영했을 때 (짧게 감사)
```
제안 그대로 반영했습니다.
redirectWithError, restoreSecurityContext 헬퍼로 분리하니 반복 5회 모두 제거되었습니다.
가독성 확실히 좋아졌습니다! 감사합니다:)
```

> 단순 반영 + commit hash 만으로 충분한 케이스에는 **A-1 담백 보고형**이 우선. 헬퍼 분리·구조 제안처럼 리뷰어 아이디어 자체가 가치 있어 효과를 짧게 인정해 주고 싶을 때만 A-3 패턴.

### 이 톤의 구성 요소

| 요소 | 설명 |
|------|------|
| 멘션 (`@닉네임`) | 직접 수신자 지정으로 시작. 지적 수용 답글에 권장 |
| "우선 ~" / "그래서 불가피하게 ~" | 사과·변명이 아니라 상황 설명을 담백하게 여는 연결어 |
| `...` | 해명 직후 살짝 늘어뜨려 딱딱함을 누그러뜨림. 남용 금지 (1~2회) |
| `!` | 강조 + 친근. 동의/감사/결론 문장 끝에 |
| `:)` | 마무리 감사. 가끔 사용 |
| `~판단됩니당` | 확언을 살짝 부드럽게. 과용 금지 (1회 이내) |
| `~싹 제거` 같은 과장 표현 지양 | 시니어 톤으로는 담백하게 "모두 제거되었습니다" |

### 하지 말 것 (PR 답글 전용)

| 금지 | 이유 |
|------|------|
| 반말 (`~함`, `~있음`) | 리뷰어가 외부/시니어일 때 무례하게 읽힘 — 존댓말 유지 |
| `~것 같습니다` | AI 냄새. `~로 판단됩니다`, `~인 상태입니다` 로 |
| 장황한 서론 ("바쁘실 텐데 리뷰 감사드립니다") | 본론 먼저 |
| 과장 표현 (`완벽하게 반영`, `싹 제거`) | 담백 톤에 어긋남 |
| 방어적 태도 ("그건 제 의도가 아니었고...") | 지적 수용 → 배경 설명 → 계획 순으로 담담하게 |

### 작성 패턴 (지적 수용 답글)

```
1. 즉시 수용 / 변경 내용 한 줄: "~ 제거하고 ~ 남겼습니다."
2. 왜 그 구조였는지 배경: "이 서비스 ~ 로 등록하면 ~ 이슈가 있었습니다..."
3. 추후 개선 계획: "~ 참고해서 추후 ~ 시도해볼 예정입니다!"
4. 현 사용처 안전성 근거 (필요 시): "~ 하므로 현 사용처는 문제 없을 것으로 판단됩니당"
```

### 작성 패턴 (제안 반영 답글)

```
1. 반영 선언: "제안 그대로 반영했습니다."
2. 구체 변경: "A, B 헬퍼로 분리하니 ~ 제거되었습니다."
3. 효과 + 감사: "가독성 확실히 좋아졌습니다! 감사합니다:)"
```

### B. CodeRabbit 봇 — 실전 원문 샘플

봇 답글은 **존댓말도 쓰지 않는다**. 평어 단정형(`~다`, `~함`, `~된다`). 멘션·감사·소프트 디테일 전부 제거. 한 답글당 2~4문장 적정.

#### 지적 거절·다른 방식으로 처리 (운영 절차로 처리한 케이스)

```
cgm_measurement 에 연계 기록까지 묶여 있어서 어느 device row 를 살릴지 일괄 정책으로 묶기 어렵다. 운영 시작 이래 누적 케이스도 1건이라 자동 dedup 마이그레이션은 과함.

별도 DML 로 중복 정리 완료. V202604202053 은 그 위에서 적용된다.
```

→ 구조: (1) 거절 사유 1줄 + (2) 정량 근거 1줄 + (3) 실제 처리 방식 / 안전망 1줄

#### 이미 반영됨 (다른 commit에서 처리)

```
이미 반영됨 (commits ebd00ae~fa4ca83).

verify(eventPublisher, never()).publishEvent(any()) 로 fallback 경로 이벤트 발행 0회를 강제.
```

→ 구조: (1) "이미 반영됨" + commit hash → (2) 어떤 코드 변경인지 1줄

#### 부분 반영 (지적 일부만 수용)

```
sensorId 검증 추가 부분만 반영 (commit a1b2c3d). null 가드는 상위 컨트롤러에서 이미 처리 중이라 중복 적용은 제외.
```

→ 구조: (1) 반영분 + commit + (2) 미반영분 + 사유. 사회적 마무리(감사 / 검토 / 향후 ~) 없음.

### 봇 답글에서 절대 쓰지 말 것

| 금지 | 이유 |
|------|------|
| `@coderabbitai` 멘션 | 본론부터. 멘션은 사회적 인사말 같은 효과 |
| `우선 ~`, `혹시 ~` 같은 완화어 | 평어 단정형과 충돌 |
| `~습니다`, `~판단됩니다` 존댓말 | 봇에게는 정보 밀도가 핵심. 존댓말이 의미 없음 |
| `!`, `:)`, `...` 소프트 디테일 | 봇이 톤을 학습 메모리에 저장하면 후속 PR에서 저자세 패턴이 굳어짐 |
| `감사합니다`, `검토하겠습니다` | 봇은 후속 액션을 약속받지 않는다. 사실만 |
| 향후 검토·도입 계획 | 봇 메모리에 노이즈로 누적. 진짜 후속 작업이면 PR 본문 "후속" 섹션으로 |

### 봇 답글이 다른 시니어 리뷰어에게도 보인다는 점

봇 답글도 PR 페이지에 그대로 노출된다. 평어로 쓰되:

- 욕설·비속어·방어적 변명·반말체(`~함`은 OK, `~해라`는 X) 금지
- 사실 진술이 명확하면 시니어가 봐도 무례하게 읽히지 않는다
- 헷갈리면 "사람 시니어가 이 답글을 같이 본다고 가정하고, 사실 진술만 남기면 OK인가?"로 자기 검증
