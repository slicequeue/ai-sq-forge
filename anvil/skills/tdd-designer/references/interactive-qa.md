## 질문 원칙

1. **한 번에 5개 이하** — 기술 질문은 맥락이 무거우므로 적게
2. **선택지 제공** — "어떤 아키텍처요?" 대신 "기존 코드가 4-Tier인데 동일하게 갈까요?"
3. **코드 근거 제시** — "현재 RaceService가 이 패턴인데, 동일하게 적용할까요?"
4. **기존 패턴 우선** — 프로젝트에 이미 있는 패턴을 따르는 게 기본
5. **확신 있으면 묻지 않는다** — 코드에서 명확히 판단 가능하면 확인만

## 시나리오별 Q&A 예시

### 시나리오 A: 새 도메인 추가 (기존 패턴 명확)

**확인 질문만:**

> 기존 코드를 확인한 결과:
> - 모듈: `pasta-api`에 구현 (기존 race 도메인 위치)
> - 패턴: 4-Tier + Repository 직접 주입
> - 이 패턴을 동일하게 따르겠습니다. 다른 의견이 있으신가요?

### 시나리오 B: 외부 시스템 연동 (기술 결정 필요)

**1차 질문:**

> 외부 연동에 대해 확인이 필요합니다:
> 1. 연동 대상 시스템의 API 문서가 있나요? (URL 또는 Apidog)
> 2. 인증 방식은 어떻게 되나요? (API Key / OAuth / JWT)
> 3. 타임아웃·재시도 정책에 대한 요구사항이 있나요?

### 시나리오 C: 배치/스케줄러 (모듈 선택 필요)

**1차 질문:**

> 배치 처리에 대해 확인합니다:
> 1. 기존 배치가 `batch-app` 모듈에 있는데, 여기에 추가할까요? 아니면 `pasta-api` 스케줄러로?
> 2. 실행 주기는? (매일 자정 / 매시간 / 이벤트 트리거)
> 3. 처리 대상 건수 예상치는? (페이지네이션 전략 판단용)

### 시나리오 D: 코드 분석 기반 TDD (PRD 없음)

**분석 결과 확인:**

> 브랜치 변경사항을 분석한 결과:
> - 신규 엔티티: `CouponEntity`, `CouponPolicy`
> - 신규 API: POST `/api/v1/coupons`, GET `/api/v1/coupons/{id}`
> - DB 마이그레이션: `V202604091200__create_coupon.sql`
>
> 이 분석이 맞나요? 추가로 포함해야 할 요구사항이 있나요?

## 답변 패턴별 후속 대응

| 사용자 답변 패턴 | 후속 대응 |
|-----------------|-----------|
| "기존이랑 같이 해줘" | → 기존 패턴 확인 후 적용, 추가 질문 없이 진행 |
| "잘 모르겠어" | → 코드에서 판단 가능하면 제안 + 확인 요청, 불가하면 우려 지점으로 기록 |
| 기획 수준 답변 | → "그 부분은 이해했습니다. 기술적으로는 ~방식으로 구현하겠습니다" |
| 여러 선택지를 줌 | → 각 선택지의 트레이드오프를 표로 정리 후 추천 |
