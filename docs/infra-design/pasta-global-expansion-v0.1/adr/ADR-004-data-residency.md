# ADR-004: 데이터 레지던시 — 민감정보 리전 Silo + 비민감 메타 공유

- **상태**: Proposed
- **작성일**: 2026-04-22
- **리뷰어**: 보안 / 법무 / 백엔드 리드
- **관련**: ADR-002 (DB), ADR-003 (리전), ADR-006 (CMEK)

---

## 컨텍스트

- pasta 헬스케어 데이터는 4개국 모두 **민감정보** 분류
- 한국 개보법 / 일본 3省2ガイドライン: **자국 내 저장이 실무 표준**
- 미국 HIPAA: 리전 제약 느슨하나 주별 법규(CMIA 등) 고려 필요
- 싱가포르 PDPA: 국외 이전 시 동등 보호 보장 + BCR/SCC 필요
- 글로벌 서비스 운영상 **설정·메타데이터**는 공유가 효율적

**결정할 사항**: "모든 데이터를 리전별로 완전 격리" vs "민감정보만 격리, 비민감 메타는 공유" 중 선택.

---

## 고려한 옵션

### Option A: **민감정보 리전 Silo + 비민감 메타 공유** ⭐ 권고

**설명**:
- **민감정보 (PHI)**: 리전별 Cloud SQL에만 저장. 국경 이동 금지.
- **비민감 메타**: 서비스 설정, 기능 플래그, 카탈로그 등은 리전 간 공유 가능 (예: 중앙 Cloud Storage or Firestore Global)
- 명확한 분류 정책 문서 필요

**민감정보 예시** (리전 silo 대상):
- 사용자 개인정보 (이름, 이메일, 전화번호)
- 건강 데이터 (혈당, 체중, 식단, 운동)
- 의료 기록, 처방, CGM 데이터
- 음식 사진 (PHI 포함 가능성)
- 인증 토큰, 세션
- 결제 정보

**비민감 메타 예시** (공유 가능):
- 서비스 공지사항 (콘텐츠)
- 정적 카탈로그 (운동 종류 마스터, 음식 영양 기준)
- 기능 플래그 / A/B 테스트 설정
- 리전 매핑 테이블

**장점**:
- 규제 정합 + 운영 효율 균형
- 공지사항 등 글로벌 업데이트 단일 지점
- 비즈니스 로직 대부분 그대로 (정적 카탈로그는 리전별 중복 회피)

**단점**:
- **"비민감"의 정의가 애매**할 수 있음 → 정책 문서 필수
- 공유 저장소도 암호화·감사 필요

### Option B: 완전 격리 (모든 데이터 리전별 복제 금지)

**설명**: 공지사항, 정적 카탈로그도 리전별 독립 저장.

**장점**:
- 규제 논란 완전 회피
- 설계 단순

**단점**:
- 공지사항 등 업데이트 4중화 부담
- 정적 데이터 중복 → 스토리지 낭비
- 과잉 대응 (비민감 정보까지 격리할 규제 근거 부족)

---

## 결정

> **선택: Option A (민감정보 silo + 비민감 메타 공유)**

### 선택 근거

1. **규제의 취지는 "민감정보" 보호** — 공지사항까지 격리할 법적 요구 없음
2. **운영 효율** — 4리전 개별 업데이트 부담 제거
3. **명확한 분류 정책으로 관리 가능** — 정책 문서 + 태그 기반 관리

### 수용한 트레이드오프

- "민감정보 여부" 판단의 회색지대 존재 → **분류 가이드라인** 별도 문서 필요
- 공유 저장소도 보안 기본값 (CMEK, IAM, Audit Log) 유지

---

## 데이터 분류 정책 (초안)

| 레벨 | 정의 | 저장 위치 | 암호화 |
|------|------|----------|--------|
| **L1: PHI (민감)** | 건강·개인 식별 가능 정보 | 리전별 Cloud SQL (silo) | CMEK (리전별 키) |
| **L2: 운영 민감** | 사용자 설정, 세션, 결제 | 리전별 Cloud SQL 또는 Cloud Storage | CMEK |
| **L3: 비민감 메타** | 공지, 카탈로그, 플래그 | 중앙 저장소 공유 가능 | Google 기본 암호화 (CMEK 권장) |
| **L4: 공개** | 마케팅 콘텐츠, 공개 문서 | CDN, 공개 GCS | 기본 |

> **주의**: 회색지대는 보수적으로 **상위 레벨로 분류**. 확신 없으면 L2로.

---

## 사용자 지역 이동 처리 원칙

**문제**: 한국 사용자가 미국 출장 시 어떻게?

**처리 원칙** (별도 상세 설계 필요):
1. 사용자 데이터는 **가입 국가** 기준 리전에 고정 (home region)
2. 타 리전 접속 시 **cross-region API 호출**로 home region 데이터 접근 (암호화 채널)
3. Cross-region 호출 log는 **감사 대상**
4. 장기 거주지 변경(예: 이민) 시 **데이터 이전 프로세스** 별도 (사용자 동의 필수)

## 결과

### 긍정적
- 규제 정합 + 운영 효율 균형
- 공지·카탈로그 글로벌 업데이트 가능
- 명확한 데이터 분류 가이드

### 부정적 / 감수
- 분류 정책 유지보수 부담
- 공유 저장소도 보안 관리 필요
- 회색지대 판단의 주관성

### 후속 작업

- [ ] Phase 0: **데이터 분류 가이드라인 문서** 작성 (별도 ADR 후보)
- [ ] Phase 1: 현 pasta 도메인 데이터 전수 분류 실시
- [ ] Phase 1: 공유 저장소 위치 결정 (중앙 GCS? Firestore Global?)
- [ ] Phase 2: 사용자 지역 이동 처리 정책 상세 설계
- [ ] Phase 2: 4개국 규제 감사 시 데이터 분류 근거 제시

## 리스크 & 완화

| 리스크 | 가능성 | 영향 | 완화 |
|--------|-------|------|------|
| 분류 오판 (L3으로 분류한 데이터가 실은 L1) | M | H | 분기별 분류 재검토 + 외부 감사 |
| 공유 저장소 장애 시 전 리전 영향 | L | M | 공유 저장소도 multi-zone HA + 백업 |
| 사용자 지역 이동 대응 미흡 | M | M | Phase 2에 별도 상세 설계 |
| 규제 당국의 "공유 데이터" 해석 차이 | L | H | 법무 사전 자문, 필요 시 Option B로 전환 준비 |
