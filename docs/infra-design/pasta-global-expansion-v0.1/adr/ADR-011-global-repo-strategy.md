# ADR-011: 글로벌 통합 레포 전략 — 3시나리오 Proposed

- **상태**: **Proposed** (팀 논의 중, 확정 대기)
- **작성일**: 2026-04-22
- **리뷰어**: 전 구성원 (코어 팀 합의 필요)
- **관련**: ADR-001, ADR-002, ADR-003, ADR-005

---

## 컨텍스트

현재 pasta 코드베이스는 **독립 레포 2개**:
- 한국 (pasta) — `asia-northeast3`, Cloud Run 29개
- 일본 (pasta-jp) — `asia-northeast1`, Cloud Run 19개 — 현재 대화 레포 (`pasta-japan-server`)
- (pasta-la Deprecated, pasta-lilly 별도 B2B 트랙)

사용자 답변:
> "아마 글로벌 버전이 하나 더 나와서 리포 기준으로 진행할 것으로 판단. 일본이 확장될 수도 있음. **아직 논의 중이라 확답 어려움**."

→ **글로벌 레포가 생기긴 하지만 어떤 구조인지 미확정**. 팀 내 합의 필요.

---

## 3가지 시나리오 (팀 논의용)

### Scenario (a): **한국 레포 진화형**

```
pasta (한국 레포) → pasta-global (진화)
  ↓
  리전별 배포: 서울 / 도쿄 / 오레곤 / 싱가포르
  ↓
  pasta-jp 레포: 일본 레거시 유지 또는 아카이브
```

**장점**:
- 한국 pasta가 사실상 본체(29개 서비스)라 자연스러움
- 레포 통합이 한국 기준 중심
- 기존 운영 팀 대부분 한국 레포 경험

**단점**:
- 일본 pasta-jp 팀이 "흡수"되는 느낌 → 조직적 저항 가능성
- pasta-jp의 지난 파생 경로·기능 차이 병합 부담
- 한국 중심 의사결정 구조 고착 위험

### Scenario (b): **신규 레포 창설형**

```
pasta (한국) + pasta-jp (일본) → 둘 다 점진 이관
                                ↓
                         pasta-global (신규 레포)
                                ↓
                         리전별 배포: 서울 / 도쿄 / 오레곤 / 싱가포르
```

**장점**:
- 레거시 중립 — 둘 다 새로 합류
- 처음부터 글로벌 아키텍처 설계 가능 (clean)
- 팀 간 정치 부담 최소

**단점**:
- **작업량 최대** — 두 레포의 수많은 서비스를 새 레포로 이관
- 이관 기간 중 3-track 병행(한·일 기존 + 글로벌 신규)
- 완전 이관까지 12개월+ 예상

### Scenario (c): **공존형**

```
pasta (한국 레포) — 한국 전용 유지
pasta-jp (일본 레포) — 일본 전용 유지
pasta-global (신규 레포) — 미국·싱가포르만 담당
```

**장점**:
- 기존 운영 무영향
- 최소 개발 부담
- 시장별 독립 운영 (국가별 커스터마이징 자유)

**단점**:
- **장기 부채** — 3개 코드베이스 동시 유지
- 기능·버그픽스가 3번 반복 위험
- 팀·도메인 지식 파편화
- 사용자 경험 일관성 떨어질 수 있음

## 결정

> **현재 상태: Proposed — 팀 확정 대기**

시나리오 확정 전까지, **3가지 모두 수용 가능한 공통 기반**을 먼저 설계한다. 이것이 v0.2 설계안의 기본 전략.

### 공통 기반 (시나리오 무관 선행 가능)

| 영역 | 공통 기반 |
|------|----------|
| 리전 배치 | Regional Silo (ADR-003) |
| 데이터 레지던시 | 4개국 규제 silo (ADR-004) |
| DB 엔진 | MySQL HA + CMEK + PITR (ADR-002) |
| Terraform | 환경×리전 매트릭스 (ADR-005) |
| 암호화·키 | 리전별 KMS (ADR-006) |
| 인증 | Workforce Identity + MFA (ADR-007) |
| 관측성 | 리전별 Log Sink (ADR-009) |

이 기반 위에 시나리오가 확정되면:
- **(a)** 한국 레포의 코드를 글로벌 레포로 변환, 리전 추가
- **(b)** 두 레포 모두 신규 레포로 이관 (최대 작업)
- **(c)** 신규 레포는 미·싱 전용, 기존 유지

---

## 시나리오별 Phase 3 영향

| Phase 3 작업 | (a) 한국 진화 | (b) 신규 창설 | (c) 공존 |
|-------------|-------------|-------------|---------|
| 한국 pasta 이관 | 진화 (in-place) | 이관 | **유지** |
| 일본 pasta-jp 이관 | 이관 or 레거시 | 이관 | **유지** |
| 글로벌 레포 코드 | pasta에서 진화 | 신규 작성 | 신규 작성 (미·싱만) |
| Cloud SQL CMEK/PITR | 진화 중 도입 | 이관 중 도입 | 기존은 ADR-012 별도 |
| 총 작업량 | 중 | **최대** | **최소** |
| 장기 부채 | 낮음 | 낮음 | **높음** |

## 권고 (팀에 제시할 의견)

> 저(에이전트)의 권고는 **Scenario (a) — 한국 레포 진화형**이지만, 사용자·팀이 결정할 일입니다.

근거:
1. 한국 pasta가 사실상 **본체 규모** (29 vs 19)
2. (b)는 작업량 과대 — 2026 연말 일정 리스크
3. (c)는 장기 부채 누적 — 확장 어려움

반박 논리 (a 반대 입장):
- 한국 중심 구조가 조직 정치에 부적합이면 (b) 또는 단계적 (c)
- 일본 pasta-jp가 특수 기능·규제 요구로 분리 유지 필요하면 (c)

## 결과

### 긍정적
- Q1 확정 지연되어도 공통 기반 작업 진행 가능
- 어떤 시나리오든 ADR-002, 003, 005, 006의 공통 기반 재사용
- 시나리오 확정 시 해당 부분만 추가 설계

### 부정적 / 감수
- Phase 3 작업 범위가 시나리오 확정 전에 정해지지 않음 → 일정 리스크
- Phase 2 종료까지 Q1 확정 안 되면 Phase 3 지연

### 후속 작업

- [ ] **Phase 0 중에 Q1 확정** (팀 합의, 2026-05 내 목표)

- [ ] (b) or (a) 채택 시 이관 로드맵 신규 ADR
