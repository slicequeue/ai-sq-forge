## 1. 배경 및 목적

**핵심 문제**: 종료일이 지난 레이스가 자동으로 완료 처리되지 않아, 운영팀이 매일 수십 건의 수작업을 수행해야 하며 누락 시 사용자에게 잘못된 레이스 상태가 노출된다.

현재 레이스의 종료일이 지나더라도 레이스 상태는 자동으로 갱신되지 않는다. 이를 처리하기 위해 운영팀은 매일 수동으로 종료된 레이스를 식별하고 완료 상태로 변경하는 작업을 반복하고 있다. 이 과정에서 처리가 누락되면 사용자는 이미 끝난 레이스를 진행 중인 것으로 인식하거나, 잘못된 참여 안내를 받는 문제가 발생한다. 본 기능은 이 반복 수작업을 제거하고 레이스 상태의 정확성과 시의성을 보장하는 것을 목적으로 한다.

## 2. 목표 (Goals)

| # | 목표 | 측정 기준 |
|---|------|-----------|
| G-1 | 운영팀의 레이스 완료 수작업 제거 | 도입 후 1개월 이내 수작업 건수 0건 |
| G-2 | 레이스 상태 정확성 향상 | 종료일 경과 후 레이스가 완료 상태로 전환되는 데 걸리는 시간 최대 60분 이내 |
| G-3 | 사용자에게 잘못된 레이스 상태 노출 차단 | 완료되어야 할 레이스가 진행 중으로 표시되는 건수 0건 유지 |
| G-4 | 자동 처리 신뢰성 확보 | 자동 완료 처리 성공률 99.9% 이상 |

## 3. 범위 (Scope)

### In Scope

- 종료일이 현재 시각 기준 이전인 레이스를 자동으로 완료 상태로 전환하는 기능
- 자동 완료 처리 결과에 대한 운영팀 알림 제공 (처리 건수, 실패 건수 포함)
- 자동 완료 처리 이력 조회 기능 (운영팀 내부 화면)
- 처리 실패 건에 대한 재처리 지원

### Out Scope

- 레이스 종료일 자체를 변경하거나 연장하는 기능
- 사용자에게 레이스 완료를 직접 알리는 푸시 알림 (별도 기능으로 관리)
- 운영팀이 특정 레이스의 자동 완료를 개별 제외(예외 등록)하는 기능
- 레이스 완료 이후의 결과 정산, 보상 지급 등 후속 프로세스 자동화

## 4. 사용자 시나리오

### 시나리오 1 — 정상 자동 완료

**Who**: 일반 사용자 (레이스 참여자)
**What**: 종료일이 지난 레이스의 상태가 자동으로 완료로 전환된다.
**Why**: 사용자가 언제든지 레이스 목록이나 상세 페이지를 열었을 때 정확한 상태를 확인할 수 있어야 한다.

> 매일 자정이 지나면, 이미 종료일이 경과한 레이스들은 자동으로 완료 상태로 전환된다. 사용자가 레이스 목록을 열면 해당 레이스는 "완료" 상태로 표시되며, 더 이상 참여 버튼이 활성화되지 않는다.

---

### 시나리오 2 — 운영팀의 처리 결과 확인

**Who**: 운영팀 담당자
**What**: 자동 완료 처리가 완료된 후 처리 결과를 확인한다.
**Why**: 수작업 없이도 처리가 정상적으로 이루어졌는지 운영팀이 검증할 수 있어야 한다.

> 자동 완료 처리가 실행되면 운영팀 담당자에게 알림이 전달된다. 알림에는 오늘 처리된 레이스 건수, 실패 건수, 실패한 레이스 목록이 포함된다. 담당자는 실패 건을 확인하고 필요한 경우 재처리를 요청할 수 있다.

---

### 시나리오 3 — 처리 실패 시 대응

**Who**: 운영팀 담당자
**What**: 일부 레이스의 자동 완료 처리가 실패했을 때 재처리를 수행한다.
**Why**: 자동화 도구가 실패하더라도 운영팀이 빠르게 수동 보완할 수 있어야 한다.

> 자동 완료 처리 중 특정 레이스의 처리가 실패하면, 해당 레이스는 실패 목록에 기록된다. 운영팀 담당자는 이력 조회 화면에서 실패 건을 확인하고 재처리 버튼을 눌러 해당 레이스만 다시 완료 처리할 수 있다.

## 5. 기능 요구사항

### 5.1 자동 완료 처리

| ID | 요구사항 |
|----|----------|
| FR-1 | 시스템은 매일 정해진 시각에 종료일이 현재 시각보다 이전인 모든 레이스를 자동으로 식별하여 완료 상태로 전환해야 한다. |
| FR-2 | 자동 완료 처리 대상은 "진행 중" 상태인 레이스에 한하며, 이미 완료, 취소, 중단 상태인 레이스는 처리 대상에서 제외된다. |
| FR-3 | 자동 완료 처리 시각은 운영팀이 관리 화면에서 변경할 수 있어야 하며, 기본값은 매일 오전 1시로 설정한다. |
| FR-4 | 한 번의 자동 완료 실행에서 처리 가능한 레이스 수에 상한을 두지 않으며, 당일 종료 대상 레이스 전건을 처리해야 한다. |
| FR-5 | 개별 레이스의 완료 처리가 실패하더라도 나머지 레이스의 처리는 중단 없이 계속 진행되어야 한다. |

### 5.2 처리 이력 및 알림

| ID | 요구사항 |
|----|----------|
| FR-6 | 시스템은 자동 완료 처리가 완료된 즉시 운영팀 담당자에게 알림을 발송해야 하며, 알림에는 처리 성공 건수, 실패 건수, 실패한 레이스 식별 정보가 포함되어야 한다. |
| FR-7 | 자동 완료 처리의 모든 실행 이력(실행 시각, 처리 건수, 실패 건수, 실패 레이스 목록)은 운영팀 내부 화면에서 최소 90일간 조회할 수 있어야 한다. |
| FR-8 | 운영팀 담당자는 이력 조회 화면에서 특정 날짜, 특정 레이스 이름으로 처리 이력을 검색할 수 있어야 한다. |

### 5.3 재처리

| ID | 요구사항 |
|----|----------|
| FR-9 | 운영팀 담당자는 실패한 레이스에 대해 이력 조회 화면에서 개별 재처리를 요청할 수 있어야 한다. |
| FR-10 | 재처리 요청 후 결과(성공/실패)는 30초 이내에 화면에 표시되어야 한다. |
| FR-11 | 재처리가 성공한 경우 해당 레이스의 상태는 즉시 완료로 전환되어 사용자 화면에 반영되어야 한다. |

## 7. 제약 및 가정

### 제약

- 레이스 종료일은 레이스 생성 시점에 이미 확정되어 있으며, 자동 완료 처리 기능은 이를 변경하지 않는다.
- 운영팀 알림 수신 채널(이메일, 사내 메신저 등)은 현재 운영팀이 사용하는 채널 중 하나를 사용하며, 신규 채널 도입은 이 기능의 범위에 포함되지 않는다.
- 자동 완료 처리 기본 실행 시각(오전 1시)은 서비스 트래픽이 가장 적은 시간대를 기준으로 설정한다.

### 가정

- 현재 "진행 중" 상태의 레이스 중 종료일이 이미 지난 건의 일평균 수는 약 50건이며, 향후 2배(100건)까지 증가할 수 있다고 가정한다.
- 레이스 상태 전환(완료)은 되돌릴 수 없으며, 완료 상태로 전환된 레이스를 다시 진행 중으로 변경하는 기능은 별도로 존재하지 않는다.
- 운영팀은 알림을 수신할 담당자 목록을 사전에 등록 및 관리할 수 있다고 가정한다.
- 레이스 완료 이후의 결과 정산 및 보상 지급은 별도 프로세스로 처리되며, 본 기능의 완료 처리가 해당 프로세스를 자동으로 트리거하지 않는다.

## 8. 성공 지표

| 지표 | 목표값 | 측정 방법 | 측정 주기 |
|------|--------|-----------|-----------|
| 운영팀 수작업 건수 | 0건/일 | 운영팀 처리 이력 조회 화면에서 수동 완료 처리 건수 집계 | 매일 |
| 자동 완료 처리 성공률 | 99.9% 이상 | (성공 건수 / 전체 대상 건수) × 100, 처리 이력에서 산출 | 매주 |
| 완료 전환 지연 시간 | 종료일 경과 후 최대 60분 이내 | 레이스 종료일과 실제 완료 상태 전환 시각의 차이를 이력에서 집계 | 매주 |
| 잘못된 상태 노출 건수 | 0건 | 완료되어야 할 레이스가 사용자 화면에 진행 중으로 표시된 건수 (고객 문의, 모니터링 기반 집계) | 매일 |
| 사용자 서비스 영향 | 응답 속도 저하 10% 미만 | 자동 완료 처리 실행 시간대의 서비스 응답 속도와 평상시 비교 | 매번 실행 시 |
