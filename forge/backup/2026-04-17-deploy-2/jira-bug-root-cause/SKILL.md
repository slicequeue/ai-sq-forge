# jira-bug-root-cause — Jira 버그 원인 규명 & 코멘트 스킬

버그 카드의 "이상해 보이는 동작"이 **버그인지 / 의도된 정책인지 / 레거시 잔재인지**를 코드에서 추적하고, 결과를 이해 당사자(QA·기획 등)가 수긍할 수 있는 형태로 Jira에 남기는 것까지가 이 스킬의 범위다.

---

## 최상위 원칙 (절대 흔들리면 안 되는 것)

### 1. "버그"라고 가정하지 마라

카드 제목이 `[BE] …하지 않음`이어도, 실제 코드를 보기 전에는 **이것이 버그인지 정책인지 모른다.** 우리가 찾아야 하는 건 "무엇을 고칠까"가 아니라 **"현재 코드의 어떤 조건이 이 관찰된 동작을 만들었는가"** 이다.

- ❌ 나쁜 접근: 스택트레이스·에러 없이 `bug-analyzer` 에이전트부터 띄움 → "무엇이 고장났다"는 서사를 미리 만들어버림
- ✅ 좋은 접근: 엔드포인트 → Controller → Service → DTO → Domain 순으로 **조건**을 읽고, 관찰 결과(예: `0개` 노출)가 어떤 분기·할당에서 발생하는지 확정

이 원칙을 어기면, 실제로는 정책인 것을 "버그"라고 리포트하게 되어 QA·PO를 잘못된 방향으로 이끈다.

### 2. 사용자는 도메인 전문가다 — 관찰 포인트를 받아라

사용자가 "이 DTO도 봐줘", "구버전 코드부터 보자", "이 조건도 따라가봐" 같은 지시를 주면 **그것이 가장 빠른 경로다.** 내 추론보다 우선한다. 중간 발견마다 짧게 보고하고 방향을 물어라.

### 3. 코멘트는 "설득"이 목적이다

최종 Jira 코멘트는 로그 덤프가 아니다. **QA 요원·기획자가 읽고 납득**해야 한다. 변수명·클래스명·`List.of()` 같은 기호는 덜어내고, "왜 이렇게 될 수밖에 없는지"를 단계로 서술한다. 해결안도 전부 나열하지 말고 **현실성 기준으로 필터링**해 제안한다.

## 실행 프로토콜

### Step 0. 티켓 식별 & 저장소 컨텍스트

사용자가 Jira URL이나 키(예: `KHCQA-246`)를 제시하면:

1. **키 추출**: URL에서 `PROJECT-NNN` 패턴 파싱
2. **MCP 가용 확인**: `mcp__atlassian__*` 도구가 보이는지 확인. 없으면 사용자에게 "Atlassian MCP가 필요합니다" 안내
3. **저장소 컨텍스트 인지**: `gh` 명령이 필요하면 반드시 `--repo virtualcare/pasta-japan-server` 또는 `GH_REPO=virtualcare/pasta-japan-server` 사용 (auto-memory의 규칙)

### Step 1. 티켓 & 첨부 이미지 수집

```
mcp__atlassian__jira_get_issue(issue_key="KHCQA-246")
mcp__atlassian__jira_get_issue_images(issue_key="KHCQA-246")
```

이미지가 있으면 **반드시** 본다. UI 스크린샷에서 다음을 읽어낸다:
- 화면 경로(어느 탭·어느 리포트) → API 엔드포인트 단서
- 실제로 보이는 수치·문구 → 어느 필드·DTO 속성인지 역추적
- 재현 조건(로그인 계정, 날짜, 환경)

사용자에게 첫 보고: **"티켓 제목·증상·재현조건·영향 화면"** 4줄 요약.

### Step 2. API/엔드포인트 특정

이 단계에서는 **"어느 Controller가 이 응답을 내리는가"** 를 확정해야 한다. 잘못 잡으면 이후 전부 헛수고다.

- 이미지에 URL이 보이면 그걸로 `Grep` (예: `"reports/glucose-spike"`)
- URL이 없으면 화면의 한글 문구(예: "주의해야 할 메뉴")를 `Grep`으로 소스에 찾기
  - messages*.properties, Swagger `@Schema(description=...)`, 프론트-서버 간 약속된 응답 키

### Step 3. 구버전 vs 신버전 코드 구분 (pasta-japan 특화)

이 프로젝트는 **moneyball 모듈(레거시, 실운영 중)** 과 **pasta-api 모듈(일본향 이식 진행 중)** 이 공존한다. 사용자가 특별한 단서를 주지 않는 한, **실제 운영 트래픽이 흐르는 쪽**을 먼저 본다.

판단 기준:
- 배포 중인지: 최근 PR 머지·태그·git log 기준
- 라우팅: `application*.yml`이나 게이트웨이 설정에서 실제 트래픽이 어디로 가는지
- 파일 생성/수정 시점: `git log --follow`로 구/신 비교

사용자에게 "운영은 moneyball의 `GlucoseSpikeAnalysisService`, 일본향 이식 본은 pasta-api의 `GlucoseReportSpikeDetailService`입니다. 어느 쪽부터 볼까요?"처럼 **선택지를 제시**하고 움직인다.

### Step 4. 조건 추적 (진짜 탐정 단계)

다음 레이어를 순서대로 읽으며 **관찰된 값**이 어디서 확정되는지 본다.

1. **Controller** → 어떤 Service·파라미터로 위임?
2. **Application Service** → 어떤 Domain 서비스·Repository 호출? 분기 조건?
3. **DTO 생성자/팩토리** → ⚠️ **필드 강제 덮어쓰기** 패턴을 주의깊게 본다
4. **Domain Service/Repository** → 실제 쿼리·필터 조건

#### 꼭 봐야 할 "조용한 킬러" 패턴

이 프로젝트에서 실제로 발견된 패턴들. 발견 즉시 기록한다.

| 패턴 | 신호 | 예시 |
|------|------|------|
| **DTO 생성자 강제 덮어쓰기** | Builder로 받은 값을 생성자 본문에서 `List.of()`로 덮어씀. 필드별로 **비대칭** 적용 | `GlucoseSpikeDetailResponse`가 `cautionFoods`·`recommendFoods`만 빈 리스트로 덮어씀, `moderateFoods`는 그대로 |
| **정책 마커 TODO 주석** | `// TODO 일본 커머셜 …에 따라 주석 처리`, `NOT_ANALYZABLE 고정` 등 | `FoodRecommendationService`의 점수 로직 전체가 주석처리되고 타입 고정 |
| **다층 방어 구조** | Domain·Application·DTO에 동일 목적의 무력화가 중복으로 들어감 | FoodRecommendationService(고정값) + DTO 생성자(빈 리스트) 2단 차단 |
| **마스터 데이터 미구성** | 카테고리·매핑 테이블이 비어있어 로직이 돌지 않음 | `pghd_food_category`가 일본향에 미구성 |

이런 패턴을 찾으면 **"버그가 아니라 정책/미완성"** 의 가능성이 급격히 올라간다.

### Step 5. 중간 보고 & 방향 재조정

큰 발견마다 사용자에게 말을 건다. 예:

> "DTO 생성자에서 `cautionFoods`·`recommendFoods`만 강제로 빈 리스트로 덮어쓰고 있습니다 (주석: 일본 커머셜에서 버튼 제외 처리). 이게 root cause일 확률이 높아 보이는데, 이 관점으로 더 파고들까요, 아니면 상위 Service부터 먼저 확인할까요?"

사용자가 "그 관점으로 가자" 또는 "아니 이것도 봐야 해"로 방향을 잡아줄 수 있다. **내 추론으로 밀고 나가지 말고** 선택지를 던진다.

### Step 6. 결론 확정 — 이것은 무엇인가?

원인 추적이 끝나면 스스로에게 묻는다:

- **버그인가?** — 코드에 논리 오류, 의도와 불일치, 회귀
- **정책/의도된 미지원인가?** — TODO·주석·정책 마커가 "현재는 막는다"고 명시
- **데이터/설정 문제인가?** — 코드는 맞는데 마스터 데이터·설정이 비어서 결과가 0

이 분류가 **코멘트의 톤**을 결정한다.
- 버그: "수정 PR 올립니다"
- 정책: "현재는 의도된 동작이며, 클라이언트에서 숨김 처리 제안"
- 데이터: "마스터 데이터 구성 필요. 담당 역할 확인 필요"

### Step 7. 코멘트 초안 작성 (QA 친화적 모드)

사용자가 "QA도 알아듣게" 류의 요청을 주면, 또는 청중이 비개발자인 것이 명백하면:

- ❌ 변수명·클래스명·DTO 필드명 금지 (`cautionFoods`, `GlucoseSpikeDetailResponse` 등)
- ❌ 코드 스니펫 금지
- ✅ 화면 상의 문구와 1:1 매핑되는 말만 사용 ("주의해야 할 메뉴", "식후 혈당 스파이크")
- ✅ **왜 0이 될 수밖에 없는지**를 단계로 서술 — "A가 막혀 있어 B가 채워지지 않고, 그래서 C도 비어있습니다"

**해결안 필터링**: 현실성 없는 옵션은 제안에 넣지 않는다. "장기 과제"로는 언급할 수 있어도 **지금 당장 제안**으로는 필터링.

코멘트 구조(권장):
```
[BE 분석] <한 줄로 결론>

<관찰된 현상 재언급>
→ 위 현상이 왜 나오는지 1, 2, 3 단계로 서술

<결론: 버그 / 정책 / 데이터 중 무엇인지 선언>

<제안: 현실성 있는 1~2안만>

<장기 과제: (선택) 별도 티켓으로 다룰 만한 것>
```

### Step 8. 사용자 컨펌 후 등록

**절대** 컨펌 없이 `jira_add_comment` 호출하지 않는다. 드래프트를 보여주고:

- 스코프(어느 옵션까지 제안할지)
- 톤(QA용 / 개발자용)
- 포맷(괄호 허용 여부, 코드블럭 허용 여부)

각각 물어보고, 수정본을 받은 뒤에만 등록.

```
mcp__atlassian__jira_add_comment(issue_key="KHCQA-246", comment=<최종>)
```

등록 후 **코멘트 URL/ID를 사용자에게 보고**.

## 가드레일

### 하드 가드레일 (절대 위반 금지)

- **컨펌 없이 Jira 코멘트 등록 금지**: 드래프트 → 사용자 확인 → 등록. 순서 바꾸지 않는다.
- **`bug-analyzer` 에이전트 자동 기동 금지**: 스택트레이스·에러 로그가 없는 "UI가 이상해요" 류 카드에는 쓰지 않는다. 코드 조건 추적이 먼저다.
- **코드 수정 금지**: 이 스킬은 **원인 규명 + 코멘트**가 목적이다. 수정이 필요하다고 판단되어도 별도 요청을 받기 전에는 파일을 고치지 않는다. (프로젝트 규칙: "파악/확인" 시 코드 수정 금지)
- **커밋·PR 금지**: 사용자의 명시적 요청 없이는 어떤 git 조작도 하지 않는다.
- **구/신 코드 혼동 금지**: moneyball vs pasta-api, 둘 다 보고 어느 쪽이 운영 트래픽인지 사용자에게 확인하기 전에는 한쪽 결론을 절대 고정하지 않는다.

### 소프트 가드레일

- 첨부 이미지는 가능한 **모두** 본다. 스크린샷 한 장에 API 단서가 있다.
- 구/신 코드를 모두 본 경우 코멘트에 "운영 코드 기준" / "이식본 기준" 명시.
- 도메인 경계를 의심해본다(예: 주의 메뉴 = food 분류 → pghd_food_category 마스터 데이터 의존).
- 해결안 제안 시 "누가 해야 하는가"를 암시할 수 있으면 좋다(프론트 / 백엔드 / 기획 / 데이터 운영).

## 자기 검증 체크리스트

코멘트 등록 **직전**에 스스로 묻는다.

1. [ ] **티켓 + 이미지** 모두 수집했는가?
2. [ ] **API 엔드포인트**를 확정했는가? (추측 아닌 grep·코드 증거 기반)
3. [ ] **구/신 코드** 중 어느 쪽을 분석했는지 인지하고 있는가?
4. [ ] **원인을 조건 레벨**로 설명할 수 있는가? (막연히 "로직이 이래서"가 아니라 "Line N의 조건이 false라서")
5. [ ] **버그 / 정책 / 데이터** 중 무엇으로 분류했는가?
6. [ ] **해결안은 현실성 필터**를 통과했는가? 불가능한 옵션을 "제안"에 넣지 않았는가?
7. [ ] **청중에 맞춘 언어**인가? QA 대상이면 변수명·코드 제거됐는가?
8. [ ] **사용자 컨펌**을 받았는가?

## 예시 — KHCQA-246 (이 스킬의 출처)

- **증상**: 리포트에 "식후 혈당 스파이크 발생 횟수 1회" + "주의해야 할 메뉴 0개"
- **초기 오판 유혹**: "스파이크가 있는데 메뉴가 없다 → 버그"
- **실제 추적 결과**:
  1. 엔드포인트 `/analysis/v1/reports/glucose-spike` → moneyball의 `GlucoseSpikeAnalysisService`
  2. Service 로직은 정상
  3. `GlucoseSpikeDetailResponse` 생성자가 `cautionFoods`, `recommendFoods`를 **강제로 `List.of()`로 덮어쓰기** (비대칭: `moderateFoods`는 그대로)
  4. 주석: "일본 커머셜 혈당 스파이크 관련 상세 조회 리포트에서 버튼 제외 처리"
  5. 상류의 `FoodRecommendationService`도 `NOT_ANALYZABLE`로 강제 고정
  6. 근본 원인: `pghd_food_category` 마스터 데이터가 일본향 미구성
- **분류**: 버그 아님 — 정책 + 데이터 이슈
- **제안**: UI 숨김(현실적 옵션 A만). 기능 복원은 "장기 과제"로만 언급
- **최종 코멘트 등록**: 사용자 컨펌 후 ID 12072 등록 완료
