# /pr

## 용도

현재 브랜치의 변경 사항을 분석하여 `dev` 브랜치 대상으로 PR을 생성하거나, 이미 열린 PR이 있으면 본문을 업데이트한다.

## 인자

없음. 현재 브랜치와 dev 간 차이를 자동 분석한다.

## 실행 로직

1. `git log dev..HEAD --oneline`, `git diff dev..HEAD --stat`으로 변경 사항 확인
2. 원격에 푸시되어 있는지 확인. 안 되어 있으면 `git push -u origin HEAD` 실행
3. `gh pr list --head "$(git branch --show-current)" --state open`으로 기존 PR 확인
4. `PR_TEMPLATE.md`가 있으면 읽고, 없으면 아래 작성 가이드에 따라 본문 작성
5. `gh pr create` (신규) 또는 `gh pr edit` (기존)으로 PR 생성/수정

## 출력 형식

PR 생성/수정 후 PR URL을 출력한다.

## PR 본문 작성 가이드

원칙: **"처음 보는 리뷰어가 빠르게 이해할 수 있도록"** 작성. 제목과 본문은 한국어.

### 필수 섹션

#### 1. `## Why need this PR❓`
- **문제**: 현재 어떤 문제가 있는지
- **해결**: 이 PR이 어떻게 해결하는지 한 줄 요약

#### 2. `## Changes ✌️`
- 변경 파일 5개 이상 → 아키텍처 트리 다이어그램
- 레이어 3개 이상 변경 → 레이어별 변경 도표
- 주요 설계 포인트 번호 매겨 설명
- 복잡한 로직 → 시퀀스/플로우 텍스트

#### 3. `## Test list 📝`
- 테스트 클래스 3개 이상 → 커버리지 도표
- 실행 방법: `./gradlew :{module}:test` 등 커맨드 포함

### 도표 사용 기준

| 상황 | 도표 |
|------|------|
| 변경 파일 5개 이상 | 아키텍처 트리 다이어그램 |
| 레이어 3개 이상 변경 | 레이어별 변경 도표 |
| 테스트 클래스 3개 이상 | 테스트 커버리지 도표 |
| 복잡한 처리 흐름 (3단계 이상) | 시퀀스/플로우 텍스트 |
| 단순 버그 수정/리팩토링 | 도표 불필요 |

## 가드레일

- target branch는 항상 `dev`
- PR_TEMPLATE.md가 있으면 반드시 모든 섹션 충실히 작성
- 기존 PR이 열려 있으면 새로 생성하지 않고 `gh pr edit`으로 업데이트
