## 1. 장애 시 동작 (RR-1)

**규칙**: 권한·과금·접근 제어처럼 "막는" 로직을 쓸 때는 **판정 불가 상황에서 열릴지 닫힐지를 코드에 명시**한다.

다음 경우를 각각 어떻게 처리할지 정하고, 정한 내용을 주석 또는 PR 본문에 남긴다.

| 상황 | 확인할 것 |
|------|-----------|
| 규칙·정책이 0건 | 전부 통과(열림)인가 전부 차단(닫힘)인가 |
| 조회 중 예외 발생 | catch 후 통과시키는가 |
| 캐시 워밍업 실패 | 빈 스냅샷으로 기동하는가, 마지막 정상값을 유지하는가 |
| 외부 조회 일시 오류 | `false`/빈 값을 돌려 자격자를 조용히 제외하는가 |

**금지**: 판정 실패를 `catch` 해서 통과시키면서 **로그도 지표도 남기지 않는 것.** 사후 탐지가 불가능해진다.

**동일 로직의 fail 정책은 대칭이어야 한다.** 한 경로는 예외를 전파해 중단하는데 다른 경로만 개별 제외하면, 탐지되지 않는 누락이 생긴다.

출처: #637, #641, #643 (규칙 0건·예외 시 유료 API 전면 무료 개방), #634 (빈 집합 = 차단 대상 없음으로 읽힘), #643 (그룹/병원 클라이언트만 오류를 삼켜 fail 정책 비대칭)

## 2. 결정성 — 순서에 의존하지 않는다 (RR-2)

**규칙**: 결과 순서가 의미를 갖는 곳에서 다음을 쓰지 않는다.

- `groupingBy`·`toMap` 의 기본 반환(HashMap) 순회 순서
- 정렬 키가 같을 때의 입력 순서 (2차 정렬 기준 없이)
- DB 조회 결과의 기본 순서 (`ORDER BY` 없이 `get(0)`, `get(size-1)`)
- `Comparator.max`/`min` 의 동률 선택

**적용**: 정렬에는 동점을 가르는 2차 기준을 반드시 붙인다. 마지막 기준은 `id` 처럼 유일한 값으로 둔다.

```java
.sorted(comparing(A::getX).reversed()
        .thenComparing(A::getStartedAt)
        .thenComparing(A::getId))   // 동점 최종 판별
```

**`limit` 은 `sorted` 뒤에 붙으면 정렬 키가 바뀔 때 구성원 자체가 바뀐다.** "순서만 바뀐다"고 서술하기 전에 상위 N 의 구성원이 유지되는지 확인한다.

출처: #608 (HashMap 순서로 센서 등록 순서 비결정), #697 (동점 2차 기준 부재), #658 (동일 fromVersion 동률이 조회 순서에 의존), #693 (limit 이 sorted 뒤라 구성원 변동)

## 3. enum 순서 결합 금지 (RR-3)

**규칙**: enum 의 **선언 순서**에 값·처방·매핑을 결합하지 않는다.

- `values()` 순서에 의존해 배열·varargs 위치로 값을 대응시키지 않는다
- `ordinal()` 을 저장하거나 비교에 쓰지 않는다

enum 순서를 바꾸거나 상수를 추가하면 **컴파일 오류 없이 조용히 오매핑**되거나 정적 초기화 시 `ArrayIndexOutOfBoundsException` 이 난다.

**적용**: 위치 인수 대신 키를 명시한 `Map` 또는 명명된 파라미터로 대응시킨다.

출처: #667 (활동수준 enum 순서에 처방값 위치 결합)

## 4. 벌크 연산과 영속성 컨텍스트 (RR-4)

**규칙**: QueryDSL·JPQL **벌크 update/delete 직후 같은 트랜잭션에서 그 엔티티를 다시 조회하지 않는다.**

벌크 연산은 DB 만 바꾸고 1차 캐시(영속성 컨텍스트)를 갱신하지 않는다. 직후 조회는 **변경 전 값**을 돌려주고, 그 값으로 다시 저장하면 벌크 연산 결과가 통째로 덮인다.

**적용** (우선순위 순)

1. 벌크 연산을 쓰지 않고 엔티티 단위로 변경
2. 벌크 연산 후 `clearAutomatically = true` 또는 명시적 `entityManager.clear()`
3. 트랜잭션을 분리

`clear()` 는 같은 컨텍스트의 다른 변경분도 날리므로 영향 범위를 확인하고 쓴다.

출처: #717 (벌크 update 후 재조회로 ADMIN 권한 유실, Critical 2건)

## 5. 예외 계층 관계 확인 (RR-5)

**규칙**: `catch` 에 예외 타입을 나열하기 전에 **상속 관계를 확인**한다.

자주 틀리는 조합이다.

| 잘못 | 이유 |
|------|------|
| `catch (BaseRuntimeException \| NumberFormatException e)` 로 `IllegalArgumentException` 을 잡으려 함 | `NumberFormatException` 은 `IllegalArgumentException` 의 **하위**다. 상위는 안 잡힌다 |
| `retryFor = CannotAcquireLockException` 만 지정 | 데드락은 번역 경로에 따라 `DeadlockLoserDataAccessException`(형제)으로도 온다 |
| `catch (JwtException e)` 로 토큰 불량과 키 서버 장애를 함께 처리 | `BadJwtException`(토큰 불량)과 `RemoteKeySourceException`(조회 실패)은 원인도 대응도 다르다 |
| 최상위 타입만 잡음 | 하위 필터가 다른 런타임 예외로 감싸 올리면 놓친다 |

**적용**: 의도한 대상이 상위인지 하위인지 확인하고, **원인이 다르면 타입을 갈라 다르게 처리**한다. 특히 "클라이언트 잘못"과 "우리 인프라 장애"는 로그 레벨과 응답이 달라야 한다.

출처: #687 (IllegalArgumentException 미포착), #8284 (DeadlockLoser 누락), #744 (토큰 불량과 JWKS 장애 동일 처리), #738 (감싸진 ClientAbortException 누락)

## 6. 응답 단위·용어 일관성 (RR-6)

**규칙**: 같은 응답 객체 안에서 **단위와 용어를 통일**한다.

- 한 카드/한 응답에 `{value: 420, unit: MINUTE}` 과 `{value: 7.0, unit: HOUR}` 를 섞지 않는다
- 같은 개념을 가리키는 Swagger 설명 문구를 필드마다 다르게 쓰지 않는다
- 필드명과 설명이 실제 채워지는 값과 일치하는지 확인한다

**적용**: 응답 DTO 를 만들거나 고칠 때 **인접 필드의 단위·용어를 먼저 읽고** 맞춘다. Swagger 는 프론트와 함께 보는 문서다.

출처: #696 (MINUTE/HOUR 혼재), #693 (Swagger 용어 불일치 2건), #698 (설명과 실제 채워지는 값 불일치)

## 7. dead config 남기지 않기 (RR-7)

**규칙**: 설정 프로퍼티의 **소비자를 제거할 때 프로퍼티도 함께 정리**한다.

아무도 읽지 않는 설정이 yml 에 남으면, 운영 중 그 값을 바꿔도 아무 일이 일어나지 않는다. 특히 **긴급 차단 토글**이 이렇게 남으면 장애 대응이 실패한다.

**적용**: 클래스·필터·빈을 삭제할 때 `grep -rn "<프로퍼티 키>"` 로 다른 소비자가 있는지 확인한다. 없으면 yml 에서 제거하거나, 남겨야 하면 "현재 미사용" 주석을 단다.

관련: 마커 빈(아무도 주입하지 않는 검증 전용 빈)은 `spring.main.lazy-initialization` 이 켜진 환경에서 인스턴스화되지 않아 검증이 실행되지 않는다.

출처: #641 (긴급 차단 토글이 dead config 화), #675 (마커 빈 lazy-init 미실행)

## 8. Spring Batch 잡 파라미터 (RR-8)

**규칙**: 배치 잡을 실행 문서나 스크립트에 적을 때 **파라미터 전달 형식을 실제로 확인**한다.

- `--name=value` 는 Spring Boot 가 **옵션 인자(프로퍼티)** 로 분류한다. `JobLauncherApplicationRunner` 는 **non-option 인자**에서 잡 파라미터를 읽으므로 값이 전달되지 않는다
- `incrementer` 는 파라미터 없이 도는 정기 실행에 적용되지 않을 수 있다. `getNextJobParameters` 의 적용 조건을 확인한다

**적용**: PR 본문에 실행 명령을 적기 전에 그 형식으로 실제 파라미터가 잡히는지 확인한다.

출처: #720 (`--targetDate=` 형식이 잡 파라미터로 미전달, Critical)

## 9. 대량 조회 방어 (RR-9)

**규칙**: 결과 건수에 상한이 없는 조회는 다음을 확인한다.

| 항목 | 기준 |
|------|------|
| 전체 로드 | 전체 사용자·전체 행을 `List` 로 한 번에 담지 않는다. 규모가 수만 이상이면 `RowCallbackHandler` 나 페이징·스트리밍 |
| `IN` 절 | 파라미터 개수 상한을 정하고, 넘으면 배치로 분할 조회 |
| 필터 순서 | 값싼 필터를 먼저 적용해 잔여 집합을 줄인 뒤 비싼 조회를 한다 |
| per-user 순차 조회 | 리스트 bulk(`IN`) 조회로 전환한다. 잔여 집합이 크면 페이지당 수백~수천 라운드트립이 된다 |

**자주 불리는 경로(홈·피드·현재 상태 조회)에 쿼리를 더할 때**
- 공용 계산기(resolver)·헬퍼가 어디서 호출되는지 먼저 grep 한다. 명령 경로에만 넣었다고 생각한 쿼리가 홈 조회에서도 매번 돈다.
- 존재 여부만 필요하면 목록 조회 + 엔티티 변환 대신 `existsBy...` 를 쓴다.
- 값싼 조건으로 먼저 걸러 추가 쿼리가 도는 조건을 좁히고, 그 조건을 PR 본문에 적는다.

출처: #746 (페이징 없는 전체 사용자 로드, IN 절 상한 부재), #643 (비싼 엔타이틀먼트를 값싼 필터보다 먼저 실행 + per-user N+1), #797 (홈 조회마다 삭제 일정 목록 전체 로드)

## 10. 주석은 코드가 말하지 못하는 것만 (RR-10)

**규칙**: 코드의 변수명·메서드명이 이미 말하는 내용을 주석으로 반복하지 않는다.

남길 주석은 **왜**다. 무엇을 하는지는 이름으로 표현한다.

- 티켓 번호·기획 문서 식별자(`GLOB-461`, `기획안.xlsx 시트2`)는 주석이 아니라 PR 본문에 둔다. 시간이 지나면 부정확해지고 코드 재사용 시 노이즈가 된다
- 주석 내용이 코드와 어긋나면 주석이 더 위험하다. 코드를 고칠 때 주석도 함께 고친다

출처: #474 (무의미한 주석 7건 연속 지적), #667 (javadoc 티켓 번호), #641·#651·#571 (주석과 코드 불일치)

## 11. DB 마이그레이션 컨벤션 (RR-11)

`db-migration` 커맨드와 함께 적용한다. **저장소 실측(마이그레이션 파일 2,010개)으로 확정한 값이다.**

| 항목 | 규칙 | 실측 근거 |
|------|------|-----------|
| PK 타입 | `BIGINT NOT NULL AUTO_INCREMENT`. **`UNSIGNED` 를 쓰지 않는다** | UNSIGNED 사용 9건(0.4%). JPA 엔티티가 `Long`/`long`(signed)이라 UNSIGNED 는 DB와 JPA 타입 불일치를 만든다 |
| charset·collation | **명시하지 않고 서버 기본을 따른다** | CHARSET 명시 24건(1.2%) |
| ENGINE | **명시하지 않는다** | ENGINE 명시 28건(1.4%) |
| 비ASCII INSERT 동반 시 | 같은 마이그레이션에서 한글·일본어를 INSERT 한다면 **대상 스키마의 기본 charset 이 utf8mb4 인지 확인**한다. 확인되지 않으면 사용자에게 알린다. "기본값이 맞겠지"로 넘어가지 않는다 | #643 에서 charset 미확인 상태로 한글 시드 투입 |
| 불리언 컬럼 | **`is_` 접두를 쓴다** | `is_active` 12건 등 `is_` 접두가 압도적. `active` 로 만들면 머지 후 rename 비용이 든다 |
| UNIQUE 제약 | 논리적으로 중복이 불가능한 조합에는 DB 레벨 UNIQUE 를 건다 | #636 (구 모델 2개에는 있었으나 신규에서 누락) |
| 제약·인덱스 이름 | `uk_{column...}` / `idx_{column...}` — 컬럼명 그대로, 약어 지양 | 기존 db-migration 커맨드 규칙 |
| 조회 패턴 인덱스 | 상태·시각으로 스캔하는 테이블은 해당 복합 인덱스를 함께 만든다 | #589 (status 인덱스 부재로 재처리 풀스캔) |
| 엔티티 `@Column` | 길이가 기본(255)과 다른 컬럼은 엔티티에 `@Column(length=...)` 또는 `columnDefinition` 을 명시한다. 누락하면 H2 기반 테스트 스키마와 운영 스키마가 갈린다 | #687 (운영 MEDIUMTEXT vs 테스트 varchar(255)) |
| 환경 의존 값 | deep link·도메인처럼 환경마다 다른 값을 마이그레이션에 하드코딩하지 않는다. 불가피하면 환경별 후속 DML 을 배포 체크리스트에 묶는다 | #509 (STG 도메인이 dev 에도 적용) |
| PR 분리 | DDL·DML 은 애플리케이션 코드와 분리된 PR 로 올린다 | #509 |
| Copyright 헤더 | 신규 마이그레이션 첫 줄은 `-- Copyright {연도} Kakao Healthcare Corp. All Rights Reserved.`. 없으면 `flyway_preflight.py` 가 실패한다. `review-lint.py` 가 검사한다 | #790 |
| 연관 데이터 동반 | 마스터 행(브랜드·제품 등)을 추가하면 그 행을 참조하는 하위 데이터(증상 문항·가이드·번역)도 함께 넣는다. "기능 플래그는 켜졌는데 하위 데이터가 0건"인 상태를 만들지 않는다. 플래그 컬럼을 켜는 INSERT 는 하위 테이블 건수를 확인한다 | #781 (brand 2~5 문항 누락) |
| 고정 ID INSERT | id 를 직접 지정해 INSERT 하면 운영 `MAX(id)` 와 코드 충돌을 PR 본문에 적고 배포 전 확인 쿼리를 남긴다 | #790 |

**작성 전 확인**: 같은 성격의 기존 마이그레이션을 먼저 읽고 패턴을 맞춘다. 새 패턴을 도입하려면 사유를 PR 본문에 적는다. **문서의 권장값보다 저장소의 실제 패턴이 우선이다** — 같은 리뷰어가 #571 에서 `UNSIGNED` 를 권장했다가 #589 에서 "기존 패턴 이탈"로 되돌린 사례가 있다.

## 12. 테스트가 실제로 무엇을 잡는지 (RR-12)

`java-layered-unit-testing` 과 함께 적용한다.

| 금지 | 설명 |
|------|------|
| 동어반복 테스트 | 검사 대상과 검사 기준이 같은 상수·같은 정규식이면 테스트는 항상 참이다. 오타를 넣어도 통과한다면 그 테스트는 아무것도 잡지 않는다 |
| 위임만 검증하는 테스트 | 서비스가 리포지토리 결과를 그대로 반환하는데 mock 이 돌려준 객체가 그대로 나오는지만 보면 깨질 수 없다 |
| 목표 경로가 실행되지 않는 테스트 | 선검사(`exists`)로 early-return 하면 잡으려던 예외 경로가 한 번도 실행되지 않을 수 있다 |
| 손으로 나열한 대상 목록 | 새 대상을 추가하면서 목록 갱신을 잊으면 안전망이 조용히 비어버린다. 패키지·리플렉션 스캔으로 대체한다. 스캔 범위가 실제 대상 전체를 덮는지도 확인한다 |
| 기본값과 같은 값으로 매핑 테스트 | 필드 기본값이 `true` 인데 `true` 로 요청하면 매핑을 빼도 통과한다. 기본값과 **다른** 값(false→true, true→false)으로 검증한다 |
| 인자를 전부 `any()` 로 받는 스텁 | 서비스가 다른 인자를 넘겨도 통과한다. 핵심 인자는 값이나 `isNull()` 로 고정한다 |
| 예외 분기를 가리는 `lenient` 스텁 | 공통 setUp 에서 "제한 없음"으로 lenient 스텁하면 예외 분기를 아무 테스트도 타지 않는다. 예외 분기 전용 테스트에서 스텁을 덮어쓴다 |
| 느슨한 JSON 단언 | `doesNotExist()` 는 JSON null 도 통과(키 부재는 `doesNotHaveJsonPath()`), `asBoolean()` 은 null·문자열도 false(먼저 `isBoolean()`), `isEmpty()` 는 빈 객체·배열도 통과(null 계약은 `value(nullValue())`) |
| 상태 저장소를 Mock 으로 정답 주입 | Repository·UseCase 를 `@Mock` + `given().willReturn()` 으로 두면 조회 조건이 바뀌어도 통과한다. 규칙 08 대로 Fake 에 저장한 뒤 조회한다 |

**확인 방법**: 검증하려는 동작을 **일부러 깨뜨렸을 때 테스트가 실패하는지** 본다. 실패하지 않으면 그 테스트는 회귀를 막지 못한다.

**경계값**: `limit`·임계값이 있는 로직은 경계를 **넘는** 픽스처를 쓴다. 상위 5건 로직을 3건으로 테스트하면 경계를 지나가지 않는다. 임계값 근처 픽스처는 임계값이 조금만 바뀌어도 의도와 다른 이유로 실패한다.

출처: #741 (동어반복), #686 (위임만 검증), #633 (목표 경로 미실행), #643·#749 (수동 목록·스캔 범위), #693 (경계 미통과), #740 (변이 통과), #791 (기본값과 같은 값), #789 (`any()` 스텁·Mock 저장소), #800 (lenient 로 예외 분기 미실행), #801·#786 (느슨한 JSON 단언), #794 (Mock UseCase)

## 13. 실패 격리 — 한 건이 전체를 깨뜨리지 않는다 (RR-13)

**규칙**: 여러 소스를 조립하는 응답(홈 카드·피드·리포트)과 여러 건을 도는 루프는, **한 소스·한 건의 실패가 어디까지 번지는지**를 정하고 코드로 막는다.

| 패턴 | 막는 방법 | 출처 |
|------|-----------|------|
| try 범위가 너무 넓다 | 독립된 조회는 각각 따로 감싼다. 부가 정보(일정) 실패가 핵심 정보(마지막 기록)까지 비우면 "기록 없음" 같은 **틀린 상태**를 내려 준다 | #777 |
| 같은 트랜잭션에 참여한 하위 조회가 예외를 낸다 | 호출부에서 catch 해도 이미 rollback-only 가 걸려 `UnexpectedRollbackException` 으로 전체가 실패한다. 실패를 허용할 조회는 트랜잭션 경계를 분리하고(`REQUIRES_NEW`·readOnly 별도 빈), 실제 프록시로 테스트한다 | #793 |
| 데이터 한 건이 예외를 던진다 | `Collectors.toMap` 의 null value·중복 키, `Optional.get()`, 마스터 데이터의 잘못된 값(0·음수·null). 한 건 때문에 피드 전체·해당 제품 사용자 전원이 500 이 되지 않게 그 건만 건너뛰거나 기본값으로 처리하고 WARN 로그를 남긴다 | #794, #800 |
| 루프 중간에 외부 호출이 실패한다 | 전체 롤백(`rollbackFor`)이면 앞서 성공한 외부 작업(푸시 예약 등)의 결과 ID 까지 사라져 외부와 DB 가 어긋난다. 건 단위 try/catch 로 성공분을 유지한다 | #799 |
| 외부 호출 성공 후 DB 저장이 실패한다 | 외부 작업 ID 가 유실되면 취소할 수 없다. 저장 실패 시 보상(취소)을 하거나, 범위 밖으로 두면 그 판단과 남는 위험을 PR 본문에 적는다 | #799 |

**판단 질문** (작성 전): "이 조회·이 한 건이 실패하면 사용자는 무엇을 보는가?" 답이 "전체 500" 또는 "틀린 상태"면 격리한다.

## 14. 동작 변경과 검증 순서 (RR-14)

**규칙**

- **기존 경로의 동작이 바뀌면 PR 본문에 적는다.** 공용 검증을 새로 만들어 기존 API(예: 수정 PUT)에도 붙이면, 그 API 가 이전에 통과시키던 요청이 400 이 된다. 의도한 변경인지 리뷰어가 묻기 전에 "기존 동작 변경" 항목으로 밝힌다.
- **검증 순서는 존재·소유 확인 → 입력 검증이다.** 남의 리소스 id 로 요청했는데 입력 검증 에러(400)가 먼저 나가면 에러 우선순위가 어긋나고 리소스 존재 여부를 흘린다.
- **판정 기준은 유일한 값으로 한다.** "마지막 기록인가"를 시각 비교로 판단하면 같은 시각·수정된 시각에서 틀린다. id 로 비교한다.
- **"최신"을 조회할 때 미래 데이터를 거른다.** 사용자가 미래 시각으로 기록할 수 있으면 `현재 시각 이하` 조건을 붙인다.
- **새 검증·분기는 그것이 붙은 모든 진입 경로(POST·PUT·배치)에서 테스트한다.** 한 경로만 테스트하면 다른 경로의 예외 분기는 아무도 실행하지 않는다.

출처: #800 (PUT 에 과거 시각 검증이 새로 붙음, 소유 확인 전에 간격 검증, 등록 경로 미검증), #784 (마지막 기록 판정을 시각으로), #793 (미래 기록이 최신으로 잡힘)

## 15. 기계 검사 (RR-L) — `review-lint.py`

이름·계층·테스트 단언처럼 **문자열로 잡히는 지적은 사람 체크리스트가 아니라 스크립트로 막는다.** 규칙이 있어도 작성 시점에 안 읽히면 같은 지적이 반복된다(#789·#791·#792 이름 규칙, #789·#794 Mock, #800 계층 — 전부 기존 규칙에 있던 내용).

```bash
python3 forge/common/review-lint.py                # merge-base(origin/dev) ~ 작업 트리
python3 forge/common/review-lint.py --head <sha>   # 특정 커밋 재검사
```

| 코드 | 검사 | 등급 |
|------|------|------|
| RR-12 | 단위 테스트에서 `*Repository`·`*UseCase`·`*QueryService` 를 `@Mock` (규칙 08 Fake 우선) | 위반 |
| RR-12 | `lenient()` 스텁, 인자 전부 `any()` 스텁, `doesNotExist()`, `asBoolean()`/`asText()`, `jsonPath(..).isEmpty()` | 확인 |
| RR-11 | 신규 마이그레이션 Copyright 헤더 누락 | 위반 |
| RR-13 | `Collectors.toMap(` 추가 | 확인 |
| LAYER | domain 패키지가 HTTP 예외·`ExceptionConstants`·web 을 import | 위반 |
| LAYER | `@RestController` 의 새 메서드가 `ResponseEntity` 를 반환하지 않음 | 확인 |
| NAMING | 컬렉션 변수에 `List` 등 접미사 없음, `Instant` 변수에 `At` 접미사 없음 | 확인 |
| NAMING | 코드 주석이 평서형 `~다.` 로 끝남 (주석은 존댓말, #791) | 확인 |
| FQCN·PII | 본문 패키지 경로, 로그 본문 `userId` | 위반 |

- **위반**은 고친다. **확인**은 해당 없으면 PR 본문이나 답글에 사유를 남긴다.
- **`[위반]` 이 남은 상태로는 완료 보고·커밋·push·PR 생성을 하지 않는다.** 사용자가 "일단 올려줘"라고 해도 같다. 위반별 수정 방향을 제시하고 고친 뒤 재실행한다. 의도적으로 남기려면 사유를 PR 본문 "리뷰 포인트"에 적고 사용자 명시 승인을 받는다 (2026-11-13 git-pr TC-8·coding-implementer TC-12 baseline 이 요청대로 위반 상태 PR·커밋)
- **`[확인]` 사유는 lint 출력 원문(코드, 파일:줄, 메시지)을 인용한 뒤 판단을 붙인다.** 메시지를 풀어 쓰다 반대로 읽는 오류가 반복 관찰됐다 (git-pr TC-6 2회)
- **실행하지 못했으면 결과를 추정해 적지 않는다.** "미실행(사유)"로 표기하고, 예상 결과를 쓸 때는 스크립트 검사 범위(위 표) 안의 항목만 쓴다. 표에 없는 유형(주석 RR-10, yml RR-7 등)을 lint 결과로 적지 않는다 (self-code-reviewer TC-10 v2.3 지어내기 사례)
- **FQCN·LAYER 위반의 리뷰 소유권**: 수정 의무는 위 규칙대로지만, 리뷰 스킬에서는 `self-code-reviewer` 가 "기계 검사" 절에 결과를 싣고 상세 분석은 `java-architecture-reviewer` 로 넘긴다(스코프 가드와의 충돌 방지)
- 실행 시점: 커밋 전(java-spring-coder·java-layered-unit-testing 종료 단계), 푸시 전(git-pr·pr-feedback-resolver), 그리고 `git push` 직전 PreToolUse 훅.
- 새 지적 유형이 문자열로 잡히면 이 표와 스크립트에 추가한다. 판단이 필요하면 RR 본문에 추가한다.
- **한계**: 줄 단위 검사라 PR 간 충돌(내가 바꾼 인터페이스를 다른 PR 의 테스트 Fake 가 구현)을 못 잡는다. 이건 최신 dev 를 합친 상태의 `compileTestJava` 로 막는다 (`git-pr` v0.5 게이트, #803)

## 16. 작성 전 질문 5개

긴 체크리스트보다 먼저, 코드를 쓰기 전에 이 다섯 개에 답한다. 답을 못 하면 그 부분이 리뷰에서 나온다.

1. 이 조회·이 한 건이 실패하면 사용자는 무엇을 보는가? (RR-13)
2. 외부 호출이 성공한 뒤 DB 저장이 실패하면 어떻게 되는가? (RR-13)
3. 마스터 데이터가 null·0·음수·누락이면 어떻게 되는가? (RR-13, RR-11)
4. 기존 경로의 동작이 바뀌는가? 바뀐다면 PR 본문에 적었는가? (RR-14)
5. 이 분기를 일부러 깨뜨리면 실패하는 테스트가 있는가? 모든 진입 경로에서? (RR-12, RR-14)


**답할 수 없는 질문의 처리** (2026-11-13 coding-implementer v0.9 트레이닝):
- 이 가드가 이미 답을 정한 항목(격리 방식, 트랜잭션 경계, 마스터 데이터 이상값 처리)은 **묻지 않고 적용**한다.
- TDD·PRD 에 근거가 없는 **제품·스키마 결정**은 구현 전에 권장안을 붙여 묻는다. 가정하고 구현한 뒤 보고 단계에서 사후 확인하지 않는다.
- 같은 실패가 "사후 확인"과 "과잉 질문" 두 방향으로 관찰됐다. 경계는 "가드에 답이 있는가"다.

## 17. 자기 검증 체크리스트

코드 작성을 마친 뒤 확인한다. 해당 없으면 건너뛴다.

- [ ] 막는 로직을 썼다면, 규칙 0건·예외·워밍업 실패 시 열리는지 닫히는지 정하고 기록했는가? (RR-1)
- [ ] 순서가 의미를 갖는 정렬에 동점 2차 기준을 붙였는가? `limit` 이 구성원을 바꾸지 않는지 확인했는가? (RR-2)
- [ ] enum 선언 순서에 값을 결합하지 않았는가? (RR-3)
- [ ] 벌크 update/delete 직후 같은 트랜잭션에서 재조회하지 않았는가? (RR-4)
- [ ] `catch` 에 나열한 예외의 상속 관계를 확인했는가? 원인이 다른 예외를 함께 처리하지 않았는가? (RR-5)
- [ ] 응답 안에서 단위와 용어가 통일됐는가? (RR-6)
- [ ] 소비자를 지운 설정 프로퍼티를 정리했는가? (RR-7)
- [ ] 배치 실행 명령이 실제로 잡 파라미터로 전달되는 형식인가? (RR-8)
- [ ] 상한 없는 조회에 페이징·분할·필터 순서를 검토했는가? (RR-9)
- [ ] 코드가 이미 말하는 내용을 주석으로 반복하지 않았는가? 주석이 코드와 일치하는가? (RR-10)
- [ ] 마이그레이션이 기존 패턴(signed PK·charset 미명시·`is_` 접두·제약 이름)을 따르는가? 비ASCII INSERT 면 대상 charset 을 확인했는가? (RR-11)
- [ ] 작성한 테스트가 동작을 일부러 깨뜨렸을 때 실패하는가? 기본값과 다른 값으로 검증했는가? 상태 저장소는 Fake 인가? (RR-12)
