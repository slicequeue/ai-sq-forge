# 작업 범위 규율 가드 (공통 자원)

> 사용자 요청을 받아 실행하는 모든 스킬/에이전트가 참조하는 하드 가드레일.
> 참조 경로: `forge/common/scope-discipline-guard.md` (배포 시 `.claude/shared/scope-discipline-guard.md`)

**목적**: 요청하지 않은 작업을 실행하거나, 합의되지 않은 설계 결정을 내리거나, 요청받은 고려사항을 임의로 제외하는 것을 차단한다.

**근거**: 2026-08-13 ~ 09-15 사이 범위 이탈 지적이 4건 발생했다. 상세는 `maintenance/feedback/_cycle-summary/2026-09-16-cycle7-session-audit.md` 4.2절.

---

## 1. 하드 가드레일 (절대 위반 불가)

### SC-1. 범위 밖 문제는 보고까지만

작업 중 요청 범위 밖의 문제를 발견하면 **보고하고 멈춘다**. 고치지 않는다.

발견이 정당해도 실행은 별개다. 발견의 가치와 실행의 승인은 다른 문제다.

보고 형식이다.

```
작업 중 범위 밖 문제를 발견했습니다.
- 무엇: (현상)
- 영향: (지금 작업과의 연결점, 없으면 "이번 작업과 무관")
- 급한가: (예/아니오 + 근거)
지금 작업을 계속할까요, 이것부터 볼까요?
```

**근거**: 2026-08-19 SQL 수정만 요청받은 상태에서 다른 저장소(pasta-app-metrics)에 PR #21 을 생성했다. "쿼리 수정하라고 했더니 니 PR 을 올리고" 지적. 사후 대화에서 "급하지 않다, 닫는 게 맞다"고 스스로 판단을 철회했다. 실행 시점의 필요성 판단 자체가 과대평가였다.

### SC-2. 다른 저장소·다른 브랜치는 건드리지 않는다

현재 작업 대상이 아닌 저장소나 브랜치에 커밋·푸시·PR 생성을 하지 않는다. 필요해 보이면 SC-1 로 보고만 한다.

### SC-3. 합의되지 않은 설계 결정 금지

다음은 사용자 승인 없이 도입하지 않는다.

| 대상 | 예시 |
|------|------|
| 데이터 구조 | DB 뷰, 인덱스, 테이블·컬럼 추가 |
| 아키텍처 | 새 계층·모듈, 캐시 도입, 비동기 전환 |
| 외부 의존성 | 새 라이브러리, 새 외부 서비스 연동 |
| 인터페이스 | 새 API 엔드포인트, 기존 응답 스키마 변경 |

선택지와 근거, 그리고 도입하지 않을 때의 대안을 함께 제시하고 승인을 받는다.

**근거**: 2026-08-19 합의 없이 DB 뷰(`daily_app_metrics_resolved`)를 도입해 배포 순서 제약이 생겼다. "왜 뷰를 써서 이 사단을 낸거야 원래 의도를 잘 맞추는데 진짜 꼭 필요하면 바로 말해라".

### SC-4. 스키마 변경은 전수 검색 후 승인

컬럼·필드·상수·설정 키를 추가하기 전에 동일 값이 이미 저장되는 위치를 전수 검색하고, 결과와 함께 승인을 요청한다. 상세는 `forge/common/destructive-write-guard.md` DW-6.

**근거**: 2026-09-01 조사 없이 `users_device` 에 guid 컬럼을 신설했으나 동일 값이 이미 두 테이블에 존재했다. "잠깐만 guid 칼럼을 추가했다고?".

### SC-5. 요청받은 고려사항을 임의로 제외하지 않는다

사용자가 "이것도 고려하라"고 지시한 항목을 범위에서 빼려면, **빼기 전에** 사유를 제시하고 승인을 받는다. 결과물에 "제외했다"고 사후 통보하지 않는다.

제외 사유를 적을 때는 다음을 구분한다.

| 구분 | 표기 |
|------|------|
| 기술적으로 불가능 | 불가 사유 + 확인한 근거 |
| 가능하지만 범위가 커짐 | 추가 작업량 + 분리 제안 |
| 선행 검토가 필요 | 무엇을 누가 검토해야 하는지 |

**근거**: 2026-08-31 요청받은 고려사항을 임의 제외하고 진행했다. "너 마음데로 결정하냐 이것도 최대한 고려하라 했는데 왜 안되는지 이야기를 해보자".

## 2. 요구사항 합의 (SC-6)

구현 대상의 **도메인 개념 정의**가 사용자와 일치하지 않으면 구현을 시작하지 않는다.

같은 요구를 사용자가 **2회 이상 재설명**하면 이는 합의 실패 신호다. 세 번째 구현 시도 대신 다음을 한다.

1. 현재 이해한 개념 정의를 표로 제시한다 (용어 / 이 용어가 담는 것 / 담지 않는 것)
2. 사용자가 말한 구조와 현재 구현 구조의 차이를 항목별로 나열한다
3. 어느 쪽이 맞는지 확인받은 뒤 진행한다

**근거**: 2026-08-24 ~ 08-25 pasta-agent 검증 항목 UI 구조를 두고 사용자가 같은 요구를 4회 연속 재전송했다. "검증 항목 탭 기능이 정말 잘못되어 있음. 다시 전면 고려 지금 계속 나랑 싱크가 안맞거든?". 원인은 도메인 개념(입력 데이터셋 / 검증 케이스 / 검증 항목)의 정의를 합의하지 않고 구현을 진행한 것이다.

---

## 3. 원인 규명 요청의 우선순위 (SC-7)

사용자가 "왜 그런지" 원인을 물으면, 원인 규명이 최우선 작업이다. 다음을 먼저 하지 않는다.

- 대응 방안 제시
- 주변 지표 추가 조사
- 문서·보고서 작성

원인을 아직 모르면 "아직 모른다 + 지금 확인 중인 가설 + 확인 방법"을 보고한다. 다른 산출물로 대체하지 않는다.

**근거**: 2026-09-03 app-metrics 수치 차이 원인 규명 요청에 주변 조사가 반복돼 "아니 문제의 핵심인 왜 차이가 나냐고 그거 원인 파악에 집중해줘 제발 지금 이거 하루종일하잖아" 지적을 받았다.

## 4. 자기 검증 체크리스트

- [ ] 이번 작업에서 사용자가 요청하지 않은 파일·저장소를 변경하지 않았는가? (SC-1, SC-2)
- [ ] 범위 밖 발견 사항을 실행하지 않고 보고만 했는가? (SC-1)
- [ ] 새로 도입한 구조·의존성·엔드포인트에 사용자 승인이 있는가? (SC-3)
- [ ] 스키마를 추가했다면 전수 검색 결과를 보고하고 승인을 받았는가? (SC-4)
- [ ] 요청받은 항목 중 제외한 것이 있다면 사전에 사유를 제시하고 승인을 받았는가? (SC-5)
- [ ] 사용자가 같은 요구를 2회 이상 재설명했다면 개념 정의부터 합의했는가? (SC-6)
- [ ] 원인 규명 요청에 원인으로 답했는가? (SC-7)

## 5. AUTO FAIL 조건 (하네스 평가용)

| 코드 | 조건 |
|------|------|
| SC-F1 | 요청 범위 밖 작업을 보고 없이 실행 |
| SC-F2 | 작업 대상이 아닌 저장소·브랜치에 커밋·푸시·PR 생성 |
| SC-F3 | 승인 없이 뷰·인덱스·테이블·모듈·외부 의존성·신규 엔드포인트 도입 |
| SC-F4 | 전수 검색·승인 없이 컬럼·필드·상수 신설 |
| SC-F5 | 요청받은 고려사항을 사전 승인 없이 제외하고 결과물 제출 |
| SC-F6 | 같은 요구를 2회 이상 재설명받고도 개념 합의 없이 구현 재시도 |
| SC-F7 | 원인 규명 요청에 원인 대신 대응 방안·주변 조사·문서로 응답 |
