# 공유 글 작성 가드 (SW-1~SW-7)

AI 로 작업한 결과를 사람에게 공유하는 글은 첫 줄만 읽어도 "무엇이 끝났고 어디까지 반영됐는지"가 나와야 한다. 끝까지 읽어야 결론이 나오는 글은 "운영에 나간 건가요?", "제가 할 건 없나요?" 같은 되물음을 만든다.

- 원본: forge `forge/common/share-writing-guard.md` (배포본 `.claude/shared/share-writing-guard.md`)
- 기계 검사: `forge/common/share-lint.py` (배포본 `.claude/shared/share-lint.py`)
- 버전: 0.1 (2026-11-13, 팀 합의 전 시범 적용)
- 근거: BLUF(결론 먼저), 구글 스니펫(짧은 불릿), PPP(한 일·막힌 것만), 깃랩 비동기 소통(되묻지 않게 맥락 포함)

## 형식

```
{무엇을} 완료 ({반영 단계})
- 한 일 2~4줄, 짧게
- 결과
{부탁이 있을 때만 한 줄}
```

예:

```
감사 로그 접속 기기 정보 원문 저장 완료 (dev, 운영 반영 전)
- 감사 로그 테이블에 컬럼 추가
- 관리자 서버 재기동, 상태 점검 200 확인
- 재기동 이후 쌓이는 로그부터 원문 저장, 이전 기록은 복구 불가
```

## 규칙

| ID | 규칙 | 위반 예 |
|----|------|---------|
| SW-1 | **첫 줄에 결론과 반영 단계.** `{무엇을} 완료 ({단계})`. 끝나지 않았으면 `완료` 자리에 `진행 중` 또는 `막힘`. 코드 반영이 없는 일(분석·조사·설계)은 단계 대신 범위를 쓴다: `{무엇을} 분석 완료 (코드 변경 없음)` | 인사말·배경으로 시작, 결론이 마지막 문장 |
| SW-2 | **한 일은 2~4줄 불릿, 짧게.** 문장으로 풀지 않는다 | 한 문단 서술, 불릿 8줄 |
| SW-3 | **결과를 쓴다.** 확인한 수치·상태(200, 0건, 통과) 위주 | "잘 됐습니다" |
| SW-4 | **부탁은 있을 때만 한 줄.** 예의 문구 없이 원하는 것만 | "혹시 시간 되시면 확인 부탁드려도 될까요?", 부탁 없는데 "요청: 없음" |
| SW-5 | **확인 안 한 단계는 쓰지 않는다.** 배포를 확인하지 않았으면 `운영 반영` 이라고 쓰지 않는다. 테스트를 돌리지 않았으면 "통과"라고 쓰지 않는다 | 머지만 하고 "운영 반영 완료" |
| SW-6 | **없는 내용은 줄을 뺀다.** 빈 칸을 "없음", "해당 없음", "-" 로 채우지 않는다 | "요청: 없음", "이슈: 해당 없음" |
| SW-7 | **유추한 내용을 쓰지 않는다.** 확인한 것만. 꼭 필요하면 `미확인:` 을 붙여 확인한 것과 섞이지 않게 한다 | "아마 운영에도 문제없을 것입니다" |

장애·운영 공유는 상태어를 `복구 완료` / `복구 진행 중` / `막힘` 으로 쓰고 단계는 `코드 변경 없음` / `수정 머지, 운영 배포 전` / `운영 반영` 으로 쓴다(예: `Dexcom 혈당 수집 장애 복구 진행 중 (수정 머지, 운영 배포 전)`). 존댓말 어미(`완료했습니다 (dev)`)는 허용하지만 괄호는 상태어 바로 뒤에 둔다. 불릿 기호는 `- ` 를 쓴다.

반영 단계 표기 (SW-1·SW-5): `dev` / `머지, 배포 확인 전` / `운영 반영`. 저장소마다 환경 이름이 다르면(stg, pre, sandbox) 그 이름을 쓰되 "확인한 가장 먼 단계"를 쓴다. 단계가 둘이면 쉼표로 잇는다(`dev, 운영 반영 전`).

## 적용 범위

| 등급 | 대상 | 적용 |
|------|------|------|
| A. 공유 글 | 완료 보고, 메신저(구글챗·슬랙) 공유, 작업 마무리 요약(Claude 가 사용자에게 하는 최종 보고 포함), 단계별 중간 보고(`진행 중`), PR 본문 맨 위 요약, 장애·에러 공유 | SW-1~7 전부 |
| B. 남는 문서 | PRD·TDD, 분석·장애 보고서, 평가 리포트, 사이클 요약, 공식 기술 문서 | 문서 맨 앞에 A 형식의 결론 블록(3~5줄). 본문은 각 문서 형식을 따르되 SW-5~7 은 본문 전체에 적용 |
| C. 기계 텍스트 | 커밋 메시지, 코드 주석, PR 인라인 리뷰 코멘트, 리뷰 답글 | 형식은 적용하지 않는다. SW-5·SW-7 만 |

등급이 애매하면 A 로 본다.

## 자기 검증 (보내기 전)

1. 첫 줄만 읽고 "무엇이 끝났는지 / 어디까지 갔는지"가 나오는가
2. 첫 줄의 반영 단계를 직접 확인했는가(명령 출력·화면·응답 코드)
3. "없음"·"해당 없음"·"-" 로 채운 줄이 없는가
4. 부탁 줄이 있다면 예의 문구 없이 한 줄인가
5. "아마", "~것 같습니다", "문제없을 것" 같은 유추가 없는가

A·B 등급 글을 파일로 쓰면 `python3 .claude/shared/share-lint.py {파일}`(forge 에서는 `forge/common/share-lint.py`)로 검사한다. `[위반]` 은 고친 뒤 보낸다. `[확인]` 은 판단해서 남기거나 고친다.

## 다른 규칙과의 관계

- 사용자·스킬이 정한 문서 형식(PR 템플릿, 보고서 양식)이 있으면 그 형식 안에서 적용한다. PR 본문은 템플릿 첫 섹션 위에 결론 블록을 둔다
- 말투(존댓말·평어)는 이 가드가 정하지 않는다. `sq-tone-writer`·`pr-comment-ko` 등 각 스킬 규칙을 따른다
- SW-5·SW-7 은 `review-recurrence-guard` §15 "미실행 추정 금지"와 같은 원칙이다
