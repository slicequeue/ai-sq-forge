# Maintenance Protocol - 실전 피드백 기반 A/S

실전 배치된 컴포넌트의 품질을 지속적으로 개선하는 프로토콜이다.

---

## A/S 디렉토리 구조

```
maintenance/feedback/{component-name}/
├── {YYYY-MM-DD}-{issue-slug}.md    # 개별 피드백 기록
└── changelog.md                     # 개선 이력
```

## Phase 1. 피드백 수집

### 피드백 기록 형식

실전 사용 중 문제가 발견되면 아래 형식으로 기록한다:

```markdown
# {날짜} - {문제 한 줄 요약}

## 상황
- **컴포넌트**: {skill/agent/command/chain/dispatcher 이름}
- **사용 프로젝트**: {어디서 사용했는지}
- **사용자 입력**: "{실제 프롬프트 또는 요약}"

## 문제
{무엇이 잘못되었는가 / 기대와 다른 결과}

## 대화 로그 (핵심 부분)
{문제가 드러나는 대화 발췌 — 전체가 아닌 핵심만}

## 원인 분석
{왜 이런 결과가 나왔는지 추정}

## 개선 방안
{SKILL.md 또는 references의 어느 부분을 어떻게 수정할지}

## 우선순위
- [ ] Critical: 가드레일 위반 / 잘못된 출력
- [ ] Major: 품질 저하 / 비효율
- [ ] Minor: 개선하면 좋은 수준
```

## Phase 1.5. 메모리 승격 점검 (월 1회, 생략 금지)

실전 프로젝트의 자동 메모리에 쌓인 교훈을 forge 스킬로 승격했는지 대조한다.

**왜 필요한가**: 메모리와 스킬은 작동 방식이 다르다. 메모리는 관련성이 인식될 때만 본문이 회수되는 **확률적** 장치이고, 스킬은 호출되면 전문이 강제 로드되는 **결정적** 장치다. 하드 가드레일이 메모리에만 있으면 지켜지지 않는다.

2026-08-31 PR #726 양식 위반은 `pr-feedback-resolver` 스킬이 **정상 발동한 상태에서** 일어났다. 스킬 본문에 그 규칙이 없었기 때문이다. 스킬이 켜져도 본문에 없는 규칙은 지켜지지 않는다.

### 점검 절차

```bash
# 1. 지난 1개월 신규·갱신된 피드백 메모리 목록
find ~/.claude/projects/<프로젝트-슬러그>/memory -name 'feedback_*.md' -newermt <YYYY-MM-DD>

# 2. 각 교훈의 핵심 규칙이 forge 자산에 있는지 대조
grep -rn "<핵심 키워드>" anvil/ forge/common/
```

### 판정과 조치

| 상태 | 조치 |
|------|------|
| forge 에 있음 | 기록만 남긴다 |
| forge 에 없음 | 어느 스킬의 어느 절에 들어갈 규칙인지 정하고 Phase 3 으로 진행 |
| forge 값이 실전과 충돌 | **배포 제외로 회피하지 말고 원본을 고친다.** 회피하면 다른 저장소로 잘못된 값이 전파된다 |

**충돌 시 어느 쪽이 맞는지 정하는 법**: 문서끼리 비교하지 않는다. 둘 다 틀렸을 때 알아낼 수 없기 때문이다. **실행 이력을 측정한다.**

```bash
# 커밋 컨벤션이면 실제 커밋 접두어 빈도
git log --all --pretty=%s | grep -cE "^<표기A>:"
# 브랜치 네이밍이면 원격 브랜치 빈도와 최신 시점
git branch -r | grep -oE "<패턴>" | sort | uniq -c
```

관행과 문서가 다르면 **관행이 정본**이고 문서를 고친다. 다만 사용자가 관행을 바꾸는 중일 수 있으므로, 실측값을 제시하고 확인을 받은 뒤 확정한다.

2026-09-16 사이클 7 에서 `refac:` 를 forge 오기로 판정했다가 실측(`refac:` 1,264 vs `refactor:` 267)으로 뒤집힌 사례가 있다. 문서 두 개(`pasta-rules/11`, 실전 `rules/11`)가 모두 관행과 어긋나 있었기 때문에 문서 대조로는 알 수 없었다.

### 심링크 무결성 검사

forge 저장소는 `.claude/rules/` 와 `.claude/commands` 를 심볼릭 링크로 원본에 연결한다. 원본 파일을 개명·이동하면 링크가 **조용히** 깨진다. 오류가 표시되지 않고 규칙이 로드되지 않은 채로 작업이 진행된다.

```bash
find .claude -type l ! -exec test -e {} \; -print   # 깨진 링크 출력. 0건이어야 정상
```

2026-09-17 점검에서 13개가 전부 깨져 있었고, 원본이 `.mdc` → `.md` 로 개명된 시점부터 5개월간 프로젝트 규칙이 로드되지 않은 상태였다. 상세는 `maintenance/feedback/_infra/2026-09-17-broken-rules-symlinks.md`.

### 사이클 단절 신호

`maintenance/feedback/` 에 **1개월 이상 기록이 없으면** 사이클이 끊긴 것이다. 즉시 이 점검을 실행한다.

2026-07-29 ~ 2026-09-16 사이 1.5개월간 기록이 없었고, 그 기간 실전 메모리에는 교훈 7건이 쌓였으나 forge 반영은 1건(14%)이었다. 그 결과 동일 실패 양상이 최소 5회 재발해 미커밋 작업 16개 파일이 복구 불가 상태로 소실됐다. 상세는 `maintenance/feedback/_cycle-summary/2026-09-16-cycle7-session-audit.md`.

## Phase 2. 분석 & 원인 진단

### 문제 분류

| 분류 | 증상 | 대응 |
|------|------|------|
| **가드레일 위반** | 하드 가드레일을 어김 | 즉시 수정 — 가드레일 문구 강화 또는 위치 이동 |
| **품질 미달** | 출력은 나오지만 기대 수준 미달 | 지침 보강, 예시 추가 (references/) |
| **범위 이탈** | 스킬이 담당하지 않는 작업을 시도 | scope 재정의, 디스패처 라우팅 수정 |
| **파괴적 쓰기** | 기존 파일·미커밋 작업물 소실, 중복 식별자 신설 | `forge/common/destructive-write-guard.md` 참조 연결 확인 + 해당 스킬에 DW 항목 명시 |
| **요청 범위 이탈** | 요청하지 않은 실행, 합의 없는 설계 결정 | `forge/common/scope-discipline-guard.md` 참조 연결 확인 + SC 항목 명시 |
| **비효율** | 토큰 과다 사용, 불필요한 반복 | 지침 간소화, 불필요한 단계 제거 |
| **트리거 오작동** | 잘못된 상황에서 스킬이 발동/미발동 | description 키워드 조정 |

### 원인 진단 체크리스트

1. [ ] SKILL.md의 지침이 모호한가?
2. [ ] 가드레일이 충분히 구체적인가?
3. [ ] references/에 해당 케이스의 예시가 있는가?
4. [ ] description의 트리거 키워드가 정확한가?
5. [ ] 본문이 너무 길어서 AI가 뒷부분을 무시한 것은 아닌가?
6. [ ] 이 규칙이 **프로젝트 메모리에만** 있고 스킬 본문에는 없는 것은 아닌가? (Phase 1.5 참조)
7. [ ] forge 기본값이 실전 저장소 규칙과 충돌하는 것은 아닌가?

## Phase 3. 개선 적용

### 개선 원칙

1. **일반화**: 특정 케이스 하나가 아닌, 유사한 케이스 전체를 커버하도록 수정
2. **최소 변경**: 문제 해결에 필요한 최소한의 변경만 적용
3. **Why 포함**: 왜 이 규칙이 추가/변경되었는지 주석 또는 changelog에 기록
4. **400줄 유지**: 수정 후에도 SKILL.md 본문 400줄 이내 유지

### 개선 적용 순서

1. `maintenance/feedback/{component-name}/{date}-{slug}.md` 피드백 분석
2. `anvil/{type}/{name}/SKILL.md` 또는 `references/` 수정
3. `forge/protocols/testing.md` 프로토콜로 재테스트 (기존 테스트 + 문제 케이스 추가)
4. 테스트 통과 시 → `maintenance/feedback/{component-name}/changelog.md` 에 기록

### Changelog 형식

```markdown
# {component-name} Changelog

## {날짜} - {변경 요약}
- **원인**: {피드백 파일 링크}
- **변경 내용**: {SKILL.md 어느 섹션을 어떻게 수정}
- **테스트 결과**: {재테스트 report 링크}
```

## Phase 4. Skill Creator 활용 (선택)

근본적 품질 개선이 필요한 경우, Anthropic의 `skill-creator` 스킬을 활용할 수 있다.

### 사용 시점
- 동일 유형의 피드백이 3회 이상 반복될 때
- 테스트 통과율이 지속적으로 낮을 때
- 컴포넌트를 처음부터 재설계해야 할 때

### 활용 방법
1. `/skill-creator` 스킬 호출
2. 기존 SKILL.md + 피드백 로그를 입력으로 제공
3. skill-creator의 eval 프로세스로 체계적 개선
4. 개선된 버전을 `anvil/`에 반영
