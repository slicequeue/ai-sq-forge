# Maintenance Protocol - 실전 피드백 기반 A/S

실전 배치된 컴포넌트의 품질을 지속적으로 개선하는 프로토콜이다.

---

## A/S 디렉토리 구조

```
maintenance/feedback/{component-name}/
├── {YYYY-MM-DD}-{issue-slug}.md    # 개별 피드백 기록
└── changelog.md                     # 개선 이력
```

---

## Phase 1. 피드백 수집

### 피드백 기록 형식

실전 사용 중 문제가 발견되면 아래 형식으로 기록한다:

```markdown
# {날짜} - {문제 한 줄 요약}

## 상황
- **컴포넌트**: {skill/agent/command/chain/dispatcher 이름}
- **사용 프로젝트**: {어디서 사용했는지}
- **사용자 입력**: "{실제 프롬프트 또는 요약}"

## 문제
{무엇이 잘못되었는가 / 기대와 다른 결과}

## 대화 로그 (핵심 부분)
{문제가 드러나는 대화 발췌 — 전체가 아닌 핵심만}

## 원인 분석
{왜 이런 결과가 나왔는지 추정}

## 개선 방안
{SKILL.md 또는 references의 어느 부분을 어떻게 수정할지}

## 우선순위
- [ ] Critical: 가드레일 위반 / 잘못된 출력
- [ ] Major: 품질 저하 / 비효율
- [ ] Minor: 개선하면 좋은 수준
```

---

## Phase 2. 분석 & 원인 진단

### 문제 분류

| 분류 | 증상 | 대응 |
|------|------|------|
| **가드레일 위반** | 하드 가드레일을 어김 | 즉시 수정 — 가드레일 문구 강화 또는 위치 이동 |
| **품질 미달** | 출력은 나오지만 기대 수준 미달 | 지침 보강, 예시 추가 (references/) |
| **범위 이탈** | 스킬이 담당하지 않는 작업을 시도 | scope 재정의, 디스패처 라우팅 수정 |
| **비효율** | 토큰 과다 사용, 불필요한 반복 | 지침 간소화, 불필요한 단계 제거 |
| **트리거 오작동** | 잘못된 상황에서 스킬이 발동/미발동 | description 키워드 조정 |

### 원인 진단 체크리스트

1. [ ] SKILL.md의 지침이 모호한가?
2. [ ] 가드레일이 충분히 구체적인가?
3. [ ] references/에 해당 케이스의 예시가 있는가?
4. [ ] description의 트리거 키워드가 정확한가?
5. [ ] 본문이 너무 길어서 AI가 뒷부분을 무시한 것은 아닌가?

## Phase 3. 개선 적용

### 개선 원칙

1. **일반화**: 특정 케이스 하나가 아닌, 유사한 케이스 전체를 커버하도록 수정
2. **최소 변경**: 문제 해결에 필요한 최소한의 변경만 적용
3. **Why 포함**: 왜 이 규칙이 추가/변경되었는지 주석 또는 changelog에 기록
4. **400줄 유지**: 수정 후에도 SKILL.md 본문 400줄 이내 유지

### 개선 적용 순서

1. `maintenance/feedback/{component-name}/{date}-{slug}.md` 피드백 분석
2. `anvil/{type}/{name}/SKILL.md` 또는 `references/` 수정
3. `forge/protocols/testing.md` 프로토콜로 재테스트 (기존 테스트 + 문제 케이스 추가)
4. 테스트 통과 시 → `maintenance/feedback/{component-name}/changelog.md` 에 기록

### Changelog 형식

```markdown
# {component-name} Changelog

## {날짜} - {변경 요약}
- **원인**: {피드백 파일 링크}
- **변경 내용**: {SKILL.md 어느 섹션을 어떻게 수정}
- **테스트 결과**: {재테스트 report 링크}
```

## Phase 4. Skill Creator 활용 (선택)

근본적 품질 개선이 필요한 경우, Anthropic의 `skill-creator` 스킬을 활용할 수 있다.

### 사용 시점
- 동일 유형의 피드백이 3회 이상 반복될 때
- 테스트 통과율이 지속적으로 낮을 때
- 컴포넌트를 처음부터 재설계해야 할 때

### 활용 방법
1. `/skill-creator` 스킬 호출
2. 기존 SKILL.md + 피드백 로그를 입력으로 제공
3. skill-creator의 eval 프로세스로 체계적 개선
4. 개선된 버전을 `anvil/`에 반영
