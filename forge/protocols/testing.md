# Testing Protocol - 컴포넌트 품질 검증

모든 컴포넌트는 이 프로토콜을 통과해야 실전 배치 가능하다.

---

## 테스트 구조

```
proving-grounds/evals/{component-name}/
├── test-cases.md          # 테스트 케이스 정의
├── results/
│   ├── baseline/          # 스킬 미사용 결과
│   │   └── {test-id}.md
│   └── with-skill/        # 스킬 사용 결과
│       └── {test-id}.md
└── report.md              # 비교 분석 리포트
```

---

## Phase 1. 테스트 케이스 설계

### 기본 테스트 케이스 (필수, 최소 3개)

각 컴포넌트에 대해 아래 형식으로 테스트 케이스를 작성한다:

```markdown
### TC-{번호}: {테스트 제목}

- **입력 프롬프트**: "{실제 사용자가 입력할 프롬프트}"
- **기대 결과**: {정답 또는 기대하는 출력 특성}
- **검증 기준**:
  - [ ] {구체적 검증 항목 1}
  - [ ] {구체적 검증 항목 2}
- **유형**: {happy-path | edge-case | negative}
```

### 테스트 유형 배분

| 유형 | 비율 | 설명 |
|------|------|------|
| Happy Path | 50% | 정상적인 사용 시나리오 |
| Edge Case | 30% | 모호한 입력, 경계 조건 |
| Negative | 20% | 잘못된 입력, 범위 밖 요청 |

## Phase 2. 테스트 실행

### Step 1: Baseline 실행 (스킬 미사용)

동일한 프롬프트를 **스킬/에이전트 없이** 일반 Claude에게 실행한다.

기록할 항목:
- 결과물 전문 (또는 요약)
- 소요 시간 (대략적)
- 토큰 사용량 (가능한 경우)
- 정확도 / 완성도 평가 (1-5점)

### Step 2: With-Skill 실행

동일한 프롬프트를 **스킬/에이전트 적용 상태**에서 실행한다.

기록할 항목:
- 결과물 전문 (또는 요약)  
- 소요 시간
- 토큰 사용량
- 정확도 / 완성도 평가 (1-5점)

## Phase 3. 결과 리포트 작성

`proving-grounds/evals/{component-name}/report.md` 에 아래 형식으로 작성:

```markdown
# {component-name} 테스트 리포트

## 요약

| 항목 | Baseline | With-Skill | 개선율 |
|------|----------|------------|--------|
| 정확도 (1-5) | {점수} | {점수} | {%} |
| 완성도 (1-5) | {점수} | {점수} | {%} |
| 가드레일 준수 | {Y/N/부분} | {Y/N/부분} | - |
| 소요 시간 | {시간} | {시간} | {%} |
| 토큰 사용량 | {토큰} | {토큰} | {%} |

## 테스트 케이스별 결과

### TC-1: {제목}
- Baseline: {요약}
- With-Skill: {요약}
- 판정: {PASS / FAIL / PARTIAL}

## 판정

- **실전 배치 가능**: 모든 Happy Path PASS + Edge Case 70% 이상 PASS
- **개선 필요**: 위 조건 미충족 → 개선 후 재테스트
- **폐기 검토**: 근본적 설계 문제 → design protocol로 재설계

## 개선 사항 (있을 경우)
- {발견된 문제와 개선 방향}
```

---

## 통과 기준 (Quality Gate)

| 기준 | 조건 |
|------|------|
| Happy Path | 100% PASS |
| Edge Case | 70% 이상 PASS |
| Negative | 범위 밖 요청을 적절히 거부/안내 |
| Baseline 대비 | 정확도 또는 완성도에서 개선 (동일하면 토큰 효율로 판단) |
| 가드레일 | 하드 가드레일 위반 0건 |
