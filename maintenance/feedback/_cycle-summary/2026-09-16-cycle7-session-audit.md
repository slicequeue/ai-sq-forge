### 4.1 미커밋 작업 소실 (심각도 최상)

| 항목 | 내용 |
|------|------|
| 일시 | 2026-08-19 20:42 (로그 타임스탬프 11:42 UTC) |
| 대상 | pasta-japan-metabase 저장소, `queries/` 하위 16개 SQL 파일 |
| 결과 | 사용자의 미커밋 수정분 전량 소실, 복구 불가 |

경과는 다음과 같다. 사용자가 커밋을 요청했다. 커밋에 diff가 남도록 "초기 커밋을 원본 상태로 되돌린 뒤 수정분을 두 번째 커밋으로 분리"하는 2단계 이력을 구성하기로 판단했다. 이 판단의 전제는 "수정분이 이미 초기 커밋에 들어 있다"였다. 실제로는 수정이 초기 커밋 **이후에** 워킹트리에 생긴 미커밋 상태였다. 스크립트로 16개 파일을 pull 시점 원본으로 일괄 덮어쓰면서 수정분이 디스크에서 사라졌다.

복구 시도는 전부 실패했다. 에디터 local history, 다른 세션 기록, APFS 스냅샷, 휴지통, git dangling blob 모두 해당 문자열을 포함한 파일이 없었다.

사용자 반응: "지금 수정한거 다 원복했냐?", "왜 날렸어".

근본 원인: **덮어쓰기 직전 `git status` 한 줄을 확인하지 않았다.** 전제를 검증 없이 사실로 삼았다.

동일 실패 양상이 2026-09-01에 재발했다. 프로젝트 메모리 `feedback_verify_before_writing` 기록에 따르면 한 세션에서 같은 패턴으로 네 번 지적받았다. `cat >` 로 `UserDeviceTest.java` 를 덮어써 기존 테스트 3건을 삭제한 건이 포함된다. 즉 1개월간 최소 5회 재발이다.

forge 대조 결과: `anvil/skills/` 의 코드 작성 스킬(java-spring-coder, coding-implementer)에 "쓰기 전 파일 존재 확인" 또는 "덮어쓰기 전 `git status` 확인" 하드 가드가 없다. `safe-mass-rename` 스킬은 롤백 브랜치와 6단계 순서 강제를 갖췄으나, 트리거가 "전역 식별자 리네임"으로 한정되어 스크립트 기반 일괄 파일 재작성을 커버하지 못한다.

### 5.1 커밋·브랜치 컨벤션 표기 불일치 (판정 정정)

**최초 판정과 정정 경위를 함께 남긴다.** 이 절은 초기 작성 시 오판이 있었고, 실측으로 뒤집혔다.

초기 판정은 다음과 같았다. forge `anvil/commands/git-commit.md` 가 커밋 타입으로 `refac:` 를 강제하는데, forge 자신의 `pasta-rules/11` §2 와 실전 `rules/11` 은 `refactor:` 로 적혀 있으므로 forge 쪽이 오기라고 보았다.

실제 저장소 히스토리를 측정한 결과 반대였다. 대상은 pasta-japan-server 전체 이력이다.

| 표기 | 커밋 접두어 건수 | 브랜치 수 | 최신 브랜치 |
|------|------------------|-----------|-------------|
| `refac` | 1,264 | 13 | 2026-06-15 |
| `refactor` | 267 | 2 | 2026-02-20 |

판단: **실제 관행은 `refac` 이며 이것이 정본이다.** 어긋나 있는 쪽은 규칙 문서(`rules/11`, 실전 `git-branch` 커맨드)다. 문서가 언젠가 `refactor` 로 바뀌었으나 관행은 따라가지 않았고, 그 결과 문서와 실행이 따로 놀고 있었다.

조치는 다음과 같다. 2026-09-16 사용자 확인을 거쳐 확정했다.

| 대상 | 조치 |
|------|------|
| forge `git-commit` v1.2 | `refac:` 유지. 근거를 실측값으로 본문에 명시 |
| forge `git-branch` v1.1 | `refac` 유지. 실전이 `refactor` 로 바뀐 것은 역배포로 되돌릴 대상 |
| forge `pasta-rules/11` | §1 브랜치·§2 커밋 타입·예시를 모두 `refac` 으로 정정해 관행과 일치시킴 |
| 실전 `rules/11`, `git-branch` | forge 정정본 배포 대상 (미실행) |
| 실전 프로젝트 메모리 `feedback_always_use_commit_skill` | "`refac:` 아니라 `refactor:`" 기술이 실측과 불일치. 해당 프로젝트 세션에서 정정 필요 (이번 범위 밖) |

교훈: forge 기본값과 실전 규칙 문서가 충돌할 때, **어느 쪽이 맞는지는 문서 대조가 아니라 실행 이력 측정으로 정한다.** 문서 두 개를 비교하면 둘 다 틀렸을 때 알아낼 수 없다. 이 항목은 `forge/protocols/maintenance.md` Phase 1.5 판정 절차에 반영했다.

## 7. 개선 액션

우선순위 순으로 제시한다. 각 항목은 forge 워크플로의 "신규 컴포넌트 개발" 절차(하네스 정의 + Negative TC 필수 + `/eval-harness` 검증)를 따른다.

### 7.1 최우선 — 파괴적 쓰기 공통 가드 신설

`forge/common/` 에 파괴적 쓰기 가드 문서를 신설하고, 파일을 쓰는 모든 스킬(java-spring-coder, coding-implementer, admin-thymeleaf-ui, tolgee, safe-mass-rename)이 참조하도록 한다.

하드 가드레일 초안이다.

| 규칙 | 내용 |
|------|------|
| 사전 확인 | 기존 파일을 덮어쓰기 전 `git status` 로 미커밋 변경 유무를 확인한다. 미커밋 변경이 있으면 작업을 멈추고 사용자에게 알린다 |
| 전제 검증 | "커밋에 이미 들어 있다", "이 파일은 원본 상태다" 같은 전제는 명령으로 확인하기 전까지 사실로 취급하지 않는다 |
| 통째 덮기 금지 | `cat >` 또는 Write 로 기존 파일을 통째 덮지 않는다. 덮어야 하면 원본을 먼저 읽는다 |
| 다중 파일 | 2개 이상 파일을 일괄 재작성할 때는 실행 전 백업 커밋 또는 브랜치를 만든다 |
| 사후 점검 | 작업 후 `git log <base>..HEAD --name-only` 로 의도치 않은 삭제가 없는지 확인한다 |

Negative TC 는 4.1절 사건(미커밋 상태에서 일괄 덮어쓰기 시도)을 그대로 재현해 차단 여부를 검증한다.

### 7.2 최우선 — 역수입 사이클 복구

프로젝트 메모리에 축적된 교훈을 forge 스킬로 승격하는 절차를 정례화한다.

| 단계 | 내용 |
|------|------|
| 1 | 미반영 교훈 6건을 해당 스킬 본문에 반영 (5절 표 기준) |
| 2 | `maintenance/feedback/{component}/2026-09-16-*.md` 로 근거 기록 |
| 3 | `/eval-harness {name} --skip-baseline` 로 회귀 검증 |
| 4 | 이후 월 1회, 프로젝트 메모리의 신규 `feedback_*` 항목을 forge 반영 여부와 대조하는 점검을 고정 일정으로 수행 |

4단계는 `forge/protocols/maintenance.md` 에 절차로 명문화한다. 이번 감사에서 확인된 공백(2026-07-29 이후 1.5개월 무기록)의 재발을 막는 장치다.

### 7.3 상 — PR 템플릿 준수 가드

`anvil/skills/git-pr/SKILL.md` 와 `anvil/skills/pr-feedback-resolver/SKILL.md` 에 다음을 추가한다.

PR 본문 작성 전 `.github/PULL_REQUEST_TEMPLATE.md` 존재 여부를 확인하고, 존재하면 섹션명을 문자 그대로 사용한다. 선택 섹션은 조건이 실제로 성립할 때만 추가한다. 템플릿이 없을 때만 스킬 기본 양식을 쓴다.

버전은 git-pr 0.2 → 0.3, pr-feedback-resolver 1.5 → 1.6 으로 올린다.

### 7.4 상 — 범위 이탈 차단 가드

작업 중 범위 밖 문제를 발견했을 때의 처리를 명문화한다. 적용 대상은 coding-implementer, java-spring-coder 및 신설 공통 가드다.

| 대상 행위 | 처리 |
|-----------|------|
| 요청 범위 밖 저장소 변경 | 보고만 하고 정지 |
| 합의되지 않은 설계 결정 (뷰·인덱스·아키텍처 도입) | 선택지와 근거를 제시하고 승인 대기 |
| 스키마 변경 (컬럼·테이블 추가) | 동일 값의 기존 저장 위치를 전수 검색한 뒤 결과와 함께 승인 요청 |
| 요청받은 고려사항 제외 | 제외 사유를 명시하고 승인 대기 |

### 7.5 중 — 커밋·브랜치 컨벤션 문서 정합 (완료)

실측 결과 관행(`refac`)이 정본이고 규칙 문서가 어긋나 있었다. forge `git-commit` v1.2·`git-branch` v1.1·`pasta-rules/11` 을 `refac` 기준으로 정합시켰고, 각 파일에 실측 근거를 본문에 남겼다. 상세는 5.1절.

남은 일은 실전 `rules/11` 과 `git-branch` 커맨드에 이 정정본을 배포하는 것이다. 실전 프로젝트 메모리 `feedback_always_use_commit_skill` 의 불일치 기술도 해당 프로젝트에서 정정해야 한다.

### 7.6 중 — 최다 사용 스킬의 forge 편입

`formal-doc-ko`, `pr-comment-ko`, `cloud-run-health-check` 를 forge 로 역수입해 하네스와 평가 루브릭을 갖춘다. 사용 빈도 1위 자산이 품질 검증 체계 밖에 있는 상태를 해소한다.

편입 시 4.4절의 지적(분량 과다, 사람 글로 읽히지 않음)을 Negative TC 로 반영한다.

### 7.7 중 — 완료 보고 전 실물 확인 가드

작업 완료를 보고하기 전에 결과물을 실제로 조회해 확인하는 절차를 공통 가드에 포함한다. 문서 반영, UI 변경, 데이터 적재 등 사용자가 눈으로 확인하는 산출물이 대상이다. 4.5절의 4개 사건이 근거다.

### 7.8 중 — 동기화 갭 해소

5.2절의 상이 5건을 건별로 판정해 forge 반영 또는 실전 재배포 중 하나로 정리한다. `retrospective` 빈 디렉터리는 실체를 만들거나 제거한다.
