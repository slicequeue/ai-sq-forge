## 2. 결론 요약

세 가지다.

첫째, **지적 빈도가 줄지 않고 있다.** PR 한 건당 사람 리뷰어 지적은 2026-06 에 0.36건까지 내려갔다가 07 월 1.58건으로 올랐고 09 월에도 1.50건이다. 같은 유형의 지적이 반복된다는 사용자 인식은 측정으로 확인된다.

둘째, **지적의 대부분은 문법 오류가 아니라 판단 누락이다.** 상위 유형은 네이밍·코드 스타일, 예외 처리, 문서와 코드 불일치, 동시성·트랜잭션, 장애 시 동작(fail-open)이다. 컴파일러도 테스트도 잡아주지 않는 영역이다.

셋째, **반복 지적 34개 유형 중 14개가 forge 코딩 스킬에 전혀 없다.** 나머지 20개는 어떤 형태로든 반영돼 있다. 즉 재발의 절반 가까이는 스킬에 규칙이 없어서 생긴 것이고, 나머지는 규칙이 있는데도 지켜지지 않은 것이다.

## 7. 스킬 커버리지 대조 (핵심)

반복 지적 34개 유형을 forge 자산(`anvil/skills/`, `anvil/agents/`, `forge/common/pasta-rules/`)과 대조했다.

### 7.1 스킬에 없는 유형 14건 — 신규 반영 대상

DDL 관련 3건은 리뷰어 판정이 시기별로 엇갈려 저장소 마이그레이션 2,010개를 실측해 확정했다. 문서의 권장값보다 저장소 실제 패턴을 정본으로 삼는다.

| 유형 | 대표 지적 | 출처 PR |
|------|-----------|---------|
| DDL PK signed 통일 | `BIGINT UNSIGNED` 가 기존 패턴에서 이탈하고 JPA `Long`(signed)과 불일치. 실측 결과 UNSIGNED 사용은 마이그레이션 2,010개 중 9개(0.4%)로 signed 가 정본 | #589 (#571 의 unsigned 권장은 #589 에서 번복) |
| 비ASCII INSERT 시 charset 확인 | 한글을 INSERT 하면서 대상 스키마 기본 charset 을 확인하지 않음. 실측상 charset 명시는 1.2%라 규칙은 "명시"가 아니라 "확인" | #643, #504 |
| 불리언 컬럼 `is_` 접두 | 기존 마이그레이션 7개가 `is_active` 인데 `active` 로 이탈. 머지 후 rename 비용 발생 | #636 |
| fail-open 판정 | 규칙 0건·예외 발생 시 전 유료 API 가 조용히 무료 개방. 탐지도 안 됨 | #637, #643, #641 |
| 결정성 — 순서 의존 | `groupingBy` HashMap 결과 순서에 등록 순서가 좌우됨 / 동점 시 2차 정렬 기준 부재로 조회 순서에 결과가 달라짐 | #608, #697, #658 |
| enum 순서 결합 | `values()` 순서에 처방값 위치가 결합돼 enum 순서만 바꿔도 조용히 오매핑 | #667 |
| 동어반복 테스트 | 검사 대상과 검사 기준이 같은 상수라 테스트가 항상 참 | #741 |
| 벌크 update 후 1차 캐시 | QueryDSL 벌크 update 가 영속성 컨텍스트를 갱신하지 않아 직후 조회가 옛 값을 읽고 덮어씀 | #717 |
| `IN` 절 파라미터 상한 | 대량 지정 시 파라미터 개수 제한·성능 문제. 배치 분할 필요 | #746 |
| catch 예외 상하위 관계 | `NumberFormatException` 은 `IllegalArgumentException` 의 하위라 상위를 못 잡음 | #687 |
| 응답 단위 일관성 | 한 카드 안에서 `duration` 은 MINUTE, `goal` 은 HOUR 로 갈림 | #696 |
| 무의미한 주석 | 코드가 이미 말하는 내용을 주석으로 반복. 한 PR 에서 7건 연속 지적 | #474 |
| dead config | 유일한 소비자가 삭제돼 아무도 읽지 않는 설정이 남음. 긴급 차단 토글이라 위험 | #641 |
| Spring Batch 잡 파라미터 | `--name=value` 는 옵션 인자로 분류돼 잡 파라미터로 안 들어감 / 파라미터 없는 정기 실행에는 incrementer 미적용 | #720 |

### 7.3 이미 반영돼 있는 유형 16건

FQCN 인라인, Bean 이름 매직 스트링, Hibernate Session 오염, N+1, 개인정보 로깅, 로그 레벨, 타임존, Swagger 용어, `@Builder` 기준, HikariCP, 커넥션 타임아웃, 청크 트랜잭션, 권한 스캔 범위, 하위 호환, mock 한계, 제약 네이밍.

이들은 규칙이 있는데도 지적이 나온 경우가 섞여 있다. 규칙 부재가 아니라 **적용 실패**이므로, 대응은 규칙 신설이 아니라 자기 검증 체크리스트 강화다.

### 8.2 리뷰 스킬 동반 반영

코드 생성 시점에 막는 것과 리뷰 시점에 잡는 것은 다르다. 생성 스킬에 넣은 규칙은 대응하는 관점 리뷰 스킬에도 검사 항목으로 넣는다.

| 생성 스킬 규칙 | 리뷰 스킬 |
|----------------|-----------|
| fail-open, 벌크 update, 결정성 | `java-business-logic-reviewer` |
| DDL 컨벤션 3건 | `java-architecture-reviewer` |
| `IN` 절, 페이징 | `java-performance-reviewer` |
| 동어반복 테스트 | `java-layered-unit-testing` 자기 검증 |

### 8.3 Negative TC

각 신규 규칙은 `forge/common/negative-tc-catalog.md` 에 패턴을 등록하고, 해당 스킬 하네스에 최소 1건의 회귀 TC 를 추가한다.
