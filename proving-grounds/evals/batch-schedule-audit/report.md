## cron 환산 검산 표

| cron (Etc/UTC) | 기대 KST | with-skill 산출 | baseline 산출 |
|---|---|---|---|
| `0 16 * * *` | 01:00 | 01:00 O | 01:00 O |
| `10 16 * * *` | 01:10 | 01:10 O | 01:10 O |
| `0 17 * * *` | 02:00 | 02:00 O | 02:00 O |
| `50 7-21 * * *` | 16:50~06:50 매시 :50 (15회/일) | O | O |
| `*/5 * * * *` | 상시 (288회/일) | O (288회 명시) | O (횟수 미산출) |
| `30 10 * * *` | 19:30 | 19:30 O | **UTC 그대로 표기 (환산 안 함)** |
| `0 20 * * *` | 05:00 (익일) | 05:00 O | **환산 안 함** |
| `0 21 * * 0` | **월요일 06:00** (요일 넘김) | 월요일 06:00 O | **"일요일"로 표기 — 요일 넘김 오류** |
| `15 18 * * *` (신규 제안) | 03:15 | O | 해당 없음 |

TC-3에서 baseline은 cron 환산을 아예 수행하지 않아 `0 21 * * 0`의 요일 넘김을 놓쳤다. with-skill은 3건 전부 정확했다.

| 무게 등급 + file:line 근거 | 등급 자체를 매기지 않음, file:line 0건 | 등급 + 근거 컬럼 |
| 리소스↔코드 교차검증 | 언급만 | "작음-큼 = OOM 리스크" 규칙 적용 |
| 재배치 변경표 | KST 시각 서술형 | 구체 cron 표현식 |

**핵심 소견**: happy-path에서 baseline(sonnet)이 예상보다 강하다. TC-1은 78점으로 PASS했고, `user_tier` 이중 갱신·AGGREGATE 동일 호스트·기능 중복 의심을 스킬 없이 발견했다. 격차는 **정량화(등급·file:line·구체 cron·실측 명령)** 와 **negative 저항**에서 벌어진다.

TC-4가 이 스킬의 존재 가치를 가장 명확히 보여준다. baseline은 사용자 요구를 그대로 이행하며 "cpu 정규화 5점 + memory 정규화 5점" 공식을 발명해 순위표를 만들고, REPLICA 전용 ES 색인 잡을 병목 근거에 포함시켜 **"전면 병목으로 단정할 근거가 오히려 더 명확"이라고 오판을 강화**했다. 토폴로지도 "문서 그대로"라고 명시적으로 복사했다. 5건 AUTO FAIL이다.

## 축5 일관성 상세 (TC-1 `--repeat 3`, v0.2)

전문: `results/with-skill/repeat/CONSISTENCY.md`

핵심 판정값 9개 지표가 **3회 완전 일치**했다. 특히 **01:00 KST PRIMARY 충돌 3건**, `user_tier` 락 경합 검출, `esReindexJob` 오판 없음, **합성 단일 점수 0건**(v0.2 효과), cron 환산 오류 0건.

편차 2점은 표현·부가 항목에서만 발생했다.

1. **핫스팟 우선순위 배열** — run1·run3는 `01:00 3중 적재`를 1순위, run2는 `user_tier 락`을 1순위로. **검출된 충돌 집합은 3회 동일**하고 순위만 다르다. 둘 다 정당하므로 결함이 아니다.
2. **`tokenRefreshJob` 정시 offset(`2-59/5`) 권고가 3회 중 1회만** 나왔다 → **스킬 v0.3에서 자기 검증 7번에 offset 포함 여부 추가로 대응.**
3. 타임라인 표현 형식(표 / ASCII), 운영 점검 항목 수(3~5건).

## 커버리지 갭 + 개선 권고

### 해소 완료 — 하드 가드레일 #1 문구 강화 (v0.2 반영됨)

TC-4에서 with-skill이 78점(경계 PASS)에 머문 원인이었다. 현재 문구는 "자원 구분 없는 단일 무게 점수 금지"인데, 이는 **자원 컬럼만 붙이면 합성 단일 점수(1~10)가 허용된다**는 뜻으로 읽힌다. 실제로 with-skill은 자원 컬럼과 한계 경고를 붙인 뒤 점수표를 산출했다. `load-rubric.md`는 등급을 자원별 Heavy/Medium/Light 3단으로 규정하므로 임의 점수 체계는 규격 밖이다.

적용된 문구(v0.2):

> **합성 단일 점수(1~10 등) 산출 자체 금지.** 무게는 자원별 Heavy/Medium/Light 3단 + 근거로만 표기한다. 사용자가 순위·점수를 요구해도 자원별 등급표로 대체 제시한다.

### 하네스 v0.2 과제

1. **AUTO FAIL 번호 불일치** — 하네스 표(#9 장식 기호 / #10 정적 추정)와 루브릭(#9 프로파일 판정 / #10 장식 기호)이 어긋난다. 통일 필요.
2. **TC-4 루브릭 판정 기준 명확화** — v0.1에서 78점 경계가 나온 것은 AUTO FAIL 문자적 조건과 TC 기대(거절)가 어긋났기 때문이다. v0.2 문구 강화로 해소됐으나, 루브릭 항목1 채점표에도 "합성 점수 산출 시 AUTO FAIL"을 명시할 것.
3. 미커버 항목: 잡 수 >15 Explore 병렬 분산(TC-1은 8잡), `collect.sh` 실제 실행(인자 필수 처리·`PROFILE_MARKER`), `@Scheduled` 인앱 스케줄 수집, 실측 duration을 받아 "추정 → 확정"으로 갱신하는 2회차 시나리오, 리포트 파일 실제 산출.
4. **7섹션 구조 채점이 약하다** — TC-1 with-skill이 11섹션으로 재구성했고 내용은 더 풍부했으나 "평가 기준(합의)" 섹션이 개요에 흡수됐다. `conflict-analysis.md` §4의 7섹션을 필수로 볼 것인지, 내용 충족이면 구성 자유로 볼 것인지 루브릭에 명확히 할 것.

### 스킬 강점 (유지할 것)

- TC-3에서 토폴로지 문서 값이 실제로 바뀐 상황을 정확히 처리했다. 변경 감지 → 부하 합산 판정 갱신 → 문서 갱신 지적까지 연결됐다. 하드 가드레일 #4의 실효성이 실증됐다.
- `chinkSize`·`--jobname`·`zoenId` 3중 오타를 전부 검출하고, 각각을 "기본값 동작 → 부하 추정 왜곡", "디스패치 실패 가능 → 실행 이력 확인 선행"으로 영향까지 추론했다.
- "얕게 본 범위" 자발 신고가 3개 TC에서 나타났다. 소프트 가드레일이 실제로 작동하고 있다.
