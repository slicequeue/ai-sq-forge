### [Phase 3-0 작성 전 질문 5개 — TDD Phase 1, 3-1 착수 전]

확인된 사실과 가정을 나눠 적는다.

**확인된 사실**
- 조회 전용 API 이고 소스는 DB 2개(체중·복약) + 외부 API 1개다
- `medication_master` 에 `dose = 0` 행이 실제로 있다
- 기존 PUT `/api/v1/weights/{id}` 가 있고 TDD 가 여기에 새 검증을 붙이라고 한다

**답변**

| # | 질문 | 답 | 근거 |
|---|------|----|------|
| Q1 | 이 조회가 실패하면 사용자는 무엇을 보는가 | 복약 일정 또는 추천 콘텐츠가 실패하면 그 카드만 비어 보이고, 마지막 체중 기록은 그대로 보인다. 전체 500 이나 "기록 없음"(틀린 상태)은 내려보내지 않는다. 소스 3개를 각각 독립 try 로 감싸고 실패 시 WARN 로그를 남긴다 | RR-13. 가드가 정한 사항이라 묻지 않고 적용 |
| Q1-보조 | 부가 조회가 같은 트랜잭션에서 예외를 내면 | 호출부 catch 만으로는 rollback-only 가 걸려 `UnexpectedRollbackException` 으로 전체가 실패한다. 실패를 허용할 ②는 별도 빈 + `REQUIRES_NEW` 또는 readOnly 분리로 경계를 나누고, 테스트는 실제 프록시로 돌린다 | RR-13 (#793). 가드가 정한 사항이라 묻지 않고 적용 |
| Q2 | 외부 호출 성공 후 DB 저장이 실패하면 | 해당 없음. 이 API 는 조회 전용이라 저장이 없다. 추천 콘텐츠 호출 결과를 DB 에 쓰지 않는다 | TDD Phase 1 범위에 저장 항목 없음 |
| Q3 | 마스터 데이터가 null·0·음수면 | `dose = 0` 은 실제로 있는 데이터다. 그 건만 건너뛰고 WARN 로그(건 식별자 포함, 사용자 식별자 제외)를 남긴다. 일정 변환에 `Collectors.toMap` 을 쓰면 null value·중복 키를 방어하거나 쓰지 않는다 | RR-13 (#794·#800). 가드가 정한 사항이라 묻지 않고 적용 |
| Q4 | 기존 경로 동작이 바뀌는가 | **바뀐다.** `RecordTimeValidator` 를 PUT 에 붙이면 이전에 통과하던 수정 요청이 400 이 될 수 있다. Phase 5 PR 본문에 "기존 동작 변경" 항목으로 넘길 메모를 지금 남긴다. 검증 순서는 소유·존재 확인 → 입력 검증이다. "마지막 기록" 판정은 시각이 아니라 id 로 하고, 미래 시각 기록이 최신으로 잡히지 않게 `현재 시각 이하` 조건을 넣는다 | RR-14 (#800·#784·#793) |
| Q5 | 이 분기를 깨뜨리면 실패하는 테스트가 있는가 | 계획한다. ①실패 시 ② 카드만 비고 체중은 유지, ③ 실패 시 동일, `dose = 0` 건 제외 + 나머지 건 정상, 체중 기록 0건과 조회 실패를 구분. 검증은 POST·PUT 양 경로에서, PUT 은 타인 id 요청이 400 이 아니라 소유 오류로 나가는 순서까지. 저장소·QueryService 는 Fake 에 저장 후 조회하고 Mock 정답 주입은 쓰지 않는다. 기본값과 다른 값으로 매핑을 검증하고 JSON 단언은 `doesNotHaveJsonPath()`·`isBoolean()` 등 엄격한 형태를 쓴다 | RR-12·RR-14 |

**답을 못 한 항목 — TDD 에 근거가 없어 구현 전에 확인이 필요합니다.** 구현을 먼저 하고 사후 확인하지 않습니다.

TDD 에서 확인되는 것은 "부가 소스 실패 시 그 카드만 비운다"는 가드 원칙까지이고, 아래 둘은 TDD 에 적혀 있지 않습니다. 응답 스키마와 검증 정책에 해당하는 제품 결정이라 임의로 정하지 않습니다 (SC-3).

**결정 1. 소스 실패 시 카드의 응답 형태**

| 선택지 | 내용 | 장점 | 단점 |
|--------|------|------|------|
| A (권장) | 카드 객체에 상태 필드를 둔다. 예: `{"status": "UNAVAILABLE", "items": []}` / 정상은 `"OK"` | 클라이언트가 "일정 없음"과 "조회 실패"를 구분한다 | 응답 스키마에 필드가 하나 늘어난다 |
| B | 실패한 카드는 빈 배열 또는 null 로만 내린다 (상태 필드 없음) | 스키마 변경이 없다 | "이번 주 일정 없음"과 "조회 실패"가 같아 보여 틀린 상태를 줄 수 있다 |
| C | 실패한 카드 키를 응답에서 생략한다 | 단순하다 | 클라이언트가 키 부재를 분기해야 한다 |

도입하지 않을 때의 대안은 B 이고, 기존 홈 응답 스키마 변경 여부는 PRD 기준으로 확인이 필요합니다.

**결정 2. `RecordTimeValidator` 의 검증 규칙**

TDD 는 공용 검증을 신설해 POST·PUT 에 붙인다고만 하고 어떤 시각을 거부하는지는 적혀 있지 않습니다.
- 거부 대상이 무엇인가: 미래 시각 / 일정 기간 이전 과거 시각 / 직전 기록과의 간격 등
- 위반 시 응답: 400 과 에러 코드 (기존 에러 코드 체계를 따를지)
- 기존 PUT 에서 이미 저장된 과거 기록을 수정하는 경우도 같은 규칙을 적용할지 (적용하면 기존 통과 요청이 400 이 되므로 Q4 의 동작 변경 폭이 커집니다)

권장안: 기존 PUT 의 현재 동작을 먼저 읽어 현황을 확인한 뒤(읽기 전용), 현재 이미 통과하던 요청을 최대한 유지하는 최소 규칙(예: 미래 시각만 거부)부터 적용하고 나머지는 후속으로 분리합니다.
