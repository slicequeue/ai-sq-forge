### 사용자 확인 요청 (3-1 구현 착수 전, 여기서 멈춤)

위 Q1·Q3 은 TDD 에 근거가 없는 설계 결정이고, 응답 스키마·트랜잭션 구조에 걸려 있어서(SC-3) 구현 후 사후 확인 대신 **구현 전에** 묻습니다.

**1. 소스 하나가 실패했을 때 응답 형태** (TDD 에 없음)

| 선택지 | 내용 | 장점 | 단점 |
|--------|------|------|------|
| A (권장) | 실패한 소스의 카드만 비우고 나머지는 정상 반환. 응답에 "조회 실패"와 "데이터 없음"을 구분할 수 있는 상태 값을 둔다 | "기록 없음" 같은 틀린 상태를 내려주지 않음 | 응답 스키마에 상태 필드 추가 (프론트 합의 필요) |
| B | 실패한 소스의 필드를 null 로 두고 상태 필드는 만들지 않음 | 스키마 변경 최소 | "기록 없음"과 "조회 실패"가 구분되지 않음 |
| C | 어느 소스든 실패하면 전체 5xx | 단순 | 부가 정보(추천 콘텐츠) 실패가 홈 전체를 막음 |

**2. 핵심 소스(체중)와 부가 소스(복약 일정·추천 콘텐츠)를 다르게 다룰지**
- 예: 체중 조회 실패는 5xx, 복약·콘텐츠 실패는 해당 카드만 비움 / 아니면 3개 모두 동일 정책
- 어느 쪽인지 정해야 동일 로직 fail 정책이 대칭(RR-1)인지 판단할 수 있습니다

**3. 트랜잭션 경계**
- `MedicationScheduleQueryService` 가 홈 조립 서비스와 같은 트랜잭션에 참여하면, 일정 조회에서 예외가 나는 순간 rollback-only 로 전체가 실패한다 (RR-13, #793)
- 선택지: (가) 조립 서비스는 트랜잭션 없이 두고 각 소스 조회가 독립 readOnly 트랜잭션 / (나) 조립 서비스는 기존 트랜잭션 유지 + 일정 조회를 `REQUIRES_NEW`·별도 readOnly 빈으로 분리
- 가 쪽이 변경이 작아 권장. 기존 홈 조립 코드의 트랜잭션 현황은 3-1 위임 전에 확인하겠습니다

**4. `dose = 0` 마스터 행 처리**
- 선택지: (가) 그 행만 건너뛰고 WARN 로그 / (나) 일정은 노출하되 dose 를 null 또는 기본값으로 / (다) 그 행도 오류로 보고 소스 실패로 처리
- 기본은 (가) 이지만, 사용자 화면에서 해당 약 일정이 사라지는 동작이라 확인이 필요합니다. 데이터 자체의 정정은 이번 범위 밖이므로 별도 보고 사항으로만 남깁니다 (SC-1)
