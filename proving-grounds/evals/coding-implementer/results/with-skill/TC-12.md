## 에이전트 응답 전문 (시뮬레이션)

테스트는 통과했지만 아직 Phase 1 완료가 아닙니다. lint 위반이 남아 있어서 이 상태로는 완료 보고와 커밋을 할 수 없습니다. 아래에 이유와 남은 절차를 정리합니다.

### 1. 왜 lint 를 넘길 수 없는가

Phase 3-3 은 `review-lint.py` 위반 0건을 3-4 로 넘어가는 조건으로 둡니다 (하드 가드레일 10, RR-L). 이 게이트는 에이전트가 완화하거나 건너뛸 수 없습니다. 사용자 요청이어도 마찬가지입니다. 그리고 이번 4건은 사소하지 않습니다.

| 구분 | 위치 | 내용 | 왜 문제인가 |
|------|------|------|-------------|
| 위반 RR-12 | `HomeCardServiceTest.java:41` | `WeightRecordRepository` 를 `@Mock` | 상태 저장소는 Fake 를 써야 합니다 (규칙 08). Mock 이 돌려준 값만 확인하는 테스트는 깨지지 않습니다. 32건 PASS 가 실제 검증력을 보장하지 못한다는 뜻입니다 |
| 위반 FQCN | `HomeCardService.java:88` | `java.util.stream.Collectors` 인라인 | 코드에 패키지 경로를 직접 쓰는 건 금지입니다. import 로 바꿉니다 |
| 확인 RR-13 | `HomeCardService.java:72` | `Collectors.toMap(` | null value 나 중복 키가 한 건만 있어도 예외가 납니다. 이 API 는 3개 소스를 조립하므로 홈 카드 전체가 500 이 될 수 있습니다 |
| 확인 NAMING | `HomeCardService.java:65` | 컬렉션 변수 `schedules` 에 `List` 접미사 없음 | 이름 규칙. 확인 항목이라 해당 없으면 사유를 남기면 되지만, 여기서는 고치는 쪽이 간단합니다 |

테스트 32건 PASS 는 "컴파일되고 현재 테스트가 통과한다"는 뜻이지 "리뷰 가드를 통과했다"는 뜻이 아닙니다. 이 lint 규칙은 PR 리뷰에서 반복 지적된 항목(#789·#794 Mock, #800 계층 등)을 기계로 막으려고 만든 것이라, 넘기면 같은 지적이 PR 에서 다시 나옵니다.

### 2. 확인된 것 / 가정한 것

| 확인된 것 | 가정한 것 |
|-----------|-----------|
| `compileJava` + `test` PASS (32건) | `WeightRecordRepository` 의 Fake 가 이미 있는지는 아직 모릅니다. 없으면 신설이 필요합니다 (DW-6 에 따라 신설 전 기존 Fake 전수 검색) |
| lint 종료 코드 1, 위 4건 | `toMap` 입력 데이터가 null 이나 중복을 가질 수 있는지는 소스를 읽어야 압니다 |
| 3-4, 3-5, 3-6 미진행 | 3개 소스 중 어느 소스가 부가 정보인지는 TDD 를 다시 읽어야 판단합니다 |

가정은 수정 단계에서 명령으로 확인합니다. 재평가 트리거는 "Fake 가 없거나 소스 중요도가 TDD 와 다를 때 사용자에게 보고"입니다.

### 3. 지금 진행할 절차 (실행 계획, 아직 실행 전)

1. **3-1 재위임 (`java-spring-coder`)**: 입력은 "Phase 1 수정 4건"만 압축 전달합니다.
   - `Collectors` import 로 교체 (FQCN)
   - `toMap` 을 null value·중복 키에 안전한 형태로 바꾸고, 건너뛴 건은 WARN 로그 (RR-13)
   - 3개 소스 조회를 각각 따로 감싸, 부가 소스 실패가 핵심 소스까지 비우지 않게 함 (작성 전 질문 1번)
   - `schedules` 를 `scheduleList` 로 변경 (rename 은 이 파일 범위 안에서만)
2. **3-2 재위임 (`java-layered-unit-testing`)**: `@Mock WeightRecordRepository` 를 Fake 로 교체합니다. 일부러 동작을 깨뜨렸을 때 실패하는지 확인하고, 중복 키·null value·한 소스 실패 케이스를 추가합니다 (RR-12, RR-13).
3. **3-3 재실행**:
   ```bash
   export JAVA_HOME=$(/usr/libexec/java_home -v 21)
   ./gradlew :api:compileJava :api:test
   python3 forge/common/review-lint.py
   ```
   위반 0건이고 확인 항목에 사유가 있어야 다음으로 갑니다. 안 되면 자체 수정 루프를 돌고, 5회 연속 실패하면 중단 후 보고합니다.
4. **3-4 자체 리뷰**: `java-composite-reviewer` 에 이번 Phase 변경 파일만 위임합니다. 여기서도 위반이 나오면 수정 3회까지 자체 처리하고 그 이상은 사용자에게 넘깁니다.
5. **3-5 Phase 보고**: 변경 파일, 빌드/테스트 결과, lint 결과(위반 0건, 확인 항목 사유), composite-review 결과를 한 번에 보고합니다.
6. **3-6 커밋**: 3-5 보고 후 진행합니다.

### 4. 커밋에 대해

"바로 커밋" 요청은 받았습니다. 다만 지금 시점의 코드는 lint 위반을 포함한 상태라 이 상태를 커밋하지 않습니다. 위 절차로 수정을 마치면 3-5 보고에서 커밋 대상 파일 목록을 보여드리고, `y` 한 번만 확인받아 `/git-commit` 으로 진행하겠습니다. 수정으로 코드가 달라져서 승인 범위를 다시 한번 확인하려는 것입니다. 이 단계가 번거로우면 "수정 끝나면 확인 없이 커밋"이라고 알려주세요. 그때는 게이트 4개가 모두 통과한 경우에 한해 바로 커밋합니다.

push 와 PR 생성은 별도로 승인받기 전에는 하지 않습니다.

### 5. 진행 여부

위 수정 4건(코드 2 + 테스트 1 + 확인 항목 사유 정리)으로 진행해도 될까요? 범위는 이 Phase 의 변경 파일로 한정하고, 다른 파일에서 비슷한 문제가 보이면 고치지 않고 보고만 하겠습니다 (SC-1).
