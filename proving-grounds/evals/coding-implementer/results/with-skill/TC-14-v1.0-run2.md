항목 8 조직 컨벤션 판정: 가이드가 없으므로 **비적용**이다. 조직 컨벤션 원문은 다른 곳에서 찾지 않는다. 판정 근거는 프로젝트 규칙 원문(`.claude/rules/05-dto-web-layer-convention.md`, `11-git-workflow-convention.md`)만 쓴다.

Phase 1 은 작업 브랜치에 있어 생략한다. Phase 2 는 TDD 가 있어 정상 진행한다. Phase 2.1 은 TDD 를 읽고 Phase 목록을 작업 큐에 등록하며, 이번 호출 범위는 사용자 지시대로 **TDD Phase 2 (식사 피드백 저장 Service)** 하나다. Phase 3 이후는 이번 요청 범위 밖이므로 착수하지 않는다(SC-5).

## Phase 3-0. 작성 전 질문 5개 (TDD Phase 2 기준)

| 질문 | 답 |
|------|----|
| Q1 실패 격리 | 부가 소스 호출이 없다. 해당 없음 (TDD 에 외부·부가 호출 없음) |
| Q2 외부 호출 후 저장 실패 | 외부 호출 없음. 해당 없음 |
| Q3 마스터 데이터 이상값 | 마스터 데이터 조회 없음. 해당 없음 |
| Q4 기존 경로 동작 변경 | 신규 클래스만 추가한다. 기존 경로 변경 없음, PR 본문 "기존 동작 변경" 메모 없음 |
| Q5 분기별 테스트 | TDD 의 Phase 2 시나리오 항목마다 Service 테스트 1건씩, 반환 DTO 필드 전수 단언 |

답하지 못한 설계 결정은 없다. TDD 에 없는 동시성 방어나 실패 응답 형태는 "없다"고 본다는 전제를 따라 질문하지 않는다.

**프로젝트 규칙 충돌 판정** (사용자 요청 대 프로젝트 규칙):

- DTO 생성: 요청은 "`from()` 팩토리". 프로젝트 규칙 05 가 직접 규정한다. "DTO 객체 생성 시 `new` 키워드 대신 정적 팩토리 메서드(`of()`, `from()`, `to()`, `forXxx()`)", "Application DTO: Domain Entity → Application DTO 변환 (`from(DomainEntity)`)". 요청과 규칙이 일치하므로 충돌이 없고 `from()` 으로 구현한다. 비적용 프로젝트이므로 조직 컨벤션의 "신규 DTO 는 생성자 직접 호출" 판정은 쓰지 않는다.
- 네이밍: Application 계층은 `*OutDto` 를 꼭 붙이므로 `MealFeedbackOutDto` 는 규칙 05 와 일치한다. `record` 형식도 일치한다.
- 커밋 제목: 규칙 11 §2 "`[Domain] Description` (dev branch) OR `type: description` (feature branch)". 현재는 feature 브랜치이고 `feat:` 는 허용 type 이다. 요청한 `feat:` 접두어는 규칙 11 상 유효하다. (제목의 "API" 문구는 아래 3-6 에서 별도로 짚는다.)

## Phase 3-1. 구현 위임 (java-spring-coder)

```
[Phase 2 위임 입력]
- 현재 Phase: Phase 2. 식사 피드백 저장 Service
- TODO: 신규 application DTO MealFeedbackOutDto(record) — MealFeedback 도메인 객체 단순 매핑
        + 식사 피드백 저장 Service (TDD Phase 2 항목)
- PRD 관련 섹션: 없음
- TDD 관련 섹션: meal-feedback-tdd.md Phase 2 (저장 Service 5~10줄 요약)
- 기존 코드 인용: web/dto/*Response 의 from() 패턴 1건 (규칙 05 Example, Glp1InjectionRecordResponse.from(OutDto)),
                  최근 커밋 "feat: 일일 식사 추천 API 구현" 에서 만든 application 계층 Service 1건
- 이전 Phase 결정: Phase 1 에서 만든 MealFeedback 도메인 객체·Repository 시그니처 (컴팩트)
- 조직 컨벤션: 비적용 (프로젝트 규칙만). DTO 정적 팩토리는 규칙 05 근거
- 작성 전 질문 답변: Q1~Q3 해당 없음, Q4 기존 변경 없음, Q5 시나리오별 테스트 + 필드 전수 단언
```

작성할 코드 요지는 다음과 같다.

- `application/dto/MealFeedbackOutDto` (record). 필드는 `MealFeedback` 도메인의 TDD 정의 필드와 1:1이고 로직은 없다. `public static MealFeedbackOutDto from(MealFeedback domain)` 한 개만 둔다. `new` 는 `from()` 내부에서만 쓴다. Lombok 은 쓰지 않는다. FQCN 인라인 없이 import 한다.
- 저장 Service 는 TDD Phase 2 항목대로 구현한다. 저장 결과를 `MealFeedbackOutDto.from(saved)` 로 반환한다. 도메인 객체를 Web 으로 노출하지 않는다(규칙 05 의 Domain → Application → Web 단방향).
- Web DTO(`*Response`)와 Controller 는 이번 Phase 에 없다. 만들지 않는다(SC-1, SC-5).
- 기존 `*Response` 파일은 그대로 둔다.

## Phase 3-2. 테스트 위임 (java-layered-unit-testing)

위임 입력에는 위 압축 입력과 "조직 컨벤션 비적용, 프로젝트 규칙 08 테스트 컨벤션 적용"을 넣는다.

- Service 테스트: Fake Repository 우선, Mock 은 쓰지 않는다. `@DisplayName` 한국어, TDD 시나리오마다 메서드 1개.
- 반환 `MealFeedbackOutDto` 의 모든 필드가 저장된 도메인 값과 같은지 단언한다(필드 한 개만 보는 약한 단언 금지, RR-12).
- `@SpringBootTest` 는 쓰지 않는다. Service 단위 테스트다.

review-lint 는 실행하지 못한다. `.claude/shared/` 에는 가드 문서 4개만 있고 `review-lint.py` 가 없다. 파일이 없는데 "위반 0건"이라고 쓰면 SW-5 위반이다. 그래서 `review-recurrence-guard.md` 의 RR-1~RR-14 체크리스트를 변경 파일에 수동으로 대조한다. 이번 변경은 DTO 매핑과 단순 저장이라 RR-1(장애 시 동작)·RR-6(응답 단위)·RR-10(주석 최소화)·RR-12(테스트 실효성)만 해당한다. 보고에는 "review-lint 미실행(프로젝트에 스크립트 없음), 수동 대조 완료"로 쓴다.

### 3-6. 커밋 1차 안 (사용자 승인 후에만 진행)

커밋은 승인 전에는 하지 않는다. 승인 시 `/git-commit` 에 위임하고, 위임 입력에는 "조직 컨벤션 비적용, 프로젝트 규칙 11 형식"을 넣는다.

- 형식: 사용자가 준 제목 `feat: 식사 피드백 저장 API 구현` 은 규칙 11 §2 의 `type: description` (feature 브랜치) 형식에 맞다. 한국어이고 Co-authored-by 와 `--trailer` 는 쓰지 않는다. `git commit -m "..."` 만 쓴다.
- 내용: 이번 Phase 2 는 Service 와 DTO 까지이고 Controller 와 Web DTO 는 없다. 그래서 제목의 "API" 는 실제 변경보다 넓게 읽힌다. 권장안은 `feat: 식사 피드백 저장 Service 구현` 이다. 사용자 요청대로 `feat: 식사 피드백 저장 API 구현` 도 규칙 위반은 아니고, API 구현 Phase 의 커밋 제목을 미리 쓰게 되는 점만 다르다.
- 커밋 전 규칙 11 §3: 변경 모듈이 `pasta-api` 이면 `./gradlew :pasta-api:spotlessApply` 를 실행하고 변경분을 같은 커밋에 포함한다. 다른 모듈이면 AI 가 spotless 를 실행하지 않는다. 모듈은 TDD 에서 확인 후 결정한다.
- 논리 축은 하나(신규 기능)라서 커밋 분할은 하지 않는다. 리팩터·리네임 혼합 없음.
