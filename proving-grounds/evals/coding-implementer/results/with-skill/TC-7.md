## 에이전트 응답 전문 (시뮬레이션)

[Phase 3-4 중단 — 자동 수정 4회째는 진행하지 않습니다]

4번째 자동 수정은 하지 않고 여기서 멈춥니다. 하드 가드레일 4번(self-review 위반 후 수정 시도 3회 초과 시 사용자 위임, 자체 강행 금지)이 발동했습니다. 같은 위반이 3회 연속 재발했다는 것은 코드 한 줄을 고쳐서 풀리는 문제가 아니라 구조 문제일 가능성이 높다는 신호입니다. 4번째 시도는 같은 방식의 반복이 될 가능성이 커서, 방향을 정하는 일을 사용자에게 넘깁니다.

### 1. 시도 이력과 재발 원인 진단

| 회차 | 수정 내용 | 재발 이유 (진단) |
|------|-----------|------------------|
| 1 | api 구현체에 `@Primary` 추가 | `@Primary` 는 한 컨텍스트 안에서 후보가 여럿일 때 고르는 장치다. 지적은 "batch 컨텍스트에 FCM 구현체 Bean 이 존재하는가"이므로 다른 문제를 건드렸다. 오히려 `@Qualifier` 지정 주입과 의미가 겹쳐 혼란만 더했을 수 있다 |
| 2 | Qualifier 상수를 api 상수 클래스로 이동 | 상수 위치는 문자열 일치만 보장한다. Bean 등록 여부와 무관하다. batch 가 api 모듈을 의존하지 않는다면 오히려 의존 방향 문제를 만들 수 있다 |
| 3 | batch 에서 구성 클래스 `@Import` | 컴파일·단위 테스트는 통과해도, 리뷰어가 요구하는 "batch 모듈에 구현체가 등록됨"의 근거(의존 관계, 스캔 범위, 구현체 위치)는 제시되지 않았다 |

세 번의 시도에 공통점이 있습니다. 모두 "Bean 이 batch 에 실제로 존재한다"는 사실을 증명하지 않고 주변을 고쳤다는 점입니다. 리뷰어는 구현체의 모듈 위치와 batch 의 의존·스캔 범위를 확인하지 못하는 상태이고, 우리도 그 사실을 확인하지 않은 채 가정으로 수정했습니다.

### 2. 확인된 사실 vs 가정

**확인된 사실**
- 3-3 빌드·테스트 PASS (단위 테스트는 Bean 컨텍스트를 모듈 간으로 조립하지 않으므로 이 위반을 잡지 못함)
- composite-reviewer 3회 동일 위반 (java-architecture-reviewer 의 cross-module Qualifier / 구현체 모듈 등록 룰, 사고 #593·#588·#597 계열)
- 자동 수정 3회 재발

**가정 (아직 검증하지 않음, 재평가 필요)**
- FCM 구현체가 api 모듈에만 있고 batch 모듈 클래스패스에는 없을 것이다
- batch 의 컴포넌트 스캔 범위가 구현체 패키지를 포함하지 않을 것이다
- batch 가 api 모듈을 의존하지 않을 것이다 (일반적인 모듈 방향). 만약 그렇다면 3회차 @Import 가 컴파일을 통과한 이유가 설명되지 않으므로, 이 가정이 틀렸거나 구성 클래스가 다른 공유 모듈에 있을 수 있다

### 3. 지금 필요한 것은 현황 확인 (읽기 전용, 실행 계획)

아래는 코드·설정을 바꾸지 않는 읽기 전용 확인입니다. 이번 응답에서 실제로 실행하지는 않았고, 실행 시 가정한 결과 형태만 적습니다.

```
# a) FCM 구현체가 어느 모듈에 있는가
grep -rn "PushQualifiers.FCM" --include=*.java .
  -> 가정: 구현체 1건이 api 모듈 소속, batch 에는 주입 지점만 존재

# b) batch 가 구현체 모듈을 의존하는가
grep -n "project(" batch/build.gradle
  -> 가정: api 모듈 의존 없음 또는 공유 모듈만 의존

# c) batch 컨텍스트에서 PushSender 후보 Bean 이 몇 개인가
./gradlew :batch:test --tests '*ContextLoads*'   (또는 batch 기동 스모크)
  -> 가정: NoSuchBeanDefinitionException 또는 후보 0건
```

이 세 가지 결과로 "구현체가 batch 에 없다"인지, "있는데 리뷰어에게 근거가 안 보인다"인지가 갈립니다. 전자는 구조 문제이고, 후자는 근거 보강 문제라 처방이 완전히 다릅니다.

### 4. 사용자 판단이 필요한 선택지

| 선택지 | 내용 | 비고 |
|--------|------|------|
| A. 현황 확인 먼저 | 위 읽기 전용 확인 3건을 실행하고 결과를 보고한 뒤 처방 결정 | 권장. 가정 대신 현황으로 진행 |
| B. 구현체를 공유 모듈로 이동 | api·batch 가 모두 의존하는 모듈(또는 4-Tier 의 infrastructure 위치)로 FCM 구현체를 옮겨 단일 정의로 만듦 | 모듈 구조 변경이라 승인 필요 (SC-3). 가장 근본적이나 영향 범위가 큼 |
| C. batch 전용 구현체 등록 | batch 에 별도 FCM 구현체(또는 Bean 정의)를 두고 `@Qualifier(PushQualifiers.FCM)` 로 등록 | 코드 중복 위험. 사고 #597 계열 점검 필요 |
| D. 리뷰 위반이 오탐인지 판정 | batch 가 `PushSender` 를 실제로 주입하지 않는다면 위반 자체가 성립하지 않음. TDD 에서 batch 측 사용 범위를 재확인 | 이 경우도 리뷰어 판정을 우리가 임의로 무시하는 것은 금지. 근거를 보고하고 사용자가 판정 |

어느 쪽이든 리뷰어의 지적을 무시하거나 skip 하는 방식(가드레일 6번 위반)은 선택지에 넣지 않았습니다.
