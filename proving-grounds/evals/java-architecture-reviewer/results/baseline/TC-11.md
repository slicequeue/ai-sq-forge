# 아키텍처 리뷰: api/feat/coupon-issue (기준 dev)

조직 컨벤션 적용 프로젝트다(`vc-conventions-guide.md` 존재). 근거는 가이드 3절 우선순위와 4-1 요약이다. 원문 폴더는 확인했다.

요청 두 가지에 대한 결론부터 적는다.

1. **"기존 관례대로 통과"는 신규 코드에는 적용하지 않는다.** 가이드 3절 우선순위는 조직 컨벤션이 "같은 파일·패키지의 기존 관례"보다 위다. 신규 파일과 이번에 추가한 줄은 컨벤션으로 본다. 기존 관례로 통과시킬 수 있는 곳은 기존 파일의 기존 줄과, 가이드 3절 표가 명시한 경우(이미 `from()` 이 있는 DTO 에 필드만 추가)뿐이다.
2. **Service 의 `UserProfileOutDto.from(...)`, `catch (CouponPolicyException e)` 는 지적은 하되 이번 PR 의 수정 요구로는 올리지 않는다.** 이번 diff 가 추가·수정한 줄이 아니고, 가이드 3절·6절이 "기존 코드를 일괄로 바꾸지 않는다, 고칠 가치가 있으면 범위 밖 제안으로 적는다"고 정한다(SC-1). 요청하신 대로 위반 사실은 아래 "범위 밖 제안"에 명시한다.

| 구분 | 내용 |
|------|------|
| 확인된 것 | diff 본문, `review-lint` 출력(위반 1, 확인 16), 가이드 3·4·6절 |
| 가정한 것 | `CouponIssueService` 의 `issue()` 는 diff 에 보이는 부분 외에 트랜잭션 경계 등이 있을 것이다(미확인). 기존 coupon 패키지에 Controller 가 이미 있는지 모른다 |

## 반드시 수정 (신규·변경 코드)

### 1. `CouponJpaEntity` 에 `@Setter` 추가 (lint 위반)
- 조직 컨벤션(lombok·entity)은 `@Setter` 전면 금지다. JPA Entity 의 상태는 `change{Field}()` 로 바꾼다.
- `expiredAt` 필드를 추가하면서 Setter 를 붙인 것으로 보인다. `@Setter` 를 제거한다. 값이 생성 시점에 정해지면 직접 선언한 생성자(`@Builder`)에 넣고, 이후 바뀌어야 하면 `changeExpiredAt(...)` 을 둔다.
- Setter 는 클래스 전체의 모든 필드에 공개 변경 경로를 만든다. 기존 필드까지 영향이 퍼지므로 "기존 관례"로 넘길 수 없다.

### 2. `CouponIssueController` 가 `presentation` 패키지에 있다
- 신규 파일이므로 `coupon.web` 에 둔다. 가이드 4-1 은 `presentation` 대신 `web` 을 쓰고, 프로젝트의 기존 패키지도 `web` 이다. 이 파일만 `presentation` 이면 의존 방향 표기(`web → application → domain ← infrastructure`)도 어긋난다.
- 이 프로젝트에서 `presentation` 이 이미 있는 다른 패키지는 이번 범위 밖이다.

### 3. `CouponIssueOutDto` 에 신규 정적 팩토리 `from()`
- 단순 필드 매핑이다. 가이드 3절 표는 "신규 클래스는 조직 컨벤션"이라 생성자 직접 호출을 쓴다. 복잡한 변환일 때만 `from` 이 허용되는데 여기는 해당하지 않는다.
- 호출부 두 곳도 같이 바꾼다. `CouponIssueService` 의 `CouponIssueOutDto.from(coupon)` 은 이번에 추가한 줄이다.
  ```java
  return new CouponIssueOutDto(coupon.getId(), coupon.getCode(), coupon.getExpiredAt());
  ```
- 프로젝트 규칙 02·03·05 가 `of`/`from` 을 요구하지만, 표의 판정은 조직 컨벤션이다. PR 본문에 "조직 컨벤션 우선 적용"을 적어 둔다.

### 4. Controller 변수명 `req`, `dto`
- 가이드 4-1 은 줄임말·일반명사를 금지하고 타입명 전체를 쓴다. 신규 파일이므로 수정한다.
  - `req` → `couponIssueRequest`
  - `dto` → `couponIssueOutDto`
- 확인 항목이지만 판정이 모호하지 않다. 두 이름 모두 목록에 명시된 금지어다.

### 5. Controller 이름
- 가이드 3절 표의 "신규 Controller 부터" 규칙대로 변경 요청이면 `CouponCommandController` 가 정본 이름이다. 발급은 변경이므로 `CouponCommandController` 로 하고, 기존 coupon Controller 가 있으면 새로 만들지 말고 거기에 둘지 먼저 정한다(가정: 존재 여부 미확인).

## 통과 (기존 관례 적용 가능)

- `CouponSummaryOutDto`: 이미 `from()` 이 있는 기존 record 에 필드만 추가했고 기존 메서드를 고쳐 썼다. 가이드 3절 표가 허용하는 경우라 새 팩토리 없이 통과한다.
- 계층 경계: Controller 가 `Request → InDto`, `OutDto → Response` 로 변환하고 web DTO 를 application 으로 넘기지 않는다. 가이드 4-1 에 맞다.
- `CouponJpaEntity` 가 infrastructure 에 있고 `{Domain}JpaEntity` 이름을 따른다. `@NoArgsConstructor(access = PROTECTED)` 도 유지된다.

## 확인 요청 / 주의 (차단은 아님)

- `CouponSummaryOutDto` 에 `expiredAt` 이 생성자 중간에 들어갔다. 타입이 달라 위치 인자 호출부는 컴파일 에러로 드러나지만, 이 DTO 를 응답까지 노출하는 경로가 있으면 기존 클라이언트에 필드가 추가된다. 하위 호환 영향을 PR 본문에 적는다.
- Controller `@RequestBody` 에 `@Valid` 가 없다. 입력 검증을 Request 객체에서 하고 있다면 해당 규칙을 따르되, diff 만으로는 확인되지 않는다.
- `CouponIssueService.issue()` 의 트랜잭션 경계와 `couponRepository.save` 이후 흐름은 diff 에 없어 판단하지 않았다.

## 범위 밖 제안 (요청하신 두 건, 이번 PR 에서 고치지 않음)

둘 다 기존 줄이며 이번 diff 가 건드리지 않았다. 위반 사실은 인정하고, 고치는 시점은 팀이 정한다.

1. `UserProfileOutDto.from(userReader.read(...))` (CouponIssueService)
   - 조직 컨벤션(생성자 직접 호출 우선) 기준으로 위반 소지가 있다. 다만 `from` 이 복잡한 변환에 해당하는지 판단해야 하고 lint 도 `[확인]` 으로만 분류하는 항목이다.
   - 더 큰 문제는 구조다. `couponPolicy.validate(userProfileOutDto)` 가 application 계층 OutDto 를 받는다. `couponPolicy` 가 domain 에 있다면 domain 이 application 을 참조하게 되어 `web → application → domain ← infrastructure` 방향에 어긋난다. 정책이 도메인 객체(예: `User`)를 직접 받는 쪽이 맞다. 이쪽이 팩토리 이름 문제보다 우선순위가 높다. 정책의 패키지 위치를 확인해야 한다(미확인).
2. `catch (CouponPolicyException e)`
   - 변수명 `e` 는 금지어(`e`·`dto`·`req` 등)다.
   - 예외를 잡아 `CouponIssueException` 으로 바꿔 던질 때 `new CouponIssueException(e)` 로 원인을 보존하는 점은 좋다. 변수명만 `couponPolicyException` 으로 바꾸면 된다.

둘을 한 PR 에 섞으면 리뷰 범위가 커지고 되돌리기 어렵다. 별도 이슈로 분리하는 것을 권한다(SC-1).
