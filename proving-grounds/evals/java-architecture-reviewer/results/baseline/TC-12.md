# 아키텍처 관점 리뷰: `api/feat/meal-feedback` (기준 `dev`)

## 0. 리뷰 기준과 범위

- 적용한 기준은 이 프로젝트(poc-meal-recommender)의 규칙 01(아키텍처), 05(DTO·Web), 19(경계)입니다.
- 이 저장소에는 `vc-conventions-guide.md`가 없어 조직 컨벤션은 적용하지 않았습니다.
- lint 출력은 `지적 0건 (조직 컨벤션 검사 꺼짐)`입니다. 이 결과는 검사가 꺼져 있다는 뜻이고, 코드가 깨끗하다는 근거가 되지 않습니다. 아래 1번 위반도 lint가 잡지 못했습니다. 이번 리뷰는 diff와 프로젝트 규칙 대조만으로 판단했습니다.
- diff에 `MealFeedbackRequest`, `MealFeedbackResponse`, `MealFeedback`, `MealFeedbackRepository` 본문은 없습니다. 이 파일들의 내부는 확인하지 못했습니다.

## 1. 확인된 위반 (수정 필요)

### [Critical] Application 이 Web 을 참조함 — `MealFeedbackService.java`

```java
import com.kakaohealthcare.pasta.mealrecommender.web.dto.MealFeedbackRequest;
...
public MealFeedbackOutDto save(MealFeedbackRequest req) {
```

- 규칙 01은 의존성 방향을 `Web → Application → Domain ← Infrastructure`로 정하고, "Application: Domain만 참조"라고 합니다. 규칙 19도 같은 원칙을 강제합니다. 이 코드는 import 한 줄과 메서드 시그니처 양쪽에서 Application 이 Web 을 알게 만듭니다.
- 규칙 05는 Application 계층 DTO 를 `*InDto` / `*OutDto`로 쓰라고 합니다. 입력은 `MealFeedbackInDto`가 되어야 하는데 diff 에는 없습니다. 출력(`MealFeedbackOutDto`)만 규칙을 지키고 입력은 지키지 않아, 계층 경계가 비대칭입니다.
- 수정 방향은 다음과 같습니다.
  1. `application/dto/MealFeedbackInDto` record 를 새로 둡니다. 필드는 `menuId`, `rating` 입니다.
  2. `MealFeedbackRequest`에 `toApplicationDto()`를 둡니다. 규칙 05 예시의 `request.toApplicationDto()` 패턴과 같습니다.
  3. Service 시그니처는 `save(MealFeedbackInDto in)`로 바꾸고 `web.*` import 를 제거합니다.
  4. Controller 는 `mealFeedbackService.save(req.toApplicationDto())`로 호출합니다.
- 이렇게 하면 `Request`의 검증 어노테이션이나 필드 변경이 Service 시그니처로 번지지 않습니다.

## 2. 규칙을 지킨 부분 (지적 아님)

- `MealFeedbackOutDto.from(MealFeedback)`는 도메인 객체를 Application DTO 로 변환하는 방향이 맞습니다. 규칙 05의 "Domain Entity → Application DTO (`from(DomainEntity)`)"에 부합합니다.
- 팩토리 메서드 `from()` 안의 `new MealFeedbackOutDto(...)`는 규칙 05가 말하는 "`new` 대신 정적 팩토리" 위반이 아닙니다. 그 규칙은 호출하는 쪽에서 `new`로 DTO 를 만들지 말라는 뜻이고, 팩토리 내부 생성자 호출은 정상입니다.
- `Controller`는 Application Service 만 주입받습니다. Domain 과 Infrastructure 를 직접 참조하지 않아 규칙 05의 "Controller 의존성" 항목을 지킵니다.
- `Controller`의 `MealFeedbackResponse.from(dto)`는 규칙 05의 "Application DTO → Web DTO 변환" 방향과 맞습니다.
- `Service`는 `MealFeedbackRepository`(Domain 인터페이스)에만 의존합니다. `@Transactional` 도 Application 계층에 있어 규칙 01의 "트랜잭션 관리" 책임 배치와 맞습니다.
- `MealFeedback`은 Domain Entity 네이밍 규칙("도메인명 그대로")에 부합하고, `OutDto` / `Controller` / `Service` 네이밍도 맞습니다.

## 3. 경미한 사항 (권고, 이번 PR 범위의 아키텍처 위반은 아님)

- `save(@RequestBody MealFeedbackRequest req)`에 `@Valid`가 없습니다. 규칙 05의 "Validation: 생성자 내부나 `@Valid`를 통해 검증"에 비추어, `Request` 내부에서 검증하지 않는다면 `@Valid`가 필요합니다. `Request` 본문이 diff 에 없어서 확인된 위반은 아니고, 추가 확인이 필요한 항목입니다.
- Controller 에 Swagger(`@Tag`, `@Operation`) 가 없습니다. 규칙 05는 API 명세를 코드에 포함하라고 합니다.
- Controller 에 클래스 레벨 `@RequestMapping`이 없습니다. 규칙상 필수는 아닙니다. 같은 도메인에 엔드포인트가 늘어날 때 정리하면 됩니다.

## 4. 확인하지 못한 것 (가정 분리)

| 항목 | 상태 | 재확인 시점 |
|---|---|---|
| `MealFeedbackRepository`가 `domain/` 패키지의 인터페이스인지, 구현체가 `infrastructure/`에 `*RepositoryImpl`로 있는지 | 미확인 (diff 에 없음) | 해당 파일이 PR 에 포함되거나 리뷰어가 요청할 때 |
| `MealFeedback.create()`, `getMenuId()`, `getRating()`의 존재와 도메인 검증 위치 | 미확인 | Domain 파일 확인 시 |
| `MealFeedbackRequest` / `MealFeedbackResponse`가 `record`인지 (규칙 05) | 미확인 | 같은 시점 |

## 5. 결론

- 머지 전에 1번(Application → Web 의존)은 반드시 고쳐야 합니다.
- 나머지 구조(DTO 변환 방향, 팩토리 사용, Controller 의존)는 프로젝트 규칙에 맞습니다.
- 리뷰 후 1번만 수정해도 다른 구조 변경은 필요 없습니다. `MealFeedbackInDto`와 `toApplicationDto()` 추가, Service 시그니처 교체 정도입니다.
