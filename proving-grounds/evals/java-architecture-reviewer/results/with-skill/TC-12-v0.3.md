## 사용자 응답

아키텍처 관점 리뷰 결과, 막아야 할 문제는 1건(두 지점)입니다.

**계층 의존성 역행 (필수 수정, HG-2)**
`MealFeedbackService` 가 `web.dto.MealFeedbackRequest` 를 import 해서 `save(MealFeedbackRequest req)` 로 받습니다. 프로젝트 규칙 01 은 Application 이 Domain 만 참조하고 Web 이 Application 을 향하도록 정해 둡니다. Application 이 Web 을 아는 지금 구조는 그 반대 방향입니다. Controller 는 Request 를 변환 없이 서비스에 넘기고 있습니다.

수정 방향은 `MealFeedbackInDto` 를 application 계층에 추가하는 것입니다. 서비스는 InDto 만 받고, Controller 가 `Request → InDto` 로 변환합니다(규칙 05 예시의 `request.toApplicationDto()` 형태). 서비스의 Web import 는 지웁니다.

**권장 (Low)**
Controller 에 `@Tag`/`@Operation` 이 없습니다(규칙 05). `@Valid` 도 보이지 않지만 Request record 생성자에서 검증한다면 무시해도 됩니다. 이번 diff 에는 Request 정의가 없어 확인하지 못했습니다.

**통과한 부분**
- `MealFeedbackOutDto.from()`, `MealFeedbackResponse.from()` 정적 팩토리 사용은 이 프로젝트 규칙 05 대로라 문제없습니다.
- DTO 명명과 record 사용, Service 의 JPA Entity 비노출, 타 도메인 Repository import 없음, FQCN 인라인 없음도 이상 없습니다.

**조직 컨벤션: 비적용**
이 저장소에는 `vc-conventions-guide.md` 가 없어서 조직 컨벤션 검사를 하지 않았습니다. `review-lint` 출력도 `지적 0건 (조직 컨벤션 검사 꺼짐)` 이었습니다. 변수명 `req`/`dto` 같은 항목은 이 프로젝트 규칙에 금지 조항이 없어 지적하지 않았습니다.
