# 홈 카드 PR 비즈니스 로직 리뷰 (요건 대비)

요청하신 "요건 3은 매핑됨으로 봐달라"는 그대로 받아들이기 어렵습니다. try 로 감싼 것만으로는 요건 3이 충족되지 않고, 오히려 요건 1, 2를 깨뜨립니다. 아래에 근거를 적습니다.

## 요건 매핑 결과

| 요건 | 판정 | 근거 |
|------|------|------|
| 1. 마지막 혈당 기록 + 기록 시각 노출 | 위반 (일정 조회 실패 시) | HomeCardService.java:36 |
| 2. 기록 없는 사용자에게만 안내 (hasRecord=false) | 위반 | HomeCardService.java:36 |

## 문제 1. 일정 조회 실패가 기록 있는 사용자를 "기록 없음"으로 바꾼다 (요건 1, 2 위반)

- `:32` 혈당 조회와 `:33` 일정 조회가 하나의 try 안에 있고, catch 에서 `HomeCardResponse.empty()`(hasRecord=false, lastRecord=null, nextSchedule=null)를 반환합니다.
- 혈당 기록이 있는 사용자가 캘린더 타임아웃(CalendarTimeoutException)을 만나면 이미 조회한 `last` 가 버려지고, hasRecord=false 인 응답을 받습니다.
- 결과적으로 요건 1(마지막 기록 노출)이 깨지고, 요건 2("기록이 한 번도 없는 사용자에게만" 안내)도 깨집니다. 기록이 있는 사용자에게 "첫 기록을 남겨보세요"가 노출됩니다.
- 요건 3이 요구하는 "정상 응답"은 일정만 비어 있고 기록은 그대로 내려가는 응답(hasRecord=true, lastRecord=값, nextSchedule=null)입니다. empty() 는 그 응답이 아닙니다.
- 외부 캘린더 연동이 있어 타임아웃이 가장 흔한 실패이므로, 이 경로는 예외 상황이 아니라 상시 발생할 수 있는 경로입니다.

## 문제 2. 트랜잭션 전파 때문에 try/catch 가 의도대로 동작하지 않을 가능성이 높다 (요건 3 자체가 미충족)

- 바깥 `getHomeCard` 는 `@Transactional(readOnly = true)`, 안쪽 `findNext` 는 `@Transactional`(기본 REQUIRED)입니다. 안쪽은 바깥 트랜잭션에 참여합니다.
- CalendarTimeoutException 은 RuntimeException 이므로 findNext 프록시를 빠져나가는 순간 공유 트랜잭션이 rollback-only 로 표시됩니다.
- 바깥에서 예외를 catch 해 정상 return 하더라도, 바깥 메서드가 끝나며 커밋할 때 UnexpectedRollbackException 이 발생합니다. 즉 사용자는 정상 응답 대신 500 을 받을 수 있습니다.
- 확인된 것: 두 어노테이션과 예외 계층(RuntimeException)은 제공된 코드와 TDD 에 있습니다. 가정한 것: 기본 전파 설정과 Spring 프록시 기반 트랜잭션 사용입니다. 재평가 트리거는 findNext 의 propagation 설정이나 AOP 모드가 다른 경우입니다. 반드시 통합 테스트로 확인해야 합니다.

## 문제 3. catch (Exception) 이 범위가 너무 넓다

- 혈당 조회의 DB 오류, NPE, 매핑 오류까지 모두 삼켜서 "기록 없음"으로 응답합니다. 장애가 정상 응답처럼 보여 감지가 어렵습니다.
- 로그도 남기지 않습니다. 요건 3 이 허용하는 것은 "일정 조회 실패"이고, 혈당 조회 실패는 허용 범위 밖입니다.

## 문제 4. 외부 호출이 DB 트랜잭션 안에 있다

- 외부 캘린더 호출(타임아웃 가능)이 트랜잭션 범위 안에서 실행되어, 대기 시간 동안 DB 커넥션을 점유합니다. 홈 카드는 호출 빈도가 높은 API 라 커넥션 풀 고갈 위험이 있습니다.

## 권장 수정 방향

1. try 범위를 `findNext` 호출 하나로 좁히고, 예외는 `CalendarTimeoutException`(필요하면 캘린더 연동 예외 계층)만 잡습니다. 로그를 남기고 `next = null` 로 두어 기록은 그대로 응답합니다.
2. 혈당 조회는 try 밖에 둡니다. 기록이 없으면 `last=null` 이므로 hasRecord=false 가 자연스럽게 나옵니다. 요건 2 가 그대로 지켜집니다.
3. 트랜잭션 전파 문제를 해소합니다.
   - 안: 파사드(`getHomeCard`)에서 `@Transactional` 을 제거하고 혈당 조회만 읽기 트랜잭션으로 수행합니다.
   - 안: 일정 조회를 별도 트랜잭션(REQUIRES_NEW 또는 NOT_SUPPORTED)으로 분리합니다.
   - findNext 는 이번 PR 에서 변경하지 않은 기존 코드이므로, 수정이 필요하면 범위 합의가 필요합니다.
4. 테스트를 추가합니다.
   - 기록 있음 + 일정 조회 타임아웃: hasRecord=true, lastRecord 값, nextSchedule=null, 예외 없이 응답.
   - 기록 없음 + 일정 정상: hasRecord=false, nextSchedule 값.
   - 혈당 조회 실패: 일정 실패와 구분되는 동작을 명시.
   - 트랜잭션 포함 통합 테스트로 UnexpectedRollbackException 이 발생하지 않는지 검증.

## 결론

현재 변경은 "예외를 던지지 않게" 하는 데 그쳤고, 요건 1, 2 를 위반하며 요건 3 의 "정상 응답"도 보장하지 못합니다(문제 2 가 사실이면 500). 요건 3 은 "매핑됨"이 아니라 "수정 필요"로 기록하겠습니다. 위 수정 후 재검토를 권합니다.
