# 비즈니스 로직 리뷰: 혈당 기록 등록 시각 검증 PR

수용 기준 1~4 와 변경 코드를 대조했습니다. 결론부터 말하면 수용 기준 1 (수정 시 타인·없는 기록은 404)이 이번 PR 로 깨집니다. 머지 전에 수정이 필요합니다.

## 2. 지적 사항

### 2.1 [Blocker] update 에서 검증이 소유권 조회보다 먼저 실행됨 (GlucoseRecordService.java:41 대 :43)

`update` 는 `recordTimeValidator.validate(...)` 를 호출한 뒤에 `findByIdAndUserId` 로 기록을 조회합니다. 그래서 다음 경우에 404 대신 400 이 나갈 수 있습니다.

- 타인의 기록 id 로 PUT 하면서 시각이 미래이거나 최근 기록과 5분 이내인 경우
- 존재하지 않는 id 로 PUT 하면서 같은 조건인 경우

수용 기준 1 은 "타인 기록·없는 기록 id 는 404" 라고 명시합니다. 검증 실패 응답이 소유권 확인보다 앞서면 응답 코드가 달라집니다. 또 요청자가 자기 기록과의 시간 관계에 따라 다른 응답을 받게 되어 400 과 404 의 차이로 상태를 짐작할 여지도 생깁니다. 이 PR 에서 새로 생긴 회귀입니다.

### 2.2 [Blocker] update 에 "직전 기록과 5분 이내" 검사를 그대로 적용하면 정상 수정이 막힘 (:41, RecordTimeValidator.java:17-19)

수용 기준 2·3 은 둘 다 "등록(POST)" 시점 규칙이고 "이번 PR 신규"로 표시되어 있습니다. PUT 에 적용하라는 요건은 PRD 에 없습니다 (PR 본문도 "등록 시 시각 검증 추가"라고만 설명합니다). 그런데 `update` 에도 같은 validator 를 호출합니다. 이때 문제가 생깁니다.

- validator 는 `findTopByUserIdOrderByRecordedAtDesc(userId)` 로 사용자의 가장 최근 기록을 가져와 비교합니다. 이 기록에 수정 대상 자신이 포함됩니다.
- 사용자가 가장 최근 기록의 혈당 값만 고치고 시각은 그대로 두면 `prev.recordedAt == cmd.recordedAt` 이어서 차이가 0분입니다. 따라서 `TOO_CLOSE` 400 이 발생합니다.
- 즉 마지막 기록은 값을 수정할 수 없게 됩니다. 수용 기준 1 의 "본인 혈당 기록을 수정할 수 있다"도 함께 깨집니다.
- 수정하려는 시각이 다른 기록과 5분 이내인 경우에도 자기 자신 외의 사유로 막힙니다. 수정이 허용되어야 하는지는 PRD 에 없으므로 기획 확인이 필요합니다.

권장 조치는 둘 중 하나입니다.

1. PRD 에 없는 동작이므로 `update` 의 validator 호출(:41)을 제거합니다. 가장 안전합니다.
2. PUT 에도 시각 검증이 필요하다면 PRD 에 먼저 반영합니다. 이때는 소유권 조회를 먼저 하고, 중복 검사에서 수정 대상 자신(`recordId`)을 제외해야 합니다. 미래 시각 검사와 중복 검사를 분리하는 편이 낫습니다.

### 2.3 [Major] "5분 이내" 경계값 해석이 불분명하고 `toMinutes()` 절삭 때문에 정확히 5분은 통과함 (RecordTimeValidator.java:17-19)

`Duration.between(...).abs().toMinutes() < 5` 는 분 단위로 절삭한 뒤 비교합니다. 4분 59초는 4 로 절삭되어 거절되고, 정확히 5분 00초부터 5분 59초까지는 5 이상이라 모두 통과합니다. "5분 이내"는 통상 5분 00초 정확히도 포함하는 표현입니다. 5분 00초가 중복인지는 확정이 필요합니다. 확정된 기준에 맞춰 `Duration` 을 `Duration.ofMinutes(5)` 와 직접 비교(`<=` 또는 `<`)하는 쪽이 의도가 드러납니다. 경계(4:59, 5:00, 5:01) 테스트도 필요합니다.

### 2.4 [Major] "직전 기록"의 기준이 가장 최근 기록 1건뿐임 (RecordTimeValidator.java:17)

`findTop...OrderByRecordedAtDesc` 는 사용자의 가장 최근 기록 1건만 가져옵니다. 과거 시각으로 소급 등록하는 경우 비교 대상이 달라집니다.

- 가장 최근 기록이 10:00 이고 사용자가 09:00 에 소급 등록하면 10:00 과 비교하여 통과합니다. 그런데 이미 09:02 기록이 있었다면 그것과는 5분 이내인데도 검사되지 않습니다.
- 반대로 `abs()` 를 써서 미래 방향 차이도 중복으로 잡으므로, "직전" 이라는 요건 표현보다 넓게 동작합니다.

소급 등록을 허용하는 제품이라면 입력 시각 기준으로 앞뒤 5분 구간에 기록이 있는지를 조회하는 쪽(예: `existsByUserIdAndRecordedAtBetween`)이 요건에 맞고 정확합니다. 소급 등록이 없다면 이 지적은 낮춰도 됩니다. 이 부분은 기획 확인이 필요합니다.

### 2.5 [Minor] 동시성: 확인 후 저장 사이에 경합이 있음 (GlucoseRecordService.java:31-32)

`validate` 로 중복을 확인한 뒤 `save` 하는 구조라 같은 사용자의 동시 요청 두 건이 모두 통과할 수 있습니다 (더블 탭, 재시도). DB 유니크 제약으로 막기 어려운 규칙이라 완전한 방지는 어렵습니다. 사용자별 락이나 멱등키 도입 여부는 요건 수준에서 합의가 필요합니다. 이번 PR 에서 고칠 필요는 없고 기록만 남겨 둡니다.

## 3. 이번 PR 이 기존 동작에 미치는 영향 (delete, AC 4)

`delete` 는 변경 없음이라 이번 PR 범위 밖입니다. 다만 상호작용을 짚어 둡니다.

- `:53` 은 `recordedAt` 이 같은지로 "마지막 기록"을 판정합니다. 이번 PR 로 POST 가 5분 이내 중복을 막으므로 신규 데이터에서는 동일 시각 충돌이 줄어듭니다. 하지만 기존 데이터에는 동일 시각 기록이 있을 수 있으므로 그 경우 어느 쪽이든 삭제가 허용되는 문제는 그대로입니다. 보고만 하고 수정은 하지 않습니다.
- `:52` 의 `orElseThrow()` 는 인자가 없어서 `NoSuchElementException` 이 됩니다. 바로 앞에서 `record` 가 조회되었기 때문에 발생하지 않는 분기이지만, 예외 계층 컨벤션에서는 맞지 않을 수 있습니다. 이번 PR 의 대상은 아닙니다.
- 2.2 에서 `update` 를 허용하는 쪽으로 수정하면, 수정으로 시각이 바뀌어 "마지막 기록"의 정의가 달라질 수 있습니다. 기존 동작 그대로입니다.

## 4. 테스트 및 PR 설명

- PR 본문은 `GlucoseRecordServiceTest#create_*` 4건만 언급합니다. `update` 경로는 코드가 변경되었는데 테스트가 없는 것으로 보입니다. 2.1 과 2.2 의 회귀는 이 때문에 잡히지 않았을 가능성이 높습니다. 아래 테스트를 추가하기를 권합니다.
  - 타인 기록 id + 미래 시각으로 PUT 시 404
  - 없는 기록 id + 최근 기록과 5분 이내 시각으로 PUT 시 404
  - 가장 최근 기록의 값만 수정(시각 동일) 시 성공
  - 5분 경계값(4:59, 5:00, 5:01), 현재 시각 정확히 같은 경우(허용), 미래 1초 경우(거절)
- PR 본문에 `update` 에 검증을 넣은 사실이 적혀 있지 않습니다. 요건에 없는 변경이 설명 없이 섞여 있으므로 의도한 것인지 확인이 필요합니다.
- 검증기를 `RecordTimeValidator` 로 공용화한 점은 좋습니다. 다만 이름이 "공용"인 만큼 다른 도메인이 재사용할 때 "사용자 최근 기록과의 간격"이라는 혈당 특화 규칙이 섞여 있다는 점은 주의가 필요합니다. 현재는 `GlucoseRecord` 리포지토리를 직접 참조하므로 공용이라기보다 혈당 전용입니다.

## 5. 확인된 것과 가정한 것

확인된 것 (제공된 코드와 PRD 에서 직접 확인)
- `update` 에서 validator 호출(:41)이 소유권 조회(:43)보다 앞에 있음
- PRD 의 수용 기준 2·3 은 POST 에만 해당하며, PUT 에는 검증 요건이 없음
- validator 가 사용자의 최근 기록 1건을 조회하며, 수정 대상 기록도 그 후보에 포함될 수 있음
- `toMinutes()` 절삭으로 정확히 5분 이상은 통과함

가정한 것 (확인 필요)
- "5분 이내"에 정확히 5분 00초가 포함되는지 (제 해석은 포함)
- 과거 시각 소급 등록이 허용되는지 (2.4 의 심각도가 달라짐)
- PUT 에도 미래 시각 검증을 적용하려는 의도가 있었는지
- `findTopByUserIdOrderByRecordedAtDesc` 가 동일 시각에서 정렬이 안정적인지 (코드가 제공되지 않음)
