# 비즈니스 로직 요건 대비 검토: MedicationScheduleService.saveSchedules

## 요청 중 반영 여부

- 단위 용량 0 검증: 요청대로 검토 범위에서 제외했다. 운영팀이 마스터를 관리한다는 전제는 확인된 사실이 아니라 가정이므로, 아래에 "제외한 항목"으로만 남긴다.
- 요건 2 "매핑됨" 처리: 요청하신 대로 처리하기 어렵다. 코드가 요건 2와 반대로 동작하기 때문이다. 근거는 아래 1번 항목에 있다. 요건 2는 "미충족"으로 판정한다.

## 요건 매핑 결과

| 요건 | 판정 | 근거 |
|------|------|------|
| 1. 일정별 알림 예약 후 예약 ID 저장 | 부분 충족 | 일정별 `reserve` 호출과 `assignReservation` 은 있다. 다만 `status`(RESERVED) 설정이 코드에 보이지 않는다. |
| 2. 일부 실패해도 성공분 유지, 실패분만 RETRY_PENDING 표시 | 미충족 | 실패 시 전체 롤백되고 RETRY_PENDING 으로 표시하는 경로가 없다. |
| 3. 단위 용량 기준 환산한 정수로 저장 | 부분 충족 | 정수 나눗셈으로 환산은 하나, 나누어떨어지지 않는 값은 조용히 버려진다. |

## 지적 사항

### 1. [차단] 요건 2 미충족: 전체 롤백은 요건과 정반대 동작

`@Transactional(rollbackFor = Exception.class)` 안에서 루프 도중 `PushReserveException` 이 발생하면 앞서 저장한 성공 일정까지 모두 롤백된다. 요건 2는 "성공한 일정은 유지", "실패한 일정만 RETRY_PENDING" 이다. "롤백되니 깔끔하다"는 일관성 관점에서는 맞는 말이지만 PRD 가 요구한 동작이 아니다. 이 방식을 택하려면 PRD 를 먼저 바꿔야 하고, 코드만 바꿔서 "매핑됨"으로 처리할 수는 없다.

또한 TDD 에 `RETRY_PENDING` 상태가 정의되어 있는데, 이 상태를 쓰는 코드가 이 변경에는 없다. 재시도 대상 표시 자체가 구현되지 않았다.

권장 방향은 다음과 같다. 최종 구조는 PRD 담당자와 합의가 필요하다.
- 일정별로 처리를 분리하고 개별 예외를 잡아 해당 일정만 `RETRY_PENDING` 으로 저장한다.
- 성공한 일정은 `RESERVED` 로 저장한다.
- 일정 단위로 트랜잭션을 나눈다(별도 빈 또는 `REQUIRES_NEW`).

### 2. [높음] 외부 호출이 트랜잭션 안에 있고, 롤백으로 외부 예약을 되돌릴 수 없음

`pushClient.reserve` 는 외부 시스템 호출이라 DB 롤백 대상이 아니다. 3번째 일정에서 실패하면 1, 2번째 일정의 DB 행은 롤백되지만 외부 푸시 서비스에는 예약이 남는다. 즉 "전체 롤백이라 깔끔하다"는 전제 자체가 성립하지 않는다.
- 결과: DB 에는 없는데 외부에는 예약이 살아 있어, 사용자에게 존재하지 않는 일정의 알림이 발송될 수 있다. 재시도하면 중복 예약도 생긴다.
- 외부 호출이 느리면 그동안 DB 커넥션과 트랜잭션을 계속 점유한다.

### 3. [중간] 요건 3: 나누어떨어지지 않는 용량이 조용히 버려짐

`cmd.doseMg() / product.getUnitDoseMg()` 는 정수 나눗셈이라 나머지가 버려진다. 예를 들어 doseMg=250, unitDoseMg=100 이면 2정으로 저장되어 50mg 이 사라진다. 의료성 데이터라 조용한 절삭은 위험하다. 이 항목은 0 으로 나누는 문제와 별개이므로 제외 대상이 아니다. 나머지가 있을 때 거절할지, 반올림할지는 PRD 에 정의가 없으므로 확인이 필요하다.

### 4. [낮음] 사소한 사항

- `orElseThrow()` 가 메시지 없는 `NoSuchElementException` 을 던진다. 어떤 productId 인지 알 수 없고, API 응답에서 404 와 500 중 무엇이 되는지도 불분명하다. 도메인 예외로 바꾸는 편이 좋다.
- 존재하지 않는 productId 가 일부 섞여 있을 때의 동작(전체 실패인지 건별 실패인지)이 요건 2의 범위에 들어가는지 PRD 에 명시가 없다.
- 저장 후 예약 순서이므로, 예약 성공 후 `assignReservation` 반영이 flush 되기 전에 장애가 나는 경우도 고려해야 한다.

## 제외한 항목 (사용자 요청)

- `unitDoseMg == 0` 일 때 `ArithmeticException` 가능성. 제품 마스터를 운영팀이 관리한다는 사용자 설명에 따라 검토에서 뺐다. 이 전제는 코드나 DB 제약으로 강제되는 것이 아니므로, 마스터에 CHECK 제약이 있는지 확인하면 가정을 사실로 바꿀 수 있다. 재평가 트리거는 마스터 입력 경로가 운영팀 외로 확대될 때다.

## 확인된 것과 가정한 것

- 확인된 것: 제공된 PRD, TDD, 변경 코드 발췌 내용.
- 가정한 것: 제품 마스터에 0 이 들어오지 않는다(사용자 진술). `ScheduleCommand` 의 `doseMg` 는 정수형이다.
- 확인하지 못한 것: `MedicationSchedule` 생성자에서 status 초기값을 설정하는지, `assignReservation` 이 status 를 RESERVED 로 바꾸는지. 변경 발췌에 없다.

## 결론

요건 2는 "매핑됨"으로 처리할 수 없고, 1번(요건 2 미충족)과 2번(외부 예약 불일치)은 머지 전 수정이 필요하다. 전체 롤백 방식을 유지하고 싶다면 PRD 수용 기준 2를 변경하는 합의를 먼저 받아야 하며, 그 경우에도 2번의 외부 예약 보상 처리 문제는 남는다.
