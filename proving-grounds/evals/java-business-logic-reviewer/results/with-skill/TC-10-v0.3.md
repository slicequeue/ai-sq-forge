# 비즈니스 로직 리뷰 리포트

## Phase 0. 문서 확보

- PRD·TDD 문서는 파일 경로나 링크가 전달되지 않았다. 사용자가 수용 기준 1건을 본문에 직접 제시했으므로 그 1건을 기준으로 리뷰한다.
- 확인 요청: PRD(`docs/prd/...` 또는 Jira)와 TDD(`docs/tdd/...` 또는 Confluence) 위치를 알려 주세요. TDD 시그니처(API·엔티티·예외·HTTP status)는 확보하지 못해 이번 리뷰에서 대조하지 않았다.
- 코드는 스니펫 3개만 전달됐다. 아래 `파일:라인` 은 파일명과 실제 라인이 없어 `스니펫 N, 주석 기준 위치` 로 표기한다. 실제 PR의 파일:라인 확인이 필요하다.

### 도메인 불변식 (Phase 1.3 격리)

- INV-1: 병원 권한 이관 전에 존재하던 권한은 이관 후에도 남아 있어야 한다 (요건 1의 "~않아야 한다" 문장).

### 모호 문구: 임의 해석하지 않고 확인 요청 (BIZ-HG-2)

1. "기존 권한이 유실되지 않는다" 의 범위는 무엇인가. 기존 권한 집합의 완전 보존인가, 아니면 `newAuthorities` 와의 합집합인가.
2. `realignByHospitalId` 가 권한을 어떻게 바꾸는지(어떤 컬럼을 어떤 값으로) 알 수 없다. 이 쿼리가 기존 권한 데이터를 덮어쓰거나 지우는지 확인이 필요하다.
3. `policy.appendAndUpdate(newAuthorities)` 가 "추가" 인지 "교체" 인지 도메인 메서드 본문이 필요하다.
4. `newAuthorities` 의 출처가 스니펫에 없다.

위 4건이 확정되지 않으면 아래 판정은 "조건부" 이다.

## 🟠 불변식 위반 (최우선)

- [BIZ-INVARIANT] 스니펫 3, `migrateAuthorities` (벌크 update → `findByHospitalId` → `appendAndUpdate` → `save`) 등급: **AUTO FAIL / Critical (조건부)**
  - 요건: "병원 권한 이관 시 기존 권한이 유실되지 않아야 한다" (INV-1)
  - 근거: `authorityRepository.realignByHospitalId(hospitalId)` 는 QueryDSL 벌크 update 이다. 벌크 update 는 영속성 컨텍스트와 dirty checking 을 거치지 않으므로 DB 값만 바뀌고 1차 캐시의 엔티티는 갱신되지 않는다. 직후 같은 트랜잭션에서 `policyRepository.findByHospitalId` 로 재조회하고(RR-4) `appendAndUpdate` + `save` 를 한다.
  - 유실 시나리오: 호출자나 앞선 로직이 같은 트랜잭션에서 해당 정책/권한 엔티티를 이미 로드했다면, 재조회는 DB 의 갱신값이 아닌 1차 캐시의 오래된 값을 돌려준다. 그 값에 append 한 뒤 `save` 하면 flush 시점에 벌크 update 결과를 덮어써 이관된 권한이 사라진다. `appendAndUpdate` 가 교체 의미라면 유실은 더 직접적이다.
  - 확정에 필요한 정보: (a) `realignByHospitalId` 와 `UserRolePermissionPolicy` 가 같은 테이블/엔티티를 다루는지, (b) 호출 경로에서 선행 로드가 있는지, (c) `@Modifying(clearAutomatically)` 나 `em.clear()` 유무.
  - 추가 사각지대: `findByHospitalId` 결과가 null(정책 미존재)일 때 NPE 로 이관 전체가 롤백된다. 요건에 병원에 정책이 없는 경우의 규칙이 있는지 확인이 필요하다.
  - 수정 제안 (읽기 전용 리뷰라 코드는 변경하지 않음):
    1. 벌크 update 직후 `em.flush()` + `em.clear()` 후 재조회하거나, `@Modifying(clearAutomatically = true, flushAutomatically = true)` 를 사용한다.
    2. 벌크 update 와 정책 갱신 중 하나로 통일한다. 이관 로직을 엔티티 단위(dirty checking)로 하면 재조회 문제 자체가 사라진다.
    3. "이관 전 권한 집합 ⊆ 이관 후 권한 집합" 을 검증하는 통합 테스트를 추가한다. 벌크 update 후 재조회, 기존 권한 보존, 정책 null 케이스를 포함한다.
    4. `appendAndUpdate` 가 합집합 의미임을 도메인 메서드 단위 테스트로 고정한다.

## 🟡 사각지대 (PRD 수용 기준 밖, 리뷰 재발 방지 검사에서 검출)

> 아래 2건은 제시된 수용 기준(요건 1)과 직접 연결되지 않는다. PRD에 과금 개방 정책이나 노출 순서 규칙이 있는지 확인되지 않아 요건 위반이 아니라 재발 방지 검사(RR) 결과로 분류한다.

- [BIZ-EDGE] 스니펫 1, `isPaid` — 장애 시 동작 (RR-1) 등급: **High**
  - 문제: 규칙 0건이면 `false`, 예외가 나도 `false` 로 모두 "무료 개방(fail-open)" 이다. 주석으로 의도는 적혀 있으나, `catch (Exception e)` 에서 로그와 지표 없이 삼킨다. 과금 규칙 조회 장애가 발생하면 유료 경로가 조용히 전부 열리고 아무도 모른다.
  - 요건 확인 필요: 장애 시 열 것인가 닫을 것인가는 PRD에 정해져 있어야 하는 정책이다. 이 판단을 스킬이 임의로 정하지 않는다.
  - 권고: (1) 정책을 PRD 와 코드 주석에 명시, (2) 예외 시 error 로그와 지표(카운터) 추가, (3) "규칙 0건" 과 "조회 실패" 를 구분, (4) 동일 판정을 쓰는 다른 경로와 fail 정책이 대칭인지 점검.

- [BIZ-EDGE] 스니펫 2, 상위 5건 노출 — 결정성 (RR-2) 등급: **Medium**
  - 문제 1: `sorted(Comparator.comparing(Meal::getCarbGram).reversed())` 에 동점 2차 기준이 없다. 5번째 경계에서 `carbGram` 이 같은 항목이 있으면 `limit(5)` 의 구성원이 호출마다 달라질 수 있다(입력 순서 의존).
  - 문제 2: 필터는 `getCarbRatio() != null` 이지만 정렬 키는 `getCarbGram` 이다. `carbGram` 이 null 이면 `Comparator.comparing` 에서 NPE 가 난다. 필터 필드와 정렬 필드가 다른 이유가 요건에 있는지 확인이 필요하다.
  - 권고: `.thenComparing(Meal::getId)` 같은 결정적 2차 기준 추가, `carbGram` null 처리 방침 명시.
