# 비즈니스 로직 리뷰 리포트

## Phase 0. 문서 확보

- PRD·TDD 파일 위치는 전달되지 않았습니다. 요청 본문에 인용된 수용 기준 1건만 근거로 리뷰합니다. 문서 경로(`docs/prd/...`, `docs/tdd/...` 또는 Jira·Confluence 링크)를 알려주시면 요건 목록과 TDD 시그니처를 보강하겠습니다.
- 코드는 스니펫 3개만 전달됐고 파일 경로·라인 번호가 없습니다. 근거는 "스니펫 N, M행"(각 스니펫 첫 줄의 주석이 1행)으로 표기합니다. 실제 `파일:라인`은 PR diff에서 확인이 필요하므로 이 리포트에는 ✅ 매핑됨 판정을 하나도 두지 않았습니다 (BIZ-HG-3).
- 확인되지 않은 TDD 항목(엔드포인트, 엔티티 필드, 예외 매핑)은 이번 리뷰에서 비교하지 못했습니다.

## 🟠 불변식 위반 (최우선)

- [BIZ-INVARIANT] 요건 1 / INV-1 — 스니펫 3 `migrateAuthorities`, 4행 벌크 update → 5행 재조회 → 7행 `save`
  - 요건: "병원 권한 이관 시 기존 권한이 유실되지 않아야 한다"
  - 실제: 4행 `realignByHospitalId` 는 QueryDSL 벌크 update 라 DB 만 바꾸고 영속성 컨텍스트(1차 캐시)는 갱신하지 않습니다. 같은 트랜잭션 5행 `findByHospitalId` 는 변경 전 값 또는 캐시된 값을 돌려줄 수 있습니다. 그 객체에 6행 `appendAndUpdate` 를 하고 7행에서 `save` 하면 벌크 update 결과가 통째로 덮입니다. 이관된 권한이 사라지는 경로이며 요건 1 을 직접 깹니다.
  - 출처: RR-4 #717 (벌크 update 후 재조회로 ADMIN 권한 유실, Critical 2건). 이번 코드는 같은 패턴을 재현합니다.
  - 등급: **AUTO FAIL / Critical**
  - 수정 제안 (코드는 수정하지 않았습니다. 우선순위 순)
    1. 벌크 update 를 쓰지 않고 엔티티 단위로 변경합니다. `policy` 를 먼저 조회해 `appendAndUpdate` 와 realign 을 도메인 메서드 하나로 처리하고 `save` 합니다.
    2. 벌크를 유지한다면 4행 직후 `clearAutomatically = true` 또는 `entityManager.clear()` 를 둡니다. `clear()` 는 같은 컨텍스트의 다른 변경분도 날리므로 영향 범위 확인이 필요합니다.
    3. 벌크 update 와 이후 변경을 트랜잭션으로 분리하고, 분리 후 재조회가 커밋된 값을 읽는지 확인합니다.
  - 테스트 지적 (RR-12): Fake·Mock 저장소 단위 테스트로는 이 결함이 재현되지 않습니다. 실제 영속성 컨텍스트가 있는 통합 테스트로 "이관 후 기존 권한 보존"을 검증해야 합니다. 벌크 update 를 일부러 제거했을 때 실패하는지도 확인해 주세요.
  - 추가 확인 요청
    - 5행 `findByHospitalId` 가 정책이 없을 때 null 을 반환하면 6행에서 NPE 입니다 (BIZ-EDGE 후보). 반환 타입이 `Optional` 인지, 정책 없는 병원이 이관 대상이 될 수 있는지 알려주세요.
    - `hospitalId` 의 존재·소유 확인이 호출부에 있는지 확인이 필요합니다 (RR-14 #800, 존재·소유 확인이 입력 검증보다 먼저). 전달된 코드에는 보이지 않습니다.

## 🟡 사각지대 · 요건 외 재발 방지 검사 결과

아래 2건은 전달된 수용 기준에 직접 연결되는 요건이 없어 별도로 보고합니다 (요건이 있다면 알려주세요, 해당 번호에 연결해 재판정합니다).

- [BIZ-EDGE] 스니펫 1 `isPaid` — 장애 시 동작 (RR-1)
  - 5행 규칙 0건 `return false`, 7~8행 예외 `return false` 는 둘 다 "유료 아님 = 무료 개방"으로 열립니다. 주석에는 의도가 적혀 있어 열림 정책 자체는 코드에 명시돼 있습니다.
  - 문제: catch 에서 로그·지표 없이 통과시킵니다. 규칙 조회 장애가 나면 유료 API 전체가 조용히 무료가 되고 사후 탐지가 불가능합니다.
  - 출처: RR-1 #637·#641·#643 (규칙 0건·예외 시 유료 API 전면 무료 개방). 규칙이 0건일 때의 열림 정책도 로그·지표 없이는 설정 누락과 구분되지 않습니다.
  - 확인 요청: 장애 시 열림이 PRD 정책(fail-open)인지 판정 문서 확인이 필요합니다. 정책이라면 PR 본문 기재, WARN 로그와 지표를 권고하고, 아니라면 닫힘 또는 마지막 정상값 유지로 바꿔야 합니다.
  - 등급: High

- [BIZ-EDGE] 스니펫 2 상위 5건 노출 — 결정성 (RR-2)
  - 4행 `comparing(Meal::getCarbGram).reversed()` 에 동점 2차 기준이 없습니다. 탄수화물 g 이 같은 식사끼리 입력 순서에 따라 순위가 달라지고, 5행 `limit(5)` 가 `sorted` 뒤에 있어 경계 동점이면 노출되는 5건의 구성원 자체가 바뀝니다. 응답이 호출마다 달라질 수 있습니다.
  - 출처: RR-2 #697 (동점 2차 기준 부재), #693 (limit 이 sorted 뒤라 구성원 변동).
  - 추가 확인: 3행 필터는 `getCarbRatio() != null` 인데 정렬 키는 `getCarbGram` 입니다. 필터와 정렬이 서로 다른 필드를 봐서, `carbGram` 이 null 이면 4행에서 NPE 가 납니다 (필드 타입이 박싱 타입이라고 가정). 의도한 필드가 어느 쪽인지 확인해 주세요.
  - 수정 제안: `.thenComparing(Meal::getId)` 같은 유일 값으로 최종 판별합니다. 경계 동점 픽스처(5건 경계를 넘는 6건 이상)로 테스트하세요 (RR-12).
  - 등급: Medium

## 확인된 것 vs 가정한 것

| 구분 | 내용 |
|------|------|
| 확인된 것 | 스니펫 3 의 호출 순서(벌크 update → 같은 트랜잭션 재조회 → save). 스니펫 1 의 catch·0건 시 `false` 반환과 로그 부재. 스니펫 2 의 정렬 키·필터 필드·`limit` 위치 |
| 가정한 것 | `realignByHospitalId` 가 `@Modifying(clearAutomatically)` 없이 실행되며 flush·clear 를 하지 않는다. `findByHospitalId` 가 JPA 영속 엔티티를 반환한다. "기존 권한"은 이관 전 권한 전부다. `getCarbGram` 은 박싱 타입이다 |
| 재평가 트리거 | 실제 repository 구현에서 clear 가 수행되면 INV-1 위반은 해소됩니다(단 7행 `save` 의 정합성은 재확인). PRD 에 fail-open 정책이 명시돼 있으면 스니펫 1 은 로그·지표 지적만 남깁니다. 스니펫 1·2 에 해당하는 요건 번호가 제공되면 그 요건에 연결해 재판정합니다 |

## 위임 안내 (스코프 밖)

- 트랜잭션 경계 설계, 벌크 쿼리 성능, `stream` 비용은 java-performance-reviewer 가, 4-Tier 계층·Bean 관계는 java-architecture-reviewer 가 담당합니다. 이 리포트는 요건 정합과 재발 방지 검사(RR-1·RR-2·RR-4)만 다룹니다. 여러 관점이 필요하면 java-composite-reviewer 로 조합 호출을 권장합니다.
- 이 리뷰는 읽기 전용이며 코드를 수정하지 않았습니다.
