- 리뷰 대상 코드는 파일 전체가 아닌 인라인 스니펫 3개(주석 "1) 과금 판정", "2) 탄수화물 상위 5건 노출", "3) 병원 권한 이관")로 제공됨. **실제 파일 경로·라인 번호가 없어 "파일:라인" 근거를 정확히 제시할 수 없음.** 아래 매핑은 편의상 "블록 1/2/3 + 블록 내 상대 라인"으로 표기하며, 이는 BIZ-HG-3(근거 없는 매핑 금지) 원칙상 **완전한 근거로 인정할 수 없는 상태**임을 명시함. 실제 리뷰 확정을 위해서는 파일 경로 확인이 필요.

## 🟠 불변식 위반 (최우선)

- **[BIZ-INVARIANT] 블록 3 `migrateAuthorities(Long hospitalId)` — 병원 권한 이관 시 기존 권한 유실 위험**
  - 요건(수용 기준 원문): "병원 권한 이관 시 기존 권한이 유실되지 않아야 한다."
  - 근거(블록 3, 상대 라인 기준):
    ```java
    authorityRepository.realignByHospitalId(hospitalId);   // QueryDSL bulk update  (라인 1)
    UserRolePermissionPolicy policy = policyRepository.findByHospitalId(hospitalId); // 라인 2
    policy.appendAndUpdate(newAuthorities);                 // 라인 3
    policyRepository.save(policy);                          // 라인 4
    ```
  - 문제:
    1. `realignByHospitalId`는 주석대로 QueryDSL **벌크 update**이며 영속성 컨텍스트를 거치지 않고 DB에 직접 반영된다. 같은 트랜잭션 안에서 바로 `findByHospitalId`로 관련 엔티티(`UserRolePermissionPolicy`)를 재조회하고 있어, `review-recurrence-guard.md`의 **RR-4(벌크 연산과 영속성 컨텍스트)** 위반 패턴과 정확히 일치한다. 이 정책 엔티티가 이번 트랜잭션에서 이미 1차 캐시에 올라 있던 상태라면 벌크 update 반영 전 값을 그대로 들고 있게 되고, 이후 `save(policy)`가 realign 결과를 통째로 덮어써 권한이 유실될 수 있다. 동일 저장소의 과거 사고(#717, "벌크 update 후 재조회로 ADMIN 권한 유실, Critical 2건")와 사실상 동일한 구조다.
    2. `policy.appendAndUpdate(newAuthorities)`가 정책의 권한 목록을 "추가"만 하는지 "치환"까지 하는지 이 스니펫만으로는 확인 불가하다. `realignByHospitalId`가 이미 반영한 권한이 `newAuthorities`(아래 3번)에 포함되지 않은 채 `appendAndUpdate`가 내부적으로 목록을 치환하는 방식이라면, `save(policy)` 시점에 realign 결과가 사라진다.
    3. `newAuthorities`는 `migrateAuthorities(Long hospitalId)` 메서드 시그니처에 파라미터로 선언돼 있지 않다 — 필드인지 상위 스코프 변수인지 스니펫만으로는 알 수 없고, `realignByHospitalId`가 반영한 권한 집합과 이 값의 관계도 불명확하다. 이 변수의 출처와 realign 대상과의 정합성을 반드시 실제 코드로 확인해야 한다(임의 해석 금지, BIZ-HG-2).
  - 판정: **불변식 위반 가능성 높음** — 벌크 update 직후 같은 트랜잭션에서 재조회·재저장하는 구조 자체가 RR-4가 경고하는 유실 패턴이며, 주어진 유일한 수용 기준을 정면으로 위반할 잠재 리스크를 갖는다.
  - 등급: **AUTO FAIL / Critical**
  - 권고:
    - 벌크 update 이후 같은 엔티티(또는 벌크 update와 겹치는 데이터를 담은 엔티티)를 재조회하지 않도록 순서를 바꾸거나(정책을 먼저 조회 → 병합 → 저장 → 마지막에 벌크 정리), 벌크 update 대신 엔티티 단위 변경으로 전환.
    - 부득이 재조회가 필요하면 벌크 update 직후 `entityManager.clear()` 또는 `@Modifying(clearAutomatically = true)`로 1차 캐시를 명시적으로 비운다(단, 같은 컨텍스트의 다른 변경분도 함께 날아가므로 영향 범위 확인 필요).
    - `newAuthorities`의 출처와 `realignByHospitalId`가 다루는 권한 집합의 관계, `appendAndUpdate`가 append-only인지 replace인지를 코드로 직접 확인.

## 🟡 사각지대 (리뷰 재발 방지 검사 — RR)

> 아래 2건은 제공된 PRD 수용 기준(권한 이관)과는 직접 관련 없으나, `review-recurrence-guard.md`가 요구하는 공통 검사 항목에서 검출됨. PRD 문서가 없어 BIZ-MISSING/PARTIAL로 분류하지 않고, 리뷰 재발 방지 관점의 사각지대로 보고함.

- **[BIZ-EDGE] 블록 1 `isPaid(String path)` — 장애 시 동작 미명시 + 무로그 통과 (RR-1)**
  ```java
  public boolean isPaid(String path) {
      try {
          List<PricingRule> rules = pricingRepository.findAllActive();
          if (rules.isEmpty()) return false;
          return rules.stream().anyMatch(r -> matches(r, path));
      } catch (Exception e) {
          return false;
      }
  }
  ```
  - 문제: 과금 판정(막는/과금하는 로직)에서 (a) 활성 규칙이 0건일 때 `false`(무료·비과금)로 판정, (b) 조회 중 예외 발생 시에도 `catch`로 삼켜 `false`로 통과시킴. 두 경우 모두 **의도한 정책(0건/예외 시 과금 안 함이 맞는지)이 코드·주석 어디에도 명시돼 있지 않고, 로그·지표도 전혀 남기지 않는다.** `review-recurrence-guard.md` RR-1의 금지 사항("판정 실패를 catch 해서 통과시키면서 로그도 지표도 남기지 않는 것")에 정확히 해당하며, 하네스 AUTO FAIL 조건 RR-F1("접근 제어·과금 판정에서 예외·0건 상황을 로그·지표 없이 통과 처리")과도 일치한다.
  - 등급: **High**
  - 권고: 0건/예외 상황의 의도된 정책을 주석 또는 PR 본문에 명시하고, `catch` 블록에 최소한 경고 로그 + 지표(카운터) 기록 추가.

- **[BIZ-EDGE] 블록 2 탄수화물 상위 5건 노출 — 동점 2차 기준 부재 + 정렬 필드/필터 필드 불일치 (RR-2)**
  ```java
  return meals.stream()
          .filter(m -> m.getCarbRatio() != null)
          .sorted(Comparator.comparing(Meal::getCarbGram).reversed())
          .limit(5)
          .toList();
  ```
  - 문제:
    1. `getCarbGram()` 값이 동률일 때 2차 정렬 기준이 없다. `review-recurrence-guard.md` RR-2에 따라 "상위 N건" 로직은 동점 시 결과가 입력 순서(예: DB 조회 순서)에 의존해 비결정적이 될 수 있다. `limit(5)`가 `sorted` 뒤에 붙어 있어 동점 처리 방식에 따라 상위 5건의 **구성원 자체**가 바뀔 수 있다.
    2. `filter`는 `getCarbRatio() != null`을 기준으로 하는데 `sorted`는 `getCarbGram()`을 기준으로 한다. 두 필드가 서로 다른데, `carbRatio`는 null이 아니지만 `carbGram`이 null인 레코드가 있다면 `Comparator.comparing(Meal::getCarbGram)`에서 `NullPointerException`이 발생할 수 있다. 필터-정렬 필드 불일치의 의도(정말 다른 필드를 기준으로 삼아야 하는지)를 확인 필요.
  - 등급: **Medium**
  - 권고: `.thenComparing(Meal::getId)` 등 동점을 가르는 2차 기준 추가. `carbGram` null 가능성이 있다면 필터 조건에 포함하거나 `Comparator.nullsLast(...)` 적용.
