## 🟠 불변식 위반 (최우선)

### [BIZ-INVARIANT] 요건 2 / INV-1 — 기록이 있는 사용자에게 "첫 기록을 남겨보세요" 안내가 내려간다

- 위치: `HomeCardService.java:28-36`
- 코드 사실
  - `:32` 혈당 기록 조회와 `:33` 일정 조회가 **하나의 try** 안에 있다.
  - `:35-36` `catch (Exception e)` 가 어떤 예외든 `HomeCardResponse.empty()` (hasRecord=false, lastRecord=null, nextSchedule=null)를 반환한다.
- 영향: 혈당 기록이 수십 건 있는 사용자도 캘린더 타임아웃 한 번에 hasRecord=false 응답을 받아 "첫 기록을 남겨보세요"를 보게 된다. "기록이 한 번도 없는 사용자에게만"이라는 요건 2 의 "만"을 정면으로 어긴다. 요건 1(값·기록 시각 노출)도 같은 경로에서 깨진다.
- 근본 원인: 부가 정보(일정) 실패가 핵심 정보(마지막 기록)까지 비워 **틀린 상태**를 내려 준다.
- 공통 가드: **RR-13 실패 격리 — "try 범위가 너무 넓다" (#777)**. 같은 유형의 사고 사례.
- 등급: **AUTO FAIL / Critical**

수정 방향 (코드는 수정하지 않았습니다)

1. try 를 조회별로 분리한다. 혈당 기록 조회(`:32`)는 try 밖에 두거나, 실패하면 empty 가 아니라 오류로 올린다. 일정 조회(`:33`)만 따로 감싼다.
2. 일정 조회의 catch 는 `catch (Exception)` 이 아니라 `CalendarTimeoutException` 등 기대하는 예외로 좁히고, `nextSchedule = null` 만 채운 응답을 만든다. hasRecord 는 기록 조회 결과로만 결정한다.
3. 테스트: "기록 있음 + 일정 조회 예외 → hasRecord=true, lastRecord 존재, nextSchedule=null" 를 반드시 추가한다. (RR-12 — 이 분기를 일부러 깨뜨리면 실패하는 테스트가 있어야 한다)

## ⚠️ 부분 매핑

### [BIZ-PARTIAL] 요건 3 "일정 조회가 실패해도 홈 카드는 정상 응답한다" — 매핑됨 아님

- 정상 경로(일정이 있으면 노출): `HomeCardService.java:33` 조회 → `:34` `HomeCardResponse.of(last, next)` 로 전달. (`of()` 내부는 미제공이라 nextSchedule 이 실제로 채워지는지는 확인하지 못함)
- 실패 경로(일정 조회 실패 시 정상 응답): 아래 두 가지 이유로 요건을 충족하지 못한다.

**이유 A. 실패 시 "정상"이 아니라 "틀린 상태"를 응답한다** (요건 2 위반과 동일 원인, `:35-36`).
일정만 비워야 하는데 기록까지 비운 empty 를 내려 준다. 정상 응답의 의미를 충족하지 못한다. — RR-13 #777

**이유 B. 트랜잭션 rollback-only 전파로 try 를 통과해도 전체가 500 이 될 가능성이 높다.**

- 코드 사실
  - `HomeCardService.getHomeCard` 는 `@Transactional(readOnly = true)` (`:28` 부근).
  - `MedicationScheduleService.findNext` 는 `@Transactional` (`MedicationScheduleService.java:40`, 기존 코드 변경 없음). 기본 전파가 REQUIRED 라 **바깥 트랜잭션에 참여**한다.
  - `CalendarTimeoutException` 은 `RuntimeException` (TDD 명시). 스프링 기본 규칙상 RuntimeException 은 롤백 대상이다.
- 추론 (스프링 전파 동작에 근거한 것이며 이 리뷰에서 실행해 확인하지는 않았음)
  - `findNext` 프록시가 예외를 만나면 참여 중인 트랜잭션을 rollback-only 로 표시한다.
  - 바깥 메서드가 예외를 catch 해 정상 반환해도 커밋 시점에 이미 rollback-only 이므로 `UnexpectedRollbackException` 이 던져진다.
  - 결과적으로 `catch` 블록이 실행되고 empty 를 반환하더라도, 메서드 종료 시 예외로 전체가 실패할 수 있다. 즉 "try 로 감쌌다"는 사실만으로는 실패 허용을 보장하지 못한다.
- 공통 가드: **RR-13 — "같은 트랜잭션에 참여한 하위 조회가 예외를 낸다" (#793)**. 호출부 catch 로 해결되지 않고 트랜잭션 경계 분리가 필요하다고 정리된 사례.
- 확인 방법: 실제 프록시가 적용된 통합 테스트(`@SpringBootTest` 또는 `@DataJpaTest` + 실제 빈)에서 `calendarClient` 만 예외를 던지게 하고 HTTP 200 과 lastRecord 존재를 단언한다. Mockito 로 `MedicationScheduleService` 를 mock 하면 이 문제를 재현하지 못한다.

수정 방향

1. 일정 조회를 트랜잭션 경계 밖으로 분리한다. (`findNext` 에 `REQUIRES_NEW`, 또는 트랜잭션 없는 별도 빈에서 캘린더 호출, 또는 `getHomeCard` 의 트랜잭션 범위를 기록 조회로 한정)
2. 일정 조회 실패는 WARN 로그(userId, 예외)를 남기고 nextSchedule=null 로 응답한다.
3. 위 1 의 통합 테스트로 "일정 실패 → 200 + 기록 유지"를 증명한다.

- 등급: **High**

## 사용자 확인 요청 (BIZ-HG-2: 임의 해석 방지)

1. 요건 3 의 "정상 응답"은 HTTP 200 + `nextSchedule=null` 을 뜻하는 것으로 읽었습니다. "일정 없음"과 "일정 조회 실패"를 클라이언트가 구분해야 하는지(예: 별도 플래그) PRD 에 명시가 없어 임의로 확장하지 않았습니다. 구분이 필요한지 확인 부탁드립니다.
2. 혈당 기록 조회 자체가 실패하는 경우(DB 장애)의 기대 동작은 PRD 에 없습니다. empty(첫 기록 안내)가 아니라 오류 응답이어야 한다는 것이 이 리뷰의 판단이나, 요건 확정은 사용자 몫입니다.
