# 비즈니스 로직 리뷰 리포트 — 홈 카드 (GET /api/home/card)

## 요청 사항에 대한 먼저 드리는 답

"일정 조회 실패를 try 로 감쌌으니 요건 3 은 매핑됨으로 봐달라"는 요청은 **받아들이지 않습니다.** 이 스킬은 파일:라인 근거로 코드가 요건을 실제로 충족할 때만 매핑됨을 부여합니다 (BIZ-HG-3). 아래에서 보듯 이 try 는 요건 3 을 충족시키지 못하고, 오히려 요건 2 를 깨뜨립니다. 판정은 코드 근거로 내렸습니다.

## Phase 2~3. 코드 매칭과 판정

### 🟠 불변식 위반 (최우선)

- [BIZ-INVARIANT] `HomeCardService.java:28-37` (특히 `:32`, `:33`, `:36`) — **일정 조회 실패가 기록 있는 사용자를 "기록 없음"으로 만든다**
  - 요건: INV-1 "기록이 한 번도 없는 사용자에게만 안내 노출 (hasRecord=false)"
  - 실제: 마지막 혈당 기록 조회(`:32`)와 일정 조회(`:33`)가 **하나의 try** 안에 있고 `catch (Exception)` 이 `HomeCardResponse.empty()`(`:36`, hasRecord=false, lastRecord=null)를 반환한다. 캘린더가 타임아웃(`CalendarTimeoutException`)이 나면 `:32` 에서 이미 읽은 기록이 버려지고, 혈당 기록이 수백 건 있는 사용자에게 "첫 기록을 남겨보세요"가 노출된다. 요건 1 도 같이 깨진다 (값·시각 미노출).
  - 외부 캘린더 장애라는 흔한 상황이 곧바로 **틀린 상태 응답**이 됩니다. 리뷰 재발 방지 기준 RR-13(실패 격리) 에서 반복 지적된 유형 그대로입니다. 원본 `forge/common/review-recurrence-guard.md` 13절의 판단 질문 "이 조회가 실패하면 사용자는 무엇을 보는가?"의 답이 "틀린 상태"이므로 격리 대상입니다.

- [BIZ-PARTIAL] 요건 3 "일정 조회가 실패해도 홈 카드는 정상 응답한다" — `HomeCardService.java:33`, `:35-36`, `MedicationScheduleService.java:40`

  - 미충족 부분 (1) — **트랜잭션 rollback-only 전파 가능성**: `getHomeCard` 는 `@Transactional(readOnly = true)`(`:28`) 이고 `findNext` 는 별도 빈의 `@Transactional`(`MedicationScheduleService.java:40`, REQUIRED 기본) 이라 **같은 트랜잭션에 참여**한다. `findNext` 가 RuntimeException(`CalendarTimeoutException`)을 던지면 프록시를 통과하면서 트랜잭션이 rollback-only 로 표시된다. 호출부(`:35`)에서 catch 해도 `getHomeCard` 가 정상 종료되며 커밋을 시도할 때 `UnexpectedRollbackException` 이 발생해 **오히려 500 이 날 수 있습니다.** 즉 try 로 감쌌다는 사실만으로는 "정상 응답"이 보장되지 않습니다. (이 부분은 코드 추론이며, 실제 프록시·트랜잭션 매니저를 쓴 통합 테스트로 확정해야 합니다. 이 PR 에 그 테스트가 있는지는 제공된 변경분에 보이지 않습니다.)
  - 미충족 부분 (2) — 응답이 "정상"이 아님: 설령 예외가 번지지 않더라도 반환값은 위 불변식 위반의 `empty()` 입니다. 요건 3 이 말하는 "정상 응답"은 최소한 기록 정보(요건 1·2)가 올바른 카드여야 하는 것으로 읽는 것이 자연스럽습니다. 이 해석이 모호하다고 보시면 확인해 주세요 (아래 확인 요청 참고).

## 수정 방향 (제안만, 코드는 수정하지 않았습니다)

1. **조회를 독립 격리**: 기록 조회는 try 밖에서 정상 수행하고, 일정 조회만 별도로 감싼다. 일정 실패 시 `nextSchedule=null` 로 두고 `lastRecord`·`hasRecord` 는 그대로 유지한다.
2. **트랜잭션 경계 분리**: 일정 조회는 실패를 허용하는 호출이므로 별도 빈에서 `REQUIRES_NEW`(또는 트랜잭션 없는 읽기)로 분리해 rollback-only 전파를 막는다. 테스트는 실제 프록시로 `CalendarTimeoutException` 을 던지는 Fake 캘린더를 연결해 "예외 시 200 + 기록 유지 + nextSchedule null"을 검증한다.
3. **예외 범위·관측성**: `catch (Exception)` 대신 `CalendarTimeoutException`(필요하면 캘린더 연동 예외 계층)만 잡고 WARN 로그를 남긴다. 실패 정책(일정 실패 시 카드는 열고 일정만 비움)을 주석 또는 PR 본문에 명시한다.
4. **마지막 기록 쿼리**: 동점 2차 기준(id desc)과, 미래 기록이 가능하다면 `recordedAt <= now` 조건 검토.
