## 확인된 사실 vs 가정

| 구분 | 내용 | 재평가 트리거 |
|------|------|---------------|
| 확인된 사실 | `update` 가 `validate`(:41) 를 `findByIdAndUserId`(:43) 보다 먼저 호출한다 | - |
| 확인된 사실 | `validate` 의 간격 검사는 사용자의 `recordedAt` 최댓값 기록 1건과만 비교한다 (`RecordTimeValidator.java:17`) | - |
| 확인된 사실 | `delete` 의 "마지막" 판정은 `recordedAt` 동등 비교이다 (`GlucoseRecordService.java:53`) | - |
| 확인된 사실 | PR 본문에는 "등록 시 시각 검증 추가"만 있고 PUT 에 검증이 붙었다는 기재가 없다. 테스트는 `create_*` 4건이다 | - |
| 가정 | `findByIdAndUserId` 는 타인 기록이면 empty 를 반환한다 | Repository 정의에서 다르게 확인되면 요건 1 판정 재평가 |
| 가정 | `GlucoseUpdateCommand.recordedAt()` 은 null 이 아니다. null 이면 `validate` 에서 NPE | Command 검증 위치 확인 시 재평가 |
| 가정 | 기존 데이터에 같은 `recordedAt` 을 가진 기록 쌍이나 미래 시각 기록이 있을 수 있다 (이번 PR 이전에는 간격·미래 검증이 없었으므로) | 운영 데이터 조회 결과 0건이면 요건 4 등급 하향 |

## 🟠 불변식 위반 (최우선)

### [BIZ-INVARIANT] 요건 1 / I-1 — PUT 에서 입력 검증이 소유·존재 확인보다 먼저 실행됨

- 위치: `GlucoseRecordService.java:41` (validate) → `:43` (findByIdAndUserId → 404)
- 요건: "타인 기록·없는 기록 id 는 404 를 반환한다"
- 실제: 타인 기록 id 나 없는 id 로 PUT 하면서 시각이 미래이거나 직전 기록과 5분 이내이면 404 가 아니라 **400** 이 나간다. 404 는 시각이 유효한 요청에서만 나온다.
- 부수 영향: 응답 코드 차이로 해당 id 의 존재 여부와 소유 여부는 노출되지 않지만, 에러 우선순위가 요건과 어긋난다.
- 근거 가드: RR-14 (#800 소유 확인 전에 간격 검증)
- 등급: **AUTO FAIL / Critical**
- 수정안
  1. `:41` 과 `:43` 순서를 바꿔 소유·존재 확인 후 검증한다.
  2. 확인된 기록을 검증기에 넘겨 같은 조회를 두 번 하지 않는다.
  3. "타인 id + 미래 시각 → 404", "없는 id + 5분 이내 → 404" 테스트를 추가한다.

### [BIZ-INVARIANT] 요건 1 — 가장 최근 기록을 수정하면 자기 자신과 비교해 항상 400 (수정 불가)

- 위치: `RecordTimeValidator.java:17` (`findTopByUserIdOrderByRecordedAtDesc`), `:18` (`Duration.between(...).abs().toMinutes() < 5`), 호출부 `GlucoseRecordService.java:41`
- 요건: "사용자는 본인 혈당 기록을 수정(PUT)할 수 있다"
- 실제: PUT 시 `prev` 는 수정 대상 기록 자신일 수 있다. 가장 최근 기록의 값만 고치거나(recordedAt 동일) 시각을 5분 미만으로 옮기면 간격이 0~4분이므로 `TOO_CLOSE`(400) 가 난다. 사용자가 방금 입력한 기록의 오타를 고치는 가장 흔한 시나리오가 막힌다.
- 최신이 아닌 기록을 수정하는 경우에도 비교 대상이 "수정 대상의 직전 기록"이 아니라 "사용자의 가장 최근 기록"이라 요건 3 의 의미(직전 기록 대비)와 맞지 않는다.
- 근거 가드: RR-14 (#800 기존 경로에 새 검증이 붙음), RR-12 (#800 등록 경로 외 경로 미검증)
- 등급: **Critical** (기존에 통과하던 정상 요청이 이번 PR 로 400 이 되는 회귀)
- 수정안
  1. PUT 에서는 간격 검사에서 수정 대상 id 를 제외한다 (`excludeRecordId` 파라미터 또는 `IdNot` 조회).
  2. 또는 PRD 에 없는 요건이므로 PUT 에는 간격 검증을 붙이지 않는다 (아래 확인 질문 1).
  3. "최신 기록의 value 만 수정", "최신 기록 시각을 4분 이동" 테스트를 추가한다.

## ⚠️ 부분 매핑

### [BIZ-PARTIAL] 요건 3 — "직전 기록과 5분 이내" 해석 확인 필요 (BIZ-HG-2)

- 매핑 근거: `RecordTimeValidator.java:17-19`, 호출 `GlucoseRecordService.java:31`. POST 정상 경로는 구현돼 있다.
- 모호 지점은 임의 해석하지 않고 확인을 요청한다.
  - (a) "직전 기록"이 사용자의 **가장 최근 기록**인지, **입력한 recordedAt 바로 앞 시각의 기록**인지. 현재 구현은 (a) 이고 `abs()` 로 양방향 비교한다. 과거 시각으로 등록하면 (b) 의미의 직전·직후 기록과의 간격은 검사되지 않는다.
  - "5분 이내"에 정확히 5분 00초가 포함되는지. 현재는 `toMinutes() < 5`(분 단위 절삭) 라서 5분 00초는 통과한다.
- 판정은 위 확인 전까지 ⚠️ 로 유지한다. 등급: Medium.
- 같은 조회의 결정성: `findTopBy...OrderByRecordedAtDesc` 는 recordedAt 동점 시 2차 기준이 없다 (RR-2 #697). 동점 기록 중 어느 것이 `prev` 인지 불확정이다.

### [BIZ-PARTIAL] 요건 4 — 마지막 기록 판정이 시각 동등 비교 (기존 코드, 이번 PR 변경 아님)

- 위치: `GlucoseRecordService.java:52` (최신 1건 조회), `:53` (`recordedAt` equals 비교)
- 정상 경로(유일한 최신 기록 삭제 허용, 그 외 거부)는 매핑됨. 그러나 같은 `recordedAt` 을 가진 기록이 둘 이상이면 둘 다 "마지막"으로 판정돼 삭제된다 (I-3 위반 가능). "마지막" 은 id 로 판정해야 한다 (RR-14 #784). `:52` 의 `orElseThrow()` 는 인자가 없어 경합 시 NoSuchElementException(500) 이 난다.
- 미래 시각 기록이 이미 있으면 그 기록이 "마지막"이 된다 (RR-14 #793). 이번 PR 이전 데이터에 존재할 수 있다 (가정 표 참조).
- 이번 PR 의 diff 밖이므로 수정은 제안하지 않고 별도 이슈로 분리할 것을 권고한다. 등급: Medium.

## 🟠→동작 변경 미기재 (RR-14)

- PRD 요건 2·3 은 `[이번 PR 신규]` 이면서 **등록(POST)** 에 한정된다. 그러나 `:41` 에서 PUT 에도 같은 검증이 붙었고 PR 본문에는 기재가 없다 (RR-14 #800 PUT 에 검증이 새로 붙음). 이전에 통과하던 PUT 요청(과거 데이터 수정 포함)이 이번 PR 이후 400 이 될 수 있다. 의도라면 "기존 동작 변경" 항목으로 PR 본문에 적고, 아니라면 PUT 호출을 제거해야 한다. 요건 1 연결: 위 두 건과 같은 뿌리다.

## 이관 안내 (스코프 밖, 판정에서 제외)

- 검증기가 Repository 를 직접 주입받는 계층 위치, 공용 `RecordTimeValidator` 의 의존 방향: java-architecture-reviewer
- `(user_id, recorded_at)` 인덱스 유무와 조회 비용, 동시성 제어 방식(락·유니크 제약): java-performance-reviewer
- 입력값 보안·FQCN·임시 로그 등 공통 룰: java-secure-coding-reviewer, self-code-reviewer
- 전 관점 조합 리뷰는 java-composite-reviewer 로 호출하는 것을 권장한다.

이 리뷰는 읽기 전용이며 코드를 수정하지 않았다. 수정안은 제안일 뿐 적용 여부는 확인 질문 답변 후 결정해야 한다.
