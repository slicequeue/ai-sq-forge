## 🟠 불변식 위반 (최우선)

### [BIZ-INVARIANT] 수정(PUT) 에 새로 붙은 검증이 최신 기록 자신과 비교해 수정 자체를 막는다
- 위치: `GlucoseRecordService.java:41`, `RecordTimeValidator.java:17-19`
- 요건: INV-2 "본인 기록 수정 가능" (요건 1)
- 근거: `update` 가 `validate(userId, cmd.recordedAt())` 를 호출하고(:41), validator 는 사용자의 **가장 최근 기록**을 `findTopByUserIdOrderByRecordedAtDesc` 로 가져와(:17) 입력 시각과의 간격이 5분 미만이면 `TOO_CLOSE` 를 던진다(:19). 수정 대상이 바로 그 최근 기록이면 비교 대상이 **자기 자신의 기존 시각**이다.
  - 값(value)만 고치는 수정: `recordedAt` 이 그대로이므로 간격 0분, 400.
  - 시각을 5분 미만으로 미세 조정: 400.
  - 방금 입력한 기록을 바로 고치는 흐름이 가장 흔한 수정 시나리오라 영향이 크다.
- 가정 구분: `cmd.recordedAt()` 이 PUT 에서 기존 값을 그대로 보내는지는 DTO 를 보지 못해 확인하지 못했다. 보내지 않고 null 이면 :15 의 `isAfter` 에서 NPE 가 난다(아래 BIZ-EDGE). 어느 쪽이든 최신 기록 수정은 실패한다.
- 등급: **AUTO FAIL / Critical**

### [BIZ-INVARIANT] 소유·존재 확인(404)보다 입력 검증(400)이 먼저 실행된다
- 위치: `GlucoseRecordService.java:41` (검증) → `:43` (조회·404)
- 요건: INV-1 "타인 기록·없는 기록 id 는 404"
- 근거: 타인 기록 id 또는 없는 id 로 PUT 하면서 시각이 미래이거나 최신 기록과 5분 이내이면 404 가 아니라 400 이 나간다. 요건 1 의 명시 상태코드와 어긋나고, 400 응답 여부로 리소스 존재 여부와 입력 유효성을 구분할 여지도 생긴다. (RR-14 "존재·소유 확인 → 입력 검증" 순서)
- 등급: **High** (요건에 명시된 상태코드 계약 위반, 위 건과 같은 줄에서 발생)

### 수정 방향 제안 (코드는 수정하지 않음)
1. `update` 에서 `findByIdAndUserId`(:43) 를 먼저 수행하고 그 다음 검증한다.
2. PUT 에서 간격 검증을 한다면 수정 대상 id 를 제외하고 비교한다. (예: validator 에 `excludeRecordId` 를 받거나 `...AndIdNot` 조회 사용)
3. 요건 2·3 은 "등록(POST)" 한정이다. PUT 에 미래 시각 검증만 필요하면 시각 검증과 중복 검증을 분리해, PUT 에는 의도한 것만 붙인다. PUT 에 검증을 붙이는 것 자체가 요건 범위 밖이므로, 유지한다면 사용자 합의가 필요하다.
4. 동작 변경을 PR 본문에 적는다 (아래 ⚠️ 항목).
5. PUT 경로 테스트를 추가한다 (최신 기록 값만 수정, 최신 기록 시각 미세 조정, 타인 id + 미래 시각 → 404).

## ⚠️ 부분 매핑

### [BIZ-PARTIAL] 요건 3 "직전 기록과 5분 이내면 중복으로 보고 400"
- 매핑: `RecordTimeValidator.java:17-19`, `GlucoseRecordService.java:31` (POST)
- 일부만 반영된 지점 (해석에 의존하므로 임의 결정하지 않고 확인을 요청한다, BIZ-HG-2):
  1. **"직전 기록"의 의미**: 코드는 사용자의 시각상 **가장 최근** 기록과 비교한다. 과거 시각으로 소급 등록하면(예: 기록 10:00, 12:00 이 있는데 10:02 를 등록) 최근 기록(12:00)과만 비교해 10:00 과의 5분 이내 중복을 못 잡는다. "직전"이 (a) 입력 시각 바로 앞 기록인지, (b) 가장 최근 등록된 기록인지, (c) 앞뒤 양쪽 이웃인지 확인이 필요하다. `.abs()` 로 양방향을 보는 점은 (a)·(c) 에 가깝지만 비교 대상은 (b) 이다.
  2. **"5분 이내"의 경계**: 코드는 `toMinutes() < 5` 라서 정확히 5분 00초 간격은 통과하고, 4분 59초는 차단된다. "5분 이내"가 5분 포함(5:00 도 중복)인지 확인이 필요하다. 포함이라면 `<=` 와 초 단위 비교가 필요하다.
- 등급: Medium

### [BIZ-PARTIAL] 요건 1 — 이번 PR 의 동작 변경 미기재 (RR-14)
- PUT 에 미래 시각·5분 간격 검증이 새로 붙어(:41) 이전에 통과하던 수정 요청이 400 이 된다. PRD 요건 2·3 은 POST 한정이고, PR 본문은 "등록 시 시각 검증 추가"만 말한다. 의도한 변경인지, PR 본문의 "기존 동작 변경" 항목으로 밝혀야 한다.
- 테스트: PR 본문의 `GlucoseRecordServiceTest#create_*` 4건은 POST 경로만 다룬다. 같은 검증이 붙은 PUT 경로는 실행하는 테스트가 없다. 검증을 붙인 모든 진입 경로에서 테스트해야 한다 (RR-14). 위 🟠 결함이 테스트에서 잡히지 않은 이유가 이것이다.
- 등급: Medium

## ✅ 매핑됨 (요약)

- 요건 2 (POST 미래 시각 400): `RecordTimeValidator.java:15` (`isAfter(now(clock))` → `InvalidInputException(FUTURE_TIME)`), 호출 `GlucoseRecordService.java:30-31`. 현재 시각과 같은 값은 허용된다. 상태코드 400 의 실제 매핑은 TDD 예외 매핑 표가 없어 `InvalidInputException` 이 400 이라는 PR 주석에 의존했다. `Clock` 주입으로 테스트 가능성은 확보돼 있다.
  - 참고: `LocalDateTime` 과 `clock` 의 타임존이 사용자 입력 시각의 기준 타임존과 같은지는 이번 발췌로 확인되지 않았다.
