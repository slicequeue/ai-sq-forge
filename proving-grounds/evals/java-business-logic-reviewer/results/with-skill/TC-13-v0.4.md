## 🟠 불변식 위반 (최우선)

### [BIZ-INVARIANT] 요건 2 / INV-1·INV-2 — 한 건 실패가 전체 롤백으로 번짐 (Critical, AUTO FAIL 대상)

- 위치: `MedicationScheduleService.java:25` `@Transactional(rollbackFor = Exception.class)`, 루프 `:28~34`, 예약 호출 `:32`
- 코드 사실
  - `pushClient.reserve(...)` (`:32`)를 감싸는 try/catch 가 없다. `PushReserveException` 이 루프를 빠져나가면서 트랜잭션 전체가 롤백된다.
  - 앞서 `:31` 에서 save 한 **성공 일정이 모두 사라진다** -> "성공한 일정은 유지"(INV-1) 위반.
  - 실패한 일정을 `RETRY_PENDING` 으로 바꾸는 코드가 변경분 어디에도 없다 -> INV-2 위반. 변경분에서 `RETRY_PENDING` 을 쓰는 줄을 찾을 수 없다(grep 대상: 변경 코드 `:25~:34` 전체).
  - 사용자 관점: 5건 중 4번째 예약이 실패하면 5건 모두 저장이 안 되고, 사용자에게는 요건이 말한 "실패한 일정만 재시도 대상" 대신 전체 실패가 보인다.
- "전체 롤백이 깔끔하다"에 대한 판단 (사실 vs 판단 분리)
  - 사실: DB 는 롤백되지만 **외부 푸시 서비스에 이미 성공한 예약 1~3번은 롤백되지 않는다.** 예약 ID 는 DB 롤백과 함께 사라져 취소할 방법이 없다 (고아 예약).
  - 사실: 사용자가 같은 요청을 재시도하면 1~3번 알림이 외부에 **중복 예약**된다.
  - 판단: "깔끔"한 것은 DB 쪽뿐이고, 외부 시스템과의 정합은 오히려 깨진다. 더구나 요건 자체가 부분 성공 유지를 요구하므로 요건 위반이다.
- 실전 사고 인용: 공통 가드 RR-13 **#799** (루프 중간 외부 호출 실패 시 전체 롤백으로 앞선 성공 결과 ID 까지 유실, 건 단위 try/catch 로 성공분 유지)
- 수정 방향 제안 (코드 변경은 하지 않음, 합의 후 구현)
  1. 건 단위로 `PushReserveException` 을 잡아 해당 일정만 `RETRY_PENDING` 으로 저장하고 루프를 계속한다.
  2. 트랜잭션 경계 주의: 건 단위 처리를 **별도 트랜잭션 빈(`REQUIRES_NEW`)** 으로 분리하는 경우, 같은 트랜잭션에 참여한 하위 호출이 예외를 내면 rollback-only 가 걸려 호출부에서 catch 해도 `UnexpectedRollbackException` 이 난다 (RR-13 #793). 실제 프록시를 통과하는 테스트로 확인할 것.
  3. `rollbackFor = Exception.class` 는 의도를 재검토한다. 부분 성공을 허용하는 메서드에서 전역 롤백 지정은 요건과 반대 방향이다.
  4. 테스트: 중간 건 예약 실패 시 (a) 앞선 건 RESERVED·예약 ID 저장, (b) 실패 건 RETRY_PENDING, (c) 뒤 건 계속 처리를 단언 (RR-12: 분기를 깨뜨리면 실패하는 테스트).

## 🟡 사각지대

### [BIZ-EDGE] 요건 3 — `unitDoseMg` 0·null, 제품 미존재, 나누어떨어지지 않는 값

- `MedicationScheduleService.java:30` `cmd.doseMg() / product.getUnitDoseMg()`
  - `unitDoseMg == 0` -> `ArithmeticException` -> (`:25` 전체 롤백) 해당 제품을 쓰는 **사용자 전원의 저장이 500 으로 실패**한다. (사용자 요청으로 판정 제외, 7절에 기록)
  - `getUnitDoseMg()` 가 `Integer`(null 가능)라면 `:30` 에서 NPE. 반환 타입은 발췌에서 확인 불가.
- `:29` `findById(...).orElseThrow()` — 메시지·비즈니스 예외 없이 `NoSuchElementException` 이 던져져 사용자에게 의미 있는 4xx 가 아닌 500 이 된다 (비즈니스 예외 경로: 명확한 메시지·HTTP status). 등급 Medium.
- 정수 나눗셈 `:30` — `doseMg` 가 `unitDoseMg` 의 배수가 아닐 때 **소수점 이하가 조용히 버려진다** (예: 250mg / 100mg = 2정, 50mg 유실). PRD 문구 "환산한 정 수"가 반올림·내림·거부 중 무엇인지 모호하므로 **임의 해석하지 않고** 8절 질문 1 로 확인을 요청한다 (BIZ-HG-2).
- 등급: Medium (0 케이스는 영향 범위 때문에 재평가 트리거와 함께 High 로 격상 가능)

## 8. 사용자 확인 필요 사항 (BIZ-HG-2: 임의 해석하지 않음)

1. **환산 규칙**: `doseMg` 가 `unitDoseMg` 의 배수가 아닐 때 "정 수"를 내림·올림·반올림·거부 중 무엇으로 할지.
2. **실패 건 저장 방식**: 예약 실패 일정을 `RETRY_PENDING` 으로 **일정 행은 저장하고 예약 ID 만 비움**으로 해석하는 것이 맞는지 (요건 2 "실패한 일정만 재시도 대상으로 표시" 기준).
3. **응답 계약**: 일부 실패 시 클라이언트에 어떤 응답(HTTP status·실패 목록)을 줄지. TDD 발췌에 없음.
4. **PushReserveException 외 예외**(타임아웃·기타 런타임)도 건 단위로 RETRY_PENDING 처리할지.

## 9. 범위 밖 발견 및 위임 안내

- 외부 호출(`pushClient.reserve`)이 DB 트랜잭션 안(`:25` 범위)에서 동기 실행되어, 푸시 서비스 지연 시 DB 커넥션 점유 시간이 길어진다 -> **java-performance-reviewer** 위임
- 트랜잭션 경계·빈 분리 구조(REQUIRES_NEW 별도 빈) 설계 -> **java-architecture-reviewer** 위임
- 위 관점까지 한 번에 보려면 **java-composite-reviewer** 로 조합 호출을 권장한다.
