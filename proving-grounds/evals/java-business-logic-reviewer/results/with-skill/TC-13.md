## 불변식 위반 (최우선)

- [BIZ-INVARIANT] `MedicationScheduleService.java:25`, `:32`, `:33` — 요건 2 위반. 실패 시 성공분이 유지되지 않음
  - 요건: I-1 "성공한 일정은 유지", I-2 "실패한 일정만 재시도 대상으로 표시"
  - 실제:
    - `:25` `@Transactional(rollbackFor = Exception.class)` 로 메서드 전체가 하나의 트랜잭션입니다.
    - `:32` `pushClient.reserve(...)` 의 `PushReserveException` 을 건 단위로 잡지 않아 루프가 중단됩니다.
    - 전체가 롤백되므로 앞서 `:31` 에서 저장한 일정과 `:33` 에서 저장한 예약 ID 가 모두 사라집니다.
    - `RETRY_PENDING` 으로 표시하는 코드는 이 변경에서 찾지 못했습니다.
  - 추가 영향 (RR-13): DB 는 롤백되는데 앞 건들의 푸시 예약은 외부 서비스에 이미 생성된 상태입니다. 예약 ID 를 DB 가 잃어 취소할 수 없고, 사용자에게는 "저장 실패"인데 알림은 발송될 수 있습니다. "깔끔한 전체 롤백"이 되지 않는 이유입니다. 실전 사례 #799 와 같은 유형입니다.
  - 등급: **AUTO FAIL / Critical**
  - 방향 (코드는 수정하지 않았습니다):
    - 건 단위 try/catch 로 `PushReserveException` 을 잡아 해당 일정을 `RETRY_PENDING` 으로 저장하고 나머지는 계속 진행합니다.
    - `rollbackFor = Exception.class` 가 요건과 충돌하는지, 외부 호출을 트랜잭션 밖으로 빼야 하는지는 설계 합의가 필요합니다. 제가 임의로 정하지 않았습니다.
    - 같은 트랜잭션 안에서 catch 할 때 `PushClient` 구현이 `@Transactional` 프록시를 거치면 rollback-only 가 걸릴 수 있어 확인이 필요합니다.
    - 일부 실패를 응답에 어떻게 알릴지(전체 200 + 실패 목록 등)는 PRD·TDD 에 없어 확인이 필요합니다.
