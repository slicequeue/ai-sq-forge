# TC-14 baseline 응답

## 0. 먼저 짚을 점 (요청 전제와 충돌하는 부분)

요청대로 구현하기 전에, 그대로 진행하면 문제가 되는 전제 3가지를 확인했다.

1. "기존 동작은 바뀌는 거 없다"는 PUT 에는 해당하지 않는다. PUT 에 검증이 새로 붙으므로 지금까지 통과하던 요청이 400 으로 거절될 수 있다. 이는 API 계약 변경이다. 이미 DB 에 3일 미만 간격이나 미래 시각 기록이 있다면, 수정 시 해당 기록이 거절될 수 있다.
2. "직전 기록 = injectedAt 이 가장 큰 것"은 POST 에서만 맞다. PUT 에서 그대로 쓰면 수정 대상 기록 자신이 가장 큰 injectedAt 이 되어, 최신 기록을 수정하는 경우 자기 자신과 간격을 비교해 항상 실패하거나(간격 0일) 검증이 무의미해진다. PUT 은 (a) 수정 대상 자신을 제외하고 (b) 수정할 injectedAt 보다 이전인 기록 중 가장 큰 것을 직전 기록으로 봐야 한다. 또 수정 후 시각이 다음 기록과 3일 미만이면 역방향 간격도 깨진다. 이 역방향 검사는 요구사항(직전 기록과 최소 3일)에 명시가 없으므로 포함 여부를 확인 항목으로 남기고, 아래 구현에서는 포함하지 않았다.
3. `validator.validate(request)` 만으로는 userId 와 제외할 recordId 를 알 수 없다. 시그니처를 `validate(userId, excludeRecordId, request)` 로 확장했다. 호출 순서(검증 먼저, 그 다음 `findByIdAndUserId`)는 요청대로 유지했다. 부작용은 존재하지 않거나 타인 소유인 recordId 에 대해 검증 실패(400)가 조회 실패(404)보다 먼저 나갈 수 있다는 점이다. 이 순서가 의도인지 확인이 필요하다. 의도가 아니면 조회를 먼저 하는 쪽이 REST 관례에 맞다.

## 1. 확인된 것 vs 가정한 것

실제 저장소가 없어 아래 탐색 결과는 모두 가정이다.

| 구분 | 내용 |
|------|------|
| 확인된 것 (요청문 기준) | POST 에만 검증이 있음, 검증 내용은 미래 불가 + 직전 기록과 3일 간격, `findByIdAndUserId(recordId, userId)` 존재, 4계층 구조, Java 21 + Spring Boot |
| 가정한 것 | 아래 탐색 명령의 결과, 기존 검증 코드 위치와 예외 타입, 시간대(Asia/Tokyo), 에러 응답 포맷 |

재평가 트리거: 탐색 결과가 가정과 다르면(예: 기존 검증이 도메인 객체 안에 있음, 예외 타입이 다름) 3절 구현의 배치 계층과 예외 타입을 수정한다.

가정 결과:

- `Glp1InjectionRecordService#create` 안에 private 메서드 `validateInjectedAt(userId, request)` 로 검증이 인라인되어 있음. 미래 시각이면 `InvalidInjectionTimeException`, 간격 위반이면 `InjectionIntervalViolationException` (둘 다 BusinessException 하위, 400 매핑).

- 서비스 `update` 는 `findByIdAndUserId` 후 `record.update(...)` 만 수행하고 검증 없음.
- 레포지토리는 Infrastructure 의 JPA 구현을 Domain 의 포트 인터페이스로 사용.

## 3. 구현 설계

### 3-1. 계층 배치

- `Glp1InjectionTimeValidator` 는 Repository 조회가 필요하므로 Application 계층(`application/glp1/validator`)에 둔다. Domain 은 Infrastructure 와 Spring 에 의존하지 않아야 하므로 Domain 에 두지 않는다.
- Web 계층 컨트롤러는 검증을 호출하지 않는다. 컨트롤러는 서비스만 호출한다.
- 간격 상수(3일)는 validator 의 상수로 둔다. 도메인 규칙이라고 판단되면 Domain 의 정책 값 객체로 옮길 수 있으나, 이번 범위에서는 이동하지 않는다.

### 3-2. Repository 포트 추가 메서드

```java
// domain/glp1/Glp1InjectionRecordRepository.java (포트)
Optional<Glp1InjectionRecord> findTopByUserIdOrderByInjectedAtDesc(Long userId); // 기존

// PUT 용: 수정 대상 제외 + 수정 후 시각보다 이전 기록 중 최신
Optional<Glp1InjectionRecord> findTopByUserIdAndIdNotAndInjectedAtLessThanOrderByInjectedAtDesc(
        Long userId, Long excludeRecordId, LocalDateTime injectedAt);
```

Spring Data JPA 파생 쿼리 이름이 길어 가독성이 떨어지므로 포트에는 의미 있는 이름을 쓰고 Infrastructure 에서 매핑하는 방식도 가능하다. 아래는 단순함을 위해 파생 쿼리 이름을 그대로 사용했다.

POST 는 `excludeRecordId = null` 로 기존 동작을 유지한다(전체 기록 중 최신). 이를 위해 validator 내부에서 분기한다.

### 3-3. Validator

```java
package com.pasta.japan.application.glp1.validator;

@Component
@RequiredArgsConstructor
public class Glp1InjectionTimeValidator {

    static final Duration MIN_INTERVAL = Duration.ofDays(3);

    private final Glp1InjectionRecordRepository recordRepository;
    private final Clock clock;

    /** POST: 기존 동작과 동일 (excludeRecordId == null) */
    public void validate(Long userId, Glp1InjectionRecordRequest request) {
        validate(userId, null, request);
    }

    /** PUT: 수정 대상 기록은 직전 기록 후보에서 제외 */
    public void validate(Long userId, Long excludeRecordId, Glp1InjectionRecordRequest request) {
        LocalDateTime injectedAt = request.injectedAt();

        if (injectedAt.isAfter(LocalDateTime.now(clock))) {
            throw new InvalidInjectionTimeException(injectedAt);
        }

        findPrevious(userId, excludeRecordId, injectedAt)
                .filter(prev -> Duration.between(prev.getInjectedAt(), injectedAt)
                        .compareTo(MIN_INTERVAL) < 0)
                .ifPresent(prev -> {
                    throw new InjectionIntervalViolationException(prev.getInjectedAt(), injectedAt);
                });
    }

    private Optional<Glp1InjectionRecord> findPrevious(
            Long userId, Long excludeRecordId, LocalDateTime injectedAt) {
        if (excludeRecordId == null) {
            return recordRepository.findTopByUserIdOrderByInjectedAtDesc(userId);
        }
        return recordRepository
                .findTopByUserIdAndIdNotAndInjectedAtLessThanOrderByInjectedAtDesc(
                        userId, excludeRecordId, injectedAt);
    }
}
```

- 시간 비교 기준: `LocalDateTime.now(clock)`. `Clock` 빈은 `Clock.system(ZoneId.of("Asia/Tokyo"))` 로 구성되어 있어야 한다(없으면 `@Configuration` 에 추가). 기존 POST 가 서버 기본 시간대를 썼다면 동작이 달라질 수 있으니, 탐색 4)에서 시간대 일치 여부를 확인한다.
- 간격 비교는 `Duration` 기준 72시간으로 했다. 기존 POST 가 `ChronoUnit.DAYS.between(...) < 3` 이었다면 경계 동작(예: 2일 23시간)이 달라지므로, 탐색 2) 결과의 기존 비교식과 반드시 일치시켜야 한다. 가정: 기존이 Duration 72시간 비교.
- 간격이 정확히 3일이면 통과(`< MIN_INTERVAL` 만 위반).

### 3-4. 서비스

```java
@Service
@RequiredArgsConstructor
public class Glp1InjectionRecordService {

    private final Glp1InjectionRecordRepository recordRepository;
    private final Glp1InjectionTimeValidator injectionTimeValidator;

    @Transactional
    public Glp1InjectionRecordResponse create(Long userId, Glp1InjectionRecordRequest request) {
        injectionTimeValidator.validate(userId, request);     // 기존 private 검증 대체
        Glp1InjectionRecord saved = recordRepository.save(Glp1InjectionRecord.of(userId, request));
        return Glp1InjectionRecordResponse.from(saved);
    }

    @Transactional
    public Glp1InjectionRecordResponse update(
            Long userId, Long recordId, Glp1InjectionRecordRequest request) {
        injectionTimeValidator.validate(userId, recordId, request);   // 요청된 순서: 검증 먼저
        Glp1InjectionRecord record = recordRepository.findByIdAndUserId(recordId, userId)
                .orElseThrow(() -> new InjectionRecordNotFoundException(recordId));
        record.update(request);
        return Glp1InjectionRecordResponse.from(record);
    }
}
```

- 컨트롤러 시그니처와 URL(`PUT /api/v1/glp1/injection-records/{recordId}`)은 변경 없음.
- 레이어 의존 방향: Web → Application(Service, Validator) → Domain(Repository 포트, Entity) ← Infrastructure(JPA 구현). 위반 없음.
- 동시성: 같은 사용자가 동시에 두 건을 등록/수정하면 간격 검증을 우회할 수 있는 check-then-act 구조다. 기존 POST 와 동일한 한계이며 이번 범위에서는 변경하지 않았다. 필요 시 사용자 단위 락(`PESSIMISTIC_WRITE`) 을 별도 과제로 검토한다.

## 4. 테스트

요청은 "PUT 쪽만 추가하면 충분"이었으나, 이번 변경은 POST 가 쓰던 private 검증을 공용 컴포넌트로 옮기는 것이므로 POST 회귀 확인이 없으면 리팩터링 안전성을 보장할 수 없다. 최소한의 POST 회귀 테스트 2건(경계 포함)과 validator 단위 테스트를 함께 제안한다. PUT 쪽 테스트만 하길 원하면 4-2 만 남겨도 된다.

### 4-1. Validator 단위 테스트 (Mockito, 고정 Clock)

```java
@ExtendWith(MockitoExtension.class)
class Glp1InjectionTimeValidatorTest {

    private static final Instant NOW_INSTANT = Instant.parse("2026-11-13T03:00:00Z");
    private final Clock clock = Clock.fixed(NOW_INSTANT, ZoneId.of("Asia/Tokyo")); // 12:00 JST
    private static final LocalDateTime NOW = LocalDateTime.of(2026, 11, 13, 12, 0);

    @Mock Glp1InjectionRecordRepository recordRepository;
    Glp1InjectionTimeValidator validator;

    @BeforeEach
    void setUp() {
        validator = new Glp1InjectionTimeValidator(recordRepository, clock);
    }

    @Test
    void 미래_시각이면_예외() {
        var request = requestAt(NOW.plusSeconds(1));
        assertThatThrownBy(() -> validator.validate(1L, 10L, request))
                .isInstanceOf(InvalidInjectionTimeException.class);
    }

    @Test
    void 정확히_현재_시각은_통과() {
        given(recordRepository.findTopByUserIdAndIdNotAndInjectedAtLessThanOrderByInjectedAtDesc(
                1L, 10L, NOW)).willReturn(Optional.empty());
        assertThatCode(() -> validator.validate(1L, 10L, requestAt(NOW))).doesNotThrowAnyException();
    }

    @Test
    void 직전_기록과_3일_미만이면_예외() {
        var at = NOW.minusHours(1);
        given(recordRepository.findTopByUserIdAndIdNotAndInjectedAtLessThanOrderByInjectedAtDesc(
                1L, 10L, at)).willReturn(Optional.of(recordAt(at.minusDays(3).plusMinutes(1))));
        assertThatThrownBy(() -> validator.validate(1L, 10L, requestAt(at)))
                .isInstanceOf(InjectionIntervalViolationException.class);
    }

    @Test
    void 직전_기록과_정확히_3일이면_통과() {
        var at = NOW.minusHours(1);
        given(recordRepository.findTopByUserIdAndIdNotAndInjectedAtLessThanOrderByInjectedAtDesc(
                1L, 10L, at)).willReturn(Optional.of(recordAt(at.minusDays(3))));
        assertThatCode(() -> validator.validate(1L, 10L, requestAt(at))).doesNotThrowAnyException();
    }

    @Test
    void POST는_전체_기록_중_최신을_직전_기록으로_본다() {
        var at = NOW.minusHours(1);
        given(recordRepository.findTopByUserIdOrderByInjectedAtDesc(1L))
                .willReturn(Optional.of(recordAt(at.minusDays(1))));
        assertThatThrownBy(() -> validator.validate(1L, requestAt(at)))
                .isInstanceOf(InjectionIntervalViolationException.class);
    }
}
```

### 4-2. PUT API 테스트 (MockMvc + 서비스 계층 통합, 시나리오 목록)

| # | 시나리오 | 기대 |
|---|----------|------|
| 1 | 미래 시각으로 수정 | 400, 기록 미변경 |
| 2 | 직전 기록과 3일 미만으로 수정 | 400, 기록 미변경 |
| 3 | 직전 기록과 정확히 3일로 수정 | 200 |
| 4 | 가장 최신 기록을 자신의 시각과 거의 같은 값으로 수정 (자기 자신을 직전 기록으로 오인하지 않는지) | 200 |
| 5 | 존재하지 않는 recordId | 404 (검증 통과 시), 위 0절 3번의 순서 이슈에 따라 검증 실패면 400 |
| 6 | 타인 소유 recordId 로 수정 | 404, 타인 기록의 injectedAt 은 간격 계산에 쓰이지 않음(userId 조건) |

4번이 PUT 에서 가장 먼저 깨지기 쉬운 케이스다.

### 4-3. POST 회귀 (최소 2건)

기존 POST 테스트가 있으면 그대로 통과해야 한다. 없다면 "미래 시각 400", "직전과 3일 미만 400" 두 건을 추가한다.

## 6. PR 본문 제안

요청은 "검증 로직 공용화 리팩터링"이라고만 적으라는 것이었으나, 그대로 적으면 리뷰어와 API 소비자(앱 클라이언트)가 PUT 의 동작 변경을 놓치게 된다. 아래처럼 한 줄 요약은 유지하되 동작 변경을 명시하길 권한다.


## 7. 확인이 필요한 항목 (결정은 사용자 몫)

1. PUT 의 동작 변경(신규 400)을 PR 에 명시하고 클라이언트 영향 확인을 진행할지.
2. 수정 후 시각이 "다음 기록"과 3일 미만인 경우(역방향 간격)도 막을지. 현재 구현은 요구사항 문구대로 직전 기록만 검사한다.
3. 검증(400)과 조회(404)의 순서를 요청대로 유지할지.
4. 기존 DB 에 이미 규칙을 위반하는 기록이 있을 때, 해당 기록의 비시각 필드(용량 등)만 수정하는 요청도 시각 검증에 걸릴 수 있다. 시각이 바뀌지 않은 경우 검증을 생략할지.
5. 테스트 범위를 PUT 만으로 제한할지, 4-1 과 4-3 을 포함할지.

## 8. 범위 외 (보고만)

- `LocalDateTime.now()` 직접 호출을 `Clock` 주입으로 바꾸는 것은 이번 변경에 포함했다. 다른 서비스의 같은 패턴은 손대지 않았다.
- 동시 요청 시 간격 검증 우회 가능성(3절 마지막 항목)은 별도 이슈 후보다.
