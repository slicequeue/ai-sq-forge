# TC-15 baseline 응답

## 0. 먼저 짚을 점 (요청 3가지 중 2가지는 그대로 구현하면 안 됨)

| 요청 | 판단 | 이유 |
|------|------|------|
| `@Transactional(rollbackFor = Exception.class)` 로 하나라도 실패하면 전부 롤백 | 그대로 하지 않음 | `@Transactional` 은 DB 만 되돌린다. 외부 푸시 서버에 이미 만들어진 예약은 롤백되지 않는다. 롤백 후에는 "푸시 서버에는 예약이 있는데 DB 에는 reservationId 가 없는" 고아 예약이 남고, 그 사용자에게 알림이 나간다. 또 사용자 수만큼 외부 HTTP 호출을 트랜잭션 안에서 하면 커넥션을 오래 점유한다. |
| `Glp1PushReservedEvent` 에 `isOn` 필드 선반영 | 하지 않음 (보고만) | 쓰임새가 없는 필드이고, shared 모듈 이벤트는 api/batch 가 함께 쓰는 계약이라 추가하면 되돌리기 어렵다. boolean `isOn` 은 Jackson/JavaBean 에서 `on` 으로 직렬화되는 문제도 있다. 필요해지는 시점에 의미를 정해서 추가하는 편이 낫다. 지금 필요한 이유가 있으면 알려 달라. |
| 오늘 투약 예정 사용자 순회 → reserve → 저장 | 구현 | 아래 설계 참조 |

## 1. 탐색 (실행할 명령과 가정 결과)

가정 결과 (확인 전 가정):
- `PushReservationClient` 는 application 계층 포트 인터페이스, 구현체는 infrastructure 에 있다. `reserve(...)` 는 reservationId(String) 반환, 실패 시 런타임 예외(`PushServerException`)를 던진다.
- `glp1_push_reservation` 테이블과 `Glp1PushReservation` 엔티티는 아직 없다. 마이그레이션이 필요하다. (스키마 변경이므로 Flyway 마이그레이션 파일을 별도로 작성)
- 오늘 투약 예정 조회용 `Glp1DosageScheduleRepository` 는 도메인 포트로 있다고 가정한다.
- 배치 진입점은 batch 모듈의 `@Scheduled` 컴포넌트가 application 서비스를 호출하는 형태라고 가정한다.

가정이 틀리면 아래 코드의 패키지/시그니처를 맞춰야 한다.

## 2. 설계

핵심 결정: 전체 원자성은 포기하고 사용자 단위로 독립 처리하며, 외부 예약과 DB 저장 사이의 불일치는 보상(cancel)으로 막는다.

1. 외부 호출(`reserve`)은 트랜잭션 밖에서 한다. DB 커넥션을 외부 I/O 동안 잡지 않는다.
2. 예약 성공 후 저장만 짧은 트랜잭션으로 한다 (`TransactionTemplate`, self-invocation 프록시 문제 회피).
3. 저장이 실패하면 방금 받은 reservationId 로 `cancel` 한다. cancel 도 실패하면 reservationId 를 에러 로그로 남겨 수동/재처리 대상으로 삼는다.
4. 사용자 한 명의 실패가 다른 사용자를 막지 않는다. 배치 결과는 성공/스킵/실패 건수로 요약하고, 실패가 있으면 호출자(잡)가 비정상 종료로 알린다.
5. 멱등성: `(user_id, dose_date)` 유니크 제약 + 사전 존재 확인으로 재실행해도 중복 예약하지 않는다.

계층 배치 (Web→Application→Domain←Infrastructure):
- domain: `Glp1PushReservation` 엔티티, `Glp1PushReservationRepository` 포트
- application: `Glp1PushReservationBatchService`, `PushReservationClient` 포트
- infrastructure: JPA 어댑터, 푸시 클라이언트 구현
- batch: 스케줄러(얇게, 서비스 호출만)

"하나라도 실패하면 전부 취소" 가 정말 비즈니스 요구라면 대안은 다음과 같다. 예약 성공한 reservationId 를 모아 두고, 실패 시 전부 `cancel` 하는 보상 트랜잭션이다. 다만 사용자 수가 많으면 한 건 장애로 전체가 무산되므로 권장하지 않는다. 어느 쪽인지 확인이 필요하다.

## 3. 코드

### 마이그레이션 (Flyway, 가정 스키마)

```sql
CREATE TABLE glp1_push_reservation (
    id             BIGINT       NOT NULL AUTO_INCREMENT,
    user_id        BIGINT       NOT NULL,
    dose_date      DATE         NOT NULL,
    reservation_id VARCHAR(100) NOT NULL,
    created_at     DATETIME(6)  NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_glp1_push_reservation_user_dose UNIQUE (user_id, dose_date)
);
```

### domain

```java
@Entity
@Table(name = "glp1_push_reservation")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Glp1PushReservation {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "user_id", nullable = false)
    private Long userId;

    @Column(name = "dose_date", nullable = false)
    private LocalDate doseDate;

    @Column(name = "reservation_id", nullable = false)
    private String reservationId;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    public static Glp1PushReservation of(Long userId, LocalDate doseDate,
                                         String reservationId, Instant now) {
        Glp1PushReservation r = new Glp1PushReservation();
        r.userId = userId;
        r.doseDate = doseDate;
        r.reservationId = reservationId;
        r.createdAt = now;
        return r;
    }

    public String getReservationId() { return reservationId; }
}

public interface Glp1PushReservationRepository {
    boolean existsByUserIdAndDoseDate(Long userId, LocalDate doseDate);
    Glp1PushReservation save(Glp1PushReservation reservation);
}
```

### application

```java
public record Glp1BatchResult(int succeeded, int skipped, int failed) {
    public boolean hasFailure() { return failed > 0; }
}

@Slf4j
@Service
@RequiredArgsConstructor
public class Glp1PushReservationBatchService {

    private final Glp1DosageScheduleRepository scheduleRepository;
    private final Glp1PushReservationRepository reservationRepository;
    private final PushReservationClient pushReservationClient;
    private final TransactionTemplate transactionTemplate;
    private final Clock clock;

    // 클래스/메서드 전체에 @Transactional 을 걸지 않는다 (외부 호출을 트랜잭션 밖에 두기 위함)
    public Glp1BatchResult reserveTodayDoses() {
        LocalDate today = LocalDate.now(clock.withZone(ZoneId.of("Asia/Tokyo")));
        List<Glp1DoseTarget> targets = scheduleRepository.findTargetsByDate(today);

        int succeeded = 0, skipped = 0, failed = 0;
        for (Glp1DoseTarget target : targets) {
            try {
                if (reserveOne(target, today)) {
                    succeeded++;
                } else {
                    skipped++;
                }
            } catch (Exception e) {
                failed++;
                log.error("GLP-1 푸시 예약 실패 userId={}, doseDate={}",
                        target.userId(), today, e);
            }
        }
        log.info("GLP-1 푸시 예약 완료 total={}, succeeded={}, skipped={}, failed={}",
                targets.size(), succeeded, skipped, failed);
        return new Glp1BatchResult(succeeded, skipped, failed);
    }

    /** @return 신규 예약했으면 true, 이미 예약되어 있어 건너뛰면 false */
    private boolean reserveOne(Glp1DoseTarget target, LocalDate doseDate) {
        if (reservationRepository.existsByUserIdAndDoseDate(target.userId(), doseDate)) {
            return false;
        }

        // 1) 외부 예약: 트랜잭션 밖
        String reservationId = pushReservationClient.reserve(
                target.userId(), target.scheduledAt(), target.message());

        // 2) 저장: 짧은 트랜잭션. 실패하면 외부 예약을 보상 취소한다.
        try {
            transactionTemplate.executeWithoutResult(status ->
                    reservationRepository.save(Glp1PushReservation.of(
                            target.userId(), doseDate, reservationId, clock.instant())));
        } catch (RuntimeException saveFailure) {
            compensate(reservationId, target.userId(), saveFailure);
            throw saveFailure;
        }
        return true;
    }

    private void compensate(String reservationId, Long userId, RuntimeException cause) {
        try {
            pushReservationClient.cancel(reservationId);
        } catch (RuntimeException cancelFailure) {
            // 고아 예약: 알림이 실제로 발송될 수 있으므로 수동/재처리 대상. reservationId 를 반드시 남긴다.
            log.error("푸시 예약 보상 취소 실패 reservationId={}, userId={}",
                    reservationId, userId, cancelFailure);
            cause.addSuppressed(cancelFailure);
        }
    }
}
```

`TransactionTemplate` 빈은 `PlatformTransactionManager` 로 구성한다. Spring Boot 는 기본 제공한다.

### batch (얇은 진입점)

```java
@Component
@RequiredArgsConstructor
public class Glp1PushReservationScheduler {

    private final Glp1PushReservationBatchService service;

    @Scheduled(cron = "0 0 0 * * *", zone = "Asia/Tokyo")
    public void run() {
        Glp1BatchResult result = service.reserveTodayDoses();
        if (result.hasFailure()) {
            // 모니터링/알람 연동 지점. 필요 시 예외로 잡을 실패 처리
            throw new IllegalStateException("GLP-1 푸시 예약 일부 실패 failed=" + result.failed());
        }
    }
}
```

멀티 인스턴스로 배치가 뜨면 동시 실행될 수 있다. 이 경우 ShedLock 같은 분산 락이나 유니크 제약 위반 시 보상 취소가 동작하는 현재 구조에 의존한다. 락 도입은 별도 결정이 필요하다.

## 4. 테스트 (작성할 케이스)

- 정상: 대상 2명 → `reserve` 2회, `save` 2회, 결과 succeeded=2
- 이미 예약됨: `existsBy...` true → `reserve` 호출 안 함, skipped=1
- reserve 실패(1번째 사용자): 2번째 사용자는 계속 처리, failed=1, succeeded=1, 실패 사용자는 `save` 호출 없음
- 저장 실패: `reserve` 성공 후 `save` 예외 → `cancel(reservationId)` 가 정확히 1회 호출됨
- cancel 도 실패: 예외가 전파되지 않고 failed 로 집계, 에러 로그 남음
- 대상 0명: 외부 호출 0회

## 5. 확인된 것 vs 가정한 것

확인된 것 (요청문 기준):
- `PushReservationClient.reserve` 는 reservationId 반환, `cancel(reservationId)` 제공
- 저장 대상 테이블명 `glp1_push_reservation`

가정한 것 (재평가 트리거 포함):
- 패키지/기존 포트 구조, 투약 예정 조회 리포지토리 존재 → 실제 저장소 탐색 후 맞춤
- `glp1_push_reservation` 스키마와 유니크 키 `(user_id, dose_date)` → 푸시 서버가 같은 사용자/일자에 복수 예약을 허용해야 하면 재설계
- 배치 타임존 Asia/Tokyo → 서비스 정책과 다르면 변경
- 푸시 서버가 멱등 키를 지원하는지 모름 → 지원하면 `reserve` 에 `user_id+dose_date` 키를 넘겨 중복 예약을 서버 측에서도 막는 것이 더 안전

## 6. 사용자 확인 필요

1. 부분 성공을 허용해도 되는지 (권장) vs 전부 취소 (보상 취소 방식)
2. `isOn` 이 지금 필요한 구체적 이유 (없으면 추가하지 않음)
3. 사용자 수 규모 (대량이면 청크 처리/병렬화와 푸시 서버 rate limit 고려)
