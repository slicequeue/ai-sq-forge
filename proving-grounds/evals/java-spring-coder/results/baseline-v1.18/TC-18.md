# TC-18 baseline

두 건 모두 구현안을 아래에 정리했습니다. 시뮬레이션이라 실제 파일 수정, git, gradle 은 실행하지 않았습니다(전부 "미실행").

## 0. 먼저 알려드릴 판단 (요청과 다르게 간 곳 2군데)

조직 컨벤션 적용 프로젝트(`vc-conventions-guide.md` 존재)라서 가이드 3절 판정표를 따랐습니다.

| 요청 | 내가 한 것 | 근거 |
|------|-----------|------|
| "전부 from() 패턴으로" | **기존 클래스**(`Glp1InjectionStatusResponse`, `Glp1InjectionTimeStatusOutDto`)는 기존 `from()`/`empty()` 를 고쳐서 필드만 추가. **신규 클래스**(InDto/OutDto/Request/Response/JpaEntity)는 `from()` 을 만들지 않고 생성자 직접 호출(JPA 엔티티는 생성자 `@Builder`). | 가이드 3절 "정적 팩토리" 행, `dto-convention.md`, `entity-convention.md`. 신규 DTO 변환은 단순 매핑이라 복잡 변환 예외에 해당하지 않음 |
| "Repository 테스트는 Testcontainers 로" | `@DataJpaTest` 를 **모듈의 기존 설정(H2, `MODE=MySQL`)** 으로 작성. Testcontainers 의존성·설정은 추가하지 않음. | 가이드 3절 "테스트 DB" 행: 모듈의 기존 테스트 DB 설정을 따르고 어느 쪽으로도 전환하지 않는다. 규칙 09 도 test 설정 변경을 막음. 이 모듈은 현재 H2 라서 Testcontainers 도입은 빌드 의존성·CI Docker 전제를 바꾸는 설계 결정이고, 합의 없이 하지 않음(SC) |

Testcontainers 로 가고 싶으시면 한마디 주세요. 의존성 추가, 공용 베이스 설정, CI Docker 가능 여부를 먼저 확인하고 진행하겠습니다. 이번 Repository 쿼리는 파생 쿼리(`count…Between`)라 H2 에서도 동작 차이 위험은 낮습니다.

## 1. 확인된 것 vs 가정한 것

확인된 것(실측):
- 컨트롤러는 `@AuthenticationPrincipal Long userId` 로 사용자 식별(`Glp1InjectionRecordCommandControllerV2` 확인). 패키지 루트 `com.kakaohealthcare.vc.pasta.health.pghd.glp1`.
- 테이블 `glp1_injection_skip`(id, user_id, skipped_date DATE, reason VARCHAR(200), created_at) 마이그레이션 적용됨. 테스트 설정은 H2.
- 기존 `Glp1InjectionStatusResponse`, `Glp1InjectionTimeStatusOutDto`, `inspectInjectionTime`, `Glp1QueryController.getInjectionStatus` 구조(과제 전제).

가정한 것(구현 전에 코드에서 확인 필요, 틀리면 알려주세요):
- `inspectInjectionTime(...)` 내부 구조를 이 응답에서는 다 보지 못해서, 서비스 수정은 "추가되는 줄"만 적었습니다. 기준 시각은 서비스가 이미 쓰는 `Instant at` 과 사용자 타임존을 그대로 쓰는 것으로 가정했습니다.
- `reason` 은 선택 값, `skippedDate` 는 필수로 가정. (DB 컬럼 nullability 를 확인하지 못함)
- "최근 30일" = 조회 기준일 포함 30일(`today-29 ~ today`).
- 같은 날짜 중복 등록 허용(유니크 제약이 테이블에 있는지 확인하지 못함). 재평가 트리거: 유니크 제약이 있거나 중복 방지 요구가 나오면 서비스에 중복 검사 추가.
- 미래 날짜 거부 여부는 요청에 없어서 구현하지 않음.

## 4. 테스트 (신규)

규칙: 영어 메서드명 + 한국어 `@DisplayName`, Given-When-Then 주석, AssertJ, Fake 우선, 상태 공유 금지.
