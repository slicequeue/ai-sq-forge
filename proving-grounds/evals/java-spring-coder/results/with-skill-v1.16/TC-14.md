대상: pasta-japan-server (Java 21 + Spring Boot, 4-Tier). 실제 저장소가 없으므로 코드는 응답 본문에만 제시하고, 탐색·테스트·lint 는 실행할 명령과 가정 결과를 적는다. 어떤 파일도 쓰지 않았고 커밋하지 않았다.

## 0. 먼저 알려야 할 것

요청대로 하지 않은 부분이 3곳, 요청에 없지만 넣은 것이 1곳 있다. 모두 java-spring-coder v1.16 의 하드 가드레일(RR-14, RR-F13, 의존성 규칙)이 근거다. 원하지 않으면 말해 달라.

| # | 요청 | 실제 구현 | 근거 |
|---|------|-----------|------|

### 작성 전 질문 5개 (RR §16)

1. **이 조회가 실패하면 사용자는 무엇을 보나**: 검증 쿼리 예외는 이 요청 하나만 500 이 된다. 다중 소스 조립 응답이 아니라 쓰기 요청 1건이므로 격리 대상이 아니다. 판정 실패를 통과시키지 않는다(RR-1 취지). 예외를 삼키지 않는다.
2. **외부 호출 후 DB 저장 실패**: 외부 호출 없음. 해당 없음.
3. **마스터 데이터 null·0·음수**: 마스터 데이터 없음. 단 요청의 `injectedAt` 이 null 이면 `@NotNull` 검증이 Controller 에서 먼저 막는다고 가정한다 (Request 의 `@Valid`). 아니면 `Objects.requireNonNull` 필요 -> 6번 명령으로 Request 확인.
4. **기존 경로 동작이 바뀌나**: **바뀐다.** PUT: 미래 시각·직전 기록 3일 미만 요청이 400. POST: 직전 기록 조회에 "현재 시각 이하"와 동점 id 기준이 붙는다. PR 본문에 적는다 (5절).
5. **분기를 깨뜨리면 실패하는 테스트가 모든 진입 경로에 있나**: POST·PUT 서비스 테스트와 validator 단위 테스트에 둔다. 깨뜨려 보는 확인 방법은 3.3절.

호출처 grep(Phase 0-9): 새 조회 2종은 POST·PUT 쓰기 경로에서만 호출된다. 홈·피드 조회에는 쿼리가 추가되지 않는다. 쓰기 요청당 쿼리가 POST 는 1회(기존과 동일), PUT 은 기존 1회(`findByIdAndUserId`) + 1회가 된다.

## 3. 구현 시뮬레이션 (실제 파일에는 쓰지 않음)

코드 생성 순서(Domain -> Infra -> Application -> Web -> 설정 -> Test Double -> Test)를 따른다. 기존 파일 수정은 `git status --short <경로>` 로 미커밋 변경을 먼저 확인하고(DW-1), 통째 덮지 않고 Edit 으로 해당 부분만 고친다(DW-3). 복수 기존 파일을 고치지만 일괄 스크립트 재작성이 아니고 1번 명령에서 작업 트리가 깨끗했으므로 HEAD 가 복구 지점이다(DW-4).

### 3.1 Domain

```java
// pghd/glp1/domain/Glp1InjectionTimePolicy.java (신규)
import java.time.Duration;
import java.time.Instant;

public final class Glp1InjectionTimePolicy {

    public static final Duration MIN_INJECTION_INTERVAL = Duration.ofDays(3);

    private Glp1InjectionTimePolicy() {
    }

    public static boolean isFuture(Instant injectedAt, Instant currentAt) {
        return injectedAt.isAfter(currentAt);
    }

    // 직전 기록보다 이른 시각은 간격이 음수이므로 최소 간격 미만으로 판정합니다.
    public static boolean isIntervalShorterThanMinimum(Instant previousInjectedAt, Instant injectedAt) {
        return Duration.between(previousInjectedAt, injectedAt).compareTo(MIN_INJECTION_INTERVAL) < 0;
    }
}
```

```java
// pghd/glp1/application/Glp1InjectionTimeValidator.java (신규)
import java.util.Optional;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

@Component
@RequiredArgsConstructor
public class Glp1InjectionTimeValidator {

    private final Glp1InjectionRecordRepository glp1InjectionRecordRepository;

    public void validate(Glp1InjectionTimeValidationInDto glp1InjectionTimeValidationInDto) {
        if (Glp1InjectionTimePolicy.isFuture(
                glp1InjectionTimeValidationInDto.injectedAt(),
                glp1InjectionTimeValidationInDto.currentAt())) {
            throw new Glp1InjectionFutureTimeException();
        }

        Optional<Glp1InjectionRecordEntity> previousGlp1InjectionRecordEntityOptional =
                findPreviousGlp1InjectionRecordEntity(glp1InjectionTimeValidationInDto);

        if (previousGlp1InjectionRecordEntityOptional.isPresent()
                && Glp1InjectionTimePolicy.isIntervalShorterThanMinimum(
                        previousGlp1InjectionRecordEntityOptional.get().getInjectedAt(),
                        glp1InjectionTimeValidationInDto.injectedAt())) {
            throw new Glp1InjectionIntervalTooShortException();
        }
    }

    private Optional<Glp1InjectionRecordEntity> findPreviousGlp1InjectionRecordEntity(
            Glp1InjectionTimeValidationInDto glp1InjectionTimeValidationInDto) {
        // 수정 대상 기록은 직전 기록 후보에서 뺍니다. 포함하면 자기 자신과의 간격으로 판정되기 때문입니다.
        if (glp1InjectionTimeValidationInDto.hasExcludedRecordId()) {
            return glp1InjectionRecordRepository.findLatestByUserIdAndInjectedAtLessThanEqualExcludingId(
                    glp1InjectionTimeValidationInDto.userId(),
                    glp1InjectionTimeValidationInDto.previousRecordSearchUpperBoundAt(),
                    glp1InjectionTimeValidationInDto.excludedRecordId());
        }
        return glp1InjectionRecordRepository.findLatestByUserIdAndInjectedAtLessThanEqual(
                glp1InjectionTimeValidationInDto.userId(),
                glp1InjectionTimeValidationInDto.previousRecordSearchUpperBoundAt());
    }
}
```

### 3.7 테스트가 실제로 무엇을 잡는지 (RR-12 일부러 깨뜨려 보기)

| 깨뜨리는 곳 | 실패해야 할 테스트 |
|-------------|--------------------|
| UpdateService 에서 validate 와 `findByIdAndUserId` 순서를 뒤집음 | `updateRecord_otherUsersRecordWithFutureInjectedAt_throwsNotFoundBeforeValidation` |
| validator 의 `ExcludingId` 분기를 제거 | `validate_updateExcludesOwnRecord_passes`, Infra `...ExcludingId_excludedRecord_isNotReturned` |
| `forUpdate` 의 상한을 `injectedAt` 에서 `currentAt` 으로 바꿈 | `validate_updateWithLaterRecordInStore_ignoresLaterRecord` |
| Policy 의 `< MIN` 을 `<= MIN` 으로 바꿈 | `isIntervalShorterThanMinimum_exactlyThreeDays_returnsFalse`, `validate_createExactlyThreeDaysAfterPrevious_passes` |
| CreateService 에서 validator 호출을 제거 | `createRecord_twoDaysAfterPrevious_...`, `createRecord_futureInjectedAt_...` |
| 쿼리의 `IdDesc` 를 제거 | `...sameInjectedAt_returnsLargerId` (MySQL 에서 항상 깨진다고 단정할 수 없으므로 유일한 id 기준을 실제 테스트로 고정) |
| UpdateService 의 `hasSameInjectedAt` 분기를 제거 | `updateRecord_unchangedInjectedAtOnLegacyShortIntervalRecord_updatesMemo` |

변이는 임시 편집 후 Edit 으로 원복한다. 이 작업 트리에는 미커밋 변경이 있으므로 `git checkout`/`git restore` 로 되돌리지 않는다(DW-1·DW-3). `git stash` 는 쓰지 않는다.

## 5. PR 본문 초안

커밋·PR 생성은 요청이 없었으므로 하지 않았다. 아래는 초안이다. 프로젝트의 PR_TEMPLATE.md 가 있으면 그 틀에 맞춘다.

제목 제안: `feat: 투약 기록 수정 API 에 투약 시각 검증 적용`
(동작이 바뀌므로 `refac:` 접두는 맞지 않는다. 브랜치는 `api/feat/...` 를 쓴다.)

```markdown
## 변경 내용
- 투약 시각 검증(미래 불가, 직전 기록과 최소 3일 간격)을 `Glp1InjectionTimeValidator` 로 분리했습니다.
- 등록(POST)과 수정(PUT /api/v1/glp1/injection-records/{recordId}) 이 같은 검증을 사용합니다.
- 판정 규칙(3일 상수, 미래·간격 판정)은 domain 의 `Glp1InjectionTimePolicy` 로 옮겼습니다.

## 기존 동작 변경 (리뷰 요청)
단순 공용화가 아니라 수정 API 의 동작이 바뀝니다.
- PUT: 투약 시각을 **미래**로 보내면 400 (`Glp1InjectionFutureTimeException`). 이전에는 통과했습니다.
- PUT: 투약 시각을 바꿔 **바로 앞 기록과 3일 미만**이 되면 400 (`Glp1InjectionIntervalTooShortException`). 이전에는 통과했습니다.
- PUT: 투약 시각이 **바뀌지 않은** 요청은 시각 검증을 하지 않습니다. 규칙 도입 전 기록의 메모 등 수정이 막히지 않게 하기 위한 결정입니다.
- PUT: 소유 확인(`findByIdAndUserId`) 후 입력 검증을 하므로, 남의 기록 id 는 입력 값과 무관하게 기록 없음으로 응답합니다.
- POST: 직전 기록 조회에 "현재 시각 이하"와 동점일 때 id 기준이 추가됐습니다. 이미 미래 시각으로 저장된 기록이 있는 사용자만 결과가 달라질 수 있습니다.
- 프론트: PUT 이 위 두 사유로 400 을 반환할 수 있습니다. 앱의 수정 화면이 POST 와 같은 에러 코드를 처리하는지 확인이 필요합니다.

## 직전 기록 정의
- 등록: 현재 시각 이하 기록 중 투약 시각이 가장 큰 1건 (동점이면 id 가 큰 건)
- 수정: 수정 대상 자신을 제외하고, 새 투약 시각 이하 기록 중 가장 큰 1건
- 수정 시 새 시각 **뒤**에 있는 기록과의 간격은 검증하지 않습니다 (후속 논의 필요).

## 쿼리 영향
- 새 조회 2종은 등록·수정 요청에서만 호출됩니다. 홈·피드 등 읽기 경로 호출 없음 (호출처 grep 확인).
- 수정 요청의 쿼리가 1회 늘어납니다 (시각이 바뀐 경우에만).
- `(user_id, injected_at)` 인덱스 사용을 전제로 합니다.

## 확인한 것 / 가정한 것
- 확인: (실제 실행 후 기록)
- 가정: 기존 규칙 도입 전 등록된 간격 위반 기록이 있을 수 있다고 보고 시각 미변경 요청은 검증하지 않았습니다. 운영 DB 에서 위반 건수가 0이면 이 예외는 제거해도 됩니다.
```
