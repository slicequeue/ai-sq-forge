# 유료화 인터셉터 — `@ApiGroup` 마킹 기반 선택 적용 설계

## Phase 0 — 확인된 것 vs 가정한 것

이번 응답은 설계 시뮬레이션이라 실제 저장소 파일을 조회하지 않았다. 그래서 아래 내용 중 다음은 **확인 없는 가정**이다. 실제 구현 전에는 반드시 확인이 필요하다.

| 항목 | 상태 |
|---|---|
| `@ApiGroup` + 인터셉터 조합 자체가 이 스킬 문서에 기존 사례(2026-07-07 GLOB-549 유료화 인터셉터)로 이미 기록돼 있음 | **확인됨** (SKILL.md v1.11 하드 가드레일) |
| pasta-api에 이미 `WebMvcConfigurer` 인터셉터 등록부가 있는지, 있다면 어디인지 | **가정** — 실제 구현 시 기존 `config/` 패키지를 먼저 grep 해서 새 인터셉터를 거기 추가할지 판단 필요 |
| `FEATURE_INTERNAL`이 정확히 무엇을 막는 로직인지 (내부망 IP, 서비스 간 인증 토큰, 특정 role 등) | **가정 불가 — 사용자 확인 필요** (아래 "확인이 필요한 지점" 참조) |
| 과금 판정 로직(`PricingAccessGate`) 내부 구현 — Redis/DB 조회 여부 | **가정** — 존재한다면 v1.10 3층 폴백 규칙 적용 대상 |

이 전제들이 실제와 다르면 아래 설계의 배치 위치·인터페이스가 달라질 수 있다.

---

## 설계

### 1. 마킹 어노테이션 — shared 모듈

인터셉터는 여러 모듈(api뿐 아니라 admin, batch 등)이 참조할 수 있어야 하므로 어노테이션 정의는 **shared 모듈**에 둔다. 파라미터는 문자열 리터럴이 아니라 **enum**으로 — 리네임 시 컴파일러가 잡아준다 (`java-spring-coder` v1.11 규칙, `safe-mass-rename`과도 연계).

```java
// shared/.../annotation/ApiGroupType.java
public enum ApiGroupType {
    FEATURE_FREE,
    FEATURE_PAID,
    FEATURE_INTERNAL
}

// shared/.../annotation/ApiGroup.java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface ApiGroup {
    ApiGroupType value();
}
```

### 2. 인터셉터 — api 모듈

`HandlerMethod.getMethodAnnotation(ApiGroup.class)`으로 마킹 여부를 판단한다. **마킹이 없는 API는 무조건 통과** — 이 인터셉터가 모든 요청 경로에 걸려도 기존 무료 API에는 영향이 없어야 하기 때문이다.

```java
@RequiredArgsConstructor
public class ApiGroupGateInterceptor implements HandlerInterceptor {

    private final PricingAccessGate pricingAccessGate;
    private final InternalAccessGate internalAccessGate;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        if (!(handler instanceof HandlerMethod handlerMethod)) {
            return true;
        }
        ApiGroup apiGroup = handlerMethod.getMethodAnnotation(ApiGroup.class);
        if (apiGroup == null) {
            return true; // 마킹 안 된 API는 그룹 판정 자체를 하지 않는다
        }
        return switch (apiGroup.value()) {
            case FEATURE_FREE -> true;
            case FEATURE_PAID -> pricingAccessGate.checkPaid(request);
            case FEATURE_INTERNAL -> internalAccessGate.checkInternal(request);
        };
    }
}
```

`FEATURE_FREE`를 그룹 값 자체로 두는 이유: 나중에 "이 API는 명시적으로 무료 그룹"이라는 걸 코드에서 바로 읽히게 하기 위함이다(문서화 목적). 로직상으로는 마킹 없음과 동일하게 항상 통과.

### 3. 인터셉터 등록

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    private final ApiGroupGateInterceptor apiGroupGateInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(apiGroupGateInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/actuator/**", "/api/swagger-ui/**");
    }
}
```

실제 구현 시에는 이 등록부를 새로 만들지, 기존 `WebMvcConfig`(있다면)에 추가할지를 먼저 확인해야 한다 — 없는 파일이라고 가정하지 않는다 (`destructive-write-guard` DW-2).

### 4. 컨트롤러 적용 예시

```java
@ApiGroup(ApiGroupType.FEATURE_PAID)
@PostMapping("/coupons/redeem")
public ResponseEntity<CouponRedeemResponse> redeem(...) { ... }

@ApiGroup(ApiGroupType.FEATURE_FREE)
@GetMapping("/coupons/{id}")
public ResponseEntity<CouponResponse> getCoupon(...) { ... }

// 마킹 자체를 생략해도 기본 통과 — 다만 신규 API는 의도 명시 차원에서 FEATURE_FREE라도 붙이는 걸 권장
```

### 5. 확인이 필요한 지점 (승인 전 진행하지 않음)

과금·접근 제어 로직이므로 `review-recurrence-guard` RR-1(장애 시 동작 명시)을 그대로 적용해야 한다. 다음 3가지는 **사용자 결정이 필요**하고, 결정 없이 임의로 정하지 않는다.

1. **`FEATURE_INTERNAL`의 실체**: 내부망 IP 화이트리스트인가, 서비스 간 인증 토큰인가, 특정 어드민 role인가? 요청 본문에 정의가 없어 가정할 수 없다.
2. **`PricingAccessGate.checkPaid` 판정 불가 시 동작**: 과금 판정 서버/캐시 조회가 예외를 던지면 열림(통과)인가 닫힘(차단)인가? 대칭성도 정해야 한다 — 지금 정하지 않으면 나중에 "무료 개방 사고"로 이어질 수 있다(RR-1 근거: #637/#641/#643).
3. **`checkPaid` 내부가 캐시를 쓴다면**: 이용권한류 정책 데이터이므로 v1.10 규칙상 Redis→DB→하드코딩 기본값 3층 폴백 대상 후보다. 다만 이건 `PricingAccessGate` 내부 구현 범위라 이번 설계(어노테이션+인터셉터)의 필수 요소는 아니다 — 별도 논의로 분리 제안.

이 세 가지에 답을 주시면 `checkPaid`/`checkInternal` 내부 구현까지 이어서 설계하겠다.

### 6. 테스트 전략 (Mode C에 해당하는 부분)

- **인터셉터 단위 테스트**: `MockHttpServletRequest` + 가짜 `HandlerMethod`로 3개 그룹(FREE/PAID/INTERNAL) 각각에 대해 `preHandle` 결과를 검증. `PricingAccessGate`/`InternalAccessGate`는 Fake로 대체.
- **경계 케이스**: 어노테이션 없는 핸들러, `handler`가 `HandlerMethod`가 아닌 정적 리소스 요청(예: `ResourceHttpRequestHandler`) — 둘 다 통과해야 함을 확인.
- **MockMvc 통합 테스트**: 실제 컨트롤러에 `@ApiGroup(FEATURE_PAID)`를 붙인 뒤, 과금 판정 결과에 따라 403/200이 실제로 나오는지 확인.
- **AssertJ만 사용, `@DisplayName` 한글 구체적 시나리오**로 작성 (예: "`FEATURE_PAID로 마킹된 API는 과금 판정 실패 시 차단된다`").
