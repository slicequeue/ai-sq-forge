## Phase 0. 사전 확인

1. **TDD 문서 탐색** — `docs/plans/*.md`, `docs/tdd/*.md` 확인 → 해당 요청에 대한 계획서 없음 → **모드 B(단순 구현)** 으로 진행
2. **JDK 확인** — `export JAVA_HOME=$(/usr/libexec/java_home -v 21)`
3. **admin 모듈 여부** — `users_device`, 로그인/로그아웃 관련 코드는 `admin/` 패키지가 아님 → 4-Tier 원칙 그대로 적용 (Controller/Thymeleaf 예외 없음)
4. **타 저장소 이식 여부** — 아님, 단일 저장소 내 작업
5. **기존 코드 패턴 파악** — `users_device` 관련 기존 Entity/Repository/Service/Controller, 그리고 로그인·로그아웃 처리 흐름을 먼저 읽었습니다.

## 전수 검색 결과 — 진행 전 확인이 필요합니다 (DW-6 / SC-3 / SC-4)

새 컬럼을 만들기 전에 동일 성격의 값이 이미 어디 있는지 전수 검색했습니다.

```bash
grep -rn "guid" --include=*.java --include=*.sql .
```

**확인된 사실**:

- `guid`(기기 식별 값)는 이미 `users_role_permission_policy`, `users_login_history` 두 테이블에 각각 저장되고 있습니다.
- 로그아웃 처리 코드 안에 해당 값을 **빈 문자열로 비우는 로직**이 존재합니다.

이 두 가지 때문에 "그냥 `users_device`에 컬럼 하나 추가"로 끝나는 작업이 아니라고 판단했습니다. 아래 3가지를 확인받고 싶습니다.

### 1) 세 번째 저장 위치가 맞는 방향인지

같은 성격의 값이 이미 2곳에 있는 상태에서 3번째 테이블에 또 저장하면, 세 값이 서로 어긋날 위험(정합성 붕괴)이 생깁니다. 다음 중 어느 쪽을 원하시는지 확인이 필요합니다.

| 옵션 | 내용 | 트레이드오프 |
|---|---|---|
| A. `users_device`를 새 SSOT로 신설 | 기기 단위 마스터 테이블을 새로 두고, 나머지 두 테이블은 이후 별도 작업으로 이 값을 참조하도록 정리 | 지금 요청 범위를 넘어서는 후속 리팩토링이 필요 (스코프 확장, 별도 승인 필요) |
| B. `users_device`에만 우선 추가, 동기화는 애플리케이션 레벨에서 처리 | 로그인 시점에 3곳에 동시 기록 | 갱신 지점이 3곳으로 늘어나 하나만 빠뜨려도 불일치 발생 |
| C. 기존 두 테이블 중 하나를 참조하도록 설계 변경 | 새 컬럼 대신 FK/조인으로 대체 | 이번 요청("컬럼 추가")과 다른 접근이라 재확인 필요 |

이 판단(신규 테이블/컬럼 신설)은 가드레일상 **합의 없이 진행할 수 없는 스키마 결정**이라 먼저 여쭤봅니다.

### 2) 로그아웃 시 guid를 비우는 로직을 어떻게 할지

이 로직이 지금처럼 남아있으면, `users_device.guid`를 새로 저장해도 **로그아웃마다 다시 비워져서 저장 자체가 무의미**해집니다. 이게 의도된 보안 정책(로그아웃 시 기기 신뢰 해제)인지, 아니면 원래 의도가 없었던 부수 효과인지 코드만 봐서는 확정할 수 없었습니다.

- 의도된 정책이라면 → `users_device.guid`도 로그아웃 시 함께 비울지, 아니면 "기기 식별"이라는 목적상 로그아웃과 무관하게 유지할지 결정이 필요합니다 (두 값의 용도가 다를 수 있음).
- 부수 효과(사실상 결함)라면 → 로그아웃 API 동작을 바꾸는 것이므로, 이 자체가 기존 API 응답/동작 변경에 해당해 승인이 필요합니다.

### 3) "관련 API도 손볼 데 있으면" 의 범위

말씀하신 관련 API 후보로 아래를 확인했습니다. 이 중 어디까지 이번 작업에 포함할지 확인 부탁드립니다.

- 로그인 API — `users_device.guid` 저장 시점 추가 필요 (거의 확실히 포함)
- 로그아웃 API — 위 2)번 결정에 따라 수정 여부 결정
- 기기 조회/관리 API가 있다면 응답 스키마에 `guid` 노출 여부 (PII 성격 값이라 응답 포함 여부는 별도 확인 필요)

## 위 사항이 확정되면 진행할 구현 계획 (개요)

아래는 **승인 후** 진행할 순서이며, 지금 시점에는 파일을 만들지 않았습니다.

1. **마이그레이션** — `db-migration` 규칙(RR-11)에 따라 애플리케이션 코드와 분리된 PR로 작성. 착수 전 `users_device`의 기존 마이그레이션 파일을 먼저 읽어 PK 타입·charset·`is_` 접두·인덱스 네이밍 패턴을 그대로 따릅니다. NOT NULL 여부는 옵션 A/B/C 결정에 따라 달라집니다.
2. **Domain** — `UserDeviceEntity`에 `changeGuid(...)` 형태의 상태 변경 메서드 추가, `Objects.requireNonNull` 검증 포함 (Setter 패턴 금지).
3. **Infrastructure** — `UserDeviceJpaEntity`에 `@Column(nullable = ...)` + `@NotNull` 병행 추가, `toEntity()`/`from()` 동기화.
4. **Application** — 로그인 플로우 Service에 guid 저장 오케스트레이션 추가. 로그아웃 Service는 2)번 결정 반영.
5. **Web** — 관련 Request/Response에 필드 추가가 필요하면 반영. guid는 기기 식별용 PII 성격이 있어 응답 노출은 최소화하고, 로그 본문에는 남기지 않습니다(마스킹).
6. **테스트** — Domain은 Fake, Web은 MockMvc, Infra는 Testcontainers(MySQL) 계층별로 작성.
7. **기존 파일 수정 전** — `LogoutService` 등 기존 파일을 고치기 전에 `git status --short <경로>`로 미커밋 변경 여부를 먼저 확인합니다(DW-1). 미커밋 변경이 있으면 중단하고 알립니다.
8. 구현 완료 후 `./gradlew :{module}:test` 실행, 실패 시 5회 미만 자동 수정 후에도 안 되면 중단·보고.
9. **커밋은 하지 않고 변경 사항만 보고**합니다(사용자 명시적 요청 시에만 커밋).

## 확인된 사실 vs 가정 분리

| 구분 | 내용 |
|---|---|
| 확인된 사실 | guid가 `users_role_permission_policy`, `users_login_history`에 이미 존재함 (grep 결과) |
| 확인된 사실 | 로그아웃 코드에 guid를 빈 문자열로 비우는 로직이 존재함 |
| 확인된 사실 | 해당 작업 대상은 admin 모듈이 아니며 TDD 계획서도 없음 (모드 B) |
| 가정(미확인) | 로그아웃 시 guid를 비우는 것이 의도된 보안 정책인지 여부 — 코드만으로 확정 불가, 확인 필요 |
| 가정(미확인) | `users_device`가 향후 SSOT가 되어야 하는지, 아니면 병행 저장으로 충분한지 — 설계 방향 미확정 |
| 가정(미확인) | 기기 조회/관리용 별도 API 존재 여부 — 이번 조사에서 특정하지 못함, 실제 저장소 기준 재확인 필요 |

## 결론

`users_device`에 guid 컬럼을 추가하는 작업 자체는 어렵지 않지만, **이미 같은 값이 2곳에 더 있고 로그아웃이 그 값을 비우는 상태**라, 그대로 진행하면 "컬럼은 생겼지만 로그아웃마다 비워져 쓸모없거나, 세 곳의 값이 서로 어긋나는" 결과가 될 가능성이 높습니다. 위 1)~3) 중 답을 주시면 그 결정에 맞춰 마이그레이션과 4-Tier 구현, 로그인/로그아웃 API 수정까지 이어서 진행하겠습니다.
