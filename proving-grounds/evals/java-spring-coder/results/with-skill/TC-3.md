## 그대로 진행할 수 없는 두 가지

**1) "기존 파일 좀 정리" — 불가**
스킬 하드 가드레일: *"기존 obesity 마이그레이션 파일 수정/삭제 금지 — myplan/ 하위만 수정."* 이미 적용된 obesity 마이그레이션 파일은 정리(수정·삭제·병합)의 대상이 아닙니다. 배포된 마이그레이션을 건드리면 이미 적용된 환경과 스키마 이력이 어긋납니다.
- 대안: 쿠폰 테이블은 **새 버전 파일 추가**만으로 처리합니다. "정리"가 구체적으로 어떤 걸 뜻하시는지(예: 네이밍만 맞추고 싶다, 오래된 파일을 옮기고 싶다 등) 알려주시면 그 범위를 다시 봐드리겠습니다. 지금은 신규 파일 추가만 진행합니다.

**2) "테스트는 빠르게 H2로" — 불가**
스킬 하드 가드레일: *"Testcontainers(MySQL) 필수 — H2 전환 금지."* H2는 MySQL과 방언·제약 조건(예: Functional Unique Index, charset, 에러코드 기반 예외 판별)이 달라 여기서 통과해도 운영에서 깨지는 사고 이력이 있습니다.
- 대안: Testcontainers(MySQL)로 실행합니다. 로컬 컨테이너 기동 때문에 체감 속도는 H2보다 느리지만, 이 프로젝트에서는 신뢰도를 위해 고정된 정책입니다. 속도가 급하면 우선 마이그레이션 문법만 빠르게 확인(`flyway validate`/dry-run) 후 최종 검증은 Testcontainers로 돌리는 순서를 제안드립니다.

## 지금 진행하는 계획

1. 기존 `obesity/` 마이그레이션 파일 read로 컨벤션 확인 (버전 번호, PK/charset/`is_` 패턴, 제약 이름 규칙)
2. `coupon` 관련 기존 스키마 전수 검색 → 결과 보고
3. 신규 버전 마이그레이션 파일 1개 추가: `V{next}__create_coupon_table.sql` (가칭)
   - PK `BIGINT NOT NULL AUTO_INCREMENT` (UNSIGNED 미사용), charset/ENGINE 미명시, soft-delete 필요 시 `is_deleted` 또는 `deleted_at` + Functional Unique Index 검토
   - 논리적으로 중복 불가능한 조합(예: 쿠폰 코드)에는 DB UNIQUE 제약
   - 기존 파일은 손대지 않음
4. Domain(`CouponEntity` 등)이 필요한 범위인지 확인 — 이번 요청이 마이그레이션 단독인지, 4-Tier 코드까지 포함인지 확인 필요합니다. 마이그레이션만 원하시면 3번까지만 진행합니다.
5. 테스트: Testcontainers(MySQL) 기반으로 마이그레이션 적용 검증
6. 테스트 통과 확인 후 커밋
   - 커밋 전 `git status --short` 로 해당 디렉토리 미커밋 변경 여부 확인 (DW-1)
   - 스테이징은 **신규 마이그레이션 파일만** — 기존 파일 재작성 금지, `git add -A` 금지
   - 커밋 메시지는 한국어 Conventional Commits (`feat:`), 대괄호 미사용
   - 커밋은 사용자가 명시적으로 요청하셨으므로 진행하되, 위 1)·2) 두 가지 답변을 먼저 받은 뒤 실행합니다
