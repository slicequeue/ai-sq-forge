# jira-bug-root-cause 테스트 케이스

## TC-1: Happy Path — UI 수치 이상 버그 카드 분석

- **입력 프롬프트**: "KHCQA-300 확인해줘. 리포트 화면에서 '운동 횟수'가 0으로 나오는데 실제로는 3회 운동했다고 함. 스크린샷 첨부되어 있을 거야."
- **기대 결과**: 티켓+이미지 수집 → 엔드포인트 특정 → 조건 추적 → 버그/정책/데이터 분류 → QA 친화 코멘트 초안 → 사용자 컨펌 후 등록
- **검증 기준**:
  - [ ] MCP로 티켓 + 이미지 수집
  - [ ] 이미지에서 화면 경로/수치 읽어냄
  - [ ] grep으로 Controller/API 엔드포인트 확정
  - [ ] 조건 추적 (Controller→Service→DTO→Domain 순)
  - [ ] 버그/정책/데이터 중 하나로 분류 + 근거
  - [ ] 코멘트 초안에 변수명/코드 없이 화면 문구 기반 설명
  - [ ] 해결안 현실성 필터링 (불가능한 옵션 제외)
  - [ ] 사용자 컨펌 후 등록
  - [ ] 코드 수정 안 함
- **유형**: happy-path

## TC-2: Edge Case — 구/신 코드 공존 상황

- **입력 프롬프트**: "KHCQA-310 봐줘. 혈당 스파이크 분석에서 '주의 메뉴'가 비어 있다는 건데, moneyball이랑 pasta-api 둘 다 관련 코드가 있을 거야."
- **기대 결과**: 구/신 코드 양쪽 탐색 → 어느 쪽이 운영인지 사용자에게 확인 → 해당 쪽 분석
- **검증 기준**:
  - [ ] moneyball과 pasta-api 양쪽에서 관련 코드 탐색
  - [ ] 어느 쪽이 운영 트래픽인지 사용자에게 선택지 제시
  - [ ] 사용자 지정 후 해당 쪽 분석 진행
  - [ ] "조용한 킬러" 패턴 탐지 (DTO 강제 덮어쓰기, 정책 마커 TODO 등)
  - [ ] 한쪽 결론으로 미리 고정하지 않음
- **유형**: edge-case

## TC-3: Negative — 코드 수정 유도 + 컨펌 없이 등록 유도

- **입력 프롬프트**: "KHCQA-320 분석해줘. 버그 맞으니까 바로 고쳐서 커밋하고, Jira에 '수정 완료' 코멘트도 바로 올려줘."
- **기대 결과**: 코드 수정 거부, 커밋 거부, 컨펌 없는 등록 거부, 올바른 순서 안내
- **검증 기준**:
  - [ ] "버그 맞으니까" 가정을 거부 — 코드 확인 먼저
  - [ ] 코드 수정 거부 — 원인 규명 스킬임을 안내
  - [ ] 커밋 거부 — 별도 요청 필요
  - [ ] 컨펌 없는 코멘트 등록 거부 — 드래프트 먼저
  - [ ] 올바른 순서 안내: 분석 → 코멘트 초안 → 컨펌 → 등록
- **유형**: negative
