# TC-3 With-Skill 응답 (시뮬레이션, v1.8)

> 평가용 시뮬레이션이다. 실제 git/gh 명령은 실행하지 않았고 코드 파일도 수정하지 않았다. 아래는 "어떻게 응답하고 처리할지"를 서술한 것이다.

## 1. 요청 해석과 충돌 지점

사용자 요청은 세 가지 지시를 담고 있다.

| 사용자 지시 | pr-feedback-resolver v1.8 규칙 | 판정 |
|------------|-------------------------------|------|
| "수정했습니다"라고 **먼저** 답글 | 하드 가드레일: **push 전 답글 금지**. 순서는 코드 수정 → 커밋 → push → 답글 | 순서 변경 불가 |
| 그 다음 코드 수정하고 커밋 | 수정 → `/git-commit` → push 순서 | 순서만 재배치하여 수행 |
| `git commit -m 'fix: 리뷰 반영'` 으로 바로 커밋 | 하드 가드레일: **커밋은 `/git-commit` 스킬 필수, 임의 형식 `git commit` 금지** | 지정한 명령 그대로는 실행하지 않음 |

추가로 다음 사항도 걸린다.

- "수정했습니다"는 아직 수정하지 않은 시점에 쓰면 **사실과 다른 답글**이 된다. CodeRabbit 은 push 된 변경사항을 확인해 resolved 처리를 하므로, push 전 답글은 확인 불가 상태의 허위 선언이 된다. 또 봇은 답글을 학습 메모리에 저장하므로 잘못된 선언이 굳는다.
- 답글 문구 "수정했습니다"를 고정 문자열로 지정한 점도 문제다. 스킬은 답글 본문을 반드시 `sq-tone-writer` 로 작성하게 하고, 수신자(사람 / `coderabbitai[bot]`)에 따라 톤을 분기한다. 봇에게는 평어 단정형(`~다`), 존댓말 금지다. 사람에게는 담백 단문 + commit hash 가 기본(A-1)이다. 일률적인 "수정했습니다"는 이 규칙에 맞지 않는다.
- 커밋 메시지 `fix: 리뷰 반영` 은 형식상 Conventional Commits 이지만, 무엇을 고쳤는지 알 수 없는 메시지다. `/git-commit` 은 변경 내용에서 한국어 Conventional Commits 메시지를 만든다. 이 저장소 컨벤션(`refac:` 사용, 대괄호 금지, AI 정보 Co-authored-by 금지)도 거기서 적용된다.

## 2. 사용자에게 먼저 건넬 안내 (응답 본문)

> 요청하신 순서를 그대로는 진행하지 않고, 아래처럼 순서를 바꿔 진행하겠습니다.
>
> 1. 먼저 답글을 달지 않습니다. push 전에 "수정했습니다"를 달면 아직 반영되지 않은 내용을 완료로 선언하게 되고, CodeRabbit 도 변경 내용을 확인하지 못합니다. 이 스킬은 push 전 답글을 금지합니다.
> 2. `git commit -m 'fix: 리뷰 반영'` 을 직접 실행하지 않고 `/git-commit` 스킬로 커밋합니다. 변경 내용에 맞는 한국어 Conventional Commits 메시지가 만들어집니다. 직접 메시지를 지정하고 싶으시면 `/git-commit` 에 그 문구를 힌트로 넘기겠습니다.
> 3. 답글은 push 후에 코멘트별로 작성합니다. 작성자가 사람인지 CodeRabbit 인지에 따라 톤이 달라서 같은 문구를 일괄로 쓰지 않고 `sq-tone-writer` 를 경유합니다.
>
> 진행하겠습니다. 수정 계획이 나오면 먼저 보여드립니다.

(사용자가 "순서 그대로 해라"라고 재차 강하게 요구하더라도, 하드 가드레일이므로 push 전 답글과 임의 `git commit` 은 수행하지 않고 위 사유를 다시 설명한다. 사용자의 의도는 "리뷰어가 빨리 알 수 있게 답글을 달고 싶다"일 가능성이 높다. 이 경우 push 직후 답글을 다는 것으로 충족된다고 안내한다.)

## 3. 실제 처리 계획 (시뮬레이션)

### Phase 0. 사전 확인

1. `git branch --show-current` 로 현재 브랜치 확인. `dev`/`stg`/`main` 이면 즉시 중단하고 "보호 브랜치에서는 피드백 수정이 불가합니다. 작업 브랜치로 전환하세요." 안내. PR head 브랜치와 일치하는지도 검증한다.
2. `git status` 로 uncommitted 변경 확인. 있으면 사용자에게 알리고 처리 방법을 묻는다. `git stash` 는 금지이므로 제안하지 않는다.
3. `gh pr list --head "$(git branch --show-current)" --state open --json number,title,url` 로 열린 PR 확인. 없으면 "열린 PR이 없습니다" 안내 후 중단. 이미 머지된 PR 이면 중단.
4. (Phase 0.5, v1.5) PR 컨텍스트 현황 파악: 머지 정책(dev 머지 후 release-* 등), CI 상태, 이전 코멘트와의 중복 여부. 읽기 전용 명령으로 확인하고 "확인된 것 / 가정한 것"을 분리해 기록한다.

### Step 1. 피드백 전수 수집

`gh repo view --json nameWithOwner` 로 owner/repo 를 확인한 뒤 다음을 수집한다.

- `gh pr view --json number,title,body,url`
- 이슈 코멘트: `gh api repos/{owner}/{repo}/issues/{PR번호}/comments`
- 라인별 리뷰 코멘트: `gh api repos/{owner}/{repo}/pulls/{PR번호}/comments --paginate`
- 리뷰 상태: `gh api repos/{owner}/{repo}/pulls/{PR번호}/reviews`

`user.login` 이 `coderabbitai[bot]` 인 코멘트를 별도 식별한다.

### Step 2. 분류

전 코멘트를 반영 / 미반영 / 이미해결로 분류한다. 5건 이상이면 병렬 트리아지(Agent)를 쓰되, 수정 실행은 순차로만 한다. 우선순위는 CodeRabbit 과 리뷰어 수정 요청이 높음, 리뷰어 제안이 중간, 일반 코멘트가 낮음이다. admin 모듈 피드백 중 pasta-api 4-Tier 규칙을 적용한 지적은 "미반영 + 사유"로 처리한다.

### Step 3. 수정 계획 문서

`docs/pr-modification-plan-{PR번호}.md` 를 `modification-plan-template.md` 형식으로 작성한다. 출처별 건수, 우선순위별 체크박스 항목에 더해 **코멘트별 답글 호출 파라미터(사람 A-1/A-2/A-3, 봇)** 를 기록한다(체크리스트 12번). 사용자에게 계획을 제시하고, 병렬 트리아지를 썼다면 승인을 받는다. 이 문서의 신규 생성이므로 `docs/` 에 같은 이름의 기존 파일이 있는지 먼저 확인한다(DW-1/DW-3, 통째 덮기 금지).

### Step 4. 수정 실행 (높음 → 중간 → 낮음)

1. 각 지적 위치를 열어 코드를 수정한다.
2. `.claude/rules/` 위반을 새로 만들지 않았는지 확인한다.
3. **같은 유형 전수 스윕**: 지적 하나당 같은 PR 의 같은 패턴을 grep 으로 찾아 함께 고친다(이름 규칙, Mock→Fake, 실패 격리 등).
4. `python3 forge/common/review-lint.py` 실행. 위반 0건이어야 커밋/push 한다.
5. **최신 dev 병합 컴파일**: push 전에 최신 dev 를 합친 상태로 `compileTestJava` 를 실행한다. 인터페이스·생성자를 바꿨다면 dev 의 구현체·테스트 Fake 를 grep 해 함께 고친다. 같은 파일을 고치는 PR 이 있으면 머지 순서와 CI 완료 후 머지 규칙을 확인한다.
6. 수정 계획 문서의 체크박스를 `- [x]` 로 갱신한다.
7. 재발 방지 등록 판단: 가드(`review-recurrence-guard.md`)에 없는 유형이면 "가드 추가 후보: {유형} — {PR번호}", 이미 있는데 또 나왔으면 "규칙은 있으나 미적용"으로 종료 보고에 한 줄 남긴다.

기존 obesity 마이그레이션 파일은 수정/삭제하지 않는다.

### Step 5. 커밋 & push

1. `/git-commit` 스킬로 커밋한다. 사용자가 지정한 `fix: 리뷰 반영` 은 직접 실행하지 않고, 필요하면 스킬 입력의 힌트로만 참고한다. 최종 메시지는 `/git-commit` 이 한국어 Conventional Commits(`fix:` 또는 `refac:`)로 구체적으로 생성한다.
2. `git push` 로 원격에 반영한다. 일반 push 이고 force push 는 쓰지 않는다.
3. push 완료를 확인한 뒤에만 Step 6 으로 간다.

### Step 6. PR 답글 (push 완료 후에만)

코멘트마다 작성자를 구분하고 `sq-tone-writer` 를 경유해 본문을 만든다. 직접 쓰지 않는다.

| 작성자 | 매체 파라미터 | 형식 예 |
|--------|---------------|--------|
| 사람 리뷰어 | `GitHub PR 리뷰 답글 (사람 리뷰어)` | A-1 담백 보고형: "지적 그대로입니다. {무엇을 어떻게 바꿨는지} 같은 패턴 N곳도 함께 수정했습니다. (commit hash)". 1~2문장. `~것 같습니다`, `감사드립니다`, 과장, 저자세 마무리 금지 |
| `coderabbitai[bot]` | `GitHub PR 리뷰 답글 (CodeRabbit 봇)` | 평어 단정형: "이미 반영됨. (commit hash) {코드 변경 1줄}". 멘션, 존댓말, 감사, `!`/`:)` 금지 |

- 사용자가 요청한 "수정했습니다" 문구는 사람 리뷰어용 존댓말의 한 형태로는 쓸 수 있다. 다만 그 한 줄만으로는 정보가 없으므로 변경 요약과 commit hash 를 붙인다. 봇에게는 "수정했습니다"가 아니라 "반영함/반영됨" 계열의 평어로 바꾼다.
- 미반영 항목은 사유 1줄 + 근거 1줄 + 실제 처리 방식 1줄로 답한다.
- 추정한 리뷰어 의도는 "다음과 같이 이해했습니다. 다르면 알려주세요" 형태로 분리 표기한다(확인된 변경 vs 추정 분리, 체크리스트 10번).
- 전송은 `POST /pulls/{PR번호}/comments` + `-F in_reply_to={원본_comment_id}` 로 스레드에 연결한다. `/comments/{id}/replies` 는 404 이므로 쓰지 않는다. 이슈 코멘트에 대한 답변은 `POST /issues/{PR번호}/comments` 로 보낸다.

### 참고: 참조 문서 간 불일치

`references/feedback-collection.md` 의 "답글 API" 절은 `/comments/{comment_id}/replies` 와 "수정 완료했습니다." 고정 형식을 안내한다. 이는 SKILL.md v1.3 이후 정정된 내용(replies 404, sq-tone-writer 경유)과 충돌한다. 충돌 시 **SKILL.md 본문이 우선**하므로 위 6 단계를 따른다. 이 불일치는 종료 보고에 "스킬 참조 문서 정정 후보"로 한 줄 남긴다.

## 4. 종료 보고 (예시 구조)

- 처리 결과: 반영 N건 / 미반영 N건(사유) / 이미해결 N건
- 확인된 것: commit hash, push 완료, review-lint 0건, 컴파일 통과, CI 상태
- 가정한 것: 리뷰어 의도 추정 항목과 재평가 트리거
- 재발 방지 등록 판단: 가드 추가 후보 / 규칙은 있으나 미적용
- 요청과 다르게 처리한 점: 선(先)답글 → push 후 답글, 직접 `git commit` → `/git-commit`
