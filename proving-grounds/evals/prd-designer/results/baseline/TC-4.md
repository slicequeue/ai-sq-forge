# [PRD] 레이스 자동 완료 기능

| 항목 | 내용 |
|------|------|
| 문서 상태 | 초안 (기획팀 리뷰용) |
| 대상 서비스 | pasta-japan-server (레이스·챌린지 도메인) |
| 작성 목적 | 종료일이 지난 레이스를 시스템이 자동으로 완료 처리하도록 하는 기능의 요구사항 정리 |

기획팀 여러분께, 바쁘신 중에 리뷰해 주셔서 감사드립니다. 배경부터 차근차근 말씀드리고, 결론과 요약은 문서 마지막에 정리하였습니다.

---

## 1. 배경

### 1.1 현재 운영 방식

현재 레이스는 종료일이 지나더라도 시스템이 상태를 자동으로 바꾸지 않습니다. 운영팀이 종료일이 지난 레이스를 찾아 수동으로 "완료" 처리하고 있습니다.

### 1.2 문제 상황

- 매일 약 50건의 수작업이 발생하고 있습니다.
- 처리가 누락되면 이미 종료된 레이스가 진행 중인 것처럼 사용자에게 노출되는 등 잘못된 상태가 보입니다.
- 운영팀의 반복 업무 부담이 크고, 사람이 하는 작업이므로 누락 가능성을 구조적으로 없애기 어렵습니다.

### 1.3 확인된 사실과 가정

| 구분 | 내용 |
|------|------|
| 확인된 사실 (요청자 제공) | 종료일 경과 레이스를 운영팀이 수동 완료 처리함 / 일 50건 내외 / 누락 시 사용자에게 잘못된 상태 노출 |
| 가정 (리뷰에서 확인 필요) | 아래 3.3, 8장의 열린 질문 참조. 실제 저장소·DB 현황은 확인하지 않았으며, 레이스 상태값과 종료일 컬럼 명칭은 가정입니다. |

## 2. 목표와 비목표

### 2.1 목표

1. 종료일이 지난 레이스를 운영팀 개입 없이 자동으로 완료 상태로 전환한다.
2. 종료일 경과 후 완료 처리까지의 지연을 정해진 허용 시간 이내로 줄인다.
3. 운영팀의 일일 수작업을 0건에 가깝게 만들고, 누락으로 인한 사용자 노출 오류를 없앤다.

### 2.2 비목표

- 레이스 순위 산정 방식 변경
- 보상·리워드 정책 변경 (자동 완료와 연계되는 후속 처리는 8장에서 확인)
- 운영팀의 수동 완료 기능 제거 (예외 상황 대응용으로 유지)

## 3. 사용자와 시나리오

### 3.1 이해관계자

| 이해관계자 | 관심사 |
|------------|--------|
| 운영팀 | 수작업 제거, 예외 건 확인 수단 |
| 앱 사용자 | 정확한 레이스 상태 표시 |
| 기획팀 | 완료 시점 정책, 사용자 경험 |
| 서버 개발팀 | 안정적 배치 동작, 장애 시 복구 |

### 3.2 주요 시나리오

1. 종료일이 지난 레이스가 정해진 주기 내에 자동으로 완료 처리된다.
2. 자동 처리 중 일부 레이스에서 오류가 발생해도 나머지 레이스는 정상 처리되고, 실패 건은 운영팀이 확인할 수 있다.
3. 운영팀이 이미 수동으로 완료한 레이스는 자동 처리 대상에서 제외되며 중복 처리되지 않는다.
4. 서버 장애 등으로 자동 처리가 일시 중단되었다가 재개되면, 밀린 레이스가 모두 처리된다.

### 3.3 가정 사항

- 완료 판단 기준은 "종료일이 현재 시각보다 이전이고 상태가 진행 중인 레이스"로 가정합니다.
- 종료일의 기준 시간대(예: 일본 표준시)는 확정이 필요합니다.

## 4. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-1 | 시스템은 종료일이 경과했고 아직 완료되지 않은 레이스를 주기적으로 조회하여 완료 상태로 전환한다. | 필수 |
| FR-2 | 이미 완료된 레이스에 다시 실행해도 결과가 달라지지 않는다(멱등). | 필수 |
| FR-3 | 한 건의 처리 실패가 다른 레이스 처리에 영향을 주지 않는다. | 필수 |
| FR-4 | 실패한 건은 다음 실행 주기에 재시도된다. | 필수 |
| FR-5 | 자동 완료 결과(처리 건수, 실패 건수, 실패 레이스 식별자)를 로그와 알림으로 확인할 수 있다. | 필수 |
| FR-6 | 다중 서버 인스턴스 환경에서 동일 레이스가 중복 처리되지 않는다. | 필수 |
| FR-7 | 운영팀의 수동 완료 기능은 유지하며, 수동·자동이 충돌하지 않는다. | 필수 |
| FR-8 | 자동 완료 기능을 설정으로 켜고 끌 수 있다(점진 배포 및 긴급 중단용). | 권장 |

## 5. 비기능 요구사항

- 신뢰성: 서버 재기동, 일시 장애 후에도 누락 없이 따라잡아 처리한다.
- 성능: 일 50건 규모에서는 부하가 미미하나, 향후 증가에 대비해 건수 상한 있는 배치 단위로 처리한다.
- 관측 가능성: 실행 시작·종료, 처리 건수, 실패 사유를 기록한다.
- 시간 기준: 종료일 비교는 단일 시간대 기준으로 통일하며 시스템 시계에 직접 의존하지 않고 주입 가능한 시계를 사용해 테스트 가능하게 한다.

## 6. 성공 지표

| 지표 | 현재 | 목표 |
|------|------|------|
| 운영팀 일일 수동 완료 건수 | 약 50건 | 0건 (예외 건 제외) |
| 종료일 경과 후 미완료 상태 노출 건수 | 누락 시 발생 | 0건 |
| 종료일 경과 후 완료 처리까지 지연 | 운영팀 처리 시점에 따라 상이 | 주기 1회 이내(예: 최대 10분, 확정 필요) |
| 자동 처리 실패율 | 해당 없음 | 1% 미만, 실패 건은 다음 주기 내 재처리 |

## 7. 범위와 단계

| 단계 | 내용 |
|------|------|
| 1단계 | 자동 완료 배치 구현, 기능 스위치, 결과 로그·알림. 처음에는 운영팀 수동 처리와 병행하여 결과 대조 |
| 2단계 | 대조 결과 일치 확인 후 수동 처리 중단, 예외 건만 수동 대응 |

## 8. 열린 질문 (기획팀 확인 요청)

1. 완료 처리 시각의 허용 지연은 어느 정도가 적절한지요(즉시, 수 분, 익일 0시 등)?
2. 종료일의 기준 시간대와 "종료일 당일 포함" 여부는 어떻게 정의하는지요?
3. 레이스 완료 시 후속 처리(순위 확정, 보상 지급, 푸시 알림 등)가 이미 존재하는지, 자동 완료 시에도 동일하게 실행해야 하는지요?
4. 종료일이 지났으나 참가자가 없거나 조건 미달인 레이스도 동일하게 완료 처리하는지요?
5. 자동 처리 실패 시 알림 대상과 채널은 어디로 하는지요?
6. 운영팀이 의도적으로 종료를 보류하는 레이스(연장 등)가 있는지요? 있다면 제외 방법이 필요합니다.

## 9. 리스크와 대응

| 리스크 | 대응 |
|--------|------|
| 완료 시 후속 처리(보상 등)가 중복 실행됨 | 멱등 설계, 상태 전환과 후속 처리의 경계 명확화 |
| 잘못된 종료일 데이터로 조기 완료됨 | 1단계 병행 운영으로 대조, 기능 스위치로 긴급 중단 |
| 다중 인스턴스 동시 실행 | 중복 실행 방지 장치(분산 락 또는 조건부 갱신) 적용 |
| 시간대 혼선 | 기준 시간대를 확정하고 테스트로 경계값 검증 |

## 10. 결론 및 요약

- 문제: 종료일이 지난 레이스를 운영팀이 매일 약 50건 수동 완료 처리하며, 누락 시 사용자에게 잘못된 상태가 노출됩니다.
- 제안: 종료일이 경과한 미완료 레이스를 주기적으로 자동 완료하는 기능을 도입합니다. 멱등성, 건별 실패 격리, 재시도, 중복 실행 방지, 결과 알림을 필수 요건으로 합니다.
- 기대 효과: 운영팀 수작업 제거, 누락으로 인한 상태 오류 제거.
- 진행 방식: 1단계에서 수동 처리와 병행 대조 후, 2단계에서 수동 처리를 중단합니다.
- 리뷰 요청: 8장의 열린 질문 6건(허용 지연, 시간대, 후속 처리, 대상 범위, 알림 대상, 보류 레이스)에 대한 기획팀의 확정이 필요합니다.
