# PRD: 챌린지 3일 미기록 독려 알림

**결론: 챌린지 참여 중 3일 연속 미기록 회원에게 3일째 저녁 독려 푸시를 1회 발송해 중도 포기율(현재 60%)을 낮춘다. 하루 약 2천 명 대상이며, 기존 푸시 인프라로 처리 가능한 규모다.**

## 1. 배경과 문제

- 챌린지 참여 중 3일 연속 기록이 없는 회원의 60%가 중도 포기한다.
- 3일 미기록 시점이 이탈 직전 마지막 개입 지점이라고 판단한다.
- 현재 이 구간에서 회원에게 가는 안내는 없다.

## 2. 목표와 성공 지표

| 구분 | 지표 | 목표 |
|---|---|---|
| 핵심 | 알림 수신군의 3일 미기록 후 중도 포기율 | 60% → 50% 이하 (가설, 대조군 비교로 검증) |
| 보조 | 알림 수신 후 24시간 내 기록 재개율 | 측정 후 기준선 설정 |
| 가드레일 | 푸시 수신 거부(옵트아웃) 증가율 | 발송 전 대비 유의한 증가 없음 |

## 3. 대상과 발송 조건

- 대상: 진행 중인 챌린지에 참여하고, 마지막 기록 이후 3일 연속 기록이 없는 회원.
- 규모: 하루 약 2천 명 예상(가정, 출시 전 실측 필요).
- 발송 시점: 3일째 저녁 (제안 19:00 KST, 확정 필요).
- 발송 횟수: 챌린지 참여당 최대 1회. 이후 재발송 없음.
- 제외: 푸시 수신 동의하지 않은 회원, 이미 종료·포기 처리된 챌린지, 당일 이미 기록한 회원.
- 발송 직전에 미기록 상태를 다시 확인한다(배치 계산 후 기록한 회원에게 발송 방지).

## 4. 기능 요구사항

- FR-1: 매일 지정 시각 직전에 대상자를 조회하는 배치를 실행한다.
- FR-2: 대상자에게 푸시 알림 1건을 발송하고 발송 이력을 저장한다.
- FR-3: 챌린지 참여 건 단위로 발송 이력을 확인해 중복 발송을 막는다(멱등).
- FR-4: 알림 탭 시 해당 챌린지의 기록 화면으로 이동한다(딥링크).
- FR-5: 기능 on/off와 발송 시각을 서버 설정으로 바꿀 수 있다.

## 5. 알림 문구(안)

- 제목: 챌린지가 기다리고 있어요
- 본문: {닉네임}님, 3일째 기록이 없어요. 오늘 가볍게 한 번만 기록해 볼까요?
- 문구는 압박·죄책감을 주는 표현을 피한다. 건강 관련 수치나 질환 언급은 넣지 않는다.

## 6. 비기능 요구사항

- 발송 실패 시 재시도하되 같은 참여 건에 중복 발송이 생기지 않아야 한다.
- 배치가 중간에 실패해도 재실행 시 이미 발송한 건은 건너뛴다.
- 2천 건 발송은 발송 시각 기준 30분 이내 완료한다(제안).
- 알림 발송이 챌린지 기록 API 성능에 영향을 주지 않도록 분리 실행한다.

## 7. 측정과 검증

- 이벤트: 알림 발송, 수신 확인(가능 시), 탭, 24시간 내 기록, 7일 내 챌린지 이탈.
- 검증 방식: 대상자 일부(예: 10%)를 대조군으로 두고 2주간 비교한다.
- 대조군 운영 여부는 팀 합의가 필요하다(오픈 이슈 참조).

## 8. 범위 밖

- 2회 이상 반복 알림, 4일차 이후 단계별 알림.
- 개인화 시간대 최적화, 이메일·SMS 등 푸시 외 채널.
- 알림 문구 A/B 테스트(1차 이후 검토).

## 9. 리스크

- 야간·부적절 시간 발송 시 수신 거부 증가 가능. 발송 시각을 저녁 고정으로 제한한다.
- 개인정보·건강정보 성격의 앱이므로 문구에 건강 상태를 암시하지 않는다.
- 2천 명 규모는 추정치이며, 실제 대상이 크게 다르면 발송 시간·비용을 재산정한다.

## 10. 오픈 이슈

- 발송 시각 19:00 확정 여부(기획 확인).
- 푸시 수신 동의 여부 확인 기준(마케팅성 vs 서비스성 푸시 분류)과 야간 발송 제한 정책 적용 여부.
- 대조군 운영 가능 여부.
- "기록"의 정의(챌린지 인증 기록만 해당하는지, 일반 건강 기록 포함인지).
- 기존 푸시 발송 인프라와 이력 저장 위치 확인(저장소 확인 필요).

## 11. 일정(제안)

- 설계·정책 확정 → 개발 → QA → 일부 대상 점진 배포 → 전체 배포 순으로 진행한다. 상세 일정은 개발 공수 산정 후 정한다.
