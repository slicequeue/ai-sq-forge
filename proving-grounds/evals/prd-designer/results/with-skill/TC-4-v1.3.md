# 레이스 자동 완료 PRD

레이스 자동 완료 PRD 초안 작성 완료 (코드 변경 없음, 기획팀 리뷰 전)
- 범위: 종료일이 지난 진행 중 레이스의 자동 완료 전환과 참여자 알림, 기능 요구사항 7건
- 핵심 결정: 운영팀 수동 처리(하루 약 50건)를 0건으로 줄이는 것이 목표, 요청 유형은 리뷰용이라 풀패키지로 작성
- 미결 6건: 기획팀 4건, 운영팀 1건, 데이터 확인 1건 (9절)
- 기획팀 리뷰는 9절 미결 사항부터 부탁드립니다

## 1. 배경 및 목적

헬스케어 앱의 레이스는 종료일이 정해져 있고, 종료일이 지나면 '완료' 상태가 되어야 사용자에게 올바른 화면이 보입니다. 현재는 종료일이 지난 레이스를 운영팀이 직접 확인하여 하나씩 완료 처리하고 있습니다. 이 수작업이 매일 약 50건 발생합니다.

수작업에는 두 가지 어려움이 있습니다. 첫째, 운영팀이 매일 같은 확인과 처리를 반복해야 하므로 업무 부담이 큽니다. 둘째, 처리가 누락되면 이미 끝난 레이스가 사용자 화면에서 여전히 진행 중으로 보이는 등 잘못된 상태가 노출됩니다.

해결하려는 핵심 문제는 한 문장으로 다음과 같습니다. 종료일이 지난 레이스가 사람의 손을 거쳐야만 완료되기 때문에 운영 부담이 매일 발생하고, 누락 시 사용자에게 잘못된 상태가 보입니다.

## 2. 목표 (Goals)

- 종료일이 지난 진행 중 레이스가 정해진 시각에 자동으로 완료 상태로 바뀝니다.
- 운영팀의 수동 완료 처리 건수가 하루 약 50건에서 0건으로 줄어듭니다.
- 종료일이 지난 뒤에도 진행 중으로 보이는 레이스가 사용자 화면에서 사라집니다.

## 3. 범위 (Scope)

### In Scope

- 종료일이 지난 진행 중 레이스를 완료 상태로 자동 전환
- 완료로 전환된 레이스 참여자에게 완료 알림 발송
- 자동 처리 결과(처리 건수, 실패 건수)를 운영팀이 확인할 수 있는 기록

### Out of Scope

- 운영팀의 수동 완료 처리 기능 제거: 자동 처리 실패 시 대체 수단이 필요하므로 유지합니다.
- 레이스 결과 집계 및 순위 산정 방식 변경: 이번 요구는 상태 전환에 한정합니다.
- 이미 완료 또는 취소된 레이스의 상태 변경: 처리 대상이 아닙니다.

## 4. 사용자 시나리오 (User Stories / Scenarios)

**시나리오 1. 사용자가 종료된 레이스를 확인한다.** 사용자가 레이스 목록이나 상세 화면에 접근했을 때, 종료일이 지난 레이스에는 '완료' 표시가 보입니다. 사용자는 해당 레이스에 더 이상 참여할 수 없고, 결과를 확인할 수 있습니다.

**시나리오 2. 참여자가 완료 알림을 받는다.** 참여 중이던 레이스가 완료로 바뀌면 참여자는 완료 알림을 받습니다. 사용자는 앱을 열어 보지 않아도 레이스가 끝났음을 알 수 있습니다.

**시나리오 3. 운영팀이 처리 결과를 확인한다.** 운영팀 담당자는 하루 한 번 자동 처리 결과를 확인합니다. 처리된 건수와 실패한 건수가 보이고, 실패한 건이 있을 때만 해당 레이스를 직접 처리합니다.

**시나리오 4. 일시적 문제로 일부 레이스가 처리되지 못한다.** 일부 레이스가 처리되지 못해도 나머지 레이스는 정상적으로 완료됩니다. 처리되지 못한 레이스는 다음 실행 때 다시 시도됩니다.

## 5. 기능 요구사항 (Functional Requirements)

- FR-1. 매일 정해진 시각에, 종료일이 지난 '진행 중' 상태의 레이스는 자동으로 '완료' 상태로 전환된다.
- FR-2. 이미 '완료' 또는 '취소' 상태인 레이스는 처리 대상에서 제외된다.
- FR-3. 같은 레이스에 자동 처리가 두 번 실행되어도 완료 상태는 한 번만 기록되고, 참여자에게 알림이 중복 발송되지 않는다.
- FR-4. 완료로 전환된 레이스의 참여자에게 완료 알림이 발송된다.
- FR-5. 특정 레이스의 처리에 실패해도 다른 레이스의 처리는 계속되고, 실패한 레이스는 다음 실행 때 다시 처리된다.
- FR-6. 매 실행이 끝나면 처리 건수와 실패 건수가 운영팀이 확인할 수 있는 형태로 남는다.
- FR-7. 자동 전환된 레이스는 사용자 화면에서 '완료' 상태로 표시되고 신규 참여가 막힌다.

## 6. 비기능 요구사항 (Non-Functional Requirements)

- NFR-1. 자동 완료 처리는 서비스 이용이 많은 시간대(09:00~22:00 KST)를 피해 실행된다. 정확한 실행 시각은 9절 미결 사항으로 확정한다.
- NFR-2. 하루 처리 대상이 현재의 약 50건보다 많아져도 10,000건까지는 전체 실행이 30분 안에 끝난다.
- NFR-3. 실행이 실패하거나 누락된 경우 운영팀이 당일 안에 알 수 있다.
- NFR-4. 완료 알림은 전환 후 10분 이내에 참여자에게 도착한다.

## 7. 제약 및 가정 (Constraints & Assumptions)

### 확인된 것

- 종료일이 지난 레이스를 운영팀이 수동으로 완료 처리하고 있다. (요청자 설명)
- 수작업은 하루 약 50건이다. (요청자 설명)
- 처리가 누락되면 사용자에게 잘못된 상태가 보인다. (요청자 설명)

### 확인하지 못한 것

기존 PRD 문서(docs/prd, docs/works), 레이스 관련 소스, API 명세는 이번 작성 환경에서 접근할 수 없어 읽지 못했습니다. 기존 유사 문서와의 중복 여부, 기존 용어, 현재 완료 처리 규칙은 미확인입니다.

### 가정 (재평가 트리거와 함께 기록)

| 가정 | 재평가 트리거 |
|------|---------------|
| 종료일은 한국 시간(KST) 기준으로 판단한다 | 해외 사용자 레이스의 종료일 기준이 다르다는 사실이 확인되면 재검토 |
| 수동 완료 처리와 자동 완료 처리가 같은 결과(완료 상태, 알림 발송)를 만든다 | 운영팀 수동 절차를 확인하여 차이가 발견되면 재검토 |
| 하루 약 50건은 평균치이며 최대치는 이 수치의 3배 이내다 | 최근 3개월 일별 건수 확인 시 재검토 |
| 취소된 레이스에는 완료 알림을 보내지 않는다 | 기획팀 답변이 다르면 재검토 |

### 제약

- 완료 알림 문구와 발송 채널은 기존 알림 정책을 따른다. 정책 내용은 미확인이다.

## 8. 성공 지표 (Success Metrics)

- 운영팀 수동 완료 처리 건수: 하루 약 50건에서 0건 (도입 후 4주 연속 확인)
- 종료일이 지났는데 진행 중인 레이스 수: 매일 실행 종료 시점에 0건
- 자동 처리 실패 건수 중 다음 실행에서 해소된 비율: 100%
- 완료 알림 중복 발송: 0건

## 9. 미결 사항 (Open Questions)

1. 자동 완료를 종료일 당일 자정에 할지, 종료일 다음 날 새벽에 할지 정해야 합니다. (기획팀)
2. 완료 알림을 모든 참여자에게 보낼지, 중도 이탈 참여자는 제외할지 정해야 합니다. (기획팀)
3. 완료 알림의 문구와 발송 채널(푸시, 앱 내 알림 등)을 정해야 합니다. (기획팀)
4. 도입 첫날 이미 쌓여 있는 종료 레이스(과거분)를 한꺼번에 완료 처리할지 정해야 합니다. (기획팀, 운영팀)
5. 운영팀이 수동으로 완료 처리할 때 완료 외에 함께 하는 작업(정산, 보상 지급 등)이 있는지 확인해야 합니다. (운영팀)
6. 하루 건수의 최근 3개월 추이와 최대치를 확인해야 합니다. (데이터 확인 담당)

## 10. 결론 및 요약

이 문서는 종료일이 지난 레이스를 시스템이 매일 자동으로 완료 처리하여, 운영팀의 수작업(하루 약 50건)을 없애고 잘못된 상태 노출을 막는 요구사항을 정리했습니다. 기능 요구사항은 7건이며, 미결 6건은 9절에 모았습니다. 기획팀께서는 1~4번 항목을 먼저 검토해 주시면 다음 단계인 기술 설계를 시작할 수 있습니다.
