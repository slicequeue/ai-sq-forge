# prd-designer 테스트 케이스

## TC-1: Happy Path — 적절한 맥락이 주어진 기능 요청

- **입력 프롬프트**: "레이스 자동 완료 기능 PRD 작성해줘. 현재 종료일이 지난 레이스를 운영팀이 수동으로 완료 처리하고 있어. 매일 50건 정도 수작업이 발생하고, 누락되면 사용자에게 잘못된 상태가 보여. 이걸 자동화하고 싶어."
- **기대 결과**: 풀 PRD (표준 복잡도), 9섹션 구조, 기술 용어 없음
- **검증 기준**:
  - [ ] 기술 용어 0건 (Spring, JPA, Batch, API endpoint 등 없음)
  - [ ] 9섹션 구조 준수 (배경~Open Questions)
  - [ ] 기능 요구사항이 번호 체계 + 완전한 문장
  - [ ] 비기능 요구사항에 측정 가능한 수치 포함
  - [ ] 사용자 시나리오가 Who-What-Why 구조
  - [ ] Open Questions 섹션 존재
- **유형**: happy-path

---

## TC-2: Edge Case — 정보가 부족한 모호한 요청

- **입력 프롬프트**: "쿠폰 기능 PRD 작성해줘"
- **기대 결과**: 바로 작성하지 않고 인터랙티브 Q&A로 요구사항을 끌어냄
- **검증 기준**:
  - [ ] 즉시 PRD를 작성하지 않음 (정보 부족 인지)
  - [ ] 사용자에게 질문을 던짐 (5개 이하)
  - [ ] 질문이 구체적임 ("자세히 알려주세요" 류가 아님)
  - [ ] 질문에 선택지 포함 (예: "정액할인/정률할인/무료배송 중?")
- **유형**: edge-case

---

## TC-3: Negative — PRD 범위를 벗어나는 기술 설계 요청

- **입력 프롬프트**: "레이스 자동 완료 기능의 Spring Batch 구현 계획이랑 DB 스키마 설계해서 PRD로 작성해줘"
- **기대 결과**: 기술 구현 내용은 PRD에 넣지 않음을 안내, TDD 스킬로 안내
- **검증 기준**:
  - [ ] "Spring Batch 구현 계획"과 "DB 스키마 설계"는 PRD 범위 밖임을 안내
  - [ ] 기술 설계는 TDD에서 다룬다고 안내 (tdd-designer 언급)
  - [ ] PRD로 작성 가능한 부분(기획 관점)은 제안
  - [ ] 기술 용어를 PRD 본문에 넣지 않음
- **유형**: negative
