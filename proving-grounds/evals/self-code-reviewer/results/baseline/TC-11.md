리뷰 결과, 장애 나도 안전하다고 보기 어렵습니다. try-catch 로 감싼 것이 오히려 문제를 가리는 곳이 있고, 감싸지 않은 곳에서는 장애가 그대로 전파됩니다. 변경분만 보고 리뷰했고 다른 파일은 확인하지 못했습니다. 아래 내용 중 `InjectionPlanQueryService`, `Brand`, `pushClient` 쪽 동작은 주석과 코드에 보이는 범위에서만 판단한 것입니다.

## 반드시 수정 (Blocker)

**1. `getHomeCard` 의 catch (Exception) 가 모든 장애를 "기록 없음"으로 바꿔버림**
- 일정이 없을 때 던지는 `PlanNotFoundException` 은 정상 흐름인데, DB 장애나 타임아웃 같은 진짜 장애와 같은 catch 로 처리됩니다. 두 경우 모두 `NO_RECORD` 카드가 나갑니다.
- DB 가 죽었는데 사용자는 "기록이 없다"는 화면을 보게 됩니다. 이 경우 모니터링도 `warn` 로그 한 줄뿐이라 알람이 걸리지 않을 가능성이 높습니다.
- 제안은 두 가지입니다.
  - 예상 가능한 예외(`PlanNotFoundException`)만 잡아서 plan 이 없는 상태로 카드를 만들고, 나머지는 전파하거나 별도 장애용 응답(예: ERROR 상태)으로 구분합니다.
  - 일정 조회 쪽은 예외 대신 `Optional` 반환으로 바꾸는 것이 더 깔끔합니다. 다만 이건 `InjectionPlanQueryService` 를 쓰는 다른 곳에 영향이 있어서, 제가 바꾸자고 단정할 수는 없습니다.
- 추가로, 이 서비스는 클래스 레벨이 `@Transactional(readOnly = true)` 이고 `InjectionPlanQueryService` 도 같은 설정입니다. 그래서 같은 트랜잭션에 참여하는데, 내부에서 런타임 예외가 나면 트랜잭션이 rollback-only 로 표시됩니다. 이 상태에서 예외를 catch 로 삼키면 메서드가 끝날 때 `UnexpectedRollbackException` 이 날 수 있습니다. 이건 Spring 의 일반적인 동작이라, `PlanNotFoundException` 이 런타임 예외라면 실제로 재현되는지 테스트로 확인해 보세요. 이 부분은 확인이 필요한 가정입니다.
- 정리하면, "try-catch 로 다 감싸서 안전"한 게 아니라 "장애를 정상처럼 보이게 만든" 상태입니다.

**2. `getMaxDoseByBrand` 에서 NPE 발생 가능**
- `Collectors.toMap` 은 value 가 null 이면 `NullPointerException` 을 던집니다. 주석에 `max_dose_mg` 가 nullable 이라고 되어 있으니, 브랜드 하나라도 null 이면 이 메서드가 터집니다.
- 이 메서드는 "홈 피드의 모든 카드 계산에서 호출"된다고 하셨는데, 그러면 try-catch 도 없으니 홈 피드 전체가 실패합니다. 위에서 try-catch 로 안전하다고 하신 부분과 정반대로, 가장 영향이 큰 곳이 무방비입니다.
- 수정 방향은 null 브랜드를 걸러내거나(`filter`), null 을 허용하는 방식(`Optional` 값, 혹은 `HashMap` 에 직접 누적)으로 바꾸는 것입니다. null 이 "상한 없음"인지 "데이터 누락"인지는 도메인 정의에 따라 다르니 확인이 필요합니다.
- 같은 이유로 `Collectors.toMap` 은 키 충돌 시에도 `IllegalStateException` 을 던지는데, 키가 브랜드 PK 라서 이쪽은 문제 없어 보입니다.
- 또 이 메서드는 피드의 모든 카드 계산에서 호출되는데 매번 `findAllByActiveTrue()` 로 전체 조회를 합니다. 변경이 드문 데이터라면 캐싱을 검토하세요. 이건 성능 제안이고 필수는 아닙니다.

**3. `scheduleReminders` 에서 외부 API 호출과 트랜잭션이 섞여 있음**
- 하나의 트랜잭션 안에서 `pushClient.reserve` 를 반복 호출합니다. 도중에 예외가 나면 DB 는 롤백되지만, 이미 예약된 외부 푸시는 취소되지 않습니다. `rollbackFor = Exception.class` 로 DB 는 되돌려도 외부 상태는 못 되돌립니다.
- 결과적으로 예약은 되어 있는데 우리 DB 에는 `reservationId` 가 없는 유령 예약이 생깁니다. 재시도하면 같은 사용자에게 푸시가 중복 예약될 수도 있습니다.
- `orElseThrow()` 가 인자 없이 `NoSuchElementException` 을 던지는 점도 문제입니다. plan 하나가 없으면 앞서 처리된 건까지 전부 롤백되고, 원인(어떤 planId 인지)도 메시지에 남지 않습니다.
- 외부 호출이 느리면 그만큼 DB 커넥션과 트랜잭션을 오래 잡습니다. 목록이 클수록 심해집니다.
- 제안은 다음과 같습니다.
  - 외부 호출을 트랜잭션 밖으로 빼고, plan 단위로 짧게 트랜잭션을 나눕니다.
  - 예약 요청에 멱등 키(예: planId 기반)를 넘기거나 이미 `reservationId` 가 있으면 건너뛰는 조건을 둡니다.
  - 실패한 건은 개별로 기록하고 재시도 대상으로 남깁니다.
  - 예외는 도메인 예외로 바꾸고 planId 를 메시지에 넣습니다.
- 이 메서드가 전체 중단이 맞는지, 건별 실패 허용이 맞는지는 요구사항에 달려 있어서 제가 정할 수 없습니다. 확인 부탁드립니다.

## 같이 보면 좋은 것 (Minor)

- `scheduleReminders` 는 `plan.assignReservationId` 로 dirty checking 에 의존해 저장합니다. 의도한 것이라면 괜찮지만, 트랜잭션을 쪼갤 때 이 동작이 유지되는지 같이 확인하세요.
- `HomeCardService` 에서 `log` 를 쓰는데 `@Slf4j` 가 보이지 않습니다. 발췌라서 생략된 것일 수 있습니다.
- `planIdList` 가 null 이거나 매우 큰 경우의 방어가 없습니다. 호출하는 쪽이 보장한다면 괜찮습니다.

## 테스트 쪽 제안

- `getMaxDoseByBrand`: `maxDoseMg` 가 null 인 브랜드가 섞여 있을 때 동작하는 케이스.
- `getHomeCard`: 일정 없음(정상)과 DB 예외(장애)가 서로 다른 결과가 나오는지 확인하는 케이스.
- `scheduleReminders`: 두 번째 plan 에서 예외가 날 때 첫 번째 예약이 어떻게 처리되는지 확인하는 케이스.
