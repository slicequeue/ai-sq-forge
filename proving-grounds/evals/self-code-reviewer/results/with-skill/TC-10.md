## 자체 코드 리뷰 결과

**브랜치**: 확인 불가 — 실제 `git branch`/`git diff dev...HEAD`를 실행할 수 있는 저장소 컨텍스트가 아니라, 사용자가 제시한 diff 스니펫(컨트롤러 메서드 1개 + `application.yml` 조각)만을 대상으로 리뷰함. (가정: 이 두 조각이 dev 대비 변경/추가분 전체다)
**비교 기준**: dev (가정)
**커밋 수**: 확인 불가 / **변경 파일**: 최소 2개 (컨트롤러 파일 1개 추정, `application.yml` 1개)
**관점 스코프**: 공통 룰만 (보안/성능/아키텍처 관점은 각 관점 스킬 또는 composite 에이전트로 별도 검토 필요)
**변경 의도 파악 근거**: PR 제목/커밋 메시지/PRD 등 연결 문서를 받지 못해, 코드에 남은 주석(`GLOB-742`, `기획안_v3.xlsx 시트4`)과 배경 설명(`ServiceAccessAuthorizationFilter` 삭제)만을 근거로 판단함 — 아래 항목 중 "가정"이라 표기한 부분은 이 근거의 한계 내 추론임.

### 필수 수정 (규칙 위반)

| # | 파일:위치 | 위반 규칙 | 내용 | 수정 방향 |
|---|----------|-----------|------|-----------|
| 1 | 컨트롤러:`search()` catch 절 | RR-5 예외 계층 관계 (review-recurrence-guard §5) — AUTO FAIL 후보(RR-F5) | `catch (BaseRuntimeException \| NumberFormatException e)`가 서로 인과가 다른 두 예외를 한 덩어리로 묶어 동일하게 "invalid" 리다이렉트 처리한다. `BaseRuntimeException`은 프로젝트 예외 계층의 최상위(추정)로 범위가 매우 넓어, 순수 입력 포맷 오류가 아닌 다른 종류의 비즈니스/인프라 예외까지 "잘못된 입력"으로 오분류해 사용자에게 보고할 위험이 있다. 반대로 `NumberFormatException`은 `IllegalArgumentException`의 하위 타입이므로, 만약 의도가 "잘못된 형식의 입력 전반"을 잡으려는 것이었다면 `NumberFormatException`이 아닌 형태의 다른 `IllegalArgumentException`은 여기서 잡히지 않는다 — 가이드 문서(review-recurrence-guard.md §5)에 실제 재발 사례로 등재된 것과 동일한 패턴 | 원인이 다른 예외는 분리한다. (a) 입력 포맷 오류 계열은 `IllegalArgumentException`(NumberFormatException 포함)으로 좁혀서 클라이언트 오류로 처리, (b) `BaseRuntimeException`(또는 그 하위의 실제 대상 타입)은 원인에 따라 별도 catch로 분리하고 로그 레벨/응답을 다르게 한다. `BaseRuntimeException` 실제 계층 구조를 확인 후 필요한 구체 타입으로 좁힐 것 |
| 2 | 컨트롤러:`search()` catch 절 내부 주석 | RR-10 주석 (review-recurrence-guard §10 / 자체 검사 항목) | `// GLOB-742, 기획안_v3.xlsx 시트4 참조` — 티켓 번호·기획 문서 식별자가 코드 주석에 박혀 있음. 시간이 지나면 부정확해지고 코드 재사용 시 노이즈가 된다 | 해당 내용은 PR 본문으로 이동하고 코드 주석에서 제거 |
| 3 | 컨트롤러:`search()` 본문 상단/조회 라인 주석 | RR-10 주석 | `// keyword 로 사용자를 검색한다`, `// 사용자 조회` — 메서드명(`search`)과 호출부(`userService.findByKeyword(keyword)`)가 이미 말하는 내용을 그대로 반복하는 주석 | 주석 제거. 코드가 스스로 설명되지 않는 "왜"가 있다면 그것만 남긴다 |
| 4 | `application.yml`: `service-access.filter.enabled` | dead config (review-recurrence-guard §7 / 스킬 "리뷰 재발 방지 검사" 표) | 배경상 이 변경에서 `ServiceAccessAuthorizationFilter`가 삭제되었고 그 필터가 `service-access.filter.enabled` 프로퍼티의 유일한 소비자였다. 그런데 `application.yml`에 해당 프로퍼티(`${SERVICE_ACCESS_FILTER_ENABLED:true}`)가 그대로 남아 있다 — 소비자 없는 dead config. 아무도 읽지 않는 설정이 남으면 운영 중 값을 바꿔도 아무 효과가 없고, 특히 접근 제어용 토글이면 장애 대응 시 혼란을 유발한다 | `grep -rn "service-access.filter.enabled\|SERVICE_ACCESS_FILTER_ENABLED"`로 다른 소비자가 정말 없는지 전체 저장소(모든 `application-*.yml` 포함)에서 재확인 후, 없으면 모든 환경 yml에서 제거. 향후 재사용 예정이면 "현재 미사용" 주석을 명시 |

### 관점 리뷰 필요 안내 (변경 성격 기반)

- 보안 관점 검토 권장: yes — `java-secure-coding-reviewer`. 사용자 입력 `keyword`가 검색 조건으로 그대로 전달됨(인젝션/이스케이프 처리 여부 미확인), 접근 제어 필터 삭제가 인가 우회로 이어지지 않는지 확인 필요
- 성능 관점 검토 권장: yes — `java-performance-reviewer`. `userService.findByKeyword`의 조회 방식(전체 스캔·LIKE 패턴·페이지네이션 여부)이 스니펫에 없어 확인 필요
- 아키텍처 관점 검토 권장: yes — `java-architecture-reviewer`. admin 모듈 여부 확정 및 컨트롤러 계층 규칙(4-Tier, `@Controller` vs `@RestController`) 대조 필요
- 전체 통합 리뷰 원하면: `java-composite-reviewer` 에이전트
