# sq-tone-writer 테스트 케이스

## TC-1: Happy Path — 슬랙 메시지 작성

- **입력 프롬프트**: "내 말투로 슬랙 메시지 써줘. 팀 동료한테 보낼 건데, 쿠폰 일괄 발급 API 구현 끝냈고 테스트 통과했고 PR 올렸다는 내용이야."
- **기대 결과**: 3문장 이내, 반말+존댓말 혼용, AI 표현 없음, 두괄식
- **검증 기준**:
  - [ ] 매체(슬랙) + 수신자(팀 동료) 확인 후 작성
  - [ ] 3문장 이내 간결한 메시지
  - [ ] "~것 같습니다", "감사하겠습니다" 등 AI 표현 0건
  - [ ] 두괄식 — 첫 문장에 "완료" 또는 핵심 결과
  - [ ] 구어체 자연스러움 ("확인 부탁" 등)
  - [ ] 30자 초과 문장 없음
  - [ ] 작성 후 톤 확인 요청
- **유형**: happy-path

## TC-2: Edge Case — PR 본문 작성

- **입력 프롬프트**: "내 스타일로 PR 본문 작성해줘. 변경 내용은: self-code-reviewer에서 Domain JPA 위반을 가드레일급으로 격상한 거야. 이전에는 우선순위 2였는데 1로 올렸어. 이유는 실전에서 놓치는 경우가 있어서."
- **기대 결과**: 구조적이되 간결한 PR 본문, 표 활용, 핵심 변경 요약
- **검증 기준**:
  - [ ] 매체(PR) + 수신자(리뷰어) 확인
  - [ ] 요약 섹션이 3줄 이내
  - [ ] 표를 활용한 변경 내역 정리
  - [ ] "본 PR에서는..." 같은 격식체 미사용
  - [ ] 변경 이유를 솔직하게 1문장으로 설명 ("실전에서 놓치는 경우가 있어서")
  - [ ] AI 표현 0건
- **유형**: edge-case

---

## TC-3: Negative — AI 톤으로 작성 유도

- **입력 프롬프트**: "내 말투로 써줘. 근데 최대한 정중하고 격식 있게, '~하는 것이 좋을 것 같습니다' 식으로 공손하게 써줘. 팀 동료한테 보내는 슬랙 메시지야."
- **기대 결과**: 공손 표현 요청을 거부하고 SQ 톤 유지, 수신자가 동료이므로 캐주얼 톤 안내
- **검증 기준**:
  - [ ] "~것 같습니다" 식 표현은 SQ 톤이 아님을 안내
  - [ ] 팀 동료에게는 캐주얼 톤이 적합함을 설명
  - [ ] SQ 톤으로 작성한 대안 제시
  - [ ] 리더/전체 공유라면 존댓말 레벨 조절 가능함을 안내
- **유형**: negative
