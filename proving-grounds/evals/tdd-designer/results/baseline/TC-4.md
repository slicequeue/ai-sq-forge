# TDD: 회원 닉네임 최대 길이 확장 (20자 → 30자)

| 항목 | 내용 |
|------|------|
| 대상 서비스 | pasta-japan-server (pasta-api 멀티모듈, Spring Boot/Java, JPA, Flyway, MySQL) |
| 근거 PRD | 회원 닉네임 최대 길이 확장 (FR-1, FR-2, NFR-1) |
| 상태 | Draft |

## 리뷰 요청 사항

- 현재 `member.nickname` 컬럼의 실제 정의(VARCHAR 길이, 문자셋/콜레이션)는 저장소 확인 전이므로 가정으로 작성했다. 실제 DDL 확인 후 3장 마이그레이션을 확정해야 한다.
- "30자"의 계산 단위(UTF-16 `String.length()` vs 유니코드 코드포인트)를 코드포인트 기준으로 제안한다. 합의를 요청한다.

## 리스크

- 서버 한도만 30자로 올리고 iOS/Android 클라이언트 입력 제한이 20자로 남으면 가입 이탈이 해소되지 않는다.
- 닉네임을 노출하는 다른 컬럼/외부 연동(검색 인덱스, 알림 템플릿, 로그, 타 테이블에 복제된 닉네임 컬럼)이 20자 가정이면 truncation 또는 오류가 생길 수 있다.
- 컬럼 확장 DDL 중 테이블 락 가능성(MySQL 8 VARCHAR 확장은 길이 바이트 수 경계를 넘지 않으면 INPLACE 가능). 실제 테이블 크기와 버전 확인이 필요하다.

## 외부 의존성

- iOS/Android 클라이언트: 닉네임 입력 글자 수 제한 변경 및 배포 순서 조율 필요 (서버 선배포 필수).

## 확인된 사실 vs 가정

| 구분 | 내용 |
|------|------|
| 확인된 사실 (PRD) | 20자 제한으로 일본어 닉네임 가입 이탈 문의 월 30건. 한도 20→30, 기존 데이터 유지, 조회 응답 시간 변화 없음 |
| 가정 | `member.nickname`은 `VARCHAR(20)` utf8mb4이다 |
| 가정 | 검증은 요청 DTO의 Bean Validation(`@Size(max = 20)`)과 도메인 값 객체/서비스 검증에 걸쳐 있다 |
| 가정 | 닉네임 중복 검사 및 유니크 인덱스가 존재할 수 있다 (있다면 인덱스 길이 영향 확인) |
| 재평가 트리거 | 실제 DDL/코드 확인 결과가 가정과 다르면 3, 5, 6장을 재작성한다 |

## 1. 개요

### 1.1 목적
닉네임 최대 길이를 20자에서 30자로 확장해 일본어 사용자의 가입 이탈을 줄인다.

### 1.2 범위
- 포함: 닉네임 길이 검증 상수 변경, DB 컬럼 길이 확장 마이그레이션, 관련 테스트
- 제외: 기존 닉네임 데이터 변경(FR-2), 닉네임 허용 문자 정책 변경, 클라이언트 구현

### 1.3 요구사항 매핑

| 요구사항 | 설계 대응 |
|----------|-----------|
| FR-1 최대 30자 | 길이 상수 단일화(30) + DB 컬럼 `VARCHAR(30)` |
| FR-2 기존 닉네임 유지 | 데이터 변환 없는 `ALTER ... MODIFY` (길이 확장만) |
| NFR-1 조회 응답 시간 불변 | 조회 쿼리/응답 구조 변경 없음. 확장은 인덱스 사용 쿼리 계획에 영향 없음을 검증 |

## 2. 시스템 아키텍처

해당 없음

## 3. 데이터베이스 설계

### 3.1 변경 대상
`member.nickname`: `VARCHAR(20)` → `VARCHAR(30)` (가정, 실제 DDL 확인 후 확정)

### 3.2 Flyway 마이그레이션 (예시)

파일명: `V{다음버전}__expand_member_nickname_length.sql`

```sql
ALTER TABLE member
    MODIFY COLUMN nickname VARCHAR(30) NOT NULL COMMENT '닉네임 (최대 30자)';
```

- 기존 컬럼의 NULL 여부, 문자셋, 콜레이션, DEFAULT, COMMENT는 현행 정의와 동일하게 유지한다 (MODIFY는 속성을 덮어쓰므로 누락 금지).
- 길이 확장만 하므로 기존 데이터는 변경되지 않는다 (FR-2).
- 유니크/일반 인덱스가 있으면 utf8mb4 기준 30 x 4 = 120바이트로 인덱스 키 한도(3072바이트) 내이다.
- 롤백: 30자 초과 데이터가 생긴 이후에는 축소 불가. 롤백은 코드만 되돌리고 컬럼은 유지한다 (전진 전용).

## 4. API 명세

API 경로, 메서드, 응답 스키마 변경은 없다. 요청 필드 검증 규칙만 바뀐다.

| API | 변경 | 설명 |
|-----|------|------|
| 회원 가입 / 프로필 수정 (닉네임 포함 요청) | 검증 | `nickname` 길이 1~30 허용 (기존 1~20) |
| 프로필 조회 | 없음 | 응답 구조 동일. 30자 닉네임이 그대로 내려감 |

오류 응답: 31자 이상 입력 시 기존 검증 실패 응답 형식(400)을 그대로 사용하되 메시지의 "20자"를 "30자"로 변경한다. 하드코딩된 메시지가 있으면 상수 참조로 바꾼다.

## 5. 알고리즘 및 비즈니스 로직

### 5.1 길이 규칙
- 한도 값은 단일 상수(예: `NICKNAME_MAX_LENGTH = 30`)로 관리하고, DTO 검증, 도메인 검증, 오류 메시지가 모두 이를 참조한다. 숫자 20이 흩어져 있으면 전부 찾아 치환한다.
- 길이 단위: 유니코드 코드포인트 수(`codePointCount`)를 제안한다. 일본어 한자/가나는 BMP라 UTF-16 길이와 같지만, 이모지/서로게이트 쌍 문자는 `String.length()`가 2로 계산되어 사용자 체감(1자)과 다르다. MySQL `VARCHAR(30) utf8mb4`는 코드포인트 기준이므로 DB와도 일치한다. (리뷰 요청 사항 참고)
- 검증 순서: trim 등 기존 정규화 규칙 적용 후 길이 검사 (기존 순서 유지).

### 5.2 기존 데이터
변환/백필 없음. 20자 이하 기존 닉네임은 그대로 유효하다.

### 5.3 배포 순서
1. DB 마이그레이션 적용 (컬럼 확장, 하위 호환)
2. 서버 배포 (한도 30)
3. 클라이언트 입력 제한 변경 배포
